## 1. Объём и проверенные предпосылки

Auth отвечает за личность, сеанс, компанию вошедшего, вычисление прав и жизненный цикл сотрудника.
Регистрация создаёт компанию и первого владельца; приглашение добавляет сотрудника в существующую
компанию. Публичный вход начинается с постоянной ссылки компании и требует email/пароль (П76).
Одинаковый email в двух компаниях означает два независимых аккаунта, пароля и набора прав.
Общей личности и переключателя компаний нет. Приглашение на 7 суток не заменяет постоянную ссылку.

Сверка сделана чтением текущего checkout, а не старых временных сводок. Пути ниже от корня репозитория.

## 2. Разрешение конфликтов и целевой контракт

| Расхождение | Действующее правило и работа |
|---|---|
| Глобальный поиск email против составного индекса | П76: публичный контекст компании разрешается сервером по постоянной ссылке **до** проверки пары email/пароль. Вход и смена email сужаются компанией. Регистрация другой компании не конфликтует по email. С1 |
| Три срока, игнорирование rememberMe | П29 + П77: 30 минут бездействия, remember — 30 суток от последней активности. С1; expires_at проверяется сервером, а не только отображается клиенту |
| Постоянная ссылка против secret_link_token пользователя | С1 вводит постоянную ссылку компании; С5 — отдельный одноразовый секрет приглашения со сроком 7 суток. Ни одна ссылка сама не аутентифицирует; URL компании не истекает через 7 суток |
| Выключенный пользователь всё ещё входит | П79: С0 проверяет is_active на защищённых запросах, С1 — на входе, С5 атомарно отключает пользователя, отзывает все сеансы и отменяет приглашения |
| users.role и user_roles; Owner и owner | П2/П3: источник полномочий — несколько строчных ролей и переопределения. Легаси role не использовать для разрешения; миграция данных и совместимый переход ответов/клиента в С1/С4 |
| Матрица auth и config | auth владеет вычислением и хранением прав, config — существующим внешним редактором матрицы. Р-Д4/Р-Д5: вычисленные права отдаёт будущий GET /api/auth/me/permissions; внешний редактор не дублировать новым auth.permission_matrix. С3/С4 |
| can_read=true для каждой роли | П33: миграция дефолта и единый алгоритм Р5 rights; П82–П84 задают начальные права соответствующих доменов. Они не разрешают перезаписывать вручную изменённую матрицу при каждом входе |
| secret_link в /me | П53/П58: убрать секрет приглашения из профиля и обновить потребителей. С1; смена поля регистрации согласуется с постоянной ссылкой, а не переименовывает старый секрет молча |
| Сеанс без компании, комментарий superadmin | Опрошенный auth:8: доступа к данным компаний нет; отдельная платформа superadmin не входит в продукт. С0 отказывает, NULL в схеме не означает привилегию |
| CSRF и лимиты названы вопросами владельцу | Опрошенные auth:3/auth:7: инженерная защита с согласованным контрактом, не продуктовое ожидание. С7 |
| Страна якобы отсутствует в UI | Поле есть, отправки нет. П80: страна компании определяет выбор пояса; несколько поясов требуют уточнения, единственный выбирается автоматически. Инициализация auth → settings через internal API, С1 |
| «Только десять видов истории» | П85 расширяет состав общей истории управлением сотрудниками; П41 оставляет события входа в серверном журнале. С4–С6 |

## 3. Отказы и граница аутентификации

Это **целевые** ответы, а не утверждение об их готовности. Конверт сохраняет `detail.code/message`
по [соглашениям](../../roo-context/api/00-conventions.md); сравнение кодов — точное.

| Случай | Ответ | Проверка клиента и сервера |
|---|---|---|
| Нет Authorization | 401 MISSING_TOKEN | Все четыре потребителя С0 одинаковы, обработчик/запись не вызываются |
| Не Bearer, пустой/повреждённый токен, неверная подпись, неверный payload/UUID | 401 INVALID_TOKEN | Не 500; не считать исключение БД ошибкой подписи |
| Истёкший срок | 401 TOKEN_EXPIRED | С0 — переходная проверка возраста подписи; С1 — срок бездействия из состояния сервера |
| Пользователь отсутствует, выключен или без компании; неизвестный/отозванный сеанс после С1 | 401 UNAUTHORIZED | Очищение токена, профиля и кэша прав; не 403, оставляющий профиль в кэше |
| Неверная пара, чужой пароль, выключенный аккаунт на входе | 401 UNAUTHORIZED с одинаковым безопасным текстом | Никакого поиска во второй компании или раскрытия существования email |
| Живой сеанс, права на действие нет | 403 FORBIDDEN | С3, не выход из системы; флаг продукта не подменяет право П1/П4 |
| Сущность принадлежит другой компании | 404 NOT_FOUND | Сужение запросов по компании сеанса; ни чтения, ни изменения чужой строки |
| Email уже занят внутри той же компании | 409 CONFLICT с fieldErrors.email | Приглашение/смена email; другая компания не конфликтует |
| Приглашение неизвестно, истекло, отменено или использовано | 401 UNAUTHORIZED, единый безопасный текст | С5: пароль и сеанс не создаются; не раскрывать данные сотрудника |
| Невалидное поле | 422 VALIDATION_ERROR с явным полем | Не выводить fieldErrors из текста; сохранить совместимость до перехода обоих концов |

Отказ CSRF/ограничителя и формат retry согласуются в С7 до кода. Это техническая часть контракта;
значения из неиспользуемых настроек не выдаются за действующие лимиты. При истечении клиент
показывает сообщение о повторном входе и сохраняет контекст постоянной ссылки компании (С1).

## 4. Сквозные обязанности auth

1. **Права.** Элемент auth.user: список — read, приглашение — create, изменение ролей,
   отключение и восстановление — edit (для POST-действий это обновление существующей сущности,
   исключение П15). Публичные login/register/приём приглашения не требуют права вошедшего;
   me, logout и me/permissions работают только с собственными данными. Редактор матрицы —
   config, доступ владельцу и админу по П12. Отдельного auth.permission_matrix нет.
   Пароли, хеши, CSRF и секреты приглашений не входят в выдачу списка сотрудников/прав/истории.
   Матрица не даёт права читать эти секреты. Доменные ограничения П5/П16–П18 сохраняются.
2. **Компания.** Компания бизнес-запроса берётся только из подтверждённой личности/сеанса.
   Постоянная ссылка — разрешённый П76 контекст **до входа**, не X-Tenant-заголовок для смены
   компании после входа. Email нормализуется одинаково, уникален парой с компанией.
   Тенантские таблицы: users, permission_items, role_permissions, user_permissions.
   tenants — реестр; sessions и user_roles наследуют принадлежность через user_id (категория Б
   плана tenancy). Добавлять им tenant_id ради копирования правила не нужно; чтение обязано
   проверять связь с пользователем компании. Новой таблице приглашений явно назначить категорию
   А с tenant_id; постоянный идентификатор компании и секрет приглашения — разные ключи.
3. **Все текущие запросы auth.** login.get_user_by_email сужается tenant_id в С1;
   register.get_user_by_email убирается как глобальный запрет в том же слайсе;
   me.get_user_by_id — внутренний резолвер проверенного user_id в С0, не публичный поиск чужого
   профиля; magic_link.get_user_by_secret_link — резолвер глобального секрета, заменяемый
   приглашением в С5; register.get_tenant_by_slug читает реестр компаний.
   Глобальная проверка email в settings/profile переносится в auth internal API и сужается
   компанией в С1. Сторож tenancy фиксирует причины исключений, после исправления не оставляет
   БАГ-13 в списке разрешённых дыр.
4. **История.** Управление сотрудниками (создание, изменение ролей, отключение, восстановление)
   и изменение матрицы пишутся через общую audit_entries; П36–П42 и П85, без копирования паролей,
   секретов и внутренних заметок. Авторство старых заказов/заметок/истории сохраняется по П79.
   Читатель истории применяет права исходной карточки и чувствительных полей до пагинации/total
   по П81. Вход, выход, неудача входа и использование ссылки — серверный журнал П41, не колокольчик.
5. **Уведомления.** Тип permissions_changed остаётся одним для изменений общей матрицы,
   независимо от места записи config/settings. Auth предоставляет вычисленные права и
   адресатов **своей** компании через internal API; запись выполняет общий эмиттер, без второго
   уведомления из auth. В С4 проверить подключение и дедупликацию П56. Подписки по П54 привязаны
   к пользователю и компании, email — умолчание, права ограничивают адресацию. Галочка сайта
   фильтрует показ, не создание; почта следует выбранному каналу. Письмо-приглашение П58 — доставка
   приглашения, не шестнадцатый тип NotificationType. Увольнение не вводит новый тип уведомления.
6. **Идемпотентность.** Регистрация — цельная операция: компания, владелец, роль, сеанс,
   инициализация настроек; применять [сквозное правило](../general/сквозное-idempotency-план.md).
   Logout повторно не меняет состояние; приём приглашения атомарен и однократен. Аутентификация
   не считается пройденной по одному наличию Idempotency-Key.
7. **Кастомные поля.** Кастомных полей у домена нет. Собственные производные URL не хранить (П68).
   Внутренние API сохраняют границы модулей; settings не пишет users.password_hash напрямую.

## 6. Решения владельца и трассировка

### Сохранённые П1–П75

Сохраняется исходная вырезка плана; строки вне auth не превращаются в новые auth-функции.
Глаголы «читает», «бросается», «даёт» в колонке работы обозначают целевое поведение слайса,
если рядом прямо не сказано, что оно уже существует. Текущее состояние отдельно зафиксировано в §1.

| П | что решено | что делает auth | слайс |

### С0 · Единый разбор токена — готовая задача реализации

**Цель:** все действующие потребители разбора Bearer получают одну проверенную личность и компанию,
единообразно отказывают до выполнения операции. Изменение техническое, без новой схемы входа,
таблиц сеансов, ролей, приглашений и продуктовых сроков. С0 — фундамент С1, а не завершение П77/П79.
**Зависимости:** нет; ни ответы владельца, ни готовность С3/С5 не нужны.

**Вход задачи:** этот раздел, auth.md, 00-conventions (§1/§4/§5), правила tenancy Т1–Т4,
исходники ниже и существующий `backend/tests/test_route_auth.py`. Сначала повторить инвентарь:

```bash
rg -n 'URLSafeTimedSerializer|\.loads\(|_resolve_user_id|Depends\(_bearer\)' backend/app
```

**Текущие потребители, каждый обязателен к переводу:**

| Файл | Функция/охват | Что меняется |
|---|---|---|
| `backend/app/modules/auth/features/me/action.py` | me, GET /api/auth/me | Удалить ручной разбор и локальный _bearer; использовать get_current_user |
| `backend/app/modules/settings/features/crud/action.py` | _resolve_user_id, все 21 роут CRUD/settings | Получать проверенную личность/компанию, убрать собственный сериализатор и повторное разрешение компании |
| `backend/app/modules/settings/features/profile/action.py` | _resolve_user_id, 3 роута профиля/пароля | Та же dependency через internal API auth; пользователь берётся из контекста |
| `backend/app/core/uploads/action.py` | _resolve_user_id, POST /api/uploads | Та же dependency; убрать прямой select(User) в _get_tenant_id. Проверить компанию **до** чтения/записи файла |

Два **издателя**, а не потребителя разбора:
`backend/app/modules/auth/features/login/domain.py` и
`backend/app/modules/auth/features/register/domain.py` переводятся на один helper подписи.
Формат payload С0 остаётся `{user_id: string}` с текущими secret_key и salt `session`.
Постоянная ссылка компании и новая модель срока появляются только в С1.

**Файлы будущей реализации:**

- Создать `backend/app/modules/auth/shared/session_tokens.py`: один сериализатор,
  `issue_session_token(user_id: UUID) -> str`, `decode_session_token(token: str) -> UUID`.
- Заполнить `backend/app/modules/auth/shared/dependencies.py`:
  `get_current_user(authorization: str | None = Header(None), db: AsyncSession = Depends(get_db))`
  принимает заголовок и DB dependency, загружает пользователя один раз,
  возвращает контекст `CurrentUser(user_id: UUID, tenant_id: UUID, user: User)`; tenant_id не nullable.
  Поле user — уже загруженная ORM-запись для проекции /me внутри auth; чужие потребители
  используют только user_id/tenant_id и не импортируют модель auth. Контекст не сериализуется
  целиком наружу; /me передаёт эту запись в builder ответа без второго запроса пользователя.
  Тип контекста определить здесь; наружу экспортировать через
  `backend/app/modules/auth/internal_api/interface.py`. Чужие модули импортируют только interface.
- Обновить четыре action-файла таблицы и два domain-файла издателей; для /me обновить
  `backend/app/modules/auth/features/me/domain.py` и при необходимости repository,
  чтобы не повторять разбор токена. Проекция ответа остаётся совместимой.
- Обновить `backend/tests/test_route_auth.py`; создать
  `backend/tests/modules/auth/test_current_user.py` и нужные `__init__.py` для unittest discovery.
  Обновить разделы существующих контрактов auth/settings/uploads по изменившимся отказам.
  Это перечень **будущих** файлов, не ссылки на якобы уже существующие тесты.

**Алгоритм и переходный срок:**

1. Отсутствие заголовка → MISSING_TOKEN; неподходящая схема, пустой токен → INVALID_TOKEN.
2. Проверка подписи, формы payload (объект), наличия строкового user_id и UUID. SignatureExpired
   ловить раньше BadSignature. Некорректный тип payload не должен дать TypeError/500.
3. Для изолированного С0 перенести текущий предел /me `max_age=86400` в один helper и распространить
   на всех четырёх читателей. Это **переходная совместимость существующего /me**, а не новый срок
   продукта. С0 нельзя выпускать как реализацию П77; С1 удаляет этот абсолютный предел для
   stateful-сеансов и вводит 30 минут/30 суток бездействия. Выдавать в С0 30-дневный remember нельзя.
4. По проверенному UUID загрузить пользователя. Нет пользователя, is_active=false или
   tenant_id=NULL → 401 UNAUTHORIZED. Компания берётся из записи пользователя, не из тела/query/
   заголовка клиента и не из несуществующего поля текущего payload.
5. Передать контекст потребителю. Бизнес-запросы сужаются tenant_id контекста. Чужой UUID ресурса
   отвечает 404, не раскрывая его компанию. Подмена X-Tenant/body/query не меняет контекст.
6. Не ловить ошибки инфраструктуры общим except Exception с выдачей INVALID_TOKEN.
   С0 не продлевает и не отзывает сеанс: состояние реализуется С1.

**Сторож:** AUTH_DEPENDENCIES знает get_current_user; старые _resolve_user_id и _bearer не
остаются разрешёнными обходами. Проверить import origin, а не только совпадение имени dependency.
PUBLIC_ROUTES сохраняет публичные login/register/link; комментарий link описывает текущий разбор
ссылки, не вход без пароля. Существующие KNOWN_GAPS продуктов не удалять без реализации их защиты
и не выдавать С0 за подключение всех бизнес-доменов. Новых исключений для четырёх потребителей нет.

**Обязательные поведенческие тесты:** реальный helper подписи и dependency, контролируемые часы,
DB fixture или подмена только репозитория; результат dependency не подменять. Каждый отрицательный
случай проверяет HTTP-статус/код и отсутствие вызова защищённой операции/записи файла.

| Случай | Ожидаемый результат |
|---|---|
| Отсутствие Authorization | 401 MISSING_TOKEN на всех четырёх потребителях |
| Неверная подпись (токен подписан другим ключом) | 401 INVALID_TOKEN на всех четырёх |
| Истечение (возраст больше переходного предела) | 401 TOKEN_EXPIRED на всех четырёх; свежий токен того же пользователя успешно проходит |
| Неактивный пользователь с корректным свежим токеном | 401 UNAUTHORIZED на всех четырёх; переключение is_active на false после выпуска тоже блокирует |
| Чужая компания | Две реальные записи компаний A/B и пользователи с одним email: токен A даёт только контекст A; запрос PATCH/DELETE валюты B через settings с токеном A → 404, строка B неизменна. Загрузка с подставленной B не создаёт запись/файл в B |
| Повреждённая схема/пустой Bearer, payload list/null, нет user_id, неверный UUID | 401 INVALID_TOKEN, ни одного 500 |
| Пользователь удалён либо без компании | 401 UNAUTHORIZED; NULL не даёт superadmin-доступ |
| Корректный активный пользователь | /me сохраняет форму ответа, settings читают свою компанию, upload записывает только свою компанию |

На уровне HTTP покрыть все четыре точки подключения и все роуты CRUD/profile сторожем.
Для чужой компании одного mock-утверждения «репозиторий вызван с A» недостаточно: нужна проверка
запроса/сохранённой строки B. Инверсия в будущей реализации: снять max_age, проверку is_active,
сужение по tenant_id или одну dependency — соответствующий тест обязан покраснеть.

**Критерий завершения С0:** поведенческие тесты + сторож + импорт четырёх роутеров проходят;
один конструктор URLSafeTimedSerializer и один вызов loads в auth/shared/session_tokens.py,
ни одного локального декодера в потребителях. Подпись, отсутствие, истечение, выключенный
пользователь и чужая компания доказаны отрицательными тестами, а не числом совпадений rg.
Команды — §8. Не объявлять С1/remember/отзыв реализованными по результатам С0.

настроек/пояса и billing для достоверного 14-дневного пробного доступа (auth:5/auth:12 опросника).
Основная реализация: auth/shared (модели, политика сеанса, репозиторий), login/register/me,
миграции; профиль settings через auth internal API. Клиентская часть — types/auth, useAuth,
authToken, LoginPage, RegisterPage, AuthLinkHandler, router и затронутые моки/тесты.

**Изменения:**

- Сервер разрешает постоянный идентификатор компании из ссылки перед поиском email; конкретное
  имя параметра/URL закрепить в auth.md до изменения схем и клиента. Использовать устойчивый
  идентификатор, не пересоздавать ссылку при переименовании компании. Это публичный контекст входа,
  а не принимаемый от клиента tenant_id защищённых запросов. Обычная форма позволяет ввести email,
  а не требует email из персонального секрета. Существующую ссылку пользователя не считать ссылкой компании.
- Согласованно снять глобальный запрет email регистрации и сузить вход/смену email в профиле.
  Составной индекс и модель привести к одному правилу. Обрабатывать коллизию БД как CONFLICT
  внутри компании. Две половины БАГ-13 нельзя выпускать отдельно.
- Сеанс идентифицируется проверенным токеном и его хешем в БД; добавить last_seen_at и revoked_at.
  У каждого входа уникальный случайный идентификатор сеанса в подписанном payload: входы одного
  user_id в одну секунду не должны сталкиваться по token_hash. Проверять связь Session.user_id
  с проверенной личностью; компания выводится по пользователю, не по полю запроса.
- Единая политика: обычный вход 30 минут, remember 30 суток **от last_seen_at**.
  Схема принимает фактически отправляемый rememberMe и явно отображает в sessions.remember;
  отсутствие флага сохраняет серверный default false, клиентский текущий default true не менять
  скрытно. Регистрационный автологин по существующему серверному default — обычный сеанс;
  localStorage на клиенте не означает remember на сервере.
- Проверять существование, отзыв, пользователя и срок **перед** продлением; при now >= expires_at
  отказать. Активный аутентифицированный запрос обновляет last_seen_at/expires_at серверным временем
  атомарно; истёкшая или отозванная запись не оживает от запроса. Не вводить абсолютный срок от
  подписи поверх П29: активный remember-сеанс может жить дольше 30 суток с момента входа.
  Не добавлять искусственный фоновый refresh ради удержания открытой вкладки.
- Миграция не добавляет tenant_id в sessions/user_roles; связь по user_id проверяется всегда.
  Старые сеансы не переводить молча в remember. В технической миграции отозвать старые токены
  без нового идентификатора и потребовать повторный вход; это явно указать в заметке о совместимости.
- На входе отключённый пользователь получает тот же отказ, что неверный пароль. Удалить secret_link
  из /me, нормализовать Owner → owner с устранением коллизий user_roles. Права не читать из role.
- П80: передать страну компании в settings; один пояс выбрать автоматически, при нескольких
  потребовать явное уточнение. Хранить идентификатор часового пояса с сезонными правилами, не
  фиксированный offset; дать последующую правку в settings. Пояс браузера не источник истины.
  UI объясняет границы дней/месяцев, фильтры, отчётные периоды и зависимые сроки.
- Привести клиентские типы обязательных имён, выбранную locale и fieldErrors к контракту.
  При 401 очищать токен, профиль и права и возвращать к входу той же компании с сообщением;
  при 403 оставлять живой сеанс. Проверить ошибки защищённых запросов, не только fetchMe.

**Приёмка:** часы в тесте: 29:59 → успех и продление, 30:00 без запросов → отказ;
remember до 30 суток → успех, на границе → отказ; активность через границу 30 суток от
первого входа сохраняет remember-сеанс. Повторный запрос не возрождает истёкший/отозванный сеанс;
конкурентное продление не отменяет отзыв. Два входа в одну секунду создают разные сеансы.
Регистрация A/B с одним email проходит, правильная пара работает только в своей компании;
пароль A в B не проходит, повтор email в B конфликтует, права/смена email не затрагивают A.
Постоянная ссылка работает повторно и после 7 суток, требует пароль, не меняется от имени компании.
Миграции проверяются на чистой и наполненной тестовой БД; исходные справочники есть у старой и
новой компании. Страна с одним/несколькими поясами, изменение в settings и переход сезона
проверяются отдельно; пробный срок получен от billing, а не константа UI. Real-mode клиент после
истечения очищает состояние и возвращает к нужной компании. Негативные тесты С0 остаются зелёными,
проверка истечения обновляется на stateful-политику.

### С2 · POST /api/auth/logout

**Зависимости:** С1; С3 не нужен (собственный сеанс).
**Изменения:** новый слайс logout и подключение роутера; отзыв текущего сеанса в БД без тела ответа
(204). Повтор для уже отозванного токена подтверждает результат без изменения/продления; для этого
использовать общий разбор подписи и поиск сеанса с режимом идемпотентного отзыва, не копию декодера.
Отсутствующая/неверная подпись сохраняет отказы §3. Другие сеансы этого аккаунта не отзывать.
**Приёмка:** вход → logout → /me/settings/upload отклоняют старый токен; повтор logout не меняет
состояние; второй сеанс остаётся живым; чужой токен/компания не дают отзыв чужой записи.
Real-mode клиент очищает хранилища даже при сетевой ошибке; проверить совместимость 204 с apiPost.

### С3 · Вычисленные права и 403

**Зависимости:** С1 (и транзитивно С0); не зависит от С2.
**Изменения:** check_permission в auth internal API получает живой контекст компании;
читает user_roles, role_permissions, user_permissions, сводит несколько ролей и персональные
переопределения по П2. Сохранить базовый строчный перечень и перспективу редактирования П3.
На проводе использовать существующие строчные имена: бухгалтер — accounting, наблюдатель — viewer,
кладовщик — warehouse (`frontend_vue/src/types/settings.ts`); accountant/observer не новые роли.
Новый GET /api/auth/me/permissions отдаёт вычисленный результат (Р-Д4/Р-Д5), не сырую матрицу.
Внешние домены вызывают общий механизм, отказ 403 FORBIDDEN. Отсутствие настройки не разрешает
доступ автоматически. Схема permission_items получает domain и ограничения из Р-Д1 rights;
миграции/инициализация П33 применяют Р5, включая N=0 и каждое CRUD-действие отдельно.
П82–П84 задают начальные доменные права, но не разрешают полную роль manager/viewer целиком.
**Приёмка:** две роли и override разрешения/запрета; различие read/edit/create/delete;
компания A не читает матрицу B; нет роли/права → 403; отключённый пользователь → 401 до проверки
прав. Порог П33: 8/10, 9/10, N=0 и независимые действия. Начальные права П82–П84 проверены по
полям/элементам, П16 не расширен; вырезание чувствительных данных выполняют доменные читатели,
включая историю/архив, а не только Vue. Клиент до получения прав ничего не разрешает и не
показывает скрываемые поля; сетевое ожидание отличается от окончательного отказа.

### С4 · Редактор матрицы, роли, история и уведомления

**Зависимости:** С3; общие interfaces config/settings, audit-feed и notifications.
**Изменения:** сохранить внешний редактор GET/PUT /api/config/permissions, описанный в config.md;
он вызывает auth internal API для чтения/записи матрицы своей компании. Смена матрицы — clean-slate
по Save. Один владелец элемента матрицы — config; текущие права пользователя — auth.
Владелец/админ меняют матрицу по П12, роли отдаёт сервер; legacy role удаляется только вместе
с потребителями UI, источником полномочий оно уже не является. После успешного сохранения —
сущностная история П42 и один общий permissions_changed по П51, с дедупликацией БД П56.
Если запись инициирована settings, используется тот же путь, а не второй тип/эмиттер.
Auth даёт адресацию по правам своей компании; подписки/доставка — notifications по П54.
**Приёмка:** посторонний получает 403, чужая матрица недоступна; Save атомарен, rollback не оставляет
историю или уведомление о несуществующей правке. Повтор события после рестарта не создаёт дубль;
письма и сайт соблюдают подписки и права, другая компания исключена. Права П82/П83/П84 редактируются
независимо, скрытая себестоимость и суммы не появляются от права полного архива автоматически.
После изменения клиент получает актуальные вычисленные права. История не содержит секретов.

### С5 · Приглашение, увольнение и восстановление сотрудника

**Зависимости:** С1 (сеансы и компания), С3 (auth.user); общая история П85 и почтовый интерфейс
settings по П53/П59. Копирование ссылки работает без настроенной почты. С4 не обязателен для
проверки прав, но единая матрица/элементы должны совпадать.
**Изменения:** защищённые операции списка/создания приглашения/повторной выдачи/отключения/
восстановления сотрудника; публичный приём приглашения с token/password в теле. Конкретные
маршруты и схемы сначала описать в auth.md, не объявлять нынешний GET /link приёмом приглашения.
Пользователь создаётся до первого входа с именем и ролью, без рабочего пароля; миграция снимает
требование рабочего password_hash для приглашённого, вход такого пользователя запрещён.
Приглашение хранит tenant_id, user_id, хеш секрета, issued_at/expires_at, consumed_at/revoked_at;
секрет выдаётся для копирования/письма, не возвращается в /me или журнале. Срок ровно 7 суток
от выдачи (П78); приём атомарно устанавливает пароль и погашает приглашение, создаёт сеанс
по общей политике. Повторное приглашение отменяет прежний неиспользованный секрет.
Увольнение одной транзакцией отключает пользователя, отзывает **все** его сеансы и отменяет
неиспользованные приглашения. История и внешние ссылки на автора сохраняются. Восстановление
возвращает ту же запись/user_id, но не оживляет отозванные сеансы/ссылки; следующий вход или
новое приглашение проверяются заново. Пароли и токены не копировать в ленту П85.
**Приёмка:** приём до 7 суток успешен, на границе/после — отказ; повтор/гонка приёма создаёт
не более одного результата, отозванная ссылка не принимается. Дубликат email в своей компании
даёт 409, в чужой не мешает. Создание/отключение без права → 403; приём публичен, создание
не входит в PUBLIC_ROUTES. Выключение сотрудника с двумя сеансами и приглашением блокирует все
три пути доступа, включая гонку продления/приёма; rollback не оставляет частичное увольнение.
Восстановление сохраняет ID/авторство/старые заказы и заметки; старые сеансы и ссылки всё ещё
недействительны. Копирование работает при ненастроенном SMTP; письмо уходит через компанию,
ошибка доставки не отменяет возможность скопировать приглашение. Общая история видна по правам.

### С6 · Серверный журнал безопасности

**Зависимости:** С2, С4, С5; [общий журнал](../general/сквозное-audit-log-план.md).
**Изменения:** общий серверный ярус П40/П41 для входа, выхода, неудачных попыток, использования
ссылки и мета-записей удаления истории. Управление сотрудниками остаётся также в сущностной
истории П85; не переносить его целиком в скрытый журнал. Не писать пароль, полный токен,
CSRF или секрет приглашения. Не выдавать таблицу безопасности во frontend API.
**Приёмка:** успешные/неуспешные операции оставляют соответствующие записи, события входа
не попадают в общую ленту/уведомления; управление сотрудниками там присутствует по правам.
В записи безопасности нет секретов, компания не подменяется клиентом, неудача до определения
компании не приписывается случайному tenant. Инверсия отключения записи краснит тест.

### С7 · CSRF и ограничение перебора как инженерная защита

**Зависимости:** С1; ответ владельца не требуется (auth:3/auth:7 опросника).
**Изменения:** документировать модель Bearer-запросов; реализовать сверку X-CSRF-Token
с текущим сеансом для изменяющих защищённых операций, исключения публичного входа/регистрации/
приёма приглашения указать явно. Ограничитель входа/регистрации реализовать по проверенным
настройкам, единый отказ/интервал повтора закрепить до клиентских изменений. Общая dependency,
не собственная проверка в каждом роуте; 403 CSRF не означает отсутствие бизнес-права FORBIDDEN.
**Приёмка:** верный CSRF проходит, отсутствующий/чужой/старый блокирует запись; публичный приём
не требует уже существующего сеанса. Ограничитель с контролируемыми часами достигает границы,
снимается после окна, работает для повторных запросов, даёт согласованный ответ UI;
проверить обход через второй экземпляр сервера. Проверки безопасности не раскрывают email
другой компании. Зелёный rg по заголовку не заменяет эти тесты.

### С8 · Устранение дублей и границы модулей

**Зависимости:** С1, С5.
**Изменения:** удалить неиспользуемую _ensure_unique_slug; общий builder для каждого вида ссылки
(постоянная компания и приглашение различаются смыслом); убрать старую сборку секрета профиля.
Смена пароля в settings вызывает auth internal API и отзывает сеансы атомарно с записью пароля.
MagicLinkInput либо используется с новой схемой приёма, либо удаляется; не держать мёртвую схему.
**Приёмка:** все вызовы найдены поиском, старые helpers/локальные сериализаторы исчезли;
смена пароля не пишет чужую модель напрямую, старые сеансы более не работают, новый вход
успешен с новым паролем. Rollback сохраняет согласованное состояние. Тесты ссылок различают
постоянный URL и одноразовый секрет, /me и профиль больше не раскрывают приглашение.
