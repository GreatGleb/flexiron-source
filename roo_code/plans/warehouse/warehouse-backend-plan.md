# План реализации домена warehouse (бэкенд)

Контракт домена — [`api/warehouse.md`](../../roo-context/api/warehouse.md) — написан **по коду**:
он говорит, что фронт зовёт, и честно называет, чего нет. Три вещи он назначать не вправе, и они
есть работа этого плана: кто прав в конфликте схемы и контракта, каким кодом отказывать там, где
сегодня не отказывает никто, и в каком порядке это строить.

Входы плана — три, а не один: нереализованные эндпоинты контракта, решения владельца из
[`00-решения-владельца.md`](../api/audit/00-решения-владельца.md) (в том числе те, номер которых в
контракте домена не встречается ни разу), и названные дыры — разделы «Обязанности сервера» и «Чего
в домене нет».

Скил слайса — [`create-api-feature.md`](../../skills/create-api-feature.md): порядок слоёв
`schemas → repository → domain → action`, миграции в `backend/alembic/`, модель в
`app/modules/warehouse/shared/models.py`, регистрация роутера в `backend/app/main.py`.

## 4. Шесть сквозных правил — что делает этот домен

Формулировки не свои: правило целиком — в [`сквозное-сводка.md`](../general/сквозное-сводка.md) и
в плане темы. Здесь — только что домен обязан внести.

1. **Права (§6)** — [сводка](../general/сквозное-сводка.md#1-права-6--план). Домен заводит раздел
   `## Права домена` в контракте и три таблицы: элементы `warehouse.batch`, `warehouse.movement`,
   `warehouse.offcut`, `warehouse.deficit`, `warehouse.stock` (≥1 `entity` на сущность);
   отображение «эндпоинт → элемент и действие» на все 37 путей ровно по разу; дефолт по семи
   строчным ролям `UserRole` (`frontend_vue/src/types/settings.ts:185-192`), складская из них —
   **`warehouse`, строчная**.
   **Два перечня ролей не смешивать** — сквозной план прав говорит это дословно: «Канонический
   перечень ролей — семь строчных значений, `UserRole`… С матрицей он не пересекается ни в регистре,
   ни в составе» (`roo_code/plans/general/сквозное-rights-план.md:173-175`). Заглавная `Warehouse` —
   роль **матрицы мока**, одна из четырёх (`frontend_vue/src/services/mocks/config.ts:186`), и она к
   шапке таблицы 3 отношения не имеет: линза П-7 краснеет ровно на заглавную роль
   (`roo_code/plans/general/сквозное-rights-план.md:569`). Прежняя редакция этой строки приписывала
   `Warehouse` обоим перечням сразу — таблица, написанная по ней, была бы отвергнута гейтом.
   Вырезаемое с замыканием названо владельцем поимённо (П18): `unitPrice`, `totalCost`,
   `marginPercent` вырезаются, `sellingPrice` заводится в ответе посчитанным.
   Механизм права домен не изобретает: матрица `item × роль × {read, edit, create, delete}` с
   переопределением на пользователя (**П2**), и складские элементы в неё **добавляются** — сегодня
   перечень элементов строится только из секций и полей карточки поставщика
   (`frontend_vue/src/services/mocks/config.ts:189`), складского в нём нет ни одного элемента.
   Дефолты склад назначает **своим доменом отдельно, по надобности роли** (**П7**: правило действует
   всегда и на всё, гранулярность — CRUD); скопировать их у соседнего домена нельзя, и именно
   поэтому строки складской роли `warehouse` (строчной, из `UserRole`) пишет этот план, а не сквозной. Какое действие читает операцию,
   решено владельцем поимённо (**П15**) — без этого решения отображение «эндпоинт → элемент и
   действие» строилось бы по HTTP-методу и было бы неверным: резка есть `edit`, значит
   `POST /cutting` ложится на `warehouse.batch` + `edit`, а не на `create`; загрузка файла партии и
   обрезка (П11) — тоже `edit`, а не самостоятельная операция; **отдельного списка именованных прав
   домен не заводит вовсе**, механизм один — матрица П2. Вырезание идёт с двумя обязанностями
   **П17**: клиент обязан знать право **до первой отрисовки**, иначе колонка себестоимости мигает
   (правило уже записано в коде — `frontend_vue/src/composables/useOrderPermissions.ts:12`), и
   вырезание обязано быть **полным** — ровно поэтому П18 вырезает ещё и `marginPercent`, иначе
   себестоимость восстанавливается делением. **П5** называет два места, где цена утечки высока, и
   оба у склада есть **своими путями**: история — пять журналов домена, где цену форматирует в
   готовую строку `oldValue`/`newValue` сам сервер (П39), то есть вырезанная из тела партии цена
   вернётся строкой журнала, если тот же признак не режет и её; аналитика — `GET /stock/:productId/cost`
   (FIFO-стоимость) и дашборд «Стоимость склада»
   (`frontend_vue/src/services/mocks/analytics.ts:326`), который питается складскими партиями, хотя
   путь принадлежит домену `analytics`. Отсюда приёмка права на себестоимость проверяет **три места
   домена, а не одно**: тело партии, `…/audit` пяти журналов и `GET /stock/:productId/cost`.
2. **Мультиарендность (§4)** — [сводка](../general/сквозное-сводка.md#2-мультиарендность-4--план).
   Тенантских таблиц домена шесть, `tenant_id` объявлен у всех
   (`grep -c tenant_id backend/app/modules/warehouse/shared/models.py` → 6). Домен перечисляет их,
   по каждой функции репозитория ссылкой показывает сужение, и чинит единственное известное
   исключение — `UniqueConstraint` строки остатка без арендатора (БАГ-28), моделью и миграцией
   разом. Клиент `tenantId` не шлёт и не начнёт: `grep -c "headers\|options"` по
   `warehouseService.ts` → 0.
3. **Аудит-лог (§9)** — [сводка](../general/сквозное-сводка.md#3-аудит-лог-9--план). Своей таблицы домен
   не заводит: `stock_audit_entries` сливается в общую `audit_entries` (П38). В таблицу ожиданий
   спеки домен вносит **мутирующие операции**: создание/правка/удаление партии, обрезка, нехватки;
   создание движения; резка; правка строки остатка — и по П36 пишет **каждая**, сегодня не пишет ни
   одна (`auditLog: []` у создания партии, обрезка, движения и нехватки). Пять значений
   `entityType` — `stock`, `batch`, `offcut`, `movement`, `deficit`. `sensitive`-записей у домена
   ни одной (`grep -c "sensitive" frontend_vue/src/types/warehouse.ts` → 0). Удаление записи — только
   владелец, неизвестная → `AUDIT_ENTRY_NOT_FOUND`; удаление партии чистит её записи явно (FK на
   девять типов сущностей одной колонкой не выразить — цена П38, названная там же).
4. **Уведомления (§10)** — [сводка](../general/сквозное-сводка.md#4-уведомления-10--план). Раздел
   `## События домена (§10)`. Сегодня домен рождает два события — `notifyBatchReceived` при создании
   партии и `notifyStockDeficit` при вновь открытой нехватке. Добавляется **`batch_expired`** (П51,
   новый тип) и оживает **`reserve_expiring`** (П52: срок брони три рабочих дня, значение в
   настройках; «рабочий день» умолчанием — без субботы и воскресенья).
   **Флаг тревоги несут два складских кода из четырёх, а не один.** Сводка: «флаг тревоги несут ровно
   три кода» ([`сквозное-сводка.md`](../general/сквозное-сводка.md#4-уведомления-10--план)); Н9
   называет эти три поимённо — `payment_overdue`, `stock_deficit` и `batch_expired`
   (`roo_code/plans/general/сквозное-notifications-план.md:303-307`), и два из трёх складские.
   Значит таблица `## События домена (§10)` (колонки сводки: код · переход ссылкой · условие ·
   дискриминатор · флаг тревоги) выходит такой:

   | код | флаг тревоги | дискриминатор |
   |---|---|---|
   | `batch_received` | нет | — |
   | `stock_deficit` | **да, но не всегда** | только когда нехватка **под подтверждённый заказ** (П55, Н9) — дискриминатор, а не сам тип |
   | `batch_expired` | **да, всегда** | флага не отбирает ничто: Н9 не ставит `batch_expired` никакого узкого условия, в отличие от `stock_deficit` |
   | `reserve_expiring` | нет | «Остальные двенадцать флага не получают никогда» (Н9) |

   **Поправка к прежней редакции плана.** Она называла флаг только у `stock_deficit`, а `batch_expired`
   подавала как «новый тип» без флага — одна строка из четырёх вышла бы неверной, и блок `alerts`
   дашборда просроченных партий не показал бы. Флаг ставит **эмиттер в момент события** (Н9), то
   есть на складе — в том же переходе, где рождается событие, а не отбором при чтении ленты.
   Четвёртая обязанность склада из перечня сквозного плана (`:401`) — пересчёт нехватки при правке
   `minStock` с обеих сторон порога (П57) — живёт в С7 и в вопросе 13.
   Списание, резка и движения уведомлений не рождают — сказано владельцем прямо.
   Эмиттер зовётся внутри условия перехода: повтор «тот же заказ просит снова» события не рождает
   уже сегодня, и это поведение сохраняется, но «уже уведомили» переезжает из памяти процесса в базу
   (П56).
5. **Идемпотентность (§11)** —
   [сводка](../general/сквозное-сводка.md#5-идемпотентность-11--план). Пять `POST` домена
   двигают склад, то есть необратимы все пять: `/batches`, `/movements`, `/cutting`, `/offcuts`,
   `/deficit` — каждому ровно одна строка «обязателен» с ценой повтора. Save карточки партии
   применяется **одной транзакцией** (П43, склад назван атомарным поимённо): сегодня это
   `patchBatch()` и следом `createMovement()` двумя запросами без общей границы, и провал второго
   заглушён. Версии записи (`If-Match`) у домена нет — last-write-wins, и контракт пишет это прямо.
6. **Кастомные поля (§8)** — [сводка](../general/сквозное-сводка.md#6-кастомные-поля-8--план).
   Сводка ставит склад в блок **«чтение (нет значения = «неизвестно», не ноль)»**, и сквозной план
   расписывает этот блок тремя пунктами: [`сквозное-custom-fields-план.md:407-412`](../general/сквозное-custom-fields-план.md)
   («Блок Г — домен-потребитель значения (`warehouse`)»), раскладка семнадцати доменов ставит
   `warehouse` в блок Г (`:432`). Три пункта блока Г ложатся на домен целиком, формулировки не свои:
   **(1)** строка `Кастомные поля: да.` и ссылка на сквозной план — домен значения **не хранит, но
   читает**; **(2)** применить КП-11 к `DENSITY_FIELD_ID` — зафиксировать в контракте, что отсутствие
   значения есть «плотность неизвестна», а не ноль; **(3)** новых потребителей по жёсткому `fieldId`
   не заводить без той же проверки.
   Потребитель у склада есть, и он один: **вес обрезка выводится из плотности материала, а плотность —
   значение кастомного поля товара**, читаемое по жёстко зашитому идентификатору
   `DENSITY_FIELD_ID = 'f-1-3'` (`frontend_vue/src/domain/cutting.ts:223`), чтение —
   `product?.fieldValues?.find((f) => f.fieldId === DENSITY_FIELD_ID)` (`:229`), точка входа —
   `resolveOffcutWeight` (`:273`), и зовут её три складских композабла:
   `frontend_vue/src/composables/useWarehouseCutting.ts:261`,
   `frontend_vue/src/composables/useWarehouseOffcutCard.ts:247`,
   `frontend_vue/src/composables/useWarehouseOffcutCreate.ts:253`. То есть вес куска на путях
   `POST /cutting`, `POST /offcuts` и `PATCH /offcuts/:offcutId` сегодня выводится из кастомного поля
   товара — **у клиента**. КП-11 уже исполнен кодом (`productDensityKgM3` при отсутствии значения даёт
   `null`, и `resolveOffcutWeight` отвечает `reason: 'no_density'`, а не нулём), но держится он
   комментарием, а не контрактом; комментарий предупреждает прямо: «если правка каталога уведёт этот
   id, вывод веса сломается ТИХО — «поля нет» превратится в «веса нет», а не в ошибку»
   (`frontend_vue/src/domain/cutting.ts:220-221`). Работа домена: **вписать это правило в контракт
   строкой** (пункт 2 блока Г) и не заводить второго потребителя по жёсткому `fieldId` без той же
   проверки (пункт 3). Серверная половина — вопрос 23: считает ли вес сервер, и если да, то той же
   функцией, а не второй её копией.
   **Поправка к прежней редакции плана — две ошибки разом.** Первая: замер «`fieldValues`/`FieldDefinition`/`fieldId`
   в типах, моке и сервисе домена — 0» был сужен до трёх файлов и не включал `frontend_vue/src/domain/cutting.ts`,
   откуда этот же план берёт 5 из 22 кодов каталога домена (раздел 1) и **пять из десяти** отказов резки
   (С5; другие пять — литералы самого мока, разводка источников — в разделе 4-бис, строка «таблица
   отказов резки»);
   замер, не смотрящий туда, где потребитель сидит, не мог дать ничего, кроме нуля, и из него был
   выведен ложный вывод «не берётся». Вторая: оговорка сводки была перенесена на **чужой предмет** —
   «нет значения = «неизвестно», не ноль» сказано сводкой про **значение кастомного поля**, то есть
   про плотность, а прежняя редакция подставила под неё `unitPrice`/`totalCost`. Цена и плотность —
   разные величины: цену держит **правило домена 2 контракта** («цена, которой никто не назвал, —
   это `null`, а не ноль»), и это отдельное правило домена, а не оговорка §8.

### Восемь решений владельца, о которых контракт домена молчит

Сквозные правила выше — не весь сквозной слой. Эти восемь решений домен обязан исполнить, и ни одно
из них в `api/warehouse.md` не названо даже номером: замер берёт их вместе с девятым, П44, который

## 4-бис. Названные дыры контракта — все 27 построчно

## 5. Порядок слайсов

Девять задач. Первая — фронтовая и ни от чего не зависит; остальные восемь — бэкенд, и порядок у них
не вкусовой: он вытекает из того, что чем считается.

### С0 · Мок-долг домена: отказ несёт код, а не текст

**Независима. Идёт первой.** Почему не отдельной дорожкой и не барьером на все 196 мест проекта:
шим `errorCode` делает полумигрированное состояние законным — откат на `message` описан в его
собственном комментарии как переходный, и там же сказано, что обратный порядок безопасен, потому что
`code` у голого `Error` отсутствует и откат срабатывает сам
(`frontend_vue/src/services/apiErrorCode.ts:44`). Барьер не нужен; правдивые отказы в своём домене
нужны.

Работа:
1. 52 места `throw new Error(` в `frontend_vue/src/services/mocks/warehouse.ts` → `ApiRequestError`
   с кодом в поле `code` и человеческим `message`. Конструктор уже есть и принимает
   `{ status, message, code, fieldErrors }` (`frontend_vue/src/types/api.ts:35-40`). Статус берётся
   по смыслу кода: `*_NOT_FOUND` → 404, `*_LINKED_TO_ORDER` и `AUDIT_ENTRY_NOT_FOUND` при чужой
   записи → 409, прочие отказы правила → 422.
2. Два места подстановки из таблицы (`frontend_vue/src/services/mocks/warehouse.ts:906`, `:1533`)
   переводятся так же: `MATERIAL_ERROR_CODE[...]` даёт код, он кладётся в `code`, а не в текст.
3. Спеки, утверждающие отказ **по тексту**, переписываются на утверждение о поле. Замер:
   `cutting.spec.ts` — 14, `unknown-id-is-refused.spec.ts` — 7, `offcut-order-pick.spec.ts` — 1,
   `warehouse-transfer-location.spec.ts` — 1, `audit-entry-identity.spec.ts` — 1; итого **24**
   утверждения в пяти файлах (`grep -rc "toThrow(['\"](BATCH_|OFFCUT_|MOVEMENT_|STOCK_|DEFICIT_|AUDIT_ENTRY_|INSUFFICIENT_|CUTTING_)"`).
   Форма: `await expect(fn()).rejects.toMatchObject({ code: 'BATCH_NOT_FOUND' })` вместо
   `toThrow('BATCH_NOT_FOUND')`.

   **Три из пяти файлов — общие, и трогать в них можно только складские строки.** Замерено
   пофайлово: `unknown-id-is-refused.spec.ts` держит 17 утверждений, из которых складских 7, а
   остальные десять — `ORDER_NOT_FOUND`, `CATEGORY_NOT_FOUND`, `PRODUCT_NOT_FOUND`,
   `NOTIFICATION_NOT_FOUND`, `BCC_EVENT_NOT_FOUND`, `FIELD_NOT_FOUND`, `SECTION_NOT_FOUND`;
   `offcut-order-pick.spec.ts` — 9, из которых складское одно (`OFFCUT_NOT_AVAILABLE`), а
   `SHIPMENT_EXCEEDS_STOCK` и `OFFCUTS_EXCEED_QUANTITY` бросает мок **заказов**
   (`grep -rl "new Error('SHIPMENT_EXCEEDS_STOCK')" frontend_vue/src/services/mocks` →
   `orders.ts`); `audit-entry-identity.spec.ts` — код `AUDIT_ENTRY_NOT_FOUND` бросают четыре мока,
   и складской из них один. Переписать чужую строку на `toMatchObject({ code })` значит её
   **уронить**: чужой мок всё ещё бросает голый `Error`, у которого поля `code` нет. Отсюда форма
   приёмки ниже — она считает складские коды, а не строки файлов.
4. Два места фронта, читающие код правильно, не трогаются — они уже через шим
   (`frontend_vue/src/composables/useWarehouseBatch.ts:341`,
   `frontend_vue/src/composables/useWarehouseOffcutCard.ts:386`). Двенадцать мест, кладущих
   `e.message` в состояние ошибки, тоже не трогаются этой задачей: они показывают текст, и текст
   теперь станет человеческим — это улучшение, а не поломка. Их перевод на таблицу ключей — БАГ-14,
   отдельная работа.

Приёмка С0, три команды, и вторая — та, которую нельзя написать шире:

### С1 · Миграция схемы под контракт и решения

Зависит от: С0 не нужна, но идёт после неё по очереди. **Одна миграция**, потому что половина правок
меняет одни и те же таблицы, и дробить их значит оставлять схему в промежуточных состояниях.
Содержимое — строка в строку из раздела 2 плюс решения:

  выводится из настроек, П19); завести
  `margin_percent`; удалить `exchange_rate` (П23); удалить `quantity_remaining`, `status`,

  на `uoms.id`, `RESTRICT` — та же правка и тот же довод, что у партии (раздел 2, строка «единица»);
  удалить `total_cost` (`:114`) — производное `quantity × unitPrice`, оба множителя в той же строке
  (П68, раздел 2, вопрос 20); колонку `currency` **до ответа на вопрос 22 не заводить** — её и сегодня нет,

  снимком на момент создания, а не вычислением при чтении — раздел 2, строка движения). Ответ
  «снимок» добавляет в эту же миграцию `currency_id` FK на `currencies.id`, `RESTRICT` — той же

  заказа внешними ключами **не становятся**: модуля `orders` на бэкенде нет;

проверить обязательно: колонки, не попавшие в автогенерацию, — самый частый способ получить схему,
расходящуюся с моделью.

### С2 · Партии: чтение и запись — 9 эндпоинтов

`GET /batches`, `POST /batches`, `GET /batches/:id`, `PATCH /batches/:id`, `DELETE /batches/:id`,
`GET /batches/:id/aggregates`, `GET /batches/:id/active-sales`, `GET /batches/:id/audit`,
`DELETE /batches/:id/audit/:entryId`.

**Почему партия первой.** Она единственная сущность домена, не ссылающаяся ни на что внутри домена:
движение ссылается на партию (`backend/app/modules/warehouse/shared/models.py:104`), обрезок — на
партию дважды (`:144`, `:155`), нехватка — на партию (`:187`), журнал — на партию (`:242`). Строить
что-либо раньше партии значит писать ссылки в никуда.

Три производных поля партии (`quantityRemaining`, `status`, `totalCost`) в этом слайсе считаются по
пустому журналу движений и дают, соответственно, полное количество и `available` — это верно и
честно до С3. Агрегаты и активные продажи — производные целиком, колонок под них нет и не будет.

Save применяется одной транзакцией (П43). Удаление партии удаляет её движения, обрезки и записи
журнала — схема каскад требует четырьмя FK, и контракт назвал схему старшим источником.

### С3 · Движения — 5 эндпоинтов

`GET /movements`, `POST /movements`, `GET /movements/:id`, `GET /movements/:id/audit`,
`DELETE /movements/:id/audit/:entryId`.

Зависит от С2 (ссылка на партию) и от С1 (колонка `offcut_id`). **Здесь оживают три производных поля
партии**: остаток и статус выводятся из журнала движений целиком — это инвариант, а не
инициализация, и мок прямо говорит, что бэкенд сделает ровно этот пересчёт при старте с сохранённого
журнала (`frontend_vue/src/services/mocks/warehouse.ts:389-416`). Список «что уносит металл» — один
на запись и на пересчёт (`OUTGOING_MOVEMENT_TYPES`), и раздвоение этого списка ломает пересчёт молча.

`DELETE /api/warehouse/movements/:movementId` в этот слайс **не входит**: у него нет функции клиента,
раздела в контракте тоже нет намеренно — что происходит с партией при удалении факта, изменившего
остаток, не сказано нигде (правило домена 18). Строка ниже, в «Требует решения владельца».

### С4 · Обрезки — 8 эндпоинтов

`GET /offcuts`, `POST /offcuts`, `GET /offcuts/offers`, `GET /offcuts/:id`, `PATCH /offcuts/:id`,
`DELETE /offcuts/:id`, `GET /offcuts/:id/audit`, `DELETE /offcuts/:id/audit/:entryId`.

Зависит от С2 и С3: создание обрезка списывает материал партии движением, а `offcut_id` на движении —
единственная дорога куска в заказ. Порядок разбора путей важен и закреплён: сравнение строкой для
`/offers` стоит **до** регулярки карточки обрезка, иначе `offers` будет прочитан как идентификатор.

Правило оценки куска живёт в домене заказов (`offcutAllocation`), и склад его не переписывает —
сервер обязан звать ту же функцию, а не вторую её копию.

**Кастомное поле здесь и есть работа блока Г** (раздел 4, правило 6). Колонка `weight_kg` заводится
хранимой и хранит **только ручное значение**; `null` означает «выводи», а не «нет веса». Вывод
читает плотность материала — значение кастомного поля товара по `DENSITY_FIELD_ID`
(`frontend_vue/src/domain/cutting.ts:223`) — и по КП-11 отсутствие значения даёт «плотность
неизвестна»: ответ остаётся `null`, отказа нет и нуля нет. Кода отказа под «плотности нет» домен
**не заводит**: это не ошибка ввода и не дефект клиента, а законное состояние каталога, и
`resolveOffcutWeight` отвечает на него `reason: 'no_density'` (`frontend_vue/src/domain/cutting.ts:303`, перечень причин — `:244`),
а не исключением. Отсюда две обязанности слайса: (а) `PATCH /offcuts/:offcutId` с `weightKg: null`
обязан **стирать** ручное значение, а не игнорировать ключ — иначе «отдать расчёту»
(`useWarehouseOffcutCreate.ts:269-270`) перестанет работать; (б) кто именно считает вес на сервере и
попадает ли он в `GET /offcuts/offers` — **вопрос 23**, до ответа колонка `weight_kg` заводится, а
серверного вывода план не назначает.

### С5 · Резка — 1 эндпоинт

`POST /cutting`. Зависит от С2, С3, С4: один вызов создаёт обрезки, списывает материал и пишет
движения. Проверяет всё **до первой записи** и проводится целиком либо не проводится — так устроен
мок, и это не деталь реализации, а требование: десять его отказов перечислены в каталоге, и все
десять обязаны отказать раньше, чем что-нибудь записано.

**Источников у этих десяти два, и переносить надо оба** (разводка и условия — в разделе 4-бис,
строка «таблица отказов резки»). Пять приходят из каталога домена `MATERIAL_ERROR_CODE`
(`frontend_vue/src/domain/cutting.ts:53-57`) — их мок только ретранслирует строкой
`throw new Error(MATERIAL_ERROR_CODE[consumption.reason])`
(`frontend_vue/src/services/mocks/warehouse.ts:1533`). Пять других в `domain/cutting.ts` не
встречаются ни разу и стоят литералами в самом `mockExecuteCutting` — по коду на строку:

- `BATCH_NOT_FOUND` (`frontend_vue/src/services/mocks/warehouse.ts:1511`)
- `CUTTING_NO_OFFCUTS` (`frontend_vue/src/services/mocks/warehouse.ts:1513`)
- `CUTTING_KERF_NOT_APPLICABLE` (`frontend_vue/src/services/mocks/warehouse.ts:1524`)
- `INSUFFICIENT_QUANTITY` (`frontend_vue/src/services/mocks/warehouse.ts:1534`)
- `CUTTING_QUANTITY_MISMATCH` (`frontend_vue/src/services/mocks/warehouse.ts:1539`)

Перенос одного домена дал бы пять кодов из
десяти и **молча потерял** три проверки, которых в домене нет вовсе: применимость пропила к
нелинейной единице, расход против остатка партии и сверку присланного `sourceQuantity` с
выведенным расходом.

Ширина реза приходит обязательным ключом `kerfMm` тела; настройка арендатора (П34) даёт умолчание
формы, а не значение запроса, и обязательности ключа не снимает.

Вес рождаемых резкой обрезков подчиняется тому же правилу блока Г, что и в С4: строка резки несёт
`weightKg` (`frontend_vue/src/composables/useWarehouseCutting.ts:312`), ручное значение отличается от
выведенного признаком `row.weightKg != null` (`:278`), а выведенное читает плотность кастомным полем
через тот же `resolveOffcutWeight` (`:261`). **Второй копии расчёта у резки нет и не заводится** —
это пункт 3 блока Г, запрет на нового потребителя по жёсткому `fieldId` без той же проверки.

### С6 · Остатки — 6 эндпоинтов

`GET /stock`, `GET /stock/:productId`, `PATCH /stock/:productId`, `GET /stock/:productId/cost`,
`GET /stock/:productId/audit`, `DELETE /stock/:productId/audit/:entryId`.

Зависит от С2 и С3, а ещё — от таблицы резервов, заведённой в С1: восемь из четырнадцати полей
строки остатка считаются из партий и резервов при
каждом чтении. FIFO-стоимость считает по **доступному**, а не по остатку: вычитается и чужой резерв,
и чужой хват разбивки — и недостачу сообщает, а не усредняет. Без таблицы резервов слайс
выдаст `availableQuantity`, равный остатку, и это будет не «пока приблизительно», а обещание
заказу металла, уже обещанного другому заказу: ровно тот дефект, от которого мок отдельно
предостерегает числами (`frontend_vue/src/services/mocks/warehouse.ts:1788-1795`).

Здесь же закрывается БАГ-02 (строку остатка не заводит никто) и БАГ-04 («нет строки остатка»
отвечает двумя разными кодами — `STOCK_ITEM_NOT_FOUND` и `STOCK_NOT_FOUND`): при производной
проекции строка существует ровно тогда, когда у товара есть партии, и второй код становится не
нужен. Какой из двух остаётся — `STOCK_ITEM_NOT_FOUND`, он у чтения и правки; `STOCK_NOT_FOUND`
уходит вместе со своим единственным местом.

### С7 · Нехватки — 7 эндпоинтов

`GET /deficit`, `POST /deficit`, `GET /deficit/:id`, `PATCH /deficit/:id`, `DELETE /deficit/:id`,
`GET /deficit/:id/audit`, `DELETE /deficit/:id/audit/:entryId`.

Зависит от С6 (`minStock` и признак нехватки) и от сквозного плана уведомлений. Здесь живёт П57:
правка `minStock` в карточке товара обязывает сервер пересчитать нехватку по этому товару **в тот же
момент** — не ждать складской операции. Обратная половина (порог опустили — нехватка, заведённая
порогом, закрывается тем же пересчётом) помечена в решении как чтение, а не слово владельца; строка
ниже.

`POST /deficit` — тот случай, где у мока шесть полей заполнены константами (БАГ-26), а клиент
написан и экрана нет: записи дефицита рождает внутрипроцессная `recordShortage`, а не эндпоинт.

### С8 · Выгрузка — 1 эндпоинт

`GET /export/:tab`. Зависит от С2, С4, С6, С7 — выгружает пять вкладок. Четыре обязанности сервера
названы контрактом: отвечать CSV, а не `ApiResponse<string>`; переводить подписи колонок по
`_locale` из query, а не по `Accept-Language`; отдавать весь отфильтрованный набор без пагинации.
Четвёртая — состав колонок — **решение владельца**, и слайс без неё не закрывается.

Клиента при этом чинить придётся вместе с сервером: `apiGet` читает `res.json()`, то есть настоящий
`text/csv` клиент прочитать не может (БАГ-27). Правка фронта входит в слайс.

## 6. Машинная приёмка каждого слайса

Общее для всех восьми бэкенд-слайсов — три команды из

# 2. Миграции применяются
cd backend && alembic upgrade head

cd backend && uvicorn app.main:app --port 8000 &
sleep 2 && curl -s http://localhost:8000/health && curl -s http://localhost:8000/api/warehouse/batches
kill %1

# 4. Тесты бэкенда (их немного, но они есть)
cd backend && python3 -m unittest discover -s tests -t .

# 5. Фронт не покраснел, и контракт сведён
cd frontend_vue && npm run test:unit

# 6. Ссылки раздела контракта резолвятся
cd frontend_vue && CONTRACT_REFS=roo_code/roo-context/api/warehouse.md npx vitest run src/services/contractRefs.spec.ts
