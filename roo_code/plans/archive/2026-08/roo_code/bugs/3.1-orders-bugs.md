## ✅ БАГ-01 — `.data-table-wrapper` недоступен странице

**File:** `frontend_vue/src/views/admin/orders/OrderCreatePage.vue:368,424`
**Severity:** Medium — широкая таблица выезжает за пределы панели вместо горизонтальной прокрутки

### Problem

Обёртки таблиц позиций и услуг используют `class="data-table-wrapper"`. Класс объявлен только в
page-specific файлах: `orders_list.css:516`, `finance_list.css:45`, `services_list.css:115`,
`warehouse_list.css:766`, `suppliers_list.css:852` — ни один из них страница не импортирует.
В `erp-base.css`, `components/_tables.css`, `orders_card.css`, `orders_create.css` определения нет.
`styles/admin/main.css:4448` его содержит, но этот файл не импортируется ниоткуда (проверено grep по
`src/`, `index.html`, `vite.config.*`) — мёртвый легаси.

Правило `overflow-x: auto; overflow-y: visible` не применяется. Таблица услуг — 7 колонок; на узком
экране она распирает `GlassPanel` вместо того, чтобы скроллиться внутри него.

### Fix

Перенести правило в `orders_card.css` (импортируется обеими страницами заказов):


## ✅ БАГ-07 — позиция, добавленная при создании заказа, уходит по себестоимости

**File:** `frontend_vue/src/views/admin/orders/OrderCreatePage.vue:480-485`
**Severity:** High — цена продажи товара без каталожной цены оказывается равна закупочной, маржа 0

### Problem

Страница создания передаёт в `AddOrderItemsModal` только `:show` и `:order-id`. Пропы
`default-margin-percent`, `default-discount-percent`, `effective-discount`, `modes` не передаются,
и `withDefaults` (`AddOrderItemsModal.vue:42`) подставляет нули.

`AddOrderItemsModal.vue:432-437` — цена строки:

```ts
function priceFor(product, cost) {
  if (product?.price != null && product.price > 0) return product.price
  if (cost === undefined || cost <= 0) return 0
  return round2(cost * (1 + props.defaultMarginPercent / 100))
}
```

При `defaultMarginPercent = 0` третья ветка даёт `cost * 1` — товар продаётся ровно по
себестоимости. Карточка того же заказа передаёт `:default-margin-percent="form.defaultMarginPercent"`
(`OrderCardPage.vue:2724`), а он берётся как
`order.defaultMarginPercent ?? settings.constants.defaultMargin` (`useOrderCard.ts:345`), где
`defaultMargin = 15` (`useSettings.ts:14`).

Итог: товар без каталожной цены, добавленный на экране создания, идёт по себестоимости; тот же товар,
добавленный минутой позже в карточке уже созданного заказа, — по себестоимости +15%. Цепочка
проверена до конца: `priceFor` → `item.unitPrice` (`:243`, `:401`) → `emit('add', items, …)` (`:516`)
→ `onItemsAdded` → `addItem` → `pricingSeedFor(unitCost, item.unitPrice)` (`useOrderCreate.ts:166`)
→ `addOrderItem(order.id, { …, unitPrice })` (`useOrderCreate.ts:305-314`).

Комментарий над самим `priceFor` называет продажу по себестоимости дефектом: «Selling at cost — which
this dialog did by overwriting the price with the FIFO figure — is not a default anybody chose». На
карточке это починено, на создании — осталось через недостающий проп.

### Fix

Передать те же значения, что и карточка. Заказа ещё нет, поэтому источник — настройки:

```vue
<AddOrderItemsModal
  :show="showAddItemsModal"
  :order-id="''"
  :default-margin-percent="settings.constants.defaultMargin"
  :default-discount-percent="settings.constants.defaultDiscountPercent"
  …
/>
```

`useOrderCreate` уже держит `useSettings()` — достаточно вернуть `settings` из композабла.

Скидку менять осторожно: `useOrderCreate.ts:310-313` намеренно отправляет `discountPercent` явно,
чтобы сервер не применил свою. Сегодня `defaultDiscountPercent` равен нулю и в настройках, и в
`useOrderCard.ts:139,346`, так что расхождения по скидке нет — расхождение только по марже.

### Поправка по итогам починки

Ветка с наценкой на сеяных данных сегодня **недостижима**: единственный товар без каталожной цены —
`Cutting Oil` (`prod-006`), и склада у него нет, поэтому себестоимости тоже нет и обе стороны отвечают
нулём. То есть в демо неверную цену увидеть нельзя; на настоящем каталоге, где товар без цены имеет
остаток, — можно. Дефект в коде реальный (проп не передавался), практическая тяжесть ниже, чем
записано в заголовке: не High, а Medium.

Проверено не тестом, а чтением: e2e-тест на равенство цен между экраном создания и карточкой добавлен
(`orders.spec.ts`, «the picker quotes the same price here as it does on a card»), но он проходит и со
сломанным кодом — проверено откатом пропов. Ветку с наценкой он не задевает по причине выше.
`page.route()` тут не помогает: при `VITE_USE_MOCKS` приложение не делает HTTP вообще.

Чтобы ветка стала проверяемой, нужен сеяный товар без каталожной цены и с партией на складе.

### Future rule

Компонент с `withDefaults` молча подставит нули там, где вызывающий забыл проп. Прежде чем
использовать чужой модал, сверить список переданных пропов с тем, что передаёт первый (эталонный)
вызывающий, а не только с обязательными полями `defineProps`.

## ✅ БАГ-09 — таблица услуг показывает себестоимость и маржу в обход права `seeCost`

**File:** `frontend_vue/src/views/admin/orders/OrderCreatePage.vue:430,432,441,443`
**Severity:** High — пользователь без права видеть себестоимость видит её при создании заказа

### Problem

Таблица услуг на странице создания рендерит колонки `orders.col_cost` и `orders.col_margin`
безусловно:

```vue
<th>{{ t('orders.col_cost') }}</th>     <!-- :430 -->
<th>{{ t('orders.col_margin') }}</th>   <!-- :432 -->
…
<td>{{ money(svc.cost * svc.quantity) }}</td>  <!-- :441 -->
<td>{{ money(svc.marginAmount) }}</td>         <!-- :443 -->
```

Карточка того же заказа прячет ровно эти величины за правом: `v-if="canSeeCost"` в семи местах
(`OrderCardPage.vue:1019,1185,1359,1446,1512,1568,2514`), где `canSeeCost` приходит из
`useOrderPermissions()` — `settings.orderPermissions.seeCost.includes(role)`.

`OrderCreatePage.vue` не импортирует `useOrderPermissions` вовсе (проверено grep по файлу; в списке
импортов :1-23 его нет). Значит для роли, исключённой из `seeCost`, себестоимость услуги и маржа
открыты на экране создания и закрыты везде дальше.

Дефолт права — пустой список: `useSettings.ts:17` → `orderPermissions: { seeCost: [], … }`.
До прихода настроек с сервера видеть себестоимость не должен никто, поэтому карточка держит ещё и
`ready: rightsReady` (`OrderCardPage.vue:176`) — чтобы не мигнуть колонками. На создании нет ни
права, ни ожидания.

Модалы добавления безопасны — проверено: в `AddOrderItemsModal.vue` и `AddOrderServicesModal.vue`
колонок себестоимости нет, только `col_unit_price` и `col_total_price`.

Комментарий самого композабла прав: «hiding the cost in the UI is a curtain, not a right» — сервер
тоже не должен слать эти числа. Здесь нет даже занавески.

### Fix

Подключить `useOrderPermissions()` на странице создания и закрыть обе колонки:

```ts
const { ready: rightsReady, canSeeCost } = useOrderPermissions()
```

```vue
<th v-if="rightsReady && canSeeCost">{{ t('orders.col_cost') }}</th>
<th v-if="rightsReady && canSeeCost">{{ t('orders.col_margin_amount') }}</th>
```

Заголовок маржи заодно привести к карточному: карточка пишет `orders.col_margin_amount`
(`OrderCardPage.vue:1512`), создание — `orders.col_margin`; в колонке лежит сумма прибыли
(`OrderService.marginAmount`), а не проценты, так что верен карточный ключ.

### Future rule

Право — не фича-флаг: одна и та же величина, скрытая на одной странице домена, должна быть скрыта
на всех. При добавлении экрана в существующий домен сверять список `v-if` по правам с эталонной
страницей домена, а не только вёрстку.

## ✅ БАГ-10 — `receivedCurrency` захардкожен вместо валюты товара

**File:** `frontend_vue/src/composables/useOrderCreate.ts:167`
**Severity:** Low — расходится с правилом сервера, но до склада не доезжает

### Problem

`addItem` ставит новой строке `receivedCurrency: 'cur-eur'` константой. Сервер выводит то же поле из
товара: `mockAddOrderItem` (`services/mocks/orders.ts:1635`) пишет
`receivedCurrency: fullProduct?.currencyId ?? 'cur-eur'` (`:1717`), и так же `:448`.

Для товара, чья себестоимость пришла в другой валюте, локальная строка до сохранения объявляет
происхождение EUR. На сохранение это не влияет — сервер перезапишет поле из товара, и таблица
создания эту колонку не показывает. Но это второе правило рядом с первым, ровно та форма, из
которой выросли прошлые находки аудита.

**✅ Починено — диагноз в исходной записи был неверен.**

Правило уже существовало и было решено владельцем 2026-08-08 (находка 24, `order-audit-currency-mixing.spec.ts`): **складской слой партии всегда в базовой валюте**, конвертации нет нигде, а партия не в базовой валюте не создаётся вовсе — `mockCreateBatch` бросает `BATCH_CURRENCY_NOT_BASE`. `WarehouseBatch.currency` так и описан: «the base currency, and nothing else».

Значит у вопроса «в какой валюте себестоимость строки» ровно один ответ, и он не зависит ни от товара, ни от партии: **базовая валюта**. Смешанной раскладки не бывает по построению, поэтому и новое поле в ответе склада не нужно — я предлагал его зря.

Опаснее оказалась серверная сторона, а не клиентская: `mockAddOrderItem` брал подпись из `fullProduct.currencyId` — это валюта **цены продажи** товара. Товар с ценой в USD получал складскую себестоимость с подписью USD, то есть ровно то смешение, ради запрета которого проведена граница в §7.1. Клиентский `'cur-eur'` был случайно верен, пока базовая валюта — евро.

**Что сделано:** добавлен `baseCurrencyOf(settings)` в `services/orderLines.ts`; на него переведены оба композабла и обе серверные точки (`mocks/orders.ts:448,1720`). Формат приведён к коду (`EUR`) — как у `Order.currency`, `WarehouseBatch.currency` и раскладки из `coverFromStock`; раньше строка заказа хранила id (`cur-eur`), а раскладка из склада — код, то есть одно поле в двух форматах. Правило записано в `types/order.ts` и в контракт §7.1.

Смена формата безопасна: поле только пишется — читателей на отображение нет (проверено grep по `receivedCurrency` и по суффиксам валют в карточке, там везде `form.currency`).

Исходный диагноз для истории: `ProductListItem`
(`types/product.ts:26-44`) валюту не несёт — `currencyId` есть только у полного `Product` (`:57`), а
`getBatchCostBreakdown` (`services/warehouseService.ts:70-77`) возвращает
`{ unitPrice, totalCost, shortageQuantity }` и тоже без валюты. Плумбинг через модал был начат и
откачен: подставлять в поле «валюта партии, из которой взята себестоимость» валюту товара — это
третье правило рядом с двумя, а не починка.

Чтобы починить, нужно поле в контракте: либо `currencyId` в `ProductListItem`, либо валюта в ответе
`/api/warehouse/stock/:id/cost` (что вернее — себестоимость приходит из партий). До тех пор в обоих
композаблах оставлена константа с комментарием, объясняющим, что значение временное и его
перезаписывает сервер.

Уточнение по итогам Group 6: карточка делает ровно тот же хардкод — `useOrderCard.ts:934`,
`receivedCurrency: 'cur-eur'`. То есть это не отклонение страницы создания, а одно общее место, где
фронтенд расходится с сервером. Severity от этого не растёт (поле нигде не выводится и
перезаписывается на сохранении), но чинить надо оба.

### Fix

Либо прокидывать валюту товара из модала в payload и ставить её, либо не ставить поле локально
вовсе (строка до сохранения не знает происхождения) — и в обоих случаях снять константу в обоих
композаблах.

## ✅ БАГ-11 — итоги заказа считаются, но нигде не показаны; режим НДС при этом зашит

**File:** `frontend_vue/src/composables/useOrderCreate.ts:265-277`
**Severity:** Medium — админ собирает заказ с ценами и не видит суммы до нажатия «Создать»

### Problem

`recalcLocalTotals()` вызывается после каждого добавления и удаления строки и считает четыре
величины — `totalCost`, `totalAmount`, `totalVat`, `totalWithVat`. Ни одна из них не выводится:
в шаблоне `OrderCreatePage.vue` (строки 151-494) нет ни одного обращения к `localOrder.total*`,
`totalAmount` и `totalWeight` композабл возвращает, а страница их не деструктурирует (проверено grep
по файлу — ноль вхождений).

Экран, на котором есть таблица позиций с ценами и таблица услуг с ценами, не показывает сумму
заказа. Считающий её код при этом исполняется на каждое изменение.

Вторая половина: `rollupOrder(lines, 'standard', settings.constants.vatRate)` — режим НДС зашит
строкой `'standard'`, с комментарием «A brand-new order is always standard-rated until the client and
the document type say otherwise, which happens after it is created». Но тип документа выбирается
именно на этом экране, и сервер выводит режим из него в момент создания:
`mockCreateOrder` (`services/mocks/orders.ts:1240`) —
`vatMode: data.documentType === 'export' ? 'export_zero' : 'standard'`.

То есть при выборе Export локальный расчёт даёт НДС 21%, а созданный заказ приходит с нулевой
ставкой. Сегодня это не видно ровно потому, что итоги не выводятся; как только их выведут, число
будет неверным для каждого экспортного заказа.

### Fix

Показать итоги (панель `orders.field_total` / `field_total_vat` / `field_total_with_vat` — ключи уже
есть во всех трёх языках) и одновременно вывести режим НДС из формы, а не из константы:

```ts
const vatMode = computed(() => (form.value.documentType === 'export' ? 'export_zero' : 'standard'))
…
const rolled = rollupOrder(lines, vatMode.value, settings.constants.vatRate)
```

Плюс пересчёт при смене `documentType` — сейчас `recalcLocalTotals` вызывается только на
добавление/удаление строк.

Если итоги выводить сознательно не хотят — убрать `recalcLocalTotals` и четыре поля из `localOrder`,
а не держать расчёт, который никто не читает.

### Future rule

Считаемая величина либо выводится, либо не считается. Расчёт без потребителя не проверяется глазами
и расходится с сервером незаметно.

## ✅ БАГ-15 — упавшее сохранение оставляет созданный заказ, а повтор создаёт второй

**File:** `frontend_vue/src/composables/useOrderCreate.ts:280-341`
**Severity:** High — при ошибке в середине пользователь видит «не удалось создать», хотя заказ создан

### Problem

`handleSave` — пять последовательных запросов без отката:

```
1. createOrder(...)                     → заказ уже существует на сервере
2. patchOrder(id, { notes })            → если notes есть
3. for item  → addOrderItem(id, …)      → N запросов
4. for svc   → addOrderService(id, …)   → M запросов
5. for file  → addOrderFile(id, …)      → K запросов
catch → toast.error(t('orders.toast_error_create')); return null
```

Любая ошибка на шагах 2-5 приводит к состоянию, где заказ на сервере есть, часть строк в нём есть, а
пользователь читает «не удалось создать заказ» и остаётся на форме со всеми своими данными. Нажатие
«Создать заказ» ещё раз проходит шаг 1 заново — на сервере появляется **второй** заказ, а первый
остаётся висеть недособранным. Ни идентификатор созданного заказа, ни факт его существования
пользователю не сообщаются.

Отказы на шаге 3 — не гипотетические, сервер их специально ввёл: `mockAddOrderItem`
(`services/mocks/orders.ts:1635`) бросает `ZERO_QUANTITY`, `CATALOG_PRODUCT_NOT_FOUND`, а
`requireFiniteNumbers` — на нечисловых значениях. Контракт (`roo_code/plans/orders/orders-backend-contract.md`, §1,
правило 6) требует именно такого поведения от сервера, то есть частичный отказ — штатный сценарий,
а не сбой сети.

Дух правила 3 того же §1 — «сначала проверить всё, потом писать» — здесь нарушен: заказ пишется
первым, а валидность строк выясняется после.

### Fix

Минимально, не трогая протокол: запомнить созданный заказ и не создавать его второй раз.

```ts
const createdOrderId = ref<string | null>(null)
…
const order = createdOrderId.value
  ? await getOrder(createdOrderId.value)
  : await createOrder({ … })
createdOrderId.value = order.id
```

и отправлять только те строки, которых в заказе ещё нет. Плюс честный текст ошибки: заказ создан,
часть строк не добавлена, вот ссылка на него — с переходом на карточку, где строки можно дослать
руками.

Правильнее — один эндпоинт создания заказа вместе со строками; тогда сервер проверит всё до записи.
Этого в контракте сейчас нет, и это решение уровня контракта, а не страницы.

### Future rule

Многошаговое сохранение обязано быть повторяемым: второй вызов после частичного отказа должен
дособрать начатое, а не начать заново. Если так не сделать — сообщение об ошибке становится ложью
о состоянии сервера.
