## ТЗ

Заказу нужны статусы завершения, отмены и возврата. Отдельно — возможность оформить **частичный возврат** внутри заказа: кнопка → попап → выбор отгруженных позиций и количеств → документ возврата, который двигает склад и деньги. Возврат показывается на карточке тремя элементами: бейдж в шапке, пометка строк в таблице состава, разделение «Сумма заказа / Возвращено / Итого» в финансовом блоке.

### Решения заказчика (2026-08-11, зафиксированы до плана)

1. **Завершён** — новый терминальный статус ПОСЛЕ `delivered` и `paid`; ни один из них не заменяет.
2. **Отклонён продавцом / Отменён покупателем / Отказ при получении** — отдельные значения `OrderStatus`, а не «причина отмены» при одном `cancelled`.
3. Возврат создаёт **только корректирующий счёт**. Платёж-возврат вносит бухгалтер отдельно, когда деньги реально ушли.
4. Каждая строка возврата независимо: **годный** (обратно в свою партию) или **брак**; и отдельно — **компенсируется деньгами или нет**. Брак без компенсации возможен.

### Решения архитектуры (следствия, зафиксированы здесь)

5. **`Refunded` и «Частичный возврат средств» — не статусы заказа.** Финансовая ось выводится из платежей (`purpose: 'refund'`) и документов возврата, ровно как уже выводится `paidPercent`. Хранить числом или ставить руками нельзя — [`orderPricing.paymentState`](../../../../../../frontend_vue/src/domain/orderPricing.ts) задаёт образец.
6. **Статус сам склад не двигает.** Двигает документ возврата. Статусы `returned` / `refused` ставятся по факту оформленного возврата, а не наоборот. Флаги `reserveOnTransition` / `writeOffOnTransition` у новых статусов — `false`.
7. **Итог заказа возврат не меняет.** `totalWithVat` остаётся; «Возвращено» и «Итого к получению» — производные.
8. **`shippedPercent` не меняется** — он про то, что уехало со склада, а оно уехало.

## 🔴 Изменение бизнес-правила (требует явного согласия при исполнении)

Сегодня [mockCreateInvoice:3560](../../../../../../frontend_vue/src/services/mocks/orders.ts#L3560) запрещает **вторую корректировку на названную сумму** для одного счёта:

```ts
if (statedNet(order, data) !== undefined && hasCorrection(order, original.id)) {
  throw new Error('INVOICE_ALREADY_CORRECTED')
}
```

**Частичный возврат при этом правиле работает ровно один раз.** Второй возврат по той же отгрузке отклоняется, хотя у клиента на руках документ, из которого ещё есть что вычесть.

Правило «один документ корректируется один раз» (модель, раздел 8) было прокси для настоящего инварианта: **корректировки не должны в сумме превысить то, что клиент держит**. Механика для настоящей проверки уже есть — [`outstandingNetOf`](../../../../../../frontend_vue/src/services/mocks/orders.ts#L3487) считает остаток документа с учётом всех корректировок.

**Правка:** корректировка на названную сумму разрешается, пока `|stated| <= outstandingNetOf(original)`; превышение — новый код `CORRECTION_EXCEEDS_ORIGINAL`. Отзыв (зеркальная корректировка) остаётся одноразовым: `isWithdrawn` не трогаем.

Это изменение поведения, а не рефакторинг. Оно фиксируется в контракте §4.6 и в модели.

## Что возврат делает — алгоритм (эталон: `mockCancelShipment`)

**Сначала проверить всё, потом писать** (§1, правило 3). Половину операции из журнала склада не откатить.

1. `assertVersion`, `requireFiniteNumbers` на количествах, непустой `reason`, непустой список строк, дубли `lineId` — отказ.
2. По каждой строке: `quantity > shipped − returned` → `RETURN_EXCEEDS_SHIPPED`.
3. **План размещения.** По каждой строке пройти неотменённые отгрузки **от новой к старой** (LIFO — вернулось то, что уехало последним), взять их движения `sale` и набрать количество; каждая названная партия обязана существовать → `RETURN_BATCH_NOT_FOUND`. Себестоимость берётся из движения — та самая, по которой товар уходил.
4. **План денег.** По компенсируемым строкам найти живые обычные счета, выставившие эту строку, и разложить возвращаемое количество по ним (от старого счёта к новому). На каждый затронутый счёт — корректировка на `−net` этого количества. Проверить: `|stated| <= outstandingNetOf(invoice)` → иначе `CORRECTION_EXCEEDS_ORIGINAL`. Невыставленное количество корректировки не порождает — клиенту за него не выставляли.
5. Только теперь запись: создать `OrderReturn`, движения `return` по партиям из плана; для строк `condition: 'defective'` — следом движение `write-off` на то же количество той же партии, `referenceType: 'order-return-writeoff'`. Два движения, а не одно: остаток партии обязан быть верен в каждый момент, а потеря — видна как списание.
6. `item.returnedQuantity += quantity`. `shippedQuantity` **не трогать** — товар уезжал.
7. Выпустить запланированные корректирующие счета, записать их id в `correctionInvoiceIds`.
8. Запись в историю заказа: строки, количества, состояние, компенсация, причина.
9. `recalcOrder`, `bumpVersion`.

**Удержание не возвращается.** В отличие от отмены отгрузки: там заказ по-прежнему должен клиенту товар, здесь клиент товар вернул и больше его не ждёт.
