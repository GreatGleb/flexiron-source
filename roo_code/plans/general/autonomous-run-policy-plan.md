# Политика автономного прогона

Правила, по которым скрипт workflow гоняет задачи без человека. Написано до скрипта: скрипт реализует это, а не изобретает заново.

## 1. Что представляют собой «сотни задач»

Замерено 2026-08-25 по `roo_code/plans/`:

| | |
|---|---|
| файлов планов | 162 |
| из них **с** чекбоксами | **25** |
| из них **без** чекбоксов вовсе | **137** |
| невыполненных пунктов (`- [ ]`) | 276 |
| выполненных пунктов (`- [x]`) | **12** |
| планов только по складу | 80 |

Единого плана с сотнями задач **нет**. Есть 161 файл по 10–33 пункта. Самый крупный — `orders/3.1-orders-plan.md` (33 невыполненных), затем `products/01-products-plan.md` (32).

**Галочка в этом проекте не является отметкой прогресса** — и её чаще всего нет вообще. Отмеченных 12 против 276 неотмеченных, а 137 планов из 162 не содержат ни одного чекбокса: это сплошной текст с анализом и шагами. Отсюда два следствия:

1. Объём работы по `- [ ]` считать нельзя — счёт и завышен (планы исполнялись без отметок), и занижен (85% планов в него не входят вовсе).
2. **Единица работы — файл плана, а не пункт.** Разбор по пунктам виден только в тех 25 файлах, где пункты есть.

## 2. Каждая задача начинается с воспроизведения

Прежде чем что-то менять, задача обязана доказать, что проблема ещё существует — тот же шаг B, что в [`fix-bugs.md`](../../skills/fix-bugs.md). Не воспроизвелась → задача закрывается как **устаревшая**, с указанием команды и вывода, доказавших это. Правок нет, коммита нет.

Проверено на выборке: `warehouse/fix-offcuts-type-column.md` заявляет, что у `.offcut-type-badge` «нет ни одного CSS-правила нигде в проекте». Правила есть — `src/styles/admin/warehouse_list.css:1076`. Выделенной колонки типа при этом действительно нет. Один и тот же план наполовину описывает прошлое, наполовину настоящее — и такой он не один.

Без этого шага прогон переделает уже сделанное и отрапортует успехом.

## 3. Зависимости и параллельность — по файлам, не по планам

- **Внутри плана** пункты идут цепочкой: следующий опирается на предыдущий.
- **Между планами** зависимостей обычно нет, но **есть общие файлы**. `WarehousePage.vue` — 3820 строк, и его правят десятки складских планов. Два агента в одном файле затрут друг друга.

Отсюда: параллельность определяется **владением файлом**, а не номером плана. Задачи, которые пишут в один файл, идут последовательно; параллельно — только задачи с непересекающимися файлами. Одновременно работает 6 агентов (8 ядер минус 2).

## 4. Правила остановки

| Условие | Что делает прогон |
|---|---|
| Машинная приёмка (`npm run verify`) красная **до** правок | стоп немедленно: ветка нездорова, гнать по ней нечего |
| Задача не сошлась (цикл 30 или баг 5/5) | задача провалена, правка в `git stash push -u`, идём дальше |
| **Две задачи подряд не сошлись** | **стоп прогона целиком** |
| Три задачи подряд «устарели» | стоп: план описывает прошлое, гнать его нельзя |
| Достигнут лимит агентов (1000 на прогон) | стоп с отчётом, остаток — следующим куском |

Почему «две подряд»: одна не сошедшаяся задача — случайность, две подряд означают, что реализация и приёмка тянут код в разные стороны, и следующие сто задач сделают то же самое. Ночь уйдёт на тридцатикратное перечитывание одного файла.

## 4a. Чистое дерево или отдельный worktree — обязательное условие

Прогон нельзя запускать в рабочем каталоге, который правит кто-то ещё. Проверено 2026-08-25: параллельная сессия держала незакоммиченными 16 спеков e2e и два файла склада.

Что произойдёт без этого правила:

- коммит на задачу заберёт чужие незакоммиченные правки в свой коммит;
- `git stash push -u` у провалившейся задачи спрячет чужую работу вместе со своей;
- финальная приёмка будет гонять чужой недописанный код и падать не по своей причине.

Перед стартом: `git status --short` пуст, либо прогон идёт в отдельном worktree (`isolation: 'worktree'` у агентов). Дерево занято чужой работой — прогон не начинается.

**Состояние на 2026-08-25: этого условия сейчас нет.** `npm run verify` красный до всяких правок —
`format:check` не проходят восемь файлов, и по правилу выше прогон не стартует вовсе. Пока не
пройдёт `npm run format`, автономный прогон запускать нечем.

## 5. Гит

Ветка `auto/<набор>` от той, куда мержим. Коммит на каждую **закрытую** задачу; провалившаяся не коммитится. Финал: полная приёмка на кончике ветки — `npm run verify` плюс e2e по уровню 2 из [`verify.md`](../../skills/verify.md) (полный набор и пара прогонов подряд: прогон трогает общий пол), плюс снятое состояние `npm run audit` и `npm run deadcode`. Эти два зелёными быть не обязаны и мерж не блокируют — но их числа идут в отчёт прогона: прогон, добавивший мёртвый файл или уязвимую зависимость, должен быть виден по разнице с числом на старте, а не обнаружиться через месяц → `git merge --no-ff` → откат всего прогона одной командой `git revert -m 1`. Пуша нет ни при каком исходе.

## 6. Размер куска

Задача = реализатор + скептик ≈ 2 агента, при лимите 1000 на прогон это ~330 задач теоретически. Резать по ~100 задач: короче отчёт, дешевле откат, раньше видно, что приёмка работает.

## 7. Первый прогон: инвентаризация (решено 2026-08-25)

Первым идёт прогон, который **ничего не меняет в коде**. Причина в разделах 1 и 2: список работы завышен неизвестно во сколько раз, и часть планов описывает прошлое. Гнать реализацию по такому списку — переделывать сделанное.

**Что делает.** Единица — **план** (162 файла). По каждому: прочитать целиком → понять, какое состояние кода он утверждает и чего требует → проверить это состояние grep'ом или чтением → вынести вердикт. Там, где в плане есть пункты (25 файлов, 276 пунктов), дополнительно вердикт по каждому пункту.

Вердикты:

| Вердикт | Условие |
|---|---|
| `сделано` | код уже соответствует плану целиком — **обязательна команда и её вывод** |
| `не начато` | проверено, что ничего из плана в коде нет |
| `частично` | часть есть, часть нет — перечислить, что именно (как `fix-offcuts-type-column`: CSS есть, колонки нет) |
| `непонятно` | план не сопоставляется с кодом; причина одной строкой |

**Скептик — только на вердикты `сделано`.** Ошибочное «не сделано» стоит одной лишней задачи, ошибочное «сделано» молча выбрасывает работу из списка. Остальные вердикты проверять вторым агентом незачем.

**Выход:** `roo_code/plans/general/inventory-2026-08-25.md` — таблица «план → пункт → вердикт → чем доказано». Правок кода нет, коммитов нет, мержить нечего, откатывать нечего.

**Параллельность:** 162 плана раздаются пачками по 4–6 на агента — выходит порядка 35 агентов, что укладывается в ориентир `large` (`workflowSizeGuideline` в `.claude/settings.json`). Одновременно работают 6. Конфликтов нет: в код никто не пишет, каждый агент возвращает свой блок отчёта, сборка — в скрипте.

**Остановки:** лимит агентов из раздела 6; правила «две подряд не сошлись» и «три подряд устарели» к инвентаризации не применяются — «устарело» здесь не сбой, а результат.

**Что дальше.** По отчёту становится известен настоящий объём: сколько задач осталось, какие независимы по файлам, какие планы можно закрыть целиком. Только после этого — пилот на 5 задачах с реальными правками, и лишь затем сотня.
