## 2. Роли и связки

Три роли, каждая назначается бэкенду отдельно — этим и достигается гибкость.

| Роль | Что делает | Права |
|---|---|---|
| оператор | читает очередь работ и планы, нарезает задачи в JSON-очередь, решает порядок | чтение репозитория, запись только в файл очереди |
| исполнитель | пишет код и тесты в разрешённых файлах задачи | запись в checkout |
| скептик | принимает результат по фактическим логам проверок | только чтение |

Маршрутизация — файлом [headless-routing.json](../../workflows/headless-routing.json),
ядро получает его флагом `--routing`; без флага обе роли остаются на Codex, как было:

```json
{
  "operator": { "backend": "claude", "model": "claude-opus-5" },
  "work":     { "backend": "zoo",    "socket": "/tmp/zoo-code.sock", "configuration": {} },
  "review":   { "backend": "claude", "model": "claude-sonnet-5" }
}
```

Имена ролей `work`/`review` — те же, которыми оперирует ядро; `operator` пока справочный,
ядро его не вызывает.

Смена связки = правка этого файла. Требование владельца «всё на Claude Code» — три раза
`claude`; «всё на Codex» — три раза `codex`; «Codex внутри Zoo Code» — `zoo` с профилем,
где провайдер openai/codex. Никакой другой код при этом не меняется.

**Скептик обязан быть не тем, кто писал.** Разные модели у автора и приёмки — требование
владельца от 2026-09-22 и уже действующее правило политики: приёмку делает отдельная сессия.
Это не пожелание в тексте, а проверка в коде: одинаковый бэкенд с одинаковыми параметрами у
обеих ролей роняет прогон на старте (`load_routing`), потому что приёмка превратилась бы в
самопроверку.

## 3. Контракт адаптера

Один интерфейс, три реализации. Адаптер обязан вернуть строго:

```json
{ "status": "done|blocked", "summary": "...", "evidence": ["..."] }
```

и записать рядом `*.stdout.log` / `*.stderr.log`. Всё остальное (чем проверять, что коммитить,
когда стоп) остаётся в ядре — адаптер ничего не решает.

### 3.1 `claude`

```
claude -p --output-format json --model <модель> \
       --permission-mode acceptEdits|plan \
       --add-dir <checkout> --settings <файл> \
       --append-system-prompt <роль> -
```

- Роль скептика — режим без записи (`--permission-mode plan` либо `--allowedTools` без Edit/Write).
- Результат разбирается из `.result` JSON-ответа; `session_id` идёт в отчёт, по нему можно
  поднять транскрипт.
- Стоимость прогона видна из `total_cost_usd` каждого вызова — это и есть счётчик потолка ночи.

### 3.2 `codex`

Как в `codex-night.py` сейчас: `-a never exec --sandbox read-only|workspace-write --json
--output-schema … --output-last-message …`. Менять нечего, кроме пути к бинарю (он не в PATH).

### 3.3 `zoo`

Единственный адаптер, которого ещё нет. Схема:

1. Поднять отдельный экземпляр VS Code:
   `code --user-data-dir <копия> --extensions-dir <как у владельца> --disable-workspace-trust <checkout>`
   с `ROO_CODE_IPC_SOCKET_PATH=<сокет>` в окружении.
2. Подключиться к сокету клиентом node-ipc, послать
   `{type:"TaskCommand", commandName:"StartNewTask", data:{configuration:{…}, text:"<задание>"}}`.
3. Слушать `TaskEvent` до конца работы, затем `CloseTask`.
4. Результат тот же JSON — исполнителя просят положить его файлом, как это делает Codex-адаптер.

**Замерено пробой 2026-09-22, а не выведено из имён событий:**

| Что оказалось | Следствие для адаптера |
|---|---|
| `taskCompleted` **не приходит** даже когда агент закрыл задачу через `attempt_completion` | ждать его нельзя — адаптер зависнет до таймаута |
| Терминальный сигнал — `taskIdle` | адаптер завершает ожидание по нему, с паузой 3 c на возможный `taskCompleted` |
| Порядок событий: `taskCreated` → `taskFocused` → `taskStarted` → поток `message` → `taskTokenUsageUpdated` → `taskIdle` | по `taskStarted` видно, что задача принята, а не потеряна |
| Ответ лежит в реплике `message` с `say: "completion_result"`, `partial: false` | частичные куски потока отбрасываются, иначе результат соберётся из обрывков |
| `taskTokenUsageUpdated` даёт `totalCost` | счётчик расхода есть и у этого бэкенда, как `total_cost_usd` у Claude |

Стоимость пробы — $0.00010656 при 7302 входных токенах: DeepSeek на два порядка дешевле
оператора, и это главный довод отдавать ему объём.

**Команда не выбирает папку.** `StartNewTask` принимает только `configuration`, `text`,
`images`, `newTab` — рабочего каталога среди них нет (проверено по схеме команды в `dist`).
Zoo Code всегда работает в той папке, на которой открыт его VS Code. Отсюда жёсткое следствие
для прогона: чтобы исполнитель работал в изолированном worktree, окно VS Code должно быть
открыто **на worktree**, а не на основном checkout. Иначе правки уйдут в рабочий каталог
владельца, а прогон увидит пустой diff и заблокирует задачу как «done без изменений».

**Вторая ловушка, найденная уже на адаптере:** сокет отдаёт события ВСЕХ задач редактора,
включая прошлые. Новая задача начинается с `taskUnfocused`/`taskAborted` предыдущей — клиент,
не смотрящий на `taskId`, принимает чужой обрыв за свой и уходит ни с чем. Проверено:
первый запуск адаптера так и умер. Поэтому клиент запоминает свой `taskId` из `taskCreated`
(`payload` — это `[taskId]`) и отбрасывает чужое.

## 4. Что делает оператор

Оператор — не «ещё один агент, который пишет код», а тот, кто превращает
[очередь работ](очередь-работ.md) и планы в машинную очередь задач: id, `sources`, `outputs`,
`depends_on`, `checks`. Формат уже задан
[codex-backend-queue-2026-09-18.json](../../workflows/codex-backend-queue-2026-09-18.json) —
оператор пишет такой же файл.

Правило из политики сохраняется: **задача без явных `checks` не запускается**, а неясность в
задании в автономном режиме роняет задачу, а не додумывается.

## 5. Как это становится 24/7

Цикл супервизора (systemd user unit, `Restart=always`):

1. Проверить, что checkout чист и ветка `auto/*`. Занято — ждать, не трогать.
2. Исходный `npm run verify`. Красный — стоп цикла с отчётом (правило политики §4).
3. Очередь пуста → вызвать оператора, получить новую порцию (~10 задач, не сотню).
4. Прогнать порцию существующим ядром: задача → исполнитель → проверки → скептик → коммит.
5. Записать отчёт, сложить расход по `total_cost_usd`, уснуть до следующего окна.

Потолки, которые должны быть в конфиге, а не в голове: расход за сутки, число задач за порцию,
максимум времени на задачу, максимум подряд заблокированных. Пуша и мержа в `main` нет ни при
каком исходе — это уже записано в политике и не смягчается ради 24/7.

Отдельный worktree обязателен: владелец работает в том же репозитории, а прогон, идущий
круглосуточно, не может ждать, пока рабочее дерево освободится.

Автор подешевел в девять раз, задача — лишь вдвое: платит приёмка, и она же теперь
главный расход. Но цена — не главный итог прогона.

**Обе модели прошли проверки и сделали неверно.** Ссылка `WarehouseCuttingPage.vue:407`
стоит в предложении «класс `class="glass-input"` ЗАБЫТ ровно в двух вызовах — здесь и…».
DeepSeek перенумеровал её на строку 410, где токен действительно есть — но на другом
элементе (`<input type="number">`), то есть указал на место, доказывающее обратное
утверждению. Резолвер позеленел, Sonnet-приёмка согласилась: она проверила букву критерия
(«токен на строке есть», «резолвер зелёный»), а не правду документа. Исправлено вручную
(`b65b674`): абзац помечен историческим, ссылка ведёт на сам вызов.

Три вывода для 24/7, каждый оплачен этим прогоном:

1. **Критерий приёмки, сформулированный как машинная проверка, будет удовлетворён буквально.**
   «Резолвер зелёный» — не то же самое, что «документ говорит правду». Критерии надо писать
   про утверждение, а не про признак.
2. **Постановка задачи может сама толкнуть на ложь.** В задании стояло «исправь номер так,
   чтобы ссылка указывала на место с этим токеном» — для предложения про ОТСУТСТВИЕ токена
   это указание неверно, и исполнитель честно его выполнил.
3. **Дешёвая приёмка ловит хуже.** Sonnet принял то, что Opus, возможно, поймал бы; проверять
   это надо отдельно, но экономить на скептике — последнее, на чём стоит экономить.
