# Сквозные правила — сводка для доменных агентов

Шесть правил для семнадцати доменов; подробности — в плане темы.

## 1. Права (§6) — [план](сквозное-rights-план.md)

**Правило.** Один вопрос к матрице: есть ли у пользователя действие `A` на элементе `E`; действий
четыре — `read`, `edit`, `create`, `delete`. Отказ — 403 `FORBIDDEN`, своих кодов нет; величина без
права вырезается, а не помечается.

**Домен:** раздел `## Права домена` + три таблицы: элементы `домен.идентификатор` (≥1 `entity` на
сущность) · эндпоинт → элемент и действие, ровно раз каждый · дефолт по семи строчным ролям. Ещё:
вырезаемое с замыканием либо «вырезать нечего»; не-CRUD операция → одно из четырёх действий;
удаление записи журнала — только `owner`; роут → элемент.

**Проверка:** `rights-contract-conformance.spec.ts` в `npm run test:unit`, ссылки — резолвером.

## 2. Мультиарендность (§4) — [план](сквозное-tenancy-план.md)

**Правило.** Арендатор — только из токена; каждая функция с `select`/`update`/`delete` по тенантской
таблице принимает `tenant_id` и сужает им запрос — писатель в своём `where`, сшитый ответ в каждом
источнике; уникальность — парой с арендатором. Исключение одно: запрос, узнающий арендатора.

**Домен:** тенантские таблицы перечислить; по каждой функции — ссылкой, сужает ли; несужённая — либо
`TENANTLESS` с причиной, либо дефект (баг-файл + `KNOWN_GAPS` с номером); роут `tenant_id` не
принимает, схемы слайса — тоже; `UniqueConstraint`/`unique=True` включает `tenant_id` — модель и
миграция разом; сервис не шлёт `tenantId`/`X-Tenant`.

**Проверка:** `cd backend && python3 -m unittest discover -s tests -t .`, `tenant-not-sent.spec.ts`.

## 3. Аудит-лог (§9) — [план](сквозное-audit-log-план.md)

**Правило.** Хранилище одно — общая `audit_entries` (своей домен не заводит), форма строки одна,
ключ UUIDv7, TTL нет. Пишет каждая меняющая состояние операция, по записи на каждое изменённое
свойство; не пишутся чтение, вызов без изменений и событие без формы строки — оно в серверный ярус.

**Домен:** мутирующие операции ссылками + свойства с подписью на три языка; непишущие — со случаем;
свой `*AuditEntry` → общий; `sensitive`-записи или «ни одного»; журнал — эндпоинтом со страницами +
умолчание сортировки; удаление записи — только владелец (403), неизвестная →
`AUDIT_ENTRY_NOT_FOUND`; удаление сущности чистит её записи явно.

**Проверка:** `audit-log-crosscut.spec.ts` — домен вносит строки в её таблицу ожиданий.

## 4. Уведомления (§10) — [план](сквозное-notifications-план.md)

**Правило.** Типов пятнадцать, коды в плане, шестнадцатого не бывает. Эмиттер зовётся внутри условия
перехода, а не из чтения; повтор отличает база уникальным `eventKey`; кому доставлено — право, что
видно — подписка (сайт работает и назад, почта только вперёд); флаг тревоги несут ровно три кода.

**Домен:** раздел `## События домена (§10)` с таблицей — код · переход ссылкой · условие ·
дискриминатор · флаг тревоги; без событий — дословно `Событий домена нет.` Ещё: `entityType` и роут,
серверный шаблон текста на три языка. Тревоги не отбирает, чистку не заводит, мимо эмиттера не
пишет.

**Проверка:** `notification-events-conformance.spec.ts` + пара в `notification-triggers.spec.ts`.

## 5. Идемпотентность и блокировка (§11) — [план](сквозное-idempotency-план.md)

**Правило.** Необратима операция, которая двигает склад или деньги, шлёт наружу неотзываемое или
создаёт запись, неудаляемую из интерфейса; сомнение — в пользу «необратима». Ей нужен
`Idempotency-Key` (UUID v4 на жест, 24 часа): без него `VALIDATION_ERROR` 422, повтор → сохранённый
ответ дословно, до завершения — `CONFLICT` 409. Save одной транзакцией — `orders` и `warehouse`,
версия записи — только `orders`, у прочих last-write-wins.

**Домен:** каждый `### POST /api/...` — ровно одна строка: «обязателен» с ценой повтора и ссылкой
либо «не требуется — операция обратима» (чем именно); по дословной строке на файл про атомарность
Save и про версию записи; расхождение с правилом — в баг-файл.

**Проверка:** гейты Г1–Г5 плана: `POST` помечен ровно раз, строки Save и версии — по одной.

## 6. Кастомные поля (§8) — [план](сквозное-custom-fields-план.md)

**Правило.** `config` и `categories` не сливаются, третьего перечня типов поля нет; сервер читает из
значения только `fieldId` и `value` и валидирует по определению (четыре кода `FIELD_VALUE_*`, 422).
Значение переживает определение: снятое поле и значения не удаляются, по снятому полю не отдаются и
не принимаются, возврат отдаёт те же. Снятие, от которого значение перестаёт показываться, требует
права (владелец, админ; иначе 403) и `confirmationCode`: `FIELD_REMOVAL_CONFIRM_REQUIRED` 409,
`FIELD_REMOVAL_CONFIRM_INVALID` 422.

**Домен:** строка `Кастомных полей у домена нет.` либо `Кастомные поля: да.` + ссылка на план. По
блокам: `config`/`categories` — набор и код подтверждения, `products` — валидация и хранение
значений, `warehouse` — пустое значение это «неизвестно», а не ноль, `settings`/`auth`/`uploads`/
`audit-feed` — механизм, строка «нет» тоже.

**Проверка:** `custom-fields-conformance.spec.ts` — среди шести «объявление "нет" не врёт».
