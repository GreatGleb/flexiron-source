# Триаж находок сверки контракта — что чинится до решений владельца

Дата: 2026-09-09. Вопрос, на который отвечает файл: какие из находок сверки контракта
зависят от нерешённых решений владельца, а какие нет.

Источник находок — 17 файлов `contract-sync-<домен>-bugs.md` в этом каталоге.
Источник решений — [`../api/audit/00-решения-владельца.md`](../api/audit/00-решения-владельца.md)
и сквозные разделы [`../../roo-context/api/00-conventions.md`](../../roo-context/api/00-conventions.md).

## Ответ коротко

**Гипотеза верна, и с большим запасом.** Из 200 находок решения владельца ждут **31**.
Остальные 166 чинятся сейчас: 151 не зависели от решений никогда, ещё 15 разблокированы
решениями П1–П42, принятыми 7–8 сентября, и до сих пор помечены в баг-файлах как ждущие.

| **Б.** Разблокировано решениями П1–П42 | 15 | 7 % |

Важность по группе А: 45 High, 75 Medium, 31 Low — то есть в очереди без решений лежит
в полтора раза больше High, чем всего находок в группе В.

## Почему «TBD» в баг-файле не значит «ждёт владельца»

Разметка «TBD» в разделах `Fix` ставилась прогоном по одной причине: план сверки
**не правит код**, поэтому автор находки не выбирал между вариантами починки, даже когда
выбор был инженерным и очевидным. Механический признак («в `Fix` стоит `TBD` или слово
«владелец») даёт 62 находки, и разбор поштучно раскладывает их так: **26** действительно
ждут владельца, **13** уже отвечены решениями П1–П42, **23** никогда не были вопросом
владельца. В обратную сторону признак тоже врёт: пять заблокированных находок он не поймал —
`products/БАГ-07`, `products/БАГ-11`, `suppliers/БАГ-02`, `-04`, `-06` говорят «сначала
контракт обязан назвать», не употребляя слова «владелец».

Примеры находок, которые признак пометил зря:

- `config/БАГ-08` — «TBD — завести коды домена `FIELD_NOT_FOUND`, `SECTION_NOT_FOUND`
  и бросать их, как это делают моки соседних доменов». Починка названа в самой находке.
- `uploads/БАГ-08` — «TBD — привести модель к `BigInteger`». Это не развилка.
- `analytics/БАГ-02` — заголовок авторизации. §5 соглашений прямо говорит: это
  «находка в баг-файле каждого такого домена, **а не разрешённое поведение**».

## А. Сто пятьдесят одна находка, которую можно чинить сегодня

### Четыре сквозных класса — 26 находок, четыре правки

Это первое, что стоит взять: класс закрывается одним местом, а не находкой за находкой.

**Класс 1. Заголовок авторизации не шлётся (9 находок).** Правка одна и она в одном слое —
`authHeaders()` из `useAuth` вызывается сборкой запроса в `api.ts`, а не каждым сервисом
поимённо. §5 соглашений уже назвал это дефектом и перечислил виновных.

- `analytics/БАГ-02` — High: единственный вызов домена не шлёт `Authorization`
- `bcc/БАГ-09` — High: пять вызовов из семи идут без единого заголовка
- `services/БАГ-05` — High: ни один из пяти вызовов домена не шлёт `Authorization`
- `finance/БАГ-01` — High: клиент финансов не шлёт ни одного заголовка, а все три таблицы домена арендаторские
- `notifications/БАГ-01` — High: клиент уведомлений не шлёт заголовков авторизации, а лента адресная
- `warehouse/БАГ-01` — High: клиент склада не шлёт ни одного заголовка на всех 37 путях
- `products/БАГ-02` — Medium: удаление записи аудита товара уходит без `Authorization`, хотя лента его подписывает
- `settings/БАГ-06` — High: заголовок `Authorization` теряется при входе без «запомнить меня»
- `uploads/БАГ-04` — Medium: мок-ветка `apiUpload` теряет заголовки, и путь 401 под моками недостижим

**Пробел, найденный этим триажем.** §5 соглашений утверждает, что находка есть «в баг-файле
каждого такого домена». Это неверно: `categoriesService.ts`, `clientsService.ts`,
`configService.ts` и `suppliersService.ts` не шлют ни одного заголовка (замер:
`grep -c 'authHeaders\|Authorization\|headers'` по каждому → `0`), а в баг-файлах
`categories`, `clients`, `config` и `suppliers` находки про заголовки **нет ни одной**
(`grep -n 'authHeaders\|заголов'` по четырём файлам → ни одного попадания по теме).
Четыре домена надо дописать — иначе класс закроется на девяти из тринадцати.

**Класс 2. Код ошибки читается из текста, а настоящий API кладёт его в `code` (7 находок).**

не сработают вовсе.

- `categories/БАГ-01` — High: код ошибки удаления читается из `message`, а настоящий API кладёт его в `code`
- `clients/БАГ-02` — High: код ошибки удаления читается из текста исключения, а настоящий API кладёт его в `code`
- `products/БАГ-01` — High: код ошибки удаления товара читается из `message`, а настоящий API кладёт его в `code`
- `settings/БАГ-17` — Medium: код `MAIL_NOT_CONFIGURED` читается из `message`, а настоящий API кладёт его в `code`
- `warehouse/БАГ-18` — Medium: `OFFCUT_LINKED_TO_ORDER` читается только из `message`

## Как это чинить

Порядок задач — скил [`fix-bugs.md`](../../skills/fix-bugs.md): один баг за цикл,
закрывает баг не тот, кто его чинил. Проверка — цикл из [`verify.md`](../../skills/verify.md).

Рекомендуемая последовательность:

1. **Четыре сквозных класса** (26 находок). Каждый — одна правка в одном слое; после них
   очередь в группе А падает до 125, и три из четырёх классов перестают воспроизводиться
   в новых домены.
2. **High из группы Б** (7 из 15). Решение уже принято, работа мелкая, а пометка «ждёт
   владельца» в баг-файле сейчас врёт — её надо снять тем же коммитом.
3. **По домену целиком**, начиная с `warehouse` (28 находок, ни одна не заблокирована) и
   `settings` (18 незаблокированных из 22).
