## ✅ БАГ-01 — `:deep()` в нескоуплённом `<style>`: два правила раскладки не доезжают до браузера

**File:** `frontend_vue/src/views/admin/orders/OrderCardPage.vue:2779-2787`
**Severity:** Medium — четыре пары полей, задуманные в строку, встают друг под другом

### Problem

Блок `<style>` в конце файла объявлен **без `scoped`** (`:2742`), а внутри него:

```css
:deep(.inline-group) { display: flex; gap: 12px; flex-wrap: wrap; }
:deep(.inline-short) { flex: 1 1 140px; min-width: 120px; }
```

`:deep()` разворачивается только компилятором scoped-стилей. Для нескоуплённого блока
`@vue/compiler-sfc` отдаёт CSS как есть — проверено вызовом `compileStyle` на этом самом файле:

```
scoped = undefined | lang = undefined
":deep(.inline-group) {\n  display: flex;\n  gap: 12px;..."
```

Браузер не знает псевдокласса `:deep` → селектор невалиден → правило отбрасывается целиком.
Больше `.inline-group` / `.inline-short` не объявлены нигде: grep по `src/styles/`
(кроме мёртвого `main.css`) даёт ноль вхождений.

Итог — четыре пары полей теряют раскладку в строку:
`field_default_margin` + `field_default_discount` (`:1034`), `field_actual_margin` +
`field_effective_discount` (`:1183`), `field_paid` + `field_outstanding` (`:1224`).
Те же классы использует `ProductCardPage.vue:358,362` и там они тоже мертвы.

### Fix

Перенести оба правила в `components/_forms.css` (глобально подключён через `admin-core.scss`)
без `:deep()`. Это раскладочные хелперы формы, а не стиль страницы заказов, и они чинятся
сразу для обеих страниц.

### Future rule

`:deep()` имеет смысл только в `<style scoped>`. Перед тем как писать его в SFC — посмотреть
на открывающий тег блока. Нескоуплённый `<style>` — это обычный CSS-файл, и `:deep()` в нём
не «на всякий случай», а гарантированно выключенное правило.

## ✅ БАГ-04 — очищенное числовое поле кладёт NaN в форму и в запрос (pitfall #25)

**File:** `frontend_vue/src/composables/useOrderCard.ts:133-142`, `OrderCardPage.vue:1038,1054,1090,1304`
**Severity:** Medium — НДС молча становится нулём, а в запрос уходит `NaN`

### Problem

Четыре поля с `v-model.number`: `form.defaultMarginPercent` (`:1038`),
`form.defaultDiscountPercent` (`:1054`), `form.vatPercent` (`:1090`),
`form.totalWeight` (`:1304`). Ни одного нормализатора: `grep -n "NaN\|isFinite"` по
`useOrderCard.ts` — **ноль вхождений**.

`v-model.number` на пустом поле даёт `NaN`. Дальше:

1. `totals` (`:310`) = `rollupOrder(lines, vatMode, NaN)`. **На экране NaN не появляется** —
   `roundTo` (`orderPricing.ts:106`) отдаёт ноль на любое неконечное число, — и это хуже,
   а не лучше: панель показывает совершенно правдоподобные «НДС 0,00» и «Итог с НДС = Цена
   без НДС». Проверено прогоном `rollupOrder([line], 'standard', NaN)`:
   `{ vatRate: null, totalVat: 0, totalGross: 400, totalNet: 400 }`. Заказ на 400,00 нетто
   при ставке 21% тихо выставляется как заказ без НДС.
2. `useDirtyCheck.diff()` сравнивает через `JSON.stringify` (там NaN → `null`, разница
   видна), а **возвращает** `toRaw(currentObj[key])`, то есть настоящий `NaN`
   (`useDirtyCheck.ts:74`). Он и уходит в `patchOrder`.
3. На моке `requireFiniteNumbers` в `mockPatchOrder` (`mocks/orders.ts:1302`) его отбивает —
   `NUMBER_NOT_FINITE`, тост «число не является конечным». То есть очищенное поле делает
   заказ несохраняемым, а сообщение не называет, какое из четырёх полей виновато.
4. На настоящем сервере между клиентом и сервером стоит `JSON.stringify`, и `NaN` уезжает
   как `null`. `mockPatchOrder` устроен как `if (delta.vatPercent !== undefined)` — то есть
   `null` пройдёт присваиванием. Это ровно тот случай, который контракт §1, правило 6
   описывает как «доходит до столбца `NOT NULL numeric` и роняет запрос».

### Поправка по итогам починки

Заголовок и severity исходной записи были завышены: я написал «весь финансовый блок
показывает NaN», и первый регрессионный тест был написан под это утверждение — он оказался
зелёным и со сломанным кодом. Причина в `roundTo`, который глотает неконечные числа. Тест
переписан на то, что проверяется: поля формы обязаны оставаться числами, и в запрос `NaN`
попадать не должен; оба падают, если снять нормализатор (проверено откатом). Severity
снижена с High до Medium — видимого мусора нет, но тихая потеря НДС и несохраняемый заказ
остаются.

Страница создания этой дыры не имеет: `v-model.number` там не используется вовсе
(проверено grep по обоим файлам).

### Fix

Нормализатор сразу после `useDirtyCheck(form)`, по образцу pitfall #25. Поля не nullable
(`OrderFormFields` объявляет их `number`), поэтому возвращать надо не `null`, а последнее
осмысленное значение: ноль для процентов и веса.

```ts
watch(form, (val) => {
  if (Number.isNaN(val.vatPercent)) val.vatPercent = 0
  …
}, { deep: true })
```

### Future rule

Pitfall #25 не про nullable-поля, а про `v-model.number`. Правило проверяется по разметке
(`grep v-model.number`), а не по типу поля: `number` без `| null` защищает от NaN ещё
меньше, чем `number | null`.

## ✅ БАГ-05 — три действия перезагружают карточку и молча уносят несохранённое

**File:** `frontend_vue/src/composables/useOrderCard.ts:562-577` (`applyStatusChange`), `:649-666` (`cancelShipment`), `:668-682` (`reserveStock`)
**Severity:** High — набранные правки строк и незаписанные поля исчезают без единого вопроса

### Problem

`load()` (`:328`) заменяет `order.value`, перезаписывает `form` и вызывает `capture()` —
то есть уносит и локальные правки строк, и dirty-базу формы. Поэтому каждое серверное
действие карточки обязано сначала либо слить несохранённое, либо отказаться. Шесть из
девяти так и делают:

| действие | защита |
|---|---|
| `shipLines` `:615` | `hasPendingChanges` → отказ, затем `saveFormFields()` |
| `splitItemLine` `:1280` | `hasPendingChanges` → отказ, затем `saveFormFields()` |
| `correctLine` `:1314` | `hasPendingChanges` → отказ, затем `saveFormFields()` |
| `confirmAllocation` `:1439` | `saveFormFields()`; строки отсечены в `previewTotal` `:1409` |
| `issueInvoiceFor` `:827` | `hasPendingChanges \|\| isDirty` → отказ |
| `confirmVatMode('gross')` `:1475` | `hasPendingChanges` → отказ, затем `saveFormFields()` |

Три — нет:

- **`applyStatusChange`** (`:562`) — `patchOrderStatus` → `load()` → `loadShipments()`.
  Ни проверки, ни слива. Смена статуса при этом сама по себе двигает склад (контракт §4.5),
  то есть это операция того же веса, что и отгрузка.
- **`cancelShipment`** (`:649`) — `cancelOrderShipment` → `load()`. Проверен только
  `shipmentsLoading`.
- **`reserveStock`** (`:668`) — `hasPendingChanges` проверен, а `saveFormFields()` нет,
  и дальше `load()`. То есть строки защищены, поля — нет.

Что видит админ: правит заметку и режим НДС, меняет статус на «Собирается» — статус
сменился, заметка исчезла, save bar погас, никто ничего не сказал. С правками строк хуже:
`load()` возвращает таблицу к серверному виду, а `pendingLineEdits` / `pendingItems`
остаются непустыми — save bar продолжает гореть, показывая изменения, которых на экране
уже нет.

### Fix

Привести все три к образцу соседей: `hasPendingChanges` → `orders.error_save_lines_first`,
затем `await saveFormFields()` перед серверным вызовом.

### Future rule

`load()` — разрушающая операция, а не просто «обновить». Любая новая функция композабла,
которая её вызывает, обязана сначала ответить на два вопроса: что делать с
`hasPendingChanges` и что делать с `isDirty`. Список защищённых вызовов держать рядом с
самим `load()`, чтобы девятый случай не пришлось искать глазами.

## ✅ БАГ-06 — карточка схлопывается в скелет при каждой перезагрузке

**File:** `frontend_vue/src/views/admin/orders/OrderCardPage.vue:185`
**Severity:** Medium — после каждого сохранения страница мигает скелетом и теряет позицию прокрутки

### Problem

```ts
const cardLoading = computed(() => loading.value || !rightsReady.value)
```

`load()` (`useOrderCard.ts:329`) ставит `loading.value = true` **безусловно**, а `load()`
вызывается после сохранения, смены статуса, отгрузки, отмены отгрузки, резерва, выставления
счёта, разделения строки, корректировки и раскладки итога. Каждый раз шаблон уходит в
первую ветку (`:859`) — три пустые панели-скелета — и возвращается обратно.

Эталонная карточка так не делает: `SupplierCardPage.vue:148` — `v-if="loading && !supplier"`,
то есть скелет только пока данных ещё нет.

Побочный эффект дороже мигания: на длинной карточке (таблица позиций, услуг, отгрузок,
платежей, счетов, файлов, история) полная перерисовка сбрасывает прокрутку в начало после
каждого сохранения.

### Fix

```ts
const cardLoading = computed(() => (loading.value && !order.value) || !rightsReady.value)
```

`rightsReady` остаётся снаружи скобок сознательно: он становится `true` один раз и именно
за ним карточка ждёт, чтобы не мигнуть колонками себестоимости.

## ✅ БАГ-07 — отменённая раскладка итога оставляет в поле сумму, которой у заказа нет

**File:** `frontend_vue/src/views/admin/orders/OrderCardPage.vue:196-214`, `useOrderCard.ts:1434-1436`
**Severity:** Medium — поле «Итог с НДС» показывает не итог заказа, и отличить это нечем

### Problem

`grossInput` синхронизируется с итогом только через watch на **изменение** итога:

```ts
watch(() => totals.value.totalGross, (value) => { grossInput.value = value.toFixed(2) }, { immediate: true })
```

Сценарий: итог 4 000,00, админ вводит 5 000, `onGrossCommit` → `previewTotal(5000)` вернул
`null` → открылся модал раскладки → админ жмёт «Отмена» → `cancelAllocation()`
(`useOrderCard.ts:1434`) обнуляет только `allocationPreview`.

`totals.totalGross` не менялся, значит watch не сработал, `grossError` пуст (ошибки не было).
Поле остаётся показывать `5000`, а заказ стоит 4 000,00 — при том, что рядом «Цена без НДС»
и «НДС» показывают старые, верные числа. Ни ошибки, ни подсказки.

Симметрично: если раскладка применена и достигнутый итог совпал с текущим до цента,
`load()` не изменит `totalGross`, и в поле останется введённая строка (`5000` вместо
`5000.00`) — косметика, но того же происхождения.

### Fix

Обработчик закрытия модала на странице возвращает поле к правде:

```ts
function onCancelAllocation() {
  cancelAllocation()
  grossError.value = null
  grossInput.value = totals.value.totalGross.toFixed(2)
}
```

и он же вешается на `@update:model-value` и на кнопку «Отмена».

### Future rule

Поле ввода, отражающее вычисляемую величину, обязано иметь путь возврата к ней **на каждый
выход из редактирования**, а не только на изменение самой величины. Watch на значение
покрывает «значение поменялось», но не «правка отменена».

## ✅ БАГ-08 — история заказа показывает себестоимость тем, у кого нет права `seeCost`

**File:** `frontend_vue/src/views/admin/orders/OrderCardPage.vue:1846-1912`, `frontend_vue/src/services/mocks/orders.ts:1790-1802,2163-2173`
**Severity:** High — право обходится там, где его не искали

### Problem

Карточка честно закрывает себестоимость и маржу в шести местах — `canSeeCost` на
`field_total_cost` (`:1019`), на `field_actual_margin` (`:1185`), на колонке маржи в обеих
таблицах (`:1359`, `:1512`), на ячейках через `LINE_CELLS` (`:261-265`), на поле
себестоимости в модале корректировки (`:2514`) — и ждёт `rightsReady`, чтобы не мигнуть
(`:185`). Проверено построчно: других мест, где на экран попадает cost/margin, нет.

Кроме одного. Таблица истории заказа (`:1853-1905`) рендерит `auditLog` **целиком, без
единого условия**, а две записи истории несут себестоимость числом:

```ts
// mocks/orders.ts:1793-1800 — ручная себестоимость
recordInHistory(order, { en: `Manual cost — ${draft.productName}`, … },
  String(before.unitCost),                       // «было»
  `${draft.unitCost} — ${draft.manualCostReason ?? '—'}`)   // «стало»

// mocks/orders.ts:2166-2172 — корректировка себестоимости
recordInHistory(order, { en: `Cost correction — ${lineNameOf(line)}`, … },
  String(before.unitCost), `${pricing.unitCost} — ${reason}`)
```

Роль вне `seeCost` открывает карточку и читает в колонках «Было» / «Стало»: `3.13` → `0.01`.
Контракт §5 требует от сервера не отдавать «`unitCost`, `costSource`, `allocations`,
`marginPercent` и всё производное от них» — запись истории производна от `unitCost` в самом
буквальном смысле.

Проверено, что вопрос не решён раньше: `grep -rln seeCost src/ tests/` даёт четыре файла
(`useOrderPermissions.ts`, `useSettings.ts`, `mocks/settings.ts`, `types/settings.ts`) —
ни одной аудитной спеки про историю.

### Fix

Запись должна сама говорить, что она про себестоимость, — иначе фильтровать нечего, а
разбирать текст свойства нельзя (он переведён на три языка).

1. `OrderAuditEntry` получает `sensitive: 'cost' | null` — присутствует всегда, как требует
   контракт §3 про однородность ответа.
2. `recordInHistory` принимает его параметром; две записи выше передают `'cost'`.
3. Сервер не отдаёт такие записи роли без права (`publicOrder`), а карточка вдобавок
   фильтрует их у себя — занавеска поверх правила, а не вместо него.

### Future rule

Проверяя право «видеть величину», проходить не только по вёрстке, которая её печатает, но
и по журналам: история, тосты, тултипы и экспорт — это те же данные, выведенные другим
путём. Список мест ищется по источнику числа (`unitCost`), а не по названию колонки.

## ✅ БАГ-09 — количество можно править в ноль, хотя строку на ноль создать нельзя

```ts
export function applyQuantityEdit(line: PricingLine, quantity: number): PricingLine {
  if (!canEditQuantity(line)) throw new Error('LINE_FULLY_SHIPPED')

```

сохранении `PATCH /items/:id { quantity: 0 }` → `mockUpdateOrderItem` → тот же
`applyQuantityEdit` → строка записывается.

При этом **создание** строки на ноль отбивается у обеих сущностей — `mocks/orders.ts:1667`

создающем эндпоинте и отсутствует на правящем: та же форма дефекта, дверью левее.

### Fix

на карточке и на сервере.

### Future rule

Проверка на создающем эндпоинте — половина правила. Второй вопрос всегда: «а править до
этого состояния можно?» Отказ надо ставить в ту функцию, через которую значение
**назначается**, а не в ту, через которую сущность **появляется**.

## ✅ БАГ-19 — закрытый модал ещё 300 мс перехватывает клики

### Problem

Сверка всех ключей `orders.*` с их употреблением дала семь мёртвых. Проверено четырьмя

2. динамическая сборка (`` `orders.${…}` ``, `'orders.' +`) — в репозитории она есть в семи

3. `useI18n()` со `scope`/`messages`, при котором `t('back')` резолвился бы внутрь
   `orders` — таких вызовов нет ни одного;
4. голое имя ключа в кавычках где угодно в `src/` и `tests/` — ноль по всем семи.

Единственные упоминания — в `.md`: исторический план `3.1-orders-plan.md` и цитата старого

## ✅ БАГ-21 — версию заказа спрашивали пять эндпоинтов из двадцати

**File:** `frontend_vue/src/services/mocks/orders.ts`, `src/services/ordersService.ts`, `src/services/mocks/index.ts`, `src/composables/useOrderCard.ts`
**Severity:** High — вторая вкладка молча затирает платёж, счёт, отгрузку и смену статуса

### Problem

Контракт §3: «версия обязательна на каждой мутации». Пересчёт по коду: `bumpVersion` вызывается
в **20** функциях мока, `assertVersion` — в **5**.

| ✅ спрашивают | ❌ не спрашивают |
|---|---|
| `mockPatchOrder` | `mockPatchOrderStatus`, `mockDeleteOrderItem`, `mockDeleteOrderService`, `mockDeleteOrderAuditEntry` |
| `mockAddOrderItem` | `mockAddOrderFile`, `mockRemoveOrderFile`, `mockAllocateOrderTotal` |
| `mockUpdateOrderItem` | `mockCorrectOrderLine`, `mockSplitOrderItem` |
| `mockUpdateOrderService` | `mockCreateShipment`, `mockCancelShipment`, `mockReserveOrder` |
| `mockAddOrderService` | `mockAddOrderPayment`, `mockDeleteOrderPayment`, `mockCreateInvoice` |

Плюс `mockDeleteOrder` — версии не спрашивал и не шагал (заказа после него нет).

Защищено оказалось ровно то, что и так уходит дельтой полей, а всё, что двигает **склад и
деньги**, — нет. Две вкладки на одном заказе ловили конфликт на правке строки и не ловили на
платеже, счёте, отгрузке и смене статуса: второй записывал поверх, и никто ничего не узнавал.

Транспорта тоже не было: у пятнадцати функций `ordersService` не было параметра версии, а
восемь из них — `DELETE`, у которого тела нет вовсе.

### Fix

1. `assertVersion` во всех двадцати мутациях мока (+ `mockDeleteOrder`).
2. `version` в пятнадцати функциях `ordersService`; у `DELETE` — заголовок `If-Match`
   (§3 называет именно его), через хелпер `ifMatch()`. `apiDelete` заголовки уже принимал.
3. Роутер мока: версия из тела для POST/PATCH, `ifMatchVersion()` из заголовка для DELETE.
4. Карточка: `withVersion` на телах, новый `atVersion()` на позиционных вызовах — 18 мест.
5. Поведение «версии не прислали — не проверяем» сохранено. Это не послабление: мок дёргают
   напрямую генератор демо-данных, внутренние вызовы мока в мок (`mockPatchOrderStatus` →
   `mockCreateShipment` / `mockReserveOrder`) и сотня спеков, у которых версии нет и быть не
   может. Версия — утверждение о прочитанном.

### Побочная находка, без которой починка ломала бы карточку

`mockRemoveOrderFile` держал `bumpVersion` **внутри** `if (idx !== -1)`: удаление по
неизвестному идентификатору не писало ничего, не шагало и отвечало «готово». Пока версию никто
не проверял, это было незаметно. С проверкой — фатально: карточка шагает счётчик
безусловно, значит после такого запроса она на шаг впереди сервера, и каждый следующий запрос
того же сохранения отклоняется конфликтом, которого не было.

Починено по правилу соседей (`mockDeleteOrderItem`, `mockDeleteOrderAuditEntry` уже так
делают): неизвестный файл — отказ `ORDER_FILE_NOT_FOUND`, а `bumpVersion` выходит из ветки.
Код заведён в §6 контракта, в таблицу сообщений `orderLineEdits` и в три языка;
`order-audit-contract-conformance.spec.ts` сверяет эти три множества механически.

### Future rule

`bumpVersion` внутри условия — это не оптимизация, а рассинхронизация с любым клиентом,
который считает шаги сам. Правило: **одна принятая запись — один шаг, ни шага на отказ.**
Мутация, которая может ничего не записать, обязана вместо этого отказать: «сделал ничего и
отчитался успехом» неотличимо от «сделал».

## ✅ БАГ-22 — прогулка фаззера зависела от того, какой сеяный заказ первым упомянул товар

**File:** `frontend_vue/src/services/mocks/order-audit-fuzz-server.spec.ts:41-58`
**Severity:** Medium — фаззер нельзя было читать как измерение

### Problem

`stockedProducts()` собирает пул товаров, обходя все заказы списка и складывая их
`productId` в `Set`. `Set` хранит порядок вставки, а список идёт от новых заказов к старым —
значит **порядок пула** определялся тем, какой сеяный заказ первым упомянул какой товар.

Фаззер индексирует этот пул сеяным генератором случайных чисел. Поэтому правка одного
демо-заказа перетасовывала весь его маршрут: та же реализация, тот же сид — и другая
последовательность операций.

Проявилось на витринном заказе (БАГ-23): состав `ORD-100` изменился, пул сдвинулся, и число
применённых операций упало с «больше 10 000» до 6 810 — при том, что ни одна проверяемая
функция не менялась. Порог сработал верно (он и стоит, чтобы ловить «фаззер ослеп»), но
причина была не в коде под тестом.

### Fix

Пул сортируется. Отображение «индекс → товар» становится устойчивым, и маршрут перестаёт
зависеть от сеяных данных.

**Порог `> 10000` не трогал** — понижать его, чтобы тест позеленел, значит выключить
единственный сторож фаззера. После сортировки прогон проходит его сам.

### Future rule

Всё, что сеяный генератор индексирует, обязано иметь определённый порядок. `Set` и
`Object.keys` его дают, но выводят из порядка вставки, то есть из данных, — и тест начинает
измерять фикстуры вместо кода.

## ✅ БАГ-23 — первый заказ списка был двумя строками и словом «отменён»

**File:** `frontend_vue/src/services/mocks/orders.ts`
**Severity:** Low — демо открывается на самом бедном заказе из ста

### Problem

Список идёт от новых к старым, значит первое, что видит человек, — `ORD-100`. У него было
две строки, отменённый статус и ни одной отгрузки, счёта, платежа, услуги или файла. Девять
рукотворных сценариев (`ORD-001`…`ORD-009`) лежат в самом хвосте, и до них надо знать, что
они есть.

### Fix

`ORD-100` собирается заново функцией `buildShowcaseOrder()` — и собирается **вызовами
эндпоинтов**, не сборкой объектов. Это то же правило, по которому живут девять сценариев, и
оно здесь важнее: заказ, набранный руками, показывает товар, уехавший с полки, на которой он
ещё лежит, цены, которых не даёт ни одна наценка, и счета, за которыми не стоит ни одной
накладной.

Что в нём теперь: строка отгруженная и выставленная в счёт, строка отгруженная наполовину,
строка с ручной ценой, строка с ручной себестоимостью и причиной, строка сверх складского
остатка (`estimate` + запись в дефицит), обычный черновик; услуга выставленная и услуга,
добавленная **после** счёта (§4.6 — та самая, ради которой появилась кнопка «Счёт за
услуги»); три отгрузки, одна из них отменена; три документа — обычный, авансовый и
корректирующий, выпущенный настоящей корректировкой цены; три платежа, включая возврат
отрицательной суммой; резервы, файлы и история, написавшая себя сама, с записью, которую
скрывает право `seeCost`.

Заказ назван в `mockOrderScenarios()` — как остальные девять, чтобы его можно было открыть
по номеру.

### Поправка по ходу работы

Первая версия проставляла заказу `totalWeight: 1840`. Спека хранилища это отбила — «invents
no weight: the value stays hand-entered while products have none». Тест прав, и правка была
именно тем украшательством, которое он запрещает: у товаров веса нет, значит и у заказа он
не берётся ниоткуда. Вес убран, тест не тронут.

### Future rule

Витрина обязана подчиняться тем же правилам, что и приложение, иначе она учит читателя
неправде о нём. Практический признак: если состояние нельзя получить, вызвав эндпоинты, —
его не должно быть и в демо.
