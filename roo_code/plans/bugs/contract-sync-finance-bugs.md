## БАГ-01 — клиент финансов не шлёт ни одного заголовка, а все три таблицы домена арендаторские

**File:** `frontend_vue/src/services/financeService.ts:20,33,42,49,63`
**Severity:** High — сервер не сможет ограничить выборку арендатором, не догадавшись, кто спрашивает
**Источник:** К6 (мультиарендность)

### Problem

Все пять вызовов домена уходят без третьего аргумента: `apiGet(path, params)` и
`apiPatch(path, data)`. `options?.headers` — единственный источник заголовков у обоих
(`frontend_vue/src/services/api.ts:144-158`, `:194-209`), значит на проводе нет ни
`Authorization`, ни чего-либо ещё. При этом схема требует `tenant_id` с `nullable=False, index=True`
у всех трёх таблиц домена — `finance_payments`, `payment_documents`, `document_archive_items`
(`backend/app/modules/finance/shared/models.py:16-21`, `:63-68`, `:98-103`).

Соседние домены с живым бэкендом заголовок шлют: `authHeaders()` возвращает `Authorization: Bearer`
(`frontend_vue/src/services/settingsService.ts:18-22`, применение `:27`; то же у
`frontend_vue/src/services/auditFeedService.ts:41`, `:46`), и сервер достаёт из токена пользователя
и его тенанта (`backend/app/modules/settings/features/crud/action.py:97-128`).

Заодно замер поправляет соседа: аудит notifications пишет, что `settingsService.ts:18,27` шлёт
«`Authorization: Bearer` + `X-CSRF-Token`». Второго заголовка там нет — во всём `frontend_vue/src`
`X-CSRF-Token` встречается **однажды**, и не в сервисе, а во входе
(`frontend_vue/src/composables/useAuth.ts:106`).

### Fix

Ввести в `financeService.ts` тот же `authHeaders()`, что у `settingsService.ts`, и передавать его
третьим аргументом во все пять вызовов.

### Future rule

Новый сервис заводится сразу с заголовками авторизации, если у сущности в схеме есть `tenant_id`.
Проверять машинно: клиент домена, чья таблица арендаторская, обязан иметь хотя бы один вызов с
`options`.

## БАГ-02 — PATCH платежа применяет тело целиком, без белого списка

**File:** `frontend_vue/src/services/mocks/finance.ts:513-522`
**Severity:** High — клиент может переписать сумму, номер, статус и породить уведомление о просрочке
**Источник:** К4 (формы запроса)

### Problem

`mockPatchPayment` заканчивается `{ ...current, ...data, updatedAt }` (`:522`) и тем же слиянием в
ветке файлов (`:513-518`). Ни одно поле не отсеивается. Подпись клиента это прямо разрешает:
`data: Partial<FinancePayment> & { fileIds?: string[] }` (`frontend_vue/src/services/financeService.ts:45-50`),
то есть `amount`, `paymentNumber`, `direction`, `status`, `paidAt`, `createdAt` — всё принимается.

Последствие не только в данных: `commit` рождает уведомление, когда статус перешёл в `overdue`
(`frontend_vue/src/services/mocks/finance.ts:484-488`), значит клиент может выписать себе событие «просрочка оплаты», послав
`{ "status": "overdue" }`. Старый контракт при этом называет `notes` **единственным** редактируемым
полем (`roo_code/roo-context/03-api-contract.md:2093-2095`) — то есть код разрешает больше, чем
задание.

Карточка сегодня шлёт только `notes` и `fileIds` (`frontend_vue/src/views/admin/finance/OutgoingPaymentCardPage.vue:77-80`),
поэтому наружу дефект не виден — но схема, снятая с такого «сервера», получит эндпоинт, правящий что угодно.

### Fix

Сузить и подпись клиента, и разбор мока до `{ notes?, fileIds? }`; всё остальное — `VALIDATION_ERROR`.
Код `VALIDATION_ERROR` в домене сейчас не бросается ни разу, хотя в каталоге старого контракта он
есть (`roo_code/roo-context/03-api-contract.md:1936`).

### Future rule

PATCH-мок пишется через явный список принимаемых полей, а не через spread тела. Spread тела — это
эндпоинт «правь что хочешь», и он не заметен ни одним тестом, пока UI шлёт мало.

## БАГ-03 — `counterpartyId` платежей не существует в сторе поставщиков

**File:** `frontend_vue/src/services/mocks/finance.ts:109-115`
**Severity:** Medium — уведомление о просрочке исходящего ведёт в пустую карточку
**Источник:** К2 (мок ↔ код)

### Problem

Пятёрка контрагентов объявлена константой внутри финансового мока с id `sup-001…sup-005` и
названиями `ArcelorMittal`, `SSAB AB`, `ThyssenKrupp`, `voestalpine`, `UAB Metalo Importas`
(`:110-114`). В сторе поставщиков id — `'1'…'6'`, и ни одной из этих компаний там нет
(`frontend_vue/src/services/mocks/suppliers.ts:9`, `:29`, `:49`, `:69`, `:89`, `:109`).

Пустой ссылкой это не остаётся: уведомление о просрочке исходящего платежа кладёт
`entityId: payment.counterpartyId` и `entityRouteName: 'admin-supplier-card'`
(`frontend_vue/src/services/mocks/notifications.ts:714-721`), а роут карточки поставщика ищет
поставщика по `:id` (`frontend_vue/src/router/index.ts:211-214`). То есть переход из ленты по такому
уведомлению открывает карточку поставщика, которого нет.

То же в архиве: `arch-7` ссылается на `relatedEntityId: 'sup-002'` с номером `'SSAB AB'`
(`frontend_vue/src/services/mocks/finance.ts:346-348`).

### Fix

Брать контрагентов из `mocks/suppliers.ts`, а не объявлять пятую копию рядом. Тогда `counterpartyName`
и `counterpartyVatCode` останутся снимком (это правильно), но `counterpartyId` будет разрешаться.

### Future rule

Ссылка на чужую сущность в моке обязана резолвиться в сторе этой сущности. Проверять спекой:
каждый `*Id` мока — существующий id соответствующего стора. У реестра входящих такая проверка уже
есть (`frontend_vue/src/services/mocks/finance-receivables.spec.ts:435`), у платежей — нет.

То есть один и тот же счёт поставщика существует в системе в двух экземплярах, у которых
**разные** `fileId`. Удаление документа с карточки платежа (PATCH с `fileIds`, `:491-519`) архив

### Fix

TBD — решение владельца: либо архив становится представлением (собирается из документов платежей,
счетов и накладных заказов, как реестр входящих собирается из счетов), либо остаётся отдельной
таблицей, и тогда нужен путь записи. Сегодняшнее третье состояние — копия без синхронизации.

### Future rule

(`frontend_vue/src/services/mocks/finance.ts:12-24`), относится и к документам: у одного файла
один владелец. Вторая запись о том же файле — это представление, а не сущность.

## БАГ-05 — список платежей и архив не сортируются вовсе

**File:** `frontend_vue/src/services/mocks/finance.ts:386-401,445-460`
**Severity:** Medium — порядок ответа определяется порядком объявления сида
**Источник:** К3/К4 (форма ответа)

### Problem

`sort` во всём финансовом моке встречается **один** раз, и он в реестре входящих
(`:101-102`). Ни `mockGetPayments`, ни `mockGetArchive` не сортируют: фильтруют и режут на страницы.
Старый контракт при этом обещает у платежей «Сортировка фиксированная — `dueDate ASC`»
(`roo_code/roo-context/03-api-contract.md:2024`), у архива — «Сортировка по `uploadedAt DESC`»
(`:2140`).

Порядок сида не совпадает ни с тем, ни с другим: сроки идут `-21`, `-9`, `+12`, `+26`, `-35` дня
(`:153`, `:177`, `:198`, `:219`, `:240`), а даты загрузки архива — `-2`, `-2`, `-2`, `-120`, `-24`,
`-22`, `-16`, `-45` (`:266`, `:280`, `:294`, `:308`, `:322`, `:336`, `:350`, `:364`). При пагинации
это ещё и меняет содержимое страниц: без `ORDER BY` вторая страница у настоящей БД может повторить
строку с первой.

### Fix

Добавить сортировку в оба мока — `dueDate ASC` у платежей, `uploadedAt DESC` у архива — и назвать
её в контракте как обязанность сервера, а не как поведение мока.

### Future rule

Список без явной сортировки — это API без определённого порядка. У каждой ветки списка в моке
обязан быть `sort`, и он обязан совпадать с тем, что обещает контракт; сегодня из трёх списков
домена его имеет один.

## БАГ-06 — единственный код ошибки домена не доходит до человека

**File:** `frontend_vue/src/views/admin/finance/OutgoingPaymentCardPage.vue:64-66,134-140`
**Severity:** Medium — «нет такого платежа» и «сеть упала» показываются одним экраном
**Источник:** К3 (коды ошибок)

### Problem

Мок бросает `PAYMENT_NOT_FOUND` в двух местах — чтение карточки (`frontend_vue/src/services/mocks/finance.ts:428`)
и её правка (`:475`). Клиент этот код нигде не читает: `catch { error.value = true }` и общий текст
`common.error_title` / `common.error_description` (`:64-66`, `:134-140`); то же на трёх списках
(`IncomingPaymentsPage.vue:62-64`, `OutgoingPaymentsPage.vue:55-57`, `DocumentArchivePage.vue:68-70`).
`grep -rn "ApiRequestError" frontend_vue/src/services/financeService.ts frontend_vue/src/views/admin/finance/`
— пусто, при том что структура с полем `code` есть (`frontend_vue/src/types/api.ts:25-47`).

воспроизводится вовсе. Тёзка того же кода в домене заказов доведён до сообщения таблицей

«платёж не найден»; для мок-режима — оборачивать ошибку ветки в `ApiRequestError` с кодом.

### Future rule

Код ошибки, который сервер обязан вернуть, должен быть прочитан хотя бы одним потребителем.
Код, брошенный моком и никем не разобранный, — это код, которого в контракте фактически нет.

На схеме это два разных поля: `id` — UUID из `UUIDMixin`, `file_id` — FK на `uploaded_files`
(`backend/app/modules/finance/shared/models.py:58-79`). Тип во фронте тоже держит оба
(`frontend_vue/src/types/finance.ts:5-13`). Совпадение их значений — свойство мока, и карточка на
него уже опирается по-разному: удаление ищет по `id` (`frontend_vue/src/views/admin/finance/OutgoingPaymentCardPage.vue:90-95`),
а отслеживание правок — по `fileId` (`:40-51`).

### Fix

Выдавать новому документу собственный `id` (счётчик `pdoc-N`, как у сидов), оставив `fileId` ссылкой
на аплоад.

### Future rule

Два поля в типе — два значения в данных. Мок, у которого они совпадают, разрешает потребителю
перепутать их, и перепутанное всплывёт на сервере, где они различаются.

## БАГ-12 — `PAYMENT_NOT_FOUND` содержит в себе код ядра `NOT_FOUND`, а сверка кодов идёт подстрокой

**File:** `frontend_vue/src/services/mocks/finance.ts:428`, `:475`
**Severity:** Medium — покажется не тем сообщением, и не сегодня, а когда сервер начнёт отвечать
**Источник:** К3 (коды ошибок), найдено инверсией подстрочного детектора

### Problem

§2 общих соглашений требует прямо: «Ни один код не является подстрокой другого», потому что фронт
местами сравнивает код подстрокой. Единственный код домена это правило **нарушает** — против
каталога ядра, а не против своих:

```bash
# код домена
grep -n "throw new Error" frontend_vue/src/services/mocks/finance.ts   # PAYMENT_NOT_FOUND ×2
# каталог ядра
awk 'NR>=13&&NR<=48' backend/app/core/exceptions.py | grep -oE '"[A-Z_]+"' | sort -u
# → CONFLICT FORBIDDEN NOT_FOUND UNAUTHORIZED VALIDATION_ERROR
```

`NOT_FOUND` (`backend/app/core/exceptions.py:13-20`) — подстрока `PAYMENT_NOT_FOUND`. Сегодня это
не проявляется по двум причинам, и обе временные: роутов у модуля `finance` нет, то есть ядро на
этих путях ничего не бросает; и финансовых кодов нет ни в одной подстрочной таблице — их вообще
никто не разбирает (БАГ-06).

Место, где подстрочность реальна, в проекте существует и знает об этой опасности: таблица заказов
сопоставляет код подстрокой и упорядочена так, чтобы содержащийся код стоял **после**
содержащего — комментарий записан прямо в коде
(`frontend_vue/src/services/orderLineEdits.ts:322-324`, пара `PAYMENT_NOT_FOUND` / 
`PAYMENT_INVOICE_NOT_FOUND` — `:326-327`). Стоит финансам появиться в такой таблице, а серверу —
начать отдавать ядровый `NOT_FOUND`, и «нет такого платежа» с «нет такого ресурса» разъедутся по
порядку строк, а не по смыслу.

Аудит домена утверждает обратное — «Подстрокой ни в кого не входит»
(`roo_code/plans/api/audit/finance.md:58`); утверждение проверялось только против доменных кодов
соседей, а каталог ядра в сравнение не попал.

### Fix

Код не тронут (план сверки код не правит). Решать не автору: либо код домена переименовать так,
чтобы он не содержал ядровый (например `PAYMENT_MISSING`), либо признать правило §2 действующим
только внутри доменного каталога и записать это в соглашения. Оба варианта — решение владельца, и
своей строки у него пока нет ни в
[`00-решения-владельца.md`](../api/audit/00-решения-владельца.md), ни в §2 соглашений.

### Future rule

Проверка «ни один код не подстрока другого» обязана сравнивать доменный каталог **с каталогом
ядра**, а не только сам с собой: ядро объявляет пять кодов, и четыре из пяти доменных семейств
проекта кончаются на `_NOT_FOUND`. Проверка, которая сравнивает набор только внутри себя, зелена по
построению.
