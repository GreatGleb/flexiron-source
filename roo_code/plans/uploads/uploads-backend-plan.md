## 2. Согласованное поведение и конфликты схемы

### 2.1. Компания-владелец и доступ

Файл принадлежит одной компании из подтверждённого сеанса. Клиент не передаёт tenantId,
tenant_id или X-Tenant ни в загрузке, ни при чтении. Одинаковый email в двух компаниях по П76
не даёт общего доступа. Каждая связь и файл должны принадлежать этой же компании.
Сеанс без пользователя/компании отвергается до чтения тела и записи на диск: 401 UNAUTHORIZED,
как в [плане auth, каталоге ошибок](../auth/auth-backend-plan.md). Живой сеанс без права — 403 FORBIDDEN.

Инженерный контракт С9: multipart загрузки расширяется контекстом `entityType` и `entityId`
(идентификатор необязателен только для новой карточки). Это контекст проверки edit по П15,
не источник компании. Для новой карточки дополнительно действует право её создания; до Save
файл остаётся draft. Сервер валидирует разрешённые типы контекста и существующую карточку,
а при привязке повторяет проверку компании и прав. Отсутствующий/негодный контекст — 422
VALIDATION_ERROR. Клиент, транспорт, мок и контракт меняются вместе; нынешний запрос контекста не несёт.

GET метаданных и маршрут скачивания проверяют текущий сеанс и разрешённый контекст доступа.
Для связанного документа — права исходной карточки либо право полного архива по П84;
для самостоятельного документа — права архива. Ссылка сама по себе доступа не даёт.
Для draft действует контекст загрузки и edit; для новой карточки сохраняется её контекст создания.
Подпись связывает файл, компанию и срок; на скачивании компания сверяется с сеансом, права
проверяются заново. Чужой файл и отсутствующий файл неразличимы: FILE_UNKNOWN, 404.
Подпись около 15 минут не отменяет проверку П84 и не разрешает вечную публичную раздачу.
Маршрут байтов спроектирован как GET /api/uploads/:id/content с подписью в query;
подпись не содержит сессионный токен. При нынешнем Bearer-транспорте клиент получает байты
авторизованным fetch и создаёт локальный object URL для preview/download, освобождая его
после использования. Обычный img/src или переход по ссылке не умеет сам добавить Bearer:
С6 обновляет такие потребители вместе с сервером, без переноса токена в URL.

### 2.2. Лимиты и формы

Серверный конфиг задаёт 20 × 1024 × 1024 байт на файл и ровно пять разрешённых MIME:
`application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`,
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `image/png`, `image/jpeg`.
SVG, GIF, WebP и произвольный `image/*` не добавляются. Клиент получает
`{ maxSizeMb: number, allowedMime: string[] }` через GET /api/uploads/limits и использует ответ
для accept, подсказки и предварительной проверки. Сервер проверяет размер и MIME независимо
от клиента; чтение ограничивается лимитом плюс один байт, а не неограниченным file.read().
Мок использует один источник лимитов для GET и своей валидации; это тестовые данные сервера,
не вторая константа в UI. Изображения карты/логотипа выбираются пересечением image MIME с ответом сервера.

POST принимает один файл и возвращает `ApiResponse<UploadedFile>` с
`{ fileId, name, size, mime, url, uploadedAt }`; дата — ISO-строка. С1 исправляет сервер, не
сужает потребителей к двум полям. Тип `size` модели согласуется с BigInteger миграции,
аргументы tenant_id/uploaded_by сервиса — UUID. GET /api/uploads/:id возвращает ту же форму
со свежей ссылкой; /limits регистрируется до динамического маршрута.

### 2.3. Хранение, удаление и восстановление

Три разных срока: подписанный URL — около 15 минут (П11); непривязанный draft — 24 часа из
конфига (П31); привязанным документам срок автоматического удаления этим планом не назначается.
Успешный Save снимает is_draft и обнуляет expires_at в той же транзакции, что создаёт связь.
Ошибка Save заказа/склада откатывает связи и оставляет загрузку черновиком; П104 запрещает
видимый частично созданный заказ. Загрузка до Save финансовой записи остаётся отдельной по П49.

Один fileId разрешён у платежа и архива: П128 не создаёт вторую копию содержимого.
Отвязка снимает только указанную связь. Физическое удаление допустимо лишь после исчезновения
всех сохраняемых ссылок; проверяются FK, JSON-списки, архив, BCC и значения file-полей.
RESTRICT сохраняется как дополнительная защита, но JSON-ссылки он не видит.
Скрытое по П73 значение продолжает удерживать файл: возврат того же определения показывает
тот же fileId и содержимое. Архивирование исходной записи также не является удалением файла.
Восстановление физически удалённого блоба, корзина и восстановление старой карты склада не
обещаются: таких решений нет; опросник settings:4 прямо не выводит их из задержки уборки.

С12 после последней отвязки переводит файл в непривязанный draft с TTL конфига. Это техническое
переиспользование механизма П31, не обещание интерфейса восстановления. Cleanup повторно
проверяет связи под той же блокировкой файла, что attach/detach, и не удаляет присоединённый
конкурентом файл. БД и файловая система не имеют общей транзакции: С5 использует компенсацию
записи и устойчивую повторяемую очередь физического удаления. Сбой unlink не считается успехом
уборки и не теряет возможность повторить удаление; отсутствие блоба при повторе допустимо.
Постановка в очередь физического удаления атомарно закрывает возможность новой привязки
этого fileId; worker повторяет удаление по устойчивому заданию. Нельзя снять блокировку,
позволить attach, а затем удалить его блоб отложенным unlink.

### 2.4. Метаданные и П72

Источник стабильных метаданных — uploaded_files. В чужих модулях копии имени, размера, MIME,
даты сохраняются по П72; uploads не объявляется исключением. Временный подписанный URL не
хранится как постоянная колонка или источник права. С8 убирает именно хранимую ссылку и читает
её через С6, сохраняя file_id и стабильные копии. Перечень событий копий: создание связи
заполняет копию; смена fileId заполняет её заново; изменение стабильных метаданных источника
обновляет все копии; удаление связи убирает её копию. Событие и изменение источника фиксируются
атомарно, обработчик повторяем; после сбоя возможна сверка и повтор доставки. Новый пользовательский
редактор метаданных не вводится. Это внутренние события синхронизации, не уведомления П51.

## 3. Ошибки

Таблица — проект каталога. Сейчас сервер различает MIME/размер статусами, но использует один
VALIDATION_ERROR; пользователь без компании получает старый NOT_FOUND. Новые FILE_* ещё
не реализованы. Транспорт читает структурированный code через общий errorCode, не текст message.

| Код | HTTP | Условие и реакция |
|---|---|---|
| MISSING_TOKEN | 401 | Нет заголовка Authorization; общий механизм С0 auth |
| INVALID_TOKEN | 401 | Неверная подпись, пустой Bearer или повреждённый payload; общий механизм С0 auth |
| TOKEN_EXPIRED | 401 | Истёк срок токена; общий механизм С0 auth |
| UNAUTHORIZED | 401 | Пользователь выключен/удалён/без компании; общий auth-путь |
| FORBIDDEN | 403 | Нет права edit/read/полного архива для выбранного пути; не сбрасывать действительный сеанс |
| VALIDATION_ERROR | 422 | Неверная форма запроса или контекст |
| FILE_TYPE_NOT_ALLOWED | 422 | MIME вне разрешённых; показать переведённую причину |
| FILE_TOO_LARGE | 413 | Размер выше лимита; показать величину из GET limits |
| FILE_UNKNOWN | 404 | Неизвестный или чужой fileId при чтении/привязке/отвязке; никаких фиктивных метаданных |
| FILE_LINK_EXPIRED | 403 | Истёк срок; один повтор авторизованного чтения и скачивания, затем явная ошибка |
| FILE_LINK_INVALID | 403 | Подпись невалидна; не повторять бесконечно |

FILE_ALREADY_ATTACHED не вводится: общий файл разрешён. Повтор содержимого на сервере не
ошибка (П50). Новые коды проверить на коллизии со всем каталогом проекта перед реализацией;
показ локализованного сообщения проверяется у потребителя, а не только в транспорте.

## 4. Сквозные правила

Применяются [сводка](../general/сквозное-сводка.md),
[tenancy Т1–Т8](../general/сквозное-tenancy-план.md) и
[idempotency Д1–Д8, Г1–Г6](../general/сквозное-idempotency-план.md).

- Права: С9 заполняет таблицы маршрутов, элементов CRUD и ролевых defaults сквозного плана;
  отдельного самостоятельного права upload по умолчанию нет. П84 применяется явно.
- Tenancy: uploaded_files — таблица категории А; новые связи/очередь удаления тоже несут
  tenant_id. store_file получает компанию из сеанса; get/attach/detach/delete/cleanup сужают
  каждый select/update/delete самостоятельно. Разрешение компании по сеансу — исключение Т4,
  оно документируется в общем стороже, а не копируется в новый маршрут. Фронт компанию не шлёт.
  У uploaded_files сейчас нет бизнес-уникальностей кроме UUID PK; оригинальное имя не уникально.
  У реестра связей уникальность проектируется по компании, файлу и идентичности связи;
  модель и миграция меняются вместе. Повтор attach той же связи не дублирует её и аудит.
- Аудит: привязка/отвязка меняют свойство исходной сущности (П36), снимок имени автора не
  зависит от nullable uploaded_by. Служебная загрузка не требует нового вида пользовательской истории.
- Уведомления: строка для раздела уведомлений контракта — `Событий домена нет.` (П51);
  это не запрет внутренних событий копий П72.
- Идемпотентность: для POST /api/uploads строка `**Ключ идемпотентности:** не требуется — операция обратима (отвязка, уборка непривязанных по П31; П50)`.
  П46 не вводит серверную дедупликацию файлов. Вызовы внутри Save наследуют транзакцию и версию
  вызывающего домена; загрузка не коммитит за чужой Save.
- Кастомные поля: значение содержит fileId; П73 сохраняет скрытую ссылку и её файл.
  Согласование словаря file с config — зависимость сквозного плана, не повод потерять значение.
  В контракте отметить участие в механизме строкой `Кастомные поля: да.` и ссылкой на
  [сквозной план полей](../general/сквозное-custom-fields-план.md), блок Д.

Следующие две строки перенести в контракт ровно по одному разу, как требуют Д3/Д4:

**Атомарность Save:** отдельными запросами — порядок не задан, частичное сохранение возможно (П43, П49). Save-формы в домене нет; привязка внутри Save заказа/склада атомарна по П43/П104.

**Версия записи:** не ведётся — last-write-wins, `If-Match` не шлётся и не читается (§11).
