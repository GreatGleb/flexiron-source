# Verify — цикл проверок

Проверка — это **цикл**, а не список команд. Один проход ничего не доказывает: починка одной находки ломает то, что уже было проверено. Поэтому проверенное после каждой правки снова становится непроверенным.

## Условие выхода

Цикл завершается, только когда выполнено **и то, и другое**:

1. **Полный свип** — все линзы области пройдены на *текущем* коде, ни одной неподтверждённой.
   Фронтенд — Л1–Л10; бэкенд — Б1–Б5 плюс Л3, Л5, Л10. Область задаётся при вызове цикла и
   сужается только явно;
2. **В этом свипе не нашлось ни одной новой находки.**

Любая правка кода сбрасывает подтверждение **у всех линз**, не только у той, что нашла проблему. Правка i18n ломает типы, правка типов ломает тест — линза, пройденная три итерации назад, больше ничего не гарантирует.

**Лимит — 30 итераций.** Итерация = один свип. Счётчик не сбрасывается ни при каких обстоятельствах. Дошло до 30 без чистого свипа → СТОП и отчёт «не сошлось» с перечнем неподтверждённых линз. «Не сошлось» — это нормальный результат работы. ✅ в такой ситуации — ложь.

## Дедупликация — без неё цикл не сходится

Ключ находки: `файл:символ:тип` — файл, имя функции/компонента/правила и класс проблемы.
**Не номер строки:** строки съезжают от собственных же правок, и та же самая отклонённая находка
возвращается «новой» на новом номере. Механизм, который должен спасать от прогорания 30 итераций,
течёт именно здесь.

Веди список **рассмотрено**:

- находка починена → в «рассмотрено»;
- находка отклонена (проверил, ложное срабатывание) → тоже в «рассмотрено», одной строкой почему.

Уже рассмотренная находка, всплывшая снова, **не считается новой** и цикл не продлевает. Без этого правила линза каждую итерацию заново «находит» отклонённое, и 30 итераций сгорают на месте.

## Журнал прогона

`roo_code/roo-context/verify-runs/<цель>.md` — создать при первом прогоне. Без журнала номер итерации и список рассмотренного живут только в контексте и теряются при перезапуске. На каждую итерацию: номер, что запускалось, находки, что починено, состояние линз.

## Машинная приёмка — вход в каждую итерацию

```bash
cd frontend_vue && npm run verify    # typecheck · lint · dupes · format:check · test:unit
```

Пять шагов, собранных в один скрипт: гейт, пройденный на три четверти, назвать пройденным не
выйдет. По отдельности — только когда красное и надо сузить: `npm run typecheck`, `npm run lint`,
`npm run dupes`, `npm run format:check`, `npm run test:unit`.

`dupes` — это jscpd, детектор копипасты. Порог 10 % в [`.jscpd.json`](../../frontend_vue/.jscpd.json)
при факте 9.69 %, прогон 111 мс. Проверено инверсией: при пороге 5 падает. Порог — храповик по
факту, а не идеал: опускать его по мере разбора дубликатов, а не ставить сразу «как надо».

Внутри `lint` с 2026-08-25 работает ещё и `eslint-plugin-sonarjs`. Пресет включён целиком, но
пятнадцать правил выключены поимённо с числом нарушений в комментарии — 233 нарушения превратили бы
линт в фон. Работают, в частности, `no-duplicated-branches`, `no-identical-expressions`,
`no-all-duplicated-branches`: дубликаты, которые jscpd не видит, потому что текст разный, а
структура одна.

Форматирование в гейте не декорация — питфолл #67: typecheck и lint про него молчат. `format:check`
покрывает `src/` **и** `tests/`: спека — такой же код.

`lint` и `format:check` кэшируются в `node_modules/.cache/` — первый прогон ~20 с, повторный 2–5 с.
Гонять их каждую итерацию дёшево, «долго» больше не оправдание.

У `lint` стоит `--max-warnings=0`. Без него предупреждение не роняет ничего: `no-explicit-any`
настроен как `warn`, и любое число `any` оставляло гейт зелёным. Флаг поставлен 2026-08-25, когда
предупреждений было ноль — то есть по правилу «шаг вводится зелёным», а не «поставим и разгребём».

- `npm run test:audit` — если трогалось что-нибудь из семьи `order-audit-*`. Это **не только**
  `src/domain/`: конфиг берёт `src/**/order-audit-*.spec.ts`, а такие спеки лежат ещё в
  `src/composables/` и `src/services/mocks/`. Правка мока заказов задевает их так же, как правка домена.
- `npm run test:e2e` — **только на финальном свипе**, и не весь набор по умолчанию: см. «Какой прогон e2e нужен» ниже. Гонять полный каждую итерацию бессмысленно.
- Красная машинная приёмка = итерация закончена сразу, линзы не смотрим: обзор кода, который не компилируется, ничего не значит.

### Шаг гейта вводится только зелёным

`prettier --check` попал в этот файл 2026-08-22 (afd4163) — и на том же коммите пять файлов в
`src/` его уже не проходили. Гейт родился красным. Красный с рождения шаг не отличает «я только что
сломал» от «так было всегда», поэтому его красное читается как фон и никем не разбирается: за
следующие трое суток через него прошли три коммита в `src/`.

Отсюда правило: новый шаг машинной приёмки добавляется сюда только после того, как дерево его
проходит. Нельзя привести к зелёному сразу — шаг не добавляется, а заводится задачей в план, и до
её закрытия в гейте его нет. Иначе получается не проверка, а строчка, которую все обходят.

Раздел ниже — применение того же правила: `npm run audit` красный, поэтому он вынесен из гейта
итерации и снабжён датой и составом, а не подмешан к шагам, которые обязаны быть зелёными.

## Какой прогон e2e нужен

Полный набор — это ~16 минут, а пара полных прогонов — больше получаса. Платить их надо там,
где они что-то доказывают, и не платить, где не доказывают. Уровня два.

**Уровень 1 — правка в одной области. Прогон затронутых файлов.**
Правка в одной области приложения или в самих спеках: запускаются спеки этой области плюс
те, кто читает тот же мок. Пара не нужна, полный набор не нужен.

Круг «кто читает тот же мок» определяется грепом по импортам мока, а не на глаз.

**Уровень 2 — правка в общем полу. Полный набор, и пара — только здесь.**
Общий пол — то, через что проходит каждый тест: `tests/e2e/helpers/`, фикстуры,
`src/services/mocks/index.ts` (диспетчер), i18n, роутер, глобальный CSS. Здесь правка задевает
весь набор, поэтому одного зелёного прогона мало: нужны два подряд на одном дереве.

**Почему уровни, а не одна планка.** 2026-08-25: проход по одноразовым чтениям тронул 27 мест
в 12 файлах спеков — то есть тесты, не приложение. Полный прогон шёл 16 минут и упал на
`clients.spec.ts`, файле из этого же прохода. Прогон двенадцати затронутых спеков нашёл бы то
же самое за три минуты. Шестнадцать минут были потрачены не на доказательство, а на ожидание.

Обратный пример того же дня: правка `helpers/ready.ts` лежит на пути всех тестов до единого —
там полный набор и пара обязательны, и они трижды находили настоящее.

### Прогон читается по коду возврата и по полному выводу — иначе он ничего не значит

Две ошибки, обе допущены 2026-08-25 в один день, обе привели к тому, что **красный прогон был
прочитан как зелёный**.

**1. Конвейер съедает код возврата.** `npx playwright test | tail -3` возвращает код `tail`, а не
Playwright. `exit 0` в такой команде означает «tail отработал», и ничего больше. Правильно так:

```bash
npx playwright test --reporter=line > run.txt 2>&1; echo "exit=$?"
```

Код берётся сразу после команды, до любых конвейеров. Если конвейер нужен — `${PIPESTATUS[0]}`.

**2. Итог Playwright — несколько строк, и `N failed` печатается ВЫШЕ `N passed`.** Обрезка хвоста
оставляет последнюю строку и отрезает ту, что меняет смысл. Так «1001 passed» было прочитано как
«почти всё зелено», хотя означало 1001 пройденных **и семь упавших**.

Отсюда правило: вывод прогона сохраняется в файл целиком, а вердикт снимается по коду возврата и по
строкам `failed`/`flaky`/`skipped`, а не по одной последней строке. Число `passed` само по себе не
вердикт: оно не отличает «все прошли» от «часть упала».

**Число тестов здесь намеренно не написано.** Оно меняется каждым пунктом плана, а
продублированное значение устаревает молча — эту болезнь мы вычищали из кода и из счётчиков
питфоллов, заводить её здесь заново незачем.

### Воркеры

`--workers=3` при 8 ядрах — это НИЖЕ дефолта Playwright (половина ядер, то есть 4). Памяти 14 ГБ,
реально держит 5–6.

Поднимать имеет смысл только после того, как починена семья гоночных чтений (пункты 1b и 1c
плана): больше воркеров — больше конкуренции, и оставшиеся гонки будут падать чаще, то есть
прогон станет быстрее и краснее одновременно. Порядок: сначала семья, потом замер времени на
4, 5 и 6 воркерах, и выбор по числу.

`retries: 0` локально — **решение, а не недосмотр**: флейки мы ловим, а не прячем. Ретраи в CI
(их там 2) для другого — там прогон должен доводиться до конца. Локально ретрай спрятал бы
ровно то, за чем мы охотимся.

## Обзорные линзы (10)

Каждая — отдельный тип проверки со своим предметом. Пройти надо все.

Правило из [`vue-rules.md`](vue-rules.md) — «новый питфолл дописывается в линзу» — держится только
если проверять, что оно выполнено: 2026-08-25 из 68 питфоллов в линзах не было 27. Разнесены все,
кроме четырёх, и эти четыре не забыты, а сознательно вне линз: **#4** (Vite отдаёт 403 на файлы вне
корня) и **#6** (`taskkill` убивает Claude Code) — про среду, а не про код; **#11** и **#47**
(typecheck+lint ≠ проверка, гонять typecheck после каждой правки) — про процесс, и им отведён весь
этот файл целиком.

### Л1. Реактивность и жизненный цикл

Проверка: `grep -n "structuredClone\|toRaw(\|useHead(\|watch(" ` по затронутым файлам, каждое вхождение прочитать.

### Л2. i18n
`@` в переводах (#1), сырые ключи в DOM (#39, #43), `tf()` без null-guard (#41), удалённые `resolveLabel`/`labelLookup` (#34), правка не того файла переводов (#35), русский в моках (#33), `toTranslatedString()` обнуляет остальные локали (#38), разные ключи «Отмена» у save bar и модала (#18), контекстные заголовки секций (#46).

### Л3. Контракт и HTTP
Метод под смысл операции (PATCH ≠ PUT), у каждого вызванного роута есть мок (#40), необходимость `/translated` перепроверена после рефакторинга (#42), contract-first соблюдён.
Проверка: собрать список всех вызовов страницы и сверить с роутами мока — глазами, поштучно.

### Л4. Мок = правда
Мок отдаёт прямую ссылку на массив (#13), доменные поля неполны (#45), инъекция сбоя как мгновение вместо состояния (#65), данные «украшены» под демо.
Мок держится ровно того же правила, что приложение: если в приложении так нельзя — в моке тоже нельзя.

### Л5. Один источник правила
Второй экземпляр того же правила рядом с первым — корень трёх аудитов подряд. Статусы, пилюли, форматтеры, хелперы, вычисление цены.
Проверка: для каждого правила, которое трогалось, — grep по всему проекту на вторую реализацию. Нашёл вторую → это находка, даже если обе работают. Перед созданием компонента — grep существующих (#61); чужой CSS-файл не источник классов (#63).

С 2026-08-25 у линзы есть машинная часть: `npm run dupes` (одинаковый текст), правила sonarjs
внутри `npm run lint` (одинаковая структура при разном тексте) и `npm run deadcode` (второй
экземпляр, который вообще никто не зовёт). **Грепа она не отменяет:** инструмент видит одинаковый
код, а линза ищет одинаковое *правило*, записанное по-разному — вычисление цены в двух местах
разными формулами машина не поймает никогда.

Пустая строка не нормализована в null (#50), `load()` разрушает несохранённое, Save UX не тот (clean-slate vs quick-actions), уход со страницы без предупреждения.

### Л9. Тесты, которые ничего не утверждают
**Самая важная линза.** Зелёный прогон не доказывает поведение. Ожидание элемента вместо пришедших данных (#64), утверждение об отсутствии там, где присутствие было невозможно (#66), утверждение, которое устраивает бездействие (#68).
Проверка — инверсия: сломать проверяемое поведение в коде и убедиться, что тест краснеет. Тест, не покрасневший на сломанном коде, не тест. Одна инверсия на каждое утверждение, а не на файл.
Сюда же: тест опирается на конкретные данные мока (#15), базовая линия скриншота не обновлена после правки UI (#22), иерархические пути в селекторах (#44).

### Л10. Целостность проекта
`src/router/index.ts` без дублей имён; `src/i18n/admin/index.ts` импортирует все домены; все флаги из представлений есть в типе `FeatureFlags` (`src/config/featureFlags.ts`); dev-сервер поднимается.

**Что заведомо вне машинной приёмки** — знать это надо, чтобы не считать зелёный `typecheck`
доказательством по всему дереву. `include` в `tsconfig.json` — это `src/**/*.ts`, `src/**/*.vue`,
`env.d.ts`, и больше ничего. Значит вне типизации:

- пять `.js` в `src/` — `main.js`, `composables/useHead.js`, `i18n/index.js`, `i18n/public.js`,
  `i18n/translations.js`. Они входят в `include`, то есть парсятся, но **не типизируются**: для
  этого нужен `checkJs: true`, а он стоит 22 ошибки — БАГ-03 в
  [`static-analysis-debt-bugs.md`](../plans/bugs/static-analysis-debt-bugs.md).

`tests/` с 2026-08-25 **внутри** и typecheck, и eslint — 83 ошибки типов и 2 ошибки линта тогда же
починены. Включение окупилось сразу: `ALL_FLAGS_ENABLED` в `tests/e2e/helpers/flags.ts` не содержал
**16 флагов из 52**, семь из них выключены по умолчанию — то есть конфигураторы колонок складских
вкладок, канбан заказов и раскрой не открывал ни один тест ни разу. Теперь список аннотирован типом
`FeatureFlags`, и забытый флаг роняет typecheck. Пункт про `ALL_FLAGS_ENABLED` в Л7 стал машинным —
глазами его пропускали.

Замер 2026-08-25: включение `tests/**` в `include` даёт **83 ошибки типов** — то есть это не пустая
формальность, там лежит настоящее (например `route.fulfill()` получает `Promise<void>` вместо
объекта в `tests/e2e/mocks/warehouse.ts`). Правка требует кода, поэтому живёт в плане, а не здесь;
но линза обязана помнить, что этот кусок дерева никем не проверен.

## Бэкенд: приёмка и линзы Б1–Б5

Машинная приёмка бэкенда слабее фронтендовой, и знать это надо до прогона, а не после: в `backend/`
нет ни pytest, ни ruff, ни mypy/pyright — 120 файлов кода и ноль тестов (проверено по
`requirements.txt` и `pyproject.toml`). Поэтому вердикт по бэкенд-задаче держится на линзах и
импорт-проверке, а не на зелёном прогоне тестов.

```bash
cd backend && python -c "from app.main import app; print('приложение импортируется')"
cd backend && python -c "from app.modules.<модуль>.features.<фича>.action import router; print('слайс импортируется')"
cd backend && alembic upgrade head      # миграции применяются
```

Подъём приложения — только неблокирующе: `uvicorn` в фоне, затем `curl /health`, затем снять
процесс. `uvicorn --reload` в автономном прогоне не завершается никогда и вешает задачу навсегда.

Проверка, которая молча пропускается, — не проверка. Строка вида
`python -m pyright app/ 2>/dev/null || echo "skipping"` всегда печатает skipping, потому что pyright
не установлен: она создаёт вид гейта и не проверяет ничего. Либо инструмент ставится и гейт
настоящий, либо строки нет.

### Б1. Изоляция модулей
Обращения к чужому модулю только через его `internal_api/interface.py`; прямых импортов из
`features/` или `shared/` другого модуля нет; в `app/core/` нет бизнес-логики.

### Б2. Модель ↔ миграция ↔ контракт
Поля, `nullable`, `server_default` совпадают во всех трёх местах; JSONB-переводы с суффиксом
`_translations`; новая модель зарегистрирована в `alembic/_alembic_imports.py`; ревизия создана и
применяется на чистой базе.

### Б3. Мультиарендность
`tenant_id` есть в моделях всех десяти модулей — значит фильтр по нему обязателен в **каждом**
запросе. Запрос без него отдаёт данные чужого арендатора, и ни один тест этого не поймает, потому
что тестов нет.

### Б4. Транзакции и N+1
Границы `commit`/`rollback` явные, не «где-то в зависимости». Связанные сущности —
`selectinload`/`joinedload`, а не запрос в цикле. В проекте эти загрузчики встречаются ровно в одном
репозитории из 120 файлов, так что искать здесь стоит.

### Б5. Контракт наружу
Метод и путь по контракту; ответ завёрнут в `ApiResponse`/`PaginatedResponse`; коды ошибок
доменные; 404 и 422 обрабатываются, а не падают пятисоткой.

Из фронтендовых линз к бэкенду применимы **Л3** (контракт), **Л5** (один источник правила),
**Л10** (целостность). Л1, Л2, Л6, Л8 — фронтендовые. **Л9** станет применима, как только в
`backend/` появится первый тест.

## Что считается пройденной линзой

Запись в журнале вида «Л4 — чисто» не считается. Пройденная линза — это три вещи: **чем проверял** (команда или греп целиком), **что вернулось**, **вывод**. Линза без команды в журнале остаётся неподтверждённой (питфолл #68 — утверждение, которое устраивает бездействие; Verification Rule из ROO.md).

Находка вне области задачи не чинится молча: она уходит в bugs-file через [`add-bug.md`](add-bug.md),
и линза считается пройденной.

**Свип от этого чистым быть не перестаёт** — иначе выход недостижим: припаркованная находка не
чинится по определению, всплывает каждую итерацию и держит цикл красным до самого лимита, а с ним и
мерж. Правило простое: чистоту свипа определяют только **новые** находки в области задачи.
Припаркованное — не новое (оно в списке «рассмотрено») и цикл не продлевает, но обязано быть
перечислено в отчёте: «в bugs-file ушло N» с номерами. Человек решает по этому списку, а не цикл.

## Вызов из других скилов

Скилы не описывают проверку сами и не заводят свои списки — они вызывают этот цикл: «прогнать цикл проверок из `verify.md` по <цели>». Область можно сузить (например, только Л2 и Л9 для правки переводов) — но условие выхода и лимит 30 итераций не меняются никогда.

**В автономном прогоне** остановок нет: цикл идёт до чистого свипа или до лимита сам. Мерж ветки разрешён **только** после чистого свипа; «не сошлось» — ветка остаётся неслитой и ждёт человека.
