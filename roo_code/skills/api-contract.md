# API Contract — написать контракт для бэкенда по коду

Задача этого скила: превратить код, который уже работает, в **задание для бэкенда**. Не описать
фронтенд, а сказать серверу, что он обязан делать, — включая то, чего во фронтенде не видно вовсе.

Выход по домену — два файла:

- `roo_code/plans/api/audit/<домен>.md` — аудит: что найдено в коде, с `файл:строка` на каждое
  утверждение;
- `roo_code/roo-context/api/<домен>.md` — сам контракт.

План работы, порядок фаз и состояние — [`roo_code/plans/api/contract-sync-plan.md`](../plans/api/contract-sync-plan.md).
Прогон по всем доменам — воркфлоу `roo_code/workflows/contract-sync.js`.

> **Это не `verify.md`.** Тот скил — цикл проверок фронтенда, линзы Л1–Л10 писались про Vue:
> реактивность, i18n, CSS. Для контракта применимы три из них, поэтому здесь своё семейство К1–К7
> и свой цикл. Машинную приёмку фронтенда (`npm run verify`) мы у него берём — она общая, потому
> что спеки контракта живут в `frontend_vue/src` и гоняются тем же `test:unit`.

## Два режима

| | Интерактивный | Автономный |
|---|---|---|
| Кто запустил | человек в чате | воркфлоу `contract-sync.js` |
| Неясность в коде | спросить и ждать | **не догадываться**: строка уходит в `audit/00-решения-владельца.md` |
| Решение «как должно быть» | принимает человек | **запрещено**: наблюдение — да, решение — нет |
| Признак готовности домена | человек посмотрел | спека зелёная + ни одной пустой графы |
| Кто закрывает домен | человек | **не автор**: отдельный агент-скептик, и у домена три попытки |

Граница между наблюдением и решением — главное правило этого скила. «В `SupplierFormSections.vue`
список валют записан константой, хотя валютами владеют настройки» — наблюдение, его делает агент.
«Список валют должен приходить из настроек арендатора» — решение, его принимает владелец. В
автономном прогоне второе превращается в догадку, которую никто не увидит.

## Источник истины — три, с порядком старшинства

Проверяется **по каждому эндпоинту отдельно**, а не по домену.

1. **Реализация бэкенда**, если она есть. Замер 2026-09-03: `backend/app` отдаёт **31 роут**, и
   они распределены крайне неровно — `settings` 24, `auth` 4, `products` 2, `core/uploads` 1.
   У остальных семи модулей (`bcc`, `billing`, `finance`, `notifications`, `services`,
   `suppliers`, `warehouse`) роутов **ноль**: модель есть, эндпоинтов нет. Все 31 вызываются
   фронтендом — бэкенд ни разу не ушёл вперёд (`comm` по двум инвентарям пуст).
   Форма ответа берётся оттуда; расхождение фронта с ней — находка про фронт, а не про контракт.
2. **Мок и клиент**, если серверной реализации нет. Мок сам называет себя reference
   implementation, с которой пишется бэкенд.
3. **Сам контракт**, если раздел написан вперёд — как задание бэкенду, которого нет ни во фронте,
   ни на сервере. Такой раздел сохраняется и помечается `**Статус:** спроектировано`.

| что нашли | что делаем |
|---|---|
| есть в бэкенде и во фронте | описываем по бэкенду; расхождение фронта — в bugs-файл домена |
| есть во фронте, бэкенда нет | описываем по клиенту и моку |
| в контракте есть, в коде нет, и это замысел | оставляем с меткой `Статус: спроектировано` |
| в контракте есть, в коде нет, и это устарело | удаляем, оставив строку в «Чего в домене нет» |
| код при чтении выглядит неверным | **код не трогаем** — находка в `plans/bugs/contract-sync-<домен>-bugs.md` |

**Ничего не удаляется молча.** Молча вычеркнутое решение теряется: `POST /api/auth/refresh` был
описан полным разделом с механикой продления сессии, а в коде его нет нигде — на весь контракт
такой случай оказался один, и именно поэтому правило нужно.

Именно в этом порядке: каждый следующий источник читается уже зная предыдущий.

**Имена файлов не угадываются, а находятся.** Замерено по всем семнадцати доменам: шаблон
`<домен>Service.ts` неверен для трёх (`audit-feed`, `sales-crm`, `auth`), `mocks/<домен>.ts` — для
четырёх (плюс `uploads`), а `types/<домен>.ts` совпадает лишь у восьми из семнадцати: у остальных

> реализации нет вовсе. Порядок старшинства — не формальность: он ловит именно это.

## Шаг 3 — формат раздела эндпоинта

Жёсткий: его парсит спека.

```markdown
### PATCH /api/orders/:orderId/items/:lineId

Правит одну строку заказа. Тело — дельта, ответ — строка целиком.
Save-режим: clean-slate, уходит по кнопке Save карточки.

Запрос:
{ quantity?: number; priceMode?: 'auto' | 'manual'; manualPrice?: number | null }

Ответ: `ApiResponse<OrderLine>`

Ошибки: `FORBIDDEN_MANUALCOST` · `LINE_NOT_FOUND` · `ORDER_LOCKED`

Реализация: `services/orderLineEdits.ts:patchOrderLine` · мок `mocks/orders.ts:mockPatchLine`
```

Обязательны заголовок ровно `### <МЕТОД> <путь>` и строка `Реализация:`. Имя параметра свободно —
спека нормализует любое `:<имя>` в `:id` с обеих сторон.

**У домена, где есть модуль бэкенда, каждый раздел несёт ещё строку `Бэкенд:`** — файл со строкой
или слово «не реализован». Без неё читатель не отличит «сервер это уже делает» от «серверу это
предстоит», а именно эта разница определяет, кто здесь источник истины. Пример: у `auth`
реализованы четыре эндпоинта из пяти, и `logout` помечен «не реализован» — при том, что клиент и
мок его имеют, то есть метка `Статус: спроектировано` тут была бы **неверна**: она про отсутствие
кода вообще, а не про отсутствие серверной части.

Три правила формата, каждое из которых уже ловило ошибку:

- **динамический сегмент не разворачивается в заголовки.** `GET /api/analytics/:page` — один
  раздел, значения `page` списком внутри. Восемь заголовков
  `### GET /api/analytics/dashboard` спека прочитает как восемь эндпоинтов, которых в коде нет;
- **упоминание пути в прозе описанием не считается** — и не должно им становиться. В старом
  контракте `POST /api/support/contact` и `GET /api/public/stats` присутствуют только фразами об
  их удалении. Спека читает лишь заголовки, поэтому такие фразы безопасны;
- **примеры в `00-conventions.md` и `README.md` не оформляются заголовком `###`** — иначе они
  читаются как описание не своего домена.

## Шаг 4 — «Обязанности сервера»: то, чего во фронтенде не видно

Валюта по умолчанию, которой владеют настройки арендатора. Уведомление после изменения. Запись в
лог сущности. Определения кастомных полей. Настройки, которых мок не отслеживает никак. **Это не
эндпоинты, и линзы К1–К5 их не видят по построению: вызова нет, сравнивать не с чем.** В
мок-режиме отсутствие такой обязанности не проявляется никак — отсюда главный источник
расхождений между фронтом и сервером.

Образец раздела — §1 «Главное: что сервер обязан делать сам» в
[`plans/orders/orders-backend-contract.md`](../plans/orders/orders-backend-contract.md): шесть
правил, и рамка названа прямо — «их нарушение не ловится тестами фронтенда, но ломает данные».

Девять граф, и **пустая графа = домен не закрыт**:

| графа | что должно быть в ответе |
|---|---|
| значения по умолчанию и их владелец | валюта, НДС, маржа, скидка: константа во фронте или настройка арендатора |
| события и уведомления | какое изменение рождает запись; почему повтор не рождает вторую |
| запись в аудит-лог | что пишется, кто автор, что помечается `sensitive` |
| кастомные поля | откуда определения, кто валидирует значения, что с полем удалённого определения |
| настройки, которых мок не отслеживает | перечислить прямо, а не умолчать |
| мультиарендность | чем ограничена выборка (`tenant_id` есть в моделях всех десяти модулей) |
| права | в какой функции проверяются — обязана быть та же, что пишет |
| транзакционность и идемпотентность | что откатывается целиком; где нужен `Idempotency-Key` |
| производные значения | что сервер считает при чтении и не хранит |

Чем искать:

```bash
# обязанность, которую мок уже реализует — её видно и можно доказать спекой
grep -rn "auditLog.push\|notify[A-Z]\|recordShortage" frontend_vue/src/services/mocks/ | grep -v spec
grep -c "^export function notify" frontend_vue/src/services/mocks/notifications.ts   # семь триггеров
cat frontend_vue/src/services/mocks/notification-triggers.spec.ts                     # чем доказаны

# константа во фронте на месте серверного значения
grep -rn "const [A-Z_]*OPTIONS\|defaultCurrency\|vatRate\|defaultMargin" frontend_vue/src --include=*.ts --include=*.vue | grep -v '\.spec\.'
# сверить с тем, чем управляют настройки
grep -rn "settings\.\(currencies\|uoms\|constants\|conversions\)" frontend_vue/src | grep -v '\.spec\.'
```

Замеренный пример этого класса: `composables/useSettings.ts:27` держит `defaultCurrency: 'EUR'`
дефолтом состояния, а `components/admin/SupplierFormSections.vue:58-63` — жёсткий список
`EUR/USD/PLN/GBP`, хотя валютами владеют настройки и пять других мест строят селект из
`settings.currencies`. Причём остальные используют `c.id` как значение, а форма поставщика — код
валюты. Наблюдение записывается в аудит и в bugs-файл; решение — владельцу.

## Шаг 5 — линзы К1–К7

Свип по всем семи. **Командой проверяется малая часть**: машинный слой доказывает
**согласованность** (контракт ↔ код ↔ мок ↔ типы) и никогда не доказывает **правильность** — если
само правило неверно, все машинные проверки останутся зелёными. Остальное — чтение кода, и делает
его агент.

Ниже — **предмет** каждой линзы. **Состояние** машинных частей меняется по ходу работы и живёт в
одном месте — таблице в [плане](../plans/api/contract-sync-plan.md), раздел «Линзы контракта»:
дублировать его здесь значило бы завести второй экземпляр того же факта. На 2026-09-04 машинная
часть есть только у К1; остальные проходятся чтением — работают, но дороже и без пола.

### К1. Инвентарь: код ↔ контракт
Каждый вызов описан; каждое описание существует в коде; раздел лежит в файле своего домена.
Машинно: `contract-conformance.spec.ts`. Глазами: правила формата из шага 3.

### К2. Мок ↔ контракт ↔ код
У каждого описанного эндпоинта есть ветка в `mocks/index.ts` (питфолл #40 из `vue-rules.md`); у
каждой ветки есть вызывающий — либо запись в реестре «клиент написан, UI нет».
Замер 2026-09-03: 179 ветвей; **одна дыра** — `POST /api/auth/register` зовётся, ветки нет, под
моками регистрация падает (против настоящего сервера работает: роут у бэкенда есть); **пять
сирот** — `DELETE /api/warehouse/movements/:id`, `GET /api/clients/translated`,
`GET /api/orders/translated`, `GET /api/settings`, `PUT /api/settings`.

### К3. Коды ошибок
Каждый код, который бросает **мок** домена, есть в каталоге раздела; ни один код не подстрока
другого (фронт сравнивает подстрокой); каждый код доходит до человекочитаемого сообщения.
Образец реализации — `mocks/order-audit-contract-conformance.spec.ts`. Замер: orders 55 кодов,
warehouse 17, settings 6, clients 3, finance 1.

**Есть модуль бэкенда — каталог берётся и с него, и он старше.** Замер по auth: три кода бэкенд
объявляет прямо в эндпоинте — `MISSING_TOKEN`, `TOKEN_EXPIRED`, `INVALID_TOKEN`
(`me/action.py:44-72`), — и ни одного из трёх мок не знает; первая версия `auth.md`, написанная по
моку, их не содержала. Остальные приходят из исключений ядра (`core/exceptions.py:20-48`):
`NOT_FOUND`, `VALIDATION_ERROR`, `UNAUTHORIZED`, `CONFLICT` — их auth бросает; `FORBIDDEN` там
объявлен, но в auth не используется, и в контракт домена он не попадает. Мок при этом бывает **слабее**: magic-link у сервера отвергает просроченный токен,
а мок принимает любой непустой — путь ошибки под моками не воспроизводится, и это тоже факт для
контракта.

### К4. Формы запроса и ответа
Тип, названный в контракте, существует в `types/*.ts`; поля совпадают по именам и nullability;
регистр не «поправлен по привычке» — домен auth целиком в `snake_case`, потому что таков ответ
FastAPI. Пять из шести дефектов раздела `# Auth` ловятся сравнением с интерфейсом.
**Есть модуль бэкенда — сверять надо с его схемами, а не с типами фронта:** три из четырёх
расхождений `auth.md` с сервером (лишнее поле `rememberMe`, обязательность `first_name`/
`last_name`, лишнее `secret_link` в `MeResponse`) видны именно так.

### К5. Источник истины
Порядок старшинства соблюдён по каждому эндпоинту; метка `Статус: спроектировано` стоит только
там, где кода нет, и **истекает**: появился вызов — красное; удалённое оставило строку в «Чего в
домене нет». У домена с модулем бэкенда у каждого раздела есть строка `Бэкенд:` — файл со строкой
или «не реализован» (шаг 3).

### К6. Обязанности сервера — главная линза, машинной части нет
Девять граф шага 4 заполнены наблюдениями с `файл:строка`; строки с ответом «нигде» вынесены в
`audit/00-решения-владельца.md`. Машинно возможно ровно одно — «раздел существует и непуст», — и
этой проверки пока **нет**: до неё линза держится на приёмщике, у которого в промпте она есть.

### К7. Ссылки и следы реализации
У каждого раздела строка `Реализация:`; файл существует, символ находится грепом; относительные
ссылки резолвятся по файловой системе. Ссылка на документ не проверяется ничем — тест падает, а
«прочитай контракт по пути X» не падает никогда: файл переименовали, и 28 ссылок в четырёх скилах
остались на прежнее имя.

**У каждой машинной проверки обязан быть свой пол.** Инвентарь моков мерился трижды, две первые
версии врали молча: построчный разбор терял многострочный `path.match(\n /^…$/)`, а разбор шаблона
до `$/` рвался о класс `[^/]`, приняв слэш внутри класса за конец. Первая версия показала 96 «дыр»
вместо одной. Проверка, чей экстрактор считает не то, хуже отсутствующей — она выдаёт зелёный
отчёт. В `contract-conformance.spec.ts` для этого стоят пол 175, запрет нелитеральных путей и
требование, чтобы каждый файл с литералом `/api/` дал хотя бы один эндпоинт.

**И у каждой — своя инверсия.** Сломай проверяемое и убедись, что покраснело именно то
утверждение. У спеки К1 девять утверждений и **двенадцать** инверсий, они перечислены в плане;
когда пишешь спеку К2–К4, К7 — перечисли свои там же. Инверсия, которая ничего не сломала, ничего
и не доказала.

Две инверсии из этих двенадцати нашли дыры в самой спеке, а не в контракте: дженерик, разнесённый
по строкам (`apiPost<\n  LoginResponse\n>(…)`), делал вызов невидимым, а литерал в двойных
кавычках в `.vue` не считался упоминанием пути. Обе закрыты — но урок общий: экстрактор проверяют
инверсией так же, как тест.

## Цикл проверок контракта

Проверка — цикл, а не один проход: правка контракта сбрасывает подтверждение у всех линз.

**Вход итерации** — машинная приёмка фронтенда, потому что спеки контракта живут в его дереве:

```bash
cd frontend_vue && npm run verify    # typecheck · lint · dupes · format:check · test:unit
```

Красная приёмка = итерация закончена сразу, линзы не смотрим.

**Выход** — и то, и другое: все семь линз пройдены на текущем состоянии, и в этом свипе не
нашлось ни одной новой находки. **Лимит 30 итераций**, счётчик не сбрасывается; дошло до 30 —
СТОП и отчёт «не сошлось» с перечнем неподтверждённых линз.

**Дедупликация:** ключ находки `файл:символ:тип`, не номер строки. Отклонённая находка идёт в
список «рассмотрено» одной строкой почему — иначе каждая итерация «находит» её заново.

**Пройденная линза — это три вещи:** чем проверял (команда или греп целиком), что вернулось,
вывод. «К3 — чисто» не считается.

**Журнал:** `roo_code/roo-context/verify-runs/contract-<домен>.md`. Только свой файл.

## Приёмка домена — что значит «закрыт»

1. `cd frontend_vue && npm run verify` — зелёный;
2. спека К1 включила домен автоматически (файл появился) и не показывает ни одного пропущенного
   эндпоинта;
3. в `audit/<домен>.md` нет ни одной пустой графы; каждое утверждение имеет `файл:строка`;
4. каждый пробел из аудита либо закрыт в тексте контракта, либо помечен строкой «осталось»;
5. раздел «Обязанности сервера» непуст, строки «нигде» вынесены в
   `audit/00-решения-владельца.md`;
6. находки про код записаны в `plans/bugs/contract-sync-<домен>-bugs.md` — и код не тронут.

## Чего этот скил не делает

- **не правит код.** Ни одной строки в `frontend_vue/src`, кроме спек контракта и генератора
  скелетов. Место, где код выглядит неверным, — находка, а не задача;
- **не пишет бэкенд.** Слайс FastAPI — это [`create-api-feature.md`](create-api-feature.md).
  Появился слайс — метка `Статус: спроектировано` снимается, и источник истины переходит к
  бэкенду (К5);
- **не проверяет фронтенд.** Страница, компонент, реактивность — [`verify.md`](verify.md),
  линзы Л1–Л10. Пересечение только в машинной приёмке;
- **не принимает решений о поведении.** Расхождение решается по старшинству источников; спорное
  и «нигде» — владельцу.
