# Sales CRM

Сводка дашборда продаж. Домен из **одного** эндпоинта — `GET /api/sales-crm/stats`, — и его ответ
это **четыре числа и ничего больше**: `activeOrders`, `pendingOrders`, `salesMtd`,
`newClientsThisMonth` ([`types/order.ts:48-57`](../../../frontend_vue/src/types/order.ts)). Ни
валюты, ни периода, ни отметки среза рядом с ними нет, поэтому **смысл каждого числа задаётся
этим файлом, а не ответом**: второй потребитель тех же четырёх чисел прочитает их так, как решит
сам.

Общие соглашения — [`00-conventions.md`](00-conventions.md) в этом каталоге. Конверт ответа (§1),
каталог кодов ядра (§2), фильтр арендатора и то, откуда сервер берёт арендатора (§4),
авторизация и заголовки (§5), права и фича-флаги (§6, §7), пагинация и «сортировка принадлежит
серверу» (§13), даты, деньги и владение валютой (§14), производные значения (§17), чем мок
отличается от сервера (§18), форма идентификатора (§19) — там, и здесь **не повторяются**: второй
экземпляр правила расходится с первым при первой же правке.

Аудит, из которого написан файл: [`plans/api/audit/sales-crm.md`](../../plans/api/audit/sales-crm.md).
Находки про код: [`contract-sync-sales-crm-bugs.md`](../../plans/bugs/contract-sync-sales-crm-bugs.md)
— семь, код не тронут.

**Источник истины домена — мок и клиент**, второй уровень старшинства из
[скила](../../skills/api-contract.md). Причина: модуля `sales-crm` на бэкенде **нет вовсе** — не
«есть, но без роутов», как у `warehouse` или `suppliers`, а нет каталога (`ls backend/app/modules/`
→ `auth bcc billing finance notifications products services settings suppliers warehouse`), нет
модели и нет таблицы. Значит форма ответа и правила счёта сняты с мока
(`mocks/orders.ts:1577-1595`), а не назначены здесь.

**Своего слоя у домена тоже нет** — единственный случай среди семнадцати: ни своего сервиса, ни
своего мока, ни своих типов. Ближе всех к нему `auth` — у него тоже нет ни `authService.ts`, ни
`mocks/auth.ts`, но свои типы есть (`frontend_vue/src/types/auth.ts`), и модуль бэкенда тоже.
Клиент живёт в [`services/ordersService.ts:53-55`](../../../frontend_vue/src/services/ordersService.ts),
тип — в `types/order.ts:48-57`, «сервер» — в
[`services/mocks/orders.ts:1577-1595`](../../../frontend_vue/src/services/mocks/orders.ts). Файлов
`salesCrmService.ts`, `mocks/salesCrm.ts`, `types/salesCrm.ts` не существует. Поэтому все ссылки
`Реализация:` ниже указывают в файлы заказов, и это не ошибка оформления.

**Метка `Статус: спроектировано` домену не подходит:** код есть и во фронте, и в моке. Строка
`Бэкенд:` по шагу 3 скила обязательна у домена с модулем бэкенда; здесь модуля нет, но строка
стоит — иначе читатель не отличит «сервер это уже делает» от «серверу это предстоит».

**Динамических сегментов у домена нет ни одного:** единственный путь — литерал без параметров, и
ветка мока сравнивает его строкой, а не регуляркой (`mocks/index.ts:540`). Разворачивать в
заголовки нечего.

### GET /api/sales-crm/stats

Отдаёт четыре сводных числа по **всем** заказам и **всем** клиентам арендатора. Существует
отдельным эндпоинтом потому, что счёт по странице списка — не счёт (см. правило домена 1).

Реализация: `services/ordersService.ts:53-55` → `getSalesCrmStats` · мок
`services/mocks/orders.ts:1577` → `mockGetSalesCrmStats`, ветка `services/mocks/index.ts:540`

Бэкенд: **модуля нет** — ни каталога `backend/app/modules/sales*`, ни модели, ни роута; ближайшее
попадание слова во всём `backend/app` не про этот домен
(`grep -rln -i "sales\|crm" backend/app --include=*.py` → один файл,
`backend/app/modules/products/shared/models.py`)

Save-режим: **read-only, quick-action и clean-slate не применимы.** Во всём домене один вызов, и он
`GET`; ни одной записи нет. Загрузка разовая — `onMounted(load)`
([`composables/useSalesCrmDashboard.ts:70`](../../../frontend_vue/src/composables/useSalesCrmDashboard.ts)),
повторное чтение возможно только руками, кнопкой в ветке ошибки (`SalesCrmPage.vue:107`).

**Запрос — пустой.** Ни сегмента пути, ни query-параметра, ни заголовка:

```
GET /api/sales-crm/stats
```

Клиент — три строки целиком: `apiGet('/api/sales-crm/stats')` без второго и третьего аргументов
(`services/ordersService.ts:53-55`), то есть без `params` и без `options.headers`, а
`options?.headers` — единственный источник заголовков у `GET`
([`services/api.ts:157-159`](../../../frontend_vue/src/services/api.ts)). Заголовков в домене нет
ни одного, включая `Authorization`
(`grep -c "Authorization\|authHeaders" frontend_vue/src/services/ordersService.ts` → `0`), при том
что канонический `authHeaders()` в проекте есть
([`composables/useAuth.ts:101-108`](../../../frontend_vue/src/composables/useAuth.ts)) — и из
сервисного слоя им не пользуется никто: импортов `useAuth` в `frontend_vue/src/services/` нет
ни одного (`grep -rln "useAuth" frontend_vue/src/services/` → `0`). Соседи, которым заголовок
нужен, завели себе копии, и копии с каноном разошлись — разбор всех четырёх реализаций «где
лежит токен» и их измеримое следствие в §5 соглашений; здесь оно не повторяется. Как сервер
узнаёт арендатора в таком вызове — общее правило §4 соглашений
(«из токена, и только из него») плюс строка владельца 4 ниже.

**Периода в запросе нет.** «Этот месяц» вычисляется на стороне сервера из его собственных часов
(`mocks/orders.ts:1578-1580`), поэтому другое окно спросить нечем — строка владельца 1.

Ответ — `ApiResponse<SalesCrmStats>` (конверт — §1 соглашений, снимает `unwrap`,
`services/api.ts:127-141`):

```ts
interface SalesCrmStats {
  activeOrders: number        // всё, что ещё в работе
  pendingOrders: number       // ждёт чьего-то действия
  salesMtd: number            // нетто-оборот с 1-го числа текущего месяца
  newClientsThisMonth: number // клиенты, зарегистрированные с 1-го числа
}                             // types/order.ts:48-57
```

Все четыре поля **обязательны**, все `number`, порядок в объекте значения не имеет. Полей рядом с
ними нет: ни `currency`, ни `asOf`/`generatedAt`, ни границ периода, ни разбивки по валютам и
статусам. Мок отдаёт объектный литерал ровно из этих четырёх ключей (`mocks/orders.ts:1589-1594`).

**Правило счёта каждого числа — часть контракта, а не деталь реализации.** Сервер обязан считать
по правилу, а не по перечню статусов (правило домена 2):

| поле | правило | где сегодня записано |
|---|---|---|
| `activeOrders` | заказ **не** `delivered` и **не** терминален; терминальны `completed`, `returned` и любая отмена | предикат `isActive` — [`domain/orderStatus.ts:103-105`](../../../frontend_vue/src/domain/orderStatus.ts), `isTerminal` — `:92-94`; счёт — `mocks/orders.ts:1590` |
| `pendingOrders` | заказ ждёт чьего-то действия | **перечислением двух статусов**: `o.status === 'new' \|\| o.status === 'confirmed'` (`mocks/orders.ts:1591`) — единственное из четырёх, посчитанное списком: БАГ-03, строка владельца 3 |
| `salesMtd` | сумма `totalAmount` (нетто, до НДС) заказов, у которых `countsAsSale(status)` и `createdAt >= начало месяца`; НДС выручкой не является | предикат `countsAsSale` — `domain/orderStatus.ts:121-123`; счёт — `mocks/orders.ts:1585-1587` |
| `newClientsThisMonth` | клиенты, чей `createdAt >= начало месяца`, **без** оглядки на `status` клиента | `mocks/orders.ts:1593`; статус клиента — `types/client.ts:31` |

Три уточнения, каждое из которых меняет число:

- **`salesMtd` привязан к дате создания заказа, а не к дате продажи** — правило домена 3;
- **`salesMtd` считает заказанное, включая возвращённое**, тогда как то же слово «выручка» в том же
  файле мока считается иначе — БАГ-01, строка владельца 7. Контракт фиксирует наблюдаемое
  поведение и **не** выбирает между тремя определениями: это решение владельца;
- **граница месяца режется местной полуночью процесса** (`mocks/orders.ts:1578-1580`), а даты
  заказа и клиента приходят разной точности — правило домена 7, БАГ-04, строка владельца 3.

Ошибки: **каталог домена пуст.** Путь чтения не бросает ничего
(`sed -n '1577,1595p' frontend_vue/src/services/mocks/orders.ts | grep -c "throw"` → `0`; ветка
`mocks/index.ts:540-542` тоже). Кодов ядра домен не наследует ни одного, потому что наследовать
некуда: бэкенда нет. Что это значит для сервера — раздел «Каталог кодов ошибок» ниже.

## Каталог кодов ошибок

**Своих кодов у домена ноль**, и это не пробел описания, а состояние кода: единственный путь —
чтение, оно не отказывает ни при каких входных данных, потому что входных данных нет. Общие коды
ядра (`NOT_FOUND`, `VALIDATION_ERROR`, `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT` — §2 соглашений)
домен сегодня не наследует: серверной части не существует.

Что из этого следует для сервера — два правила, оба выведены из кода, а не из вкуса:

1. **Появившийся отказ обязан нести код, а не текст** (§2 соглашений). Сегодня во фронте кода
   принять некому: `catch` кладёт `e instanceof Error ? e.message : String(e)`
   (`useSalesCrmDashboard.ts:63-64`), а страница печатает это сырым — `<p>{{ error }}</p>`
   ([`views/admin/sales-crm/SalesCrmPage.vue:106`](../../../frontend_vue/src/views/admin/sales-crm/SalesCrmPage.vue)).
   Таблица перевода кодов в фразы в проекте есть и рядом используется
   (`ERROR_KEYS` — [`services/orderLineEdits.ts:300`](../../../frontend_vue/src/services/orderLineEdits.ts),
   читает её `lineEditErrorKey` — `:415-421`; вызов на чтении карточки заказа —
   [`composables/useOrderCard.ts:412`](../../../frontend_vue/src/composables/useOrderCard.ts) с
   причиной рядом: «A key, not the exception's own words», `:409-411`) — этот домен её не зовёт:
   БАГ-07.
2. **В это поле попадёт и чужой код.** Дашборд читает три домена одним `Promise.all`
   (`useSalesCrmDashboard.ts:30-52`) — сводку, страницу заказов и страницу клиентов, — и отказ
   любого из трёх обнуляет страницу целиком (`SalesCrmPage.vue:106`, ветка `v-else-if="error"`
   вместо всего содержимого). Список заказов умеет отказать четырьмя кодами
   (`UNKNOWN_SORT_KEY`, `UNKNOWN_SORT_DIRECTION`, `INVALID_DATE_FILTER`, `INVALID_PAGE` —
   `mocks/orders.ts:1444`, `:1447`, `:1453`, `:1465`), и в поле ошибки сводки читатель увидит
   именно их. Каталог этих кодов принадлежит домену `orders`, а не этому.

## Обязанности сервера

То, чего во фронтенде не видно вовсе: в мок-режиме отсутствие такой обязанности не проявляется
никак. Девять граф — наблюдения по коду; строки, у которых ответа нет **нигде**, вынесены в
[«Пробелы, оставленные владельцу»](#пробелы-оставленные-владельцу) и в
[`audit/00-решения-владельца.md`](../../plans/api/audit/00-решения-владельца.md).

**1. Значения по умолчанию и их владелец.** Настраиваемых значений у домена нет ни одного — есть
четыре константы, и все четыре стоят на месте серверных:

- **валюта** — знак `€` вшит в форматтер страницы: `` return `€ ${value.toFixed(2)}` ``
  (`SalesCrmPage.vue:43-45`, применение `:149`), тогда как валютой владеют настройки
  (`constants.defaultCurrency`, [`types/settings.ts:15-18`](../../../frontend_vue/src/types/settings.ts),
  справочник [`services/mocks/settings.ts:68-85`](../../../frontend_vue/src/services/mocks/settings.ts)),
  и заказ её у настроек уже спрашивает
  ([`composables/useOrderCreate.ts:43`](../../../frontend_vue/src/composables/useOrderCreate.ts),
  применение `mocks/orders.ts:1638`). Общее правило — §14 соглашений («справочник принадлежит
  серверу, во фронте его копии быть не должно»); здесь это БАГ-02;
- **окно периода** — «этот месяц» жёстко: `setDate(1)` плюс `setHours(0,0,0,0)` от текущей даты
  сервера (`mocks/orders.ts:1578-1580`);
- **глубина двух виджетов** — `pageSize: 5` дважды константой в потребителе
  (`useSalesCrmDashboard.ts:42`, `:50`) против 25 у обоих списков (§13 соглашений). Справочника под
  неё нет;
- **число KPI и их порядок** — четыре панели литералами в шаблоне (`SalesCrmPage.vue:113-153`),
  скелет загрузки тоже знает четыре (`:101`). Сервер о составе панели не знает ничего — в отличие
  от аналитики, где `kpis` приходит массивом.

Кому принадлежат валюта сводки, окно периода и глубина виджетов — **нигде**: строка владельца 1.

**2. События и уведомления.** Домен не рождает ни одного, и это доказуемо его составом — один
`GET`: `sed -n '1577,1595p' … | grep -c "notify\|auditLog.push"` → `0`, и ни один из семи
эмиттеров (§10 соглашений) сводки не касается
(`grep -cin "sales\|crm" frontend_vue/src/services/mocks/notifications.ts` → `0`).

Обратная сторона важнее: **домен показывает результат чужих событий, не подписываясь ни на одно.**
Три события заказов — смена статуса, готовность склада, поступление оплаты (`mocks/orders.ts:1837`,
`:3929`, `:4001`) — двигают ровно те статусы, из которых считаются `activeOrders`, `pendingOrders`
и `salesMtd`, а дашборд узнаёт об этом только при следующем `onMounted`
(`useSalesCrmDashboard.ts:70`). Обновления после чужой записи у домена нет: кеша нет, состояние
создаётся заново на каждый вызов композабла (`useSalesCrmDashboard.ts:8-16`). Пробела здесь нет —
наблюдение полное.

**3. Запись в аудит-лог.** Чтение сводки следа не оставляет:
`sed -n '1577,1595p' … | grep -c "appendHistory\|auditLog"` → `0`; замкнутый перечень девяти
сущностей ленты (§9 соглашений, [`types/audit.ts:16-26`](../../../frontend_vue/src/types/audit.ts))
сводки не содержит — все девять чужие. Путей записи в файле-хозяине **два**, и сводку не
задевает ни один: помощник `appendHistory` (`mocks/orders.ts:1874-1893`) с двумя вызывающими
(`grep -n "appendHistory(" frontend_vue/src/services/mocks/orders.ts` → `1827`, `1874`
определение, `1905`) и прямой `auditLog.push` в сиде (`mocks/orders.ts:546`), который пишет мимо
помощника. Сид — тоже путь записи, а не оформление: комментарий над ним
(`mocks/orders.ts:530-532`) прямо обязывает его к правилам эндпоинтов («the demo store is held to
the rules the API is held to»).

Нужно ли писать след о самом просмотре месячного оборота — **нигде**: строка владельца 2.

**4. Кастомные поля.** Домен их не касается ни в одну сторону:
`grep -c "fieldValues\|FieldDefinition\|fieldId"` по `useSalesCrmDashboard.ts` и `SalesCrmPage.vue`
→ `0` у обоих; у типа ответа четыре числовых поля и ничего расширяемого (`types/order.ts:48-57`).
Разрезов сводки по кастомному полю нет ни одного, хотя библиотека определений существует отдельным
доменом (§8 соглашений). У заказа, из которого сводка считается, кастомных полей нет вовсе. Это
наблюдение, а не пробел: расширять сводку кастомными разрезами никто не просил, запрета в коде
тоже нет.

**5. Настройки, которых мок не отслеживает.** Четыре, и каждая двигает как минимум одно из четырёх
чисел:

- **справочник статусов заказа.** Настройки хранят пятнадцать записей `st-<имя>`
  (`services/mocks/settings.ts:208-346`), фронт — те же пятнадцать имён константой
  (`domain/orderStatus.ts:15-31`); статус, заведённый через настройки, получает id `st-<N>`
  (`services/mocks/settings.ts:544`), которого в перечислении нет. Прямое следствие для сводки:
  **новый статус попадает в `activeOrders` автоматически** (он «не терминальный»), **в `salesMtd`
  тоже** (он «не new, не отмена, не returned»), **а в `pendingOrders` — никогда**, потому что там
  список (`mocks/orders.ts:1591`);
- **ставка НДС.** `salesMtd` объявлен нетто («VAT is not revenue», `types/order.ts:53-54`) и берёт
  `totalAmount`, то есть сумму до налога; ставка лежит на самом заказе (`vatPercent`,
  `types/order.ts:467`) и после создания за настройками не следует;
- **часовой пояс арендатора.** Нет нигде
  (`grep -ci "timezone" frontend_vue/src/types/settings.ts` → `0`; на бэкенде единственное
  попадание — свойство типа колонки `DateTime(timezone=True)`,
  `backend/app/modules/settings/shared/models.py:57`), а граница месяца режется местной полуночью
  процесса (`mocks/orders.ts:1578-1580`) — БАГ-04;
- **статус клиента.** `newClientsThisMonth` считает всех, чей `createdAt` в этом месяце
  (`mocks/orders.ts:1593`), не глядя на `status: 'active' | 'inactive'`
  ([`types/client.ts:31`](../../../frontend_vue/src/types/client.ts)). Комментарий типа говорит
  «registered», то есть считать всех — намерение, а не промах (`types/order.ts:55`), но записано
  это только комментарием.

Какие статусы считаются «ожидающими» и в каком поясе режется месяц — **нигде**: строка владельца 3.

**6. Мультиарендность.** Общее правило — §4 соглашений: `tenant_id` объявлен в моделях всех десяти
модулей, фильтр по арендатору обязателен в каждом запросе, а арендатор берётся из токена. Что
принадлежит этому домену:

- в домене про арендатора нет ничего: `grep -ci "tenant"` по `useSalesCrmDashboard.ts` и
  `SalesCrmPage.vue` → `0` у обоих, вызов идёт без `options` (`services/ordersService.ts:54` против
  `services/api.ts:157-159`);
- **сводка читает два хранилища сразу** — заказы напрямую (`mocks/orders.ts:1590`, `:1591`,
  `:1585`) и клиентов через `mockGetClients()` (`:1593`, определение
  [`services/mocks/clients.ts:1046-1048`](../../../frontend_vue/src/services/mocks/clients.ts)),
  оба плоские на процесс. **Фильтр арендатора обязан стоять на обеих выборках**, и пропущенный на
  любой из них течёт именно в это число — то есть туда, где заметен меньше всего;
- таблиц ни заказа, ни клиента на бэкенде не существует, поэтому проверить фильтр сегодня нечем.

Как сервер узнаёт арендатора при вызове без заголовков — **нигде**: строка владельца 4.

**7. Права — в какой функции проверяются.** Ни в одной. Единственный гейт — **тарифный**, а не
ролевой: маршрут закрыт фича-флагом `adminSalesCrm`
([`router/index.ts:139-142`](../../../frontend_vue/src/router/index.ts), значение — константа
[`config/featureFlags.ts:24`](../../../frontend_vue/src/config/featureFlags.ts), ключ
[`types/features.ts:21`](../../../frontend_vue/src/types/features.ts)); тот же ключ засеян у
сервера в реестре фич
(`backend/alembic/versions/8cf3bfa380dd_phase_12_plans_multi_role.py:81-83`), и эндпоинта между
реестром и константой нет ни одного — частный случай засеянного решения владельца №1 (§7
соглашений), замеренный на этом домене.

На пути чтения не вызывается ни одна проверка права:
`sed -n '1577,1595p' … | grep -c "requireRight\|maySeeCost"` → `0`, ветка мока
(`mocks/index.ts:540-542`) тоже; серверная проверка прав — заглушка `return True` (§6 соглашений).

**Элемента матрицы прав про сводку не существует:** элементы строятся из секций и полей карточки
поставщика и только из них (`items.push({ itemId: sec.id, … type: 'section' })` и то же для полей —
[`services/mocks/config.ts:189-204`](../../../frontend_vue/src/services/mocks/config.ts)).
Два попадания `grep -in "sales\|crm\|dashboard" frontend_vue/src/services/mocks/config.ts` —
это **имя роли** `Sales` в списке адресов (`:181`) и в `PERMISSION_ROLES` (`:186`), а не элемент
матрицы; аудит домена записал по этому грепу `0`, и счёт в нём неверен, хотя вывод верен
(поправка отмечена в журнале прогона).

**Следствие измеримо:** месячный оборот компании видит любая роль, открывшая страницу, — тогда как
три права заказов существуют ровно про видимость денег (`seeCost`, `manualCost`, `correction` —
`services/mocks/settings.ts:62-66`, потребитель
[`composables/useOrderPermissions.ts:28-30`](../../../frontend_vue/src/composables/useOrderPermissions.ts)),
и `seeCost` применяется только к истории заказа (`mocks/orders.ts:1390-1393`, применение
`:1384-1386`). Себестоимость и выручка — разные вещи, и права на вторую нет нигде: строка
владельца 5.

**8. Транзакционность и идемпотентность.** Записей у домена нет, поэтому `Idempotency-Key` и
`If-Match` (§11 соглашений) не применимы по составу:
`grep -c "apiPost\|apiPut\|apiPatch\|apiDelete\|apiUpload"` по строкам домена → `0`, единственный
вызов — `apiGet` (`services/ordersService.ts:54`).

Единственное требование этого класса, которое к чтению всё-таки относится, — **согласованность
среза**, и она нарушена наблюдаемо: три независимых чтения одним `Promise.all`
(`useSalesCrmDashboard.ts:30-52`), между которыми хранилище может измениться, так что виджет
способен показать заказ, которого KPI ещё не считает. Отметки времени в ответе нет вовсе
(`types/order.ts:48-57`) — назвать момент среза нечем. Обязан ли сервер отдавать сводку и виджеты
на одну отметку — **нигде**: строка владельца 6.

**9. Производные значения (считать, не хранить).** Общее правило — §17 соглашений. У этого домена
**весь ответ целиком производный, своих таблиц у него нет** (модуля в `backend/app/modules/` нет,
миграции нет). Все четыре считаются при каждом чтении, ни одно не хранится:

- `activeOrders` — `STORE.filter((o) => isActive(o.status)).length` (`mocks/orders.ts:1590`);
- `pendingOrders` — `o.status === 'new' || o.status === 'confirmed'` (`mocks/orders.ts:1591`);
- `salesMtd` — `filter(countsAsSale && createdAt >= monthStart).reduce(round2(sum + totalAmount))`
  (`mocks/orders.ts:1585-1587`); нетто по построению, потому что `totalAmount` сам производный —
  его пишет `recalcOrder` (`mocks/orders.ts:179`, сама запись — `:206`);
- `newClientsThisMonth` — счёт по **чужому** домену:
  `mockGetClients().filter(createdAt >= monthStart).length` (`mocks/orders.ts:1593`), причём
  `mockGetClients()` копирует всё хранилище клиентов целиком (`structuredClone(STORE)`,
  `services/mocks/clients.ts:1046-1048`) — вместе с журналом и историей контактов, — чтобы
  получить одно число. На сервере это `count(*)` с фильтром арендатора, а не выборка сущностей.

**Сводка — третье кросс-доменное вычисление в файле заказов** (первые два — сводка счетов клиента
и реестр входящих). Из чего именно признаётся выручка — из заказанного, из отгруженного минус
возвращённое, или из выставленного — в коде сказано трижды и по-разному: БАГ-01, строка
владельца 7.

## Правила домена

Живут только в этом домене; общие — в [`00-conventions.md`](00-conventions.md).

1. **Сводка существует потому, что счёт по странице — не счёт.** Правило записано в коде трижды и
   одними словами: в типе — «a count taken through a window stops moving the moment the window is
   full, without ever saying so» (`types/order.ts:44-47`); у клиента — «a page of the orders list
   cannot produce them» (`services/ordersService.ts:50-51`); у потребителя — «deriving them from a
   page of the list made them stop moving as soon as the store outgrew the page — silently, which
   is the worst way for a number to be wrong» (`useSalesCrmDashboard.ts:23-28`). Дефект был живым:
   «the store holds 100 orders and the dashboard used to read exactly 100»
   ([`services/mocks/orders.spec.ts:2975-2977`](../../../frontend_vue/src/services/mocks/orders.spec.ts)),
   и e2e назван по нему
   ([`tests/e2e/admin/sales-crm/sales-crm.spec.ts:24`](../../../frontend_vue/tests/e2e/admin/sales-crm/sales-crm.spec.ts)).
   **Для сервера отсюда запрет: сводка не собирается из ответа списка, у неё своя выборка по всему
   хранилищу.**
2. **Два из четырёх правил — предикаты, а не списки статусов, и это осознанный отказ от списка.**
   `isActive` сформулирован как «не доставлен и не терминален» (`domain/orderStatus.ts:103-105`) с
   причиной рядом: «a list goes stale on the next status somebody adds, and it went stale exactly
   that way once already» (`:99-101`). `countsAsSale` — как исключение трёх видов (`:121-123`) с
   той же причиной: старый список `confirmed | shipped | delivered` «quietly left out `paid`»
   (`:117-119`). **Сервер обязан хранить правило, а не перечень:** пятнадцать статусов (`:15-31`)
   будут расти. Третье число, `pendingOrders`, этому правилу не следует — БАГ-03.
3. **`salesMtd` привязан к дате создания заказа, а не к дате продажи.** Фильтр —
   `new Date(o.createdAt) >= monthStart` (`mocks/orders.ts:1586`), где `createdAt` ставится при
   создании и не двигается никогда (`:1668`). Заказ, созданный 30-го и оплаченный 2-го, попадает в
   оборот прошлого месяца; заказ, созданный в этом месяце и оплаченный через полгода, — в оборот
   этого. Даты отгрузки, счёта и платежа фильтр не касается ни одной, хотя все три у заказа есть
   (`shippedAt`, `issuedAt`, `paidAt` — `mocks/orders.ts:939`, `:763`, `:839`).
4. **Единственная «сортировка» домена — не его: две панели просят у сервера пять новейших, а не
   выбирают пять из полученного.** `sortBy: 'createdAt'`, `sortDir: 'desc'`, `pageSize: 5` уходят в
   оба запроса (`useSalesCrmDashboard.ts:39-51`). Общее правило — §13 соглашений.
5. **Домен один в проекте, у которого нет ни своего сервиса, ни своего мока, ни своих типов, и при
   этом есть свой префикс `/api/`.** Практическое следствие для сверки: К2 (мок ↔ контракт ↔ код)
   для этого домена проверяет **чужой** файл, а строки `Реализация:` указывают в
   `services/ordersService.ts` и `services/mocks/orders.ts` — и это не ошибка оформления. `auth`
   устроен **иначе**: у него есть и свои типы (`frontend_vue/src/types/auth.ts`), и модуль
   бэкенда — и именно поэтому «один в проекте» сказано без оговорок.
6. **Демо-хранилище само двигает свою историю вперёд, иначе три из четырёх чисел были бы
   постоянным нулём.** `demoClock` анкерит сид к дню открытия демо, и причина названа прямо: «a few
   weeks after they were written, "sales this month" and "new clients this month" are permanently
   zero, and the demo shows a business that stopped trading»
   ([`services/mocks/demoClock.ts:4-9`](../../../frontend_vue/src/services/mocks/demoClock.ts)). У
   клиентов сдвиг **свой**, по их собственной последней дате, потому что общий сдвиг заказов «would
   leave the newest client weeks in the past and "new clients this month" at zero» (`:33-38`).
   Отсюда запрет для тестов, записанный там же: «a seeded date is not the same string tomorrow.
   Nothing may assert one; assert distances and order instead» (`demoClock.ts:16-17`). **Сдвиг
   часов — свойство мока; серверу его делать не нужно** (§18 соглашений).
7. **Дата у клиента и дата у заказа — разной точности, и сводка сравнивает их с одним порогом.**
   Клиент несёт день без времени (`YYYY-MM-DD`: создание `services/mocks/clients.ts:1085`, сдвиг
   `demoClock.ts:55-61`), заказ — полный ISO-инстант (`mocks/orders.ts:513`, `:1668`). `demoClock`
   разбирает день **как местный**, дописывая `'T00:00:00'` (`:56`), а сводка разбирает ту же строку
   голым `new Date(...)` (`mocks/orders.ts:1593`), то есть как UTC. **Для схемы бэкенда это два
   разных типа колонки — `date` против `timestamptz`, и контракт обязан их различать.** БАГ-04.
8. **Ответ не несёт ни валюты, ни периода, ни отметки среза — только четыре числа**, поэтому всё,
   что о них известно, живёт в комментариях типа (`types/order.ts:49-56`). Для сервера это значит:
   смысл каждого числа задаётся контрактом, а не ответом.
9. **Пилюля статуса берётся из единой карты, и этот домен был причиной её появления.**
   `ORDER_STATUS_PILL[order.status]` (`SalesCrmPage.vue:208`) плюс собственный импорт CSS (`:12`),
   и причина записана в самой карте: «a component may not borrow CSS from another page's file, and
   the CRM badge is the proof: it asked for `order-status--*` classes nobody had ever defined»
   (`domain/orderStatus.ts:36-41`). Фолбэк `|| 'order-status-pill--new'` стоит во всех четырёх
   местах чтения карты, то есть **неизвестный статус от сервера везде покрасится как «новый», а
   подпись напечатает сырой ключ** `orders.status_<что пришло>` (`SalesCrmPage.vue:210`). Правило
   кросс-доменное; строка владельца 8.
10. **Дашборд — единственный потребитель, и он один на три домена.** `useSalesCrmDashboard`
    зовётся ровно из одного места (`SalesCrmPage.vue:28`) и читает три домена одним `Promise.all`
    (`useSalesCrmDashboard.ts:30-52`): `sales-crm`, `orders`, `clients`. Отказ любого из трёх
    обнуляет страницу целиком, а сводка, которая сама не бросает ничего, показывает чужой код
    ошибки. БАГ-07.

## Чего в домене нет

Ничего не вычеркнуто молча. **Из прежнего монолита у этого домена удалять было нечего:** раздела
там нет ни одного, и это замерено, а не предположено —
`grep -c "^### .*sales-crm" roo_code/roo-context/03-api-contract.md` → `0`, путь `api/sales-crm` не
встречается в нём ни разу.

| было описано | чем доказано отсутствие |
|---|---|
| единственное упоминание CRM в монолите — «Планируется добавить флаги для модулей CRM / Warehouse / Orders / Logistics / Staff по мере появления их UI» ([`03-api-contract.md:235`](../03-api-contract.md)) | это не описание эндпоинта: `grep -c "CRM" roo_code/roo-context/03-api-contract.md` → `1`, строка лежит в блоке 1–293 (общие соглашения), а флаг `adminSalesCrm` в коде существует и равен `true` (`config/featureFlags.ts:24`) — то есть «планируется» неверно даже как обещание. Правило о флагах снято и заменено §7 соглашений |
| раздел эндпоинта `GET /api/sales-crm/stats` | не существовало: путь `sales-crm/stats` назван среди сорока не описанных монолитом (`plans/api/contract-sync-plan.md:229`). Значит все пробелы этого файла — пробелы **в коде**, а не неверные утверждения монолита |

Кроме этого в домене **нет и никогда не было описано**:

- **параметров запроса** — ни периода, ни арендатора, ни валюты: путь литеральный, вызов без
  `params` и без `headers` (`services/ordersService.ts:54`);
- **второго эндпоинта** — ни разрезов сводки, ни ленты активности, ни воронки: во всём коде
  ровно два файла упоминают префикс домена, и оба показаны выше;
- **любой записи** — домен read-only по составу (`grep -c "apiPost\|apiPut\|apiPatch\|apiDelete"`
  по строкам домена → `0`);
- **обновления без перезагрузки страницы** — ни подписки, ни поллинга, ни кеша:
  `onMounted(load)` и кнопка «Повторить» (`useSalesCrmDashboard.ts:70`, `SalesCrmPage.vue:107`).

**«Клиент написан, UI нет»** — реестр пуст: у единственного эндпоинта домена потребитель есть, и он
один (правило домена 10).

## Пробелы аудита — что закрыто, что осталось

Пять пробелов, найденных аудитом, и все пять — **в коде**, а не в прежнем описании (его не было).

1. **Выручка домена определена иначе, чем выручка в том же файле мока** (БАГ-01). В контракте
   закрыто **описанием наблюдаемого**: правило `salesMtd` записано в таблице раздела эндпоинта и в
   графе 9 «Обязанностей сервера» вместе с расхождением. Выбор между тремя определениями —
   владельцу: **осталось** (строка 7).
2. **Валюты у числа нет ни в типе, ни в ответе** (БАГ-02). Закрыто: форма ответа описана как
   четыре числа без валюты, и это названо прямо в шапке и в графе 1. Чем валюту назвать — владельцу:
   **осталось** (строка 1).
3. **Правило `pendingOrders` записано перечислением статусов**, а не предикатом (БАГ-03). Закрыто
   описанием: таблица раздела эндпоинта показывает контраст с двумя соседними числами, правило
   домена 2 объясняет, почему список ошибочен, графа 5 — что следует из нового статуса. Перечень
   «ожидающих» — владельцу: **осталось** (строка 3).
4. **Часового пояса, в котором режется «этот месяц», нет нигде** (БАГ-04). Закрыто описанием
   наблюдаемого: местная полночь процесса плюс разная точность двух дат (правило домена 7), включая
   следствие для схемы (`date` против `timestamptz`). Пояс — владельцу: **осталось** (строка 3).
5. **Ни одна из четырёх величин не проверена тестом, который сломался бы от неверного правила**
   (БАГ-05, БАГ-06; e2e утверждает два числа из четырёх). Контрактом это не закрывается: пробел не
   в описании, а в проверках кода, и правка кода этому файлу запрещена. Записано находками в
   [`contract-sync-sales-crm-bugs.md`](../../plans/bugs/contract-sync-sales-crm-bugs.md):
   **осталось**.
