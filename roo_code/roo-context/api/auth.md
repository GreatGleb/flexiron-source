# Auth

Вход, регистрация, выход, проверка сессии и разбор секретной ссылки. Пять эндпоинтов, все в
пространстве `/api/auth`.

**Общие соглашения — [`00-conventions.md`](00-conventions.md), и здесь они не повторяются.**
Конверт ответа и разбор ошибки — §1; коды ядра и правило «отказ несёт код, а не текст» — §2;
«сессия живёт не в cookie», заголовки и четыре реализации «где лежит токен» — §5; матрица прав и
заглушка `check_permission` — §6; мультиарендность — §4; непрозрачность `id` — §19; чем мок
отличается от обязанностей сервера — §18. Ниже — только то, что живёт в этом домене.

**Источник истины — бэкенд, а не мок.** `backend/app/modules/auth/` реализует **четыре эндпоинта
из пяти**: login, register, me, link — их роутеры включены в `backend/app/main.py:120,116,117,118`.
У `logout` серверной реализации нет ни в каком виде: каталогов в
`backend/app/modules/auth/features/` четыре (`login`, `magic_link`, `me`, `register`), а
`grep -rn "logout" backend/app` пуст. Формы запросов и ответов ниже сняты со схем бэкенда; где
фронт с ними расходится, стоит номер находки в
[`contract-sync-auth-bugs.md`](../../plans/bugs/contract-sync-auth-bugs.md).

Потребители: [`composables/useAuth.ts`](../../../frontend_vue/src/composables/useAuth.ts) —
login `:119`, register `:146`, fetchMe `:200`, logout `:232`; и
[`views/public/AuthLinkHandler.vue`](../../../frontend_vue/src/views/public/AuthLinkHandler.vue)
`:129` — разбор ссылки. UI есть у всех пяти: реестра «клиент написан, UI нет» у домена нет.

**Регистр полей — `snake_case`**, как их отдаёт бэкенд: `first_name`, `last_name`, `csrf_token`,
`expires_at`, `tenant_id`, `is_active` (`login/schemas.py:15-34`). Домен auth единственный, где
так: он писался под форму ответа FastAPI, и `types/auth.ts:3-19` эту форму повторяет буквально.
Приводить поля к `camelCase` «по привычке» нельзя ни на одной стороне.

**`id` и `tenant_id` объявлены типом `UUID`** (`login/schemas.py:18,25`), на проводе это строка,
во фронте тип `string`. Общее правило непрозрачности идентификатора — §19 соглашений; домену оно
добавляет один частный случай: неразбираемый UUID в payload токена — отказ `INVALID_TOKEN`, а не
500 (см. `decode_session_token` в `backend/app/modules/auth/shared/session_tokens.py`).

**Защищены два эндпоинта из пяти.** `GET /api/auth/me` и `POST /api/auth/logout` уходят с
`authHeaders()` (`useAuth.ts:200-202`, `:232`); `login`, `register` и `link` публичны — вызваны без
третьего аргумента (`useAuth.ts:119`, `:146`, `AuthLinkHandler.vue:129`). Механика заголовков и
хранилищ — §5 соглашений.

## Каталог кодов ошибок домена

| код | статус | эндпоинт | где объявлен |
|---|---|---|---|
| `MISSING_TOKEN` | 401 | me | `backend/app/modules/auth/shared/dependencies.py:26-29` |
| `TOKEN_EXPIRED` | 401 | me | `backend/app/modules/auth/shared/session_tokens.py:19-22` |
| `INVALID_TOKEN` | 401 | me | `backend/app/modules/auth/shared/session_tokens.py:23-38` |
| `UNAUTHORIZED` | 401 | me, login, link | пользователь отсутствует, неактивен или без компании; неверная пара или ссылка |
| `VALIDATION_ERROR` | 422 | `POST /api/auth/register` | `register/domain.py:37-43`, код из `core/exceptions.py:23-27` |
| `CONFLICT` | 409 | `POST /api/auth/register` | `register/domain.py:87`, код из `core/exceptions.py:44-48` |

Три первых кода принадлежат общей аутентификации С0 и используются также settings и uploads.
Проверка прав и её FORBIDDEN не входят в С0.

`POST /api/auth/logout` не бросает ничего: серверной реализации нет, а клиент глотает любую ошибку
пустым `catch` (`useAuth.ts:210-214`).

**Мок кодов не знает.** Единственный код, который он бросает, — `MISSING_TOKEN` на пустой токен
ссылки (`mocks/index.ts:292`), и этот код выдуман: настоящий сервер на отсутствующий `token`
отвечает штатной 422 Pydantic, потому что параметр объявлен `Query(...)`
(`magic_link/action.py:23`).

Прочие отказы мока — голый `Error(<текст>)` без `status`
(`mocks/index.ts:298`, `:878`), из-за чего ветка `err.status === 401` (`useAuth.ts:207`) под моками
недостижима: **ни один путь отказа домена в демо не воспроизводится** (БАГ-14).

### POST /api/auth/login

Вход по email и паролю. Quick-action: уходит на сервер по submit формы `LoginPage.vue:155`.

Запрос (по схеме бэкенда `LoginInput`, `backend/app/modules/auth/features/login/schemas.py:8-12`):

```ts
{ email: string; password: string }
```

Ровно два поля, ни одного необязательного. Формат email не проверяет никто: у сервера это `str`, а
не `EmailStr` (`login/schemas.py:11`), клиент проверяет только непустоту (`LoginPage.vue:158-166`).

**`rememberMe` — параметр клиента, а не контракта.** Фронтовый `LoginInput` объявляет третье поле
(`types/auth.ts:21-26`), форма всегда его шлёт (`LoginPage.vue:169-173`, значение по умолчанию
`true` — `:125`), и `useAuth.login` передаёт тело целиком (`useAuth.ts:119`). Серверная схема такого
поля не объявляет, а `extra` у неё не разрешён (`login/schemas.py:8-12`; расширяемые переводы описаны в `core/schemas.py:5-13`) — pydantic
его отбрасывает. Клиенту флаг решает одно: `localStorage` или `sessionStorage`
(`useAuth.ts:81-90`). Серверного продления он не даёт: `remember_ttl_days = 30`
(`core/config.py:18`) не читается ни одной строкой, а колонка `sessions.remember` пишется дефолтом
`False` (`login/repository.py:32`) — вход её не передаёт вовсе (`login/domain.py:74-80`).

Ответ:

```ts
interface LoginResponse {
  user: UserInfo
  session: { token: string; csrf_token: string; expires_at: string }
}

interface UserInfo {
  id: string
  email: string
  first_name: string
  last_name: string
  phone: string | null
  locale: string
  role: string
  tenant_id: string | null
  is_active: boolean
}
```

`login/schemas.py:15-43`; `types/auth.ts:3-19,39-42` повторяют форму поле в поле, расхождений нет.
Конверт — `ApiResponse` с `message = "Login successful"` (`login/action.py:35-38`).

После успеха клиент кладёт токен и CSRF в выбранное хранилище (`useAuth.ts:120`), кэширует
пользователя в `localStorage['auth_user_cache']` (`:121`), сбрасывает кэш настроек
(`useSettings().resetState()` — `useAuth.ts:124-125`, `useSettings.ts:651`) и уходит на
`/admin/analytics/dashboard` (`:126`).

**`expires_at` не читает никто, и это относится к обеим сторонам.** Во фронте поле встречается
дважды: объявление типа (`types/auth.ts:18`) и присвоение в моке (`mocks/index.ts:898`) — ни одного
чтения (`grep -rn "expires_at" frontend_vue/src --include=*.ts --include=*.vue | grep -v spec` даёт
кроме них только ключи перевода `field_expires_at` чужого домена `warehouse`). На сервере колонка
пишется (`login/repository.py:26-45`) и не читается никогда. Истечение обнаруживается общей проверкой возраста подписи на всех четырёх потребителях С0.
Отсюда следствие для бэкенда: **`expires_at` в ответе сегодня — не то, чем сервер руководствуется**
(БАГ-08, БАГ-09).

Ошибки: неверная пара — `401 UNAUTHORIZED` с сообщением `Invalid email or password`
(`login/domain.py:57,61`). Текст один и тот же и для неизвестного адреса, и для неверного пароля:
разные тексты выдавали бы существование адреса. Кода клиент здесь не разбирает — `authError` это
`message` из ответа (`useAuth.ts:127-130`, показ `LoginPage.vue:174-175`).

Бэкенд: `auth/features/login/action.py:22` · схемы `login/schemas.py:8-43`
Реализация: `composables/useAuth.ts:119` · мок `mocks/index.ts:875` (принимает любую непустую пару,
**пароль не проверяет вовсе** — `:880`; пустое поле — текст `Email and password are required`
(`:878`); мок-пользователь на русском — БАГ-02, роль `'admin'` против серверного `owner` — БАГ-12)

### POST /api/auth/register

Регистрация пользователя и компании с автологином. Quick-action, submit формы
`RegisterPage.vue:302`.

Запрос (по схеме бэкенда `RegisterInput`,
`backend/app/modules/auth/features/register/schemas.py:8-18`):

```ts
{
  email: string
  password: string
  company_name: string
  vat_code: string
  first_name: string        // обязателен на сервере
  last_name: string         // обязателен на сервере
  locale?: string           // по умолчанию 'ru'
  phone?: string | null
}
```

Два расхождения с фронтом, оба записаны находками:

- тип `RegisterInput` в `types/auth.ts:28-37` объявляет необязательными **два поля, у которых на
  сервере дефолта нет**: `first_name?` и `last_name?` (`register/schemas.py:16-17`) — БАГ-04.
  (`locale?` и `phone?` необязательны законно: у серверных дефолт есть — `register/schemas.py:15`,
  `:18`.) Форма оба всегда отправляет (`RegisterPage.vue:340-349`), так что сейчас это ловушка для
  следующего вызывающего, а не живой отказ;
- `locale` форма шлёт литералом `'ru'` (`RegisterPage.vue:348`), хотя сервер сохраняет это значение
  пользователю в базу (`register/repository.py:87`). Локаль интерфейса на момент регистрации
  теряется (БАГ-03).

Формат `vat_code` проверяет только сервер — `^[A-Z]{2}[A-Z0-9]{2,12}$` после `strip().upper()`
(`register/domain.py:37-43`); клиентская валидация здесь **слабее** серверной, она проверяет шесть
полей на непустоту и не смотрит на формат (`RegisterPage.vue:312-335`, выход без запроса `:337`).

Ответ — `UserInfo` россыпью (не вложенным объектом) плюс сессия и ссылка; HTTP-статус `201 Created`
(`register/action.py:22`):

```ts
interface RegisterResponse {
  id: string
  email: string
  first_name: string
  last_name: string
  phone: string | null
  locale: string
  role: string
  tenant_id: string | null
  is_active: boolean
  session: { token: string; csrf_token: string; expires_at: string }
  /** Показывается пользователю во всплывающем окне сразу после регистрации. */
  secret_link: string
}
```

`register/schemas.py:29-42`, сборка `register/domain.py:153-169`; `types/auth.ts:44-56` повторяет
форму точно. Клиент разбирает её вручную: ставит сессию с `rememberMe = true` **жёстко**
(`useAuth.ts:129-140` — галочки «запомнить» у регистрации нет), пересобирает `UserInfo` из плоских полей
(`useAuth.ts:130-140`), кэширует (`:141`), сбрасывает кэш настроек (`:144-145`) и возвращает `secret_link`
строкой (`useAuth.ts:146`). Редиректа после регистрации нет: страница показывает ссылку в попапе
(`RegisterPage.vue:351`, разметка `:203-218`) и остаётся на месте, хотя сессия уже установлена.

**Регистрация всегда создаёт нового арендатора и делает автора владельцем.** `create_tenant`
вызывается в одном месте на весь бэкенд (`register/domain.py:97-103`), slug выводится из названия
компании с числовым суффиксом при коллизии (`:90-95`), сразу после этого через чужой internal API
создаётся синглтон карточки компании (`:106-112` → `app.modules.settings.internal_api.interface`).
`User(...)` конструируется тоже ровно в одном месте (`register/repository.py:80`), и та же функция
назначает роль (`:90`, `:97`). **Способа завести второго пользователя внутри существующего
арендатора на сервере нет ни одного**, хотя список пользователей во фронте есть
(`mocks/settings.ts:190-207` — шесть ролей). Для бэкенда это задача, а не описание существующего;
строка владельцу.

**Ошибки должны приходить с кодом, иначе форма не подсветит поле.** Разбор конверта — §1
соглашений; домену принадлежит соответствие «текст сообщения → поле формы», которое делает
`inferFieldFromMessage` (`services/api.ts:86-106`) при `code: 'VALIDATION_ERROR'`:
`vat`/`company code` → `vat_code`, `email` → `email`, `password`/`pwd` → `password`, `phone` →
`phone`, `first_name`/`first name` (а также `name` без слов `company` и `last`) → `first_name`,
`last_name`/`last name` → `last_name`, `company` → `company_name`; при `code: 'CONFLICT'` со словом
`email` → `email`. Порядок проверок значим: `vat` разбирается раньше `email`. Форма читает
`err.fieldErrors` (`RegisterPage.vue:353-361`) и показывает общий текст только если ни одно поле не
подсветилось (`:363-366`).

> **Текст сообщения сейчас — часть контракта, и это плохо.** Поле выводится из подстроки в
> сообщении, а не из данных ответа. Две живые пары проверены и сходятся:
> `ValidationError("Invalid VAT code format. …")` (`register/domain.py:39-42`) → `vat_code`;
> `ConflictError("A user with this email already exists")` (`register/domain.py:87`) → `email`.
> Переформулировка любого из этих сообщений молча ломает подсветку поля. Явное имя поля в ответе
> (`detail: { code, field, message }`) — БАГ-06 и строка владельцу; до решения **эти сообщения
> менять нельзя**.

Третий путь отказа — штатная 422 Pydantic за пропущенное обязательное поле; её клиент разбирает
отдельной веткой по `loc` (§1 соглашений).

Бэкенд: `auth/features/register/action.py:22` (отдаёт `201 Created`) · схемы
`register/schemas.py:8-42`
Реализация: `composables/useAuth.ts:146` · **мока нет** — БАГ-01: ветки `/api/auth/register` в
`mocks/index.ts` не существует (`grep -n "auth/register" src/services/mocks/index.ts` пуст), запрос
доходит до `ApiRequestError` с кодом `NOT_FOUND` и текстом «[mock] POST … not found»
(`mocks/index.ts:1306-1310`). Под моками регистрация падает целиком, против настоящего сервера работает

### POST /api/auth/logout

Локальное забывание сессии. Тело — `{}`, ответ не читается ничем: результат `apiPost` не
присваивается, вызов обёрнут в пустой `try/catch` (`useAuth.ts:210-217`). Заголовки добавляет общий клиент api.ts.
Quick-action, единственный вызывающий — пункт меню шапки (`AdminTopbar.vue:58-61`).

Клиент чистит хранилища **в любом случае** — даже если запрос упал: `clearSession()` и переход на
`redirectTo` (по умолчанию `/`) идут после `catch` (`useAuth.ts:216-217`).

**Серверного logout пока нет.** Таблица sessions пишется при входе и регистрации,
но не читается при аутентификации. С0 проверяет подпись, переходный возраст и текущую запись
пользователя (существование, активность, компания). Серверный отзыв остаётся работой С1/С2.

Отсюда две поправки к прежним формулировкам, обе сняты как недоказуемые:

- **«идемпотентен»** — не наблюдение, а требование к несуществующему коду: у мока отказа нет
  (`mocks/index.ts:1004-1007`), у сервера бросать нечему;
- **«токен остаётся действительным до истечения `expires_at`»** — неверно: `expires_at` сервер не
  читает нигде, срок решает `max_age=86400` подписи (`backend/app/modules/auth/shared/session_tokens.py:19`).

В мок-режиме (`VITE_USE_MOCKS !== 'false'`) запрос не отправляется вовсе и сессия не чистится:
ранний выход с одним `router.push` (`useAuth.ts:201-208`). Админка остаётся доступной без входа —
это осознанное поведение демо (`useAuth.ts:218-221`, комментарий там же), а не недоделка; ветка
мока, которая чистит пользователя (`mocks/index.ts:906`), при этом мертва — до неё не доходят.

Бэкенд: **не реализован** — в `backend/app/modules/auth/features/` есть login, register, me,
magic_link и нет logout; `grep -rn "logout" backend/app` пуст. Метка `Статус: спроектировано` тут
была бы неверна: она про отсутствие кода вообще, а клиент и мок эндпоинт имеют — отсутствует
только серверная половина.
Реализация: `composables/useAuth.ts:232` · мок `mocks/index.ts:905`

### GET /api/auth/me

Проверка живой сессии на старте приложения. Требует `authHeaders()`. Запроса нет вовсе, если токена
нет в хранилищах (`useAuth.ts:189-193`).

Ответ по схеме бэкенда `MeResponse` (`backend/app/modules/auth/features/me/schemas.py:7-19`) — это
`UserInfo` **плюс одно поле**:

```ts
{ ...UserInfo, secret_link?: string | null }
```

`secret_link` фронт не знает: `fetchMe` типизирует ответ как `UserInfo` (`types/auth.ts:3-13`,
вызов `useAuth.ts:200-202`), и поле молча отбрасывается. Описано как есть, потому что сервер его
отдаёт и **собирает на каждый запрос профиля** (`me/domain.py:11-13`); что с ним делать — решение
владельца (БАГ-05).

**Отказы С0:** общий get_current_user возвращает 401 MISSING_TOKEN без заголовка;
401 INVALID_TOKEN при неверной схеме, пустом токене, неверной подписи, payload или UUID;
401 TOKEN_EXPIRED при возрасте подписи больше 86400 секунд;
401 UNAUTHORIZED для отсутствующего, неактивного пользователя или пользователя без компании.
Ошибка БД не маскируется под INVALID_TOKEN.

/me использует уже загруженную запись: build_current_user собирает прежний MeResponse
без второго SQL-запроса. Поле secret_link пока сохраняется для совместимости С0.

Клиент различает два случая, и сервер обязан их различать тоже:

- `401` или `404` → токен недействителен: чистится сессия и кэш пользователя
  (`useAuth.ts:207-209`);
- любая другая ошибка (сеть, `5xx`) → сессия сохраняется, показывается закэшированный пользователь
  (`:210`, до ответа сервера кэш подставляется в `currentUser` — `:196`). Отдавать `500` вместо
  `401` на истёкшем токене значит оставить человека залогиненным.

Единственный триггер — `onMounted(() => { fetchMe() })` в корне (`App.vue:20-22`), без ожидания завершения запроса.
Ручного обновления профиля нет: у `fetchMe` второго вызывающего в `src/` не существует
(`grep -rn "fetchMe" src` — объявление `useAuth.ts:188`, экспорт `useAuth.ts:231`, вызов `App.vue:18,21`).
Потребитель ответа ровно один — шапка админки: имя склеивается из `first_name`+`last_name` с тремя
запасными ветками (`AdminTopbar.vue:17-23`), роль показывается ключом settingsUsers.role_<role>
(`:25-28`, словарь `i18n/admin/settings.ts:231-237`).

**Переходный срок С0:** decode_session_token проверяет max_age=86400 для /me,
settings CRUD, profile и uploads. Оба издателя используют issue_session_token;
формат остаётся `{user_id: string}`, secret_key и salt=session прежние.
Это перенос существующего ограничения /me, не реализация П77, remember или отзыва.
Сроки expires_at при входе и регистрации пока прежние и при чтении токена не используются.
Целевые 30 минут/30 суток бездействия реализуются в С1.

Бэкенд: `auth/features/me/action.py:12-15` · схемы `me/schemas.py:7-19`
Реализация: `composables/useAuth.ts:200` · мок `mocks/index.ts:392-403` (отдаёт объект, положенный
входом, — без `secret_link`; отказ есть и с кодом: `ApiRequestError({ status: 401, code:
'UNAUTHORIZED', ... })`, текст «Not authenticated» (`:397-401`))

### GET /api/auth/link

Проверка секретной ссылки. Токен идёт в query: `?token=<...>`, параметр обязателен
(`token: str = Query(...)` — `magic_link/action.py:23`). Тела нет; заголовков нет — эндпоинт
публичный.

**Ссылка приходит не письмом.** Отправки почты в домене нет ни строки
(`grep -rn "mail\|Mail" backend/app/modules/auth backend/app/core` даёт только слово `email` в
именах полей), единственный SMTP в проекте лежит в чужом домене
(`app/modules/bcc/features/send_request/transport.py:11`). До человека ссылка доходит ровно двумя
путями: полем `secret_link` ответа регистрации (`register/domain.py:150`, показ
`RegisterPage.vue:203-218`) и тем же полем в `GET /api/auth/me` (`me/domain.py:11-13`), которое
фронт отбрасывает (БАГ-05).

**Ссылка не даёт входа — она подставляет email.** Сессии `verify_secret_link` не создаёт
(`magic_link/domain.py:31-42`, докстринг `:29-30` говорит это прямо). Фронт кладёт адрес в
`sessionStorage['prefilled_email']` (`AuthLinkHandler.vue:141`) и уводит на `/login` (`:145`), где
адрес подставляется **один раз** и ключ стирается (`LoginPage.vue:132-143`). Пароль всё равно
нужен.

Ответ: `MagicLinkVerifyResponse { email: string }` — `magic_link/schemas.py:12-19`, сборка
`magic_link/domain.py:40-42`.

Конверт `ApiResponse` с `message = "Link verified successfully"`
(`magic_link/action.py:37-40`).

Клиент типизирует ответ как `unknown` и достаёт адрес функцией
`extractEmail`, которая принимает **две** формы — `{ email }` и `{ user: { email } }`
(`AuthLinkHandler.vue:97-112`); вторая ветка недостижима, сервер такой формы не отдаёт.

Схема `MagicLinkInput { token }` (`magic_link/schemas.py:6-9`) объявлена и роутом не используется:
токен принимается как `Query`, а не телом.

Ошибки бэкенда — обе `401 UNAUTHORIZED` (`magic_link/action.py:44`):

- `Invalid or expired secret link` — токен неизвестен или просрочен (`magic_link/domain.py:34`);
- `Account is deactivated` — ссылка верна, но пользователь отключён (`:37`).

Ни то, ни другое клиент не разбирает: любая ошибка гасится одним текстом
`t('authLink.invalidLink')`, код и статус не читаются (`AuthLinkHandler.vue:146-149`).

**Сообщение обещает срок, которого не существует.** `secret_link_token` лежит в колонке без даты
(`auth/shared/models.py:57-59`), выдаётся при регистрации (`register/domain.py:115`) и не
ротируется нигде — то есть слово «expired» в тексте отказа сегодня недостижимо. Единственная
запись поля после регистрации — **добор в чужом домене**: `_ensure_secret_link` в
`settings/features/profile/domain.py:22-41` генерирует токен, если его нет (`:32`), и собирает тот
же URL третьей копией (`:38-41`); зовут её `GET /api/settings/profile` и `PATCH
/api/settings/profile` (`:54`, `:100`). Судьба поля — строка владельцу; третья копия сборки URL —
БАГ-16.

Мок ведёт себя иначе и **слабее**: пустой токен — `MISSING_TOKEN` (кода, которого у сервера нет),
любой непустой принимается и всегда отвечает одним адресом `director@metalltorg.com`
(`mocks/index.ts:303-307`). Путь «просроченная или неизвестная ссылка» под моками не
воспроизводится вовсе.

Save-режим: не форма. Quick-action по монтированию страницы — `onMounted` шлёт запрос сразу
(`AuthLinkHandler.vue:114-129`).

Бэкенд: `auth/features/magic_link/action.py:21` · схемы `magic_link/schemas.py:6-19`
Реализация: `views/public/AuthLinkHandler.vue:129` · мок `mocks/index.ts:303`

## Обязанности сервера

Девять граф аудита ([`plans/api/audit/auth.md`](../../plans/api/audit/auth.md), раздел
«Обязанности сервера») — то, чего во фронтенде не видно и что линзы согласованности не ловят по
построению. Ответ «нигде» не назначается контрактом: он идёт строкой в
[`audit/00-решения-владельца.md`](../../plans/api/audit/00-решения-владельца.md), раздел
«auth — аудит 2026-09-04».

**1. Значения по умолчанию и их владелец — владеет код бэкенда, не настройки арендатора.** Из шести
значений ниже три не сходятся сами с собой: срок сессии задан тремя разными числами, роль записана в
двух регистрах, а продление по «запомнить меня» объявлено и не читается никем.

| значение | где задано | состояние |
|---|---|---|
| срок сессии | `login/domain.py:71` (24 ч литералом), `register/domain.py:140` (`session_ttl_hours`), `core/config.py:17` (**8**), `backend/app/modules/auth/shared/session_tokens.py:19` (`max_age=86400`) | три числа на одно правило — БАГ-09, строка владельцу |
| продление по «запомнить меня» | `core/config.py:18` (`remember_ttl_days = 30`), `login/repository.py:32` (колонка дефолтом `False`) | не читается никем |
| роль первого пользователя | `register/repository.py:90` (`role="owner"`), `:97` (`role_name="Owner"`) | разный регистр в одной функции — БАГ-12, строка владельцу |

Валюта, НДС и маржа домену auth не принадлежат: ими владеют настройки (`useSettings.ts:27`).

**2. События и уведомления — ни одного, ни на одной стороне.** В моке уведомлений семь эмиттеров
(`grep -c "^export function notify" src/services/mocks/notifications.ts` → 7), и ни один не
касается пользователя, входа или сессии (`grep -ric "login\|session"` по тому же файлу → 1, и это
комментарий). На бэкенде отправки почты в auth нет (см. `GET /api/auth/link`). Практическое
следствие: `secret_link` — единственный способ восстановить доступ — не отправляется никому. Вход
с нового устройства, смена пароля, деактивация не рождают ничего. Строка владельцу: чем ссылка
попадает к человеку, закрывшему попап.

**3. Запись в аудит-лог — нигде.** У auth нет ни одной записи: `grep -c "auditLog"
src/services/mocks/index.ts` → 0, ветки домена (`:296`, `:303`, `:875`, `:905`) журнал не трогают.
На бэкенде таблицы журнала нет вовсе (`grep -rln "audit_log" backend/app` → 0 файлов); история
существует только у заказа и отдельным доменом `audit-feed` (§9 соглашений), и оба про сущности, а
не про сессии. Кто, когда и откуда входил, чем попытка закончилась — не хранится нигде. Строка
владельцу.

**4. Кастомные поля — домену не принадлежат и в нём отсутствуют.** Ни в одной из пяти форм ответа
нет ни fieldValues, ни ссылки на определения (`login/schemas.py:15-43`,
`register/schemas.py:29-42`, `me/schemas.py:7-19`, `magic_link/schemas.py:12-19`); у пользователя
на схеме фиксированный набор колонок (`auth/shared/models.py:39-81`). Общий механизм — §8
соглашений.

**5. Настройки, которых мок не отслеживает** — перечислены прямо, потому что каждая делает демо
непохожим на сервер: мок не проверяет **пароль** (`mocks/index.ts:880`), не проверяет **токен
ссылки** (`:305-307`), не знает **срока сессии** (кладёт `+86400000` мс безотносительно ответа,
`:898`), не умеет **регистрацию** вовсе (ветки нет — БАГ-01), не отдаёт `secret_link` в `/me`
(`:296-299`), не знает ни одного из трёх кодов `/me` и бросает голый `Error` вместо
`ApiRequestError` (`:298`, `:878`) — БАГ-14.

**6. Мультиарендность — арендатор рождается только регистрацией, а фильтра по арендатору в самом
auth нет.** `create_tenant` вызывается в одном месте (`register/domain.py:97-103`, репозиторий
`register/repository.py:46-61`).

`get_user_by_email` ищет по всей таблице без `tenant_id`
(`login/repository.py:20-23`, `register/repository.py:40-42`), `get_user_by_secret_link` — тоже
(`magic_link/repository.py:14-16`). При этом уникальность в БД **составная**:
`ix_users_tenant_id_email` на паре `(tenant_id, email)`
(`alembic/versions/3a0b5d31bde7_phase_1_tenants_auth_users_sessions.py:54`), а колонка `email`
объявлена без ограничения глобальной уникальности (`auth/shared/models.py:50-52`) — БАГ-13, строка владельцу. Остальные модули
берут арендатора из пользователя токена (`backend/app/modules/auth/shared/dependencies.py:36-42`) — общее
правило в §4 соглашений; у auth к нему две домашние поправки: `users.tenant_id` **nullable** с
комментарием «NULL = superadmin» (`auth/shared/models.py:40,44-49`), и он объявлен
`ondelete="RESTRICT"`, а не `CASCADE`, как сказано про остальные модули в §4 (`:44-49`). Ни одного
места, где роль superadmin что-то даёт, в коде нет.

**7. Права — в auth не проверяются нигде.** Единственная функция, которая должна была это делать, —
заглушка `return True` с комментарием «Placeholder — implement actual RBAC logic here»
(`auth/internal_api/interface.py:27-38`), вызывающих у неё нет.
В С0 auth/shared/dependencies.py реализует проверку личности и компании, но не матрицы прав. Модели `PermissionItem`,
`RolePermission`, `UserPermission` существуют (`auth/shared/models.py:145-236`) и не читаются ни
одним `select()` (`grep -rn` по трём именам в `backend/app` даёт только определения и строку
докстринга `auth/__init__.py:3`).

Мультиролевая `user_roles` пишется при регистрации
(`register/repository.py:96-99`) и не читается ни разу; наружу отдаётся legacy-колонка `role`,
помеченная `⚠️ DEPRECATED` (`auth/shared/models.py:60-63`), — её отдают и `GET /api/auth/me`
(`me/domain.py:23`), и `GET /api/settings/profile` (`settings/features/profile/domain.py:61`). Во
фронте роль из auth используется ровно в одном месте и только как подпись
(`AdminTopbar.vue:25-28`), а права заказов читают роль **из другого источника** — профиля настроек
(`mocks/orders.ts:1849-1856`, применение `:1855-1860`). То есть «кто я» существует двумя
экземплярами, связанными только тем, что обе стороны читают ту же колонку. Общая картина прав —
§6 соглашений; какая из двух систем ролей главная — строка владельцу.

**8. Транзакционность и идемпотентность.** Одна транзакция на запрос обеспечивается зависимостью
`get_db`: `commit()` после выхода из обработчика, `rollback()` на любом исключении
(`core/database.py:22-30`). Для регистрации это существенно: она делает пять записей — арендатор,
карточка компании через чужой модуль, пользователь, роль, сессия (`register/domain.py:97-147`), и
все они откатываются вместе. **Идемпотентности нет ни у одного эндпоинта домена:**
`Idempotency-Key` в auth не читается и не шлётся (`grep -rn "Idempotency" backend/app` пуст; общее
правило — §11 соглашений), повторный вход создаёт **вторую строку** в `sessions`
(`login/repository.py:35-44` — безусловный `db.add`), и удаления сессий нет нигде.
**`X-CSRF-Token` генерируется, отдаётся и хранится, но не проверяется ни разу**: все тринадцать
попаданий `csrf` в `backend/app` — генерация (`login/domain.py:37-39,68`, `register/domain.py:57-59,139`),
колонка (`auth/shared/models.py:124`) и поля схем (`login/schemas.py:33`,
`register/schemas.py:25`); чтения заголовка нет ни одного, при том что клиент шлёт его на каждом
защищённом запросе (`useAuth.ts:101-108`) — БАГ-10. Отзыв сессии и CSRF — строка владельцу.

**9. Производные значения — сервер считает, а не хранит.** `secret_link` собирается при чтении и не
хранится: в БД лежит только `secret_link_token` (`auth/shared/models.py:57-59`), а полный URL
склеивается из `settings.frontend_url` в **трёх** местах — `register/domain.py:150`,
`me/domain.py:13` и `settings/features/profile/domain.py:38-41` (БАГ-16); `frontend_url` — константа
конфига (`core/config.py:27`), то есть в проде ссылка зависит от переменной окружения, а не от
`Origin` запроса. `token_hash` — производная от токена (SHA-256 — `login/domain.py:32-34`, вызов `:65`), хранится
вместо самого токена. Отображаемое имя сервер **не считает**: поля `name` в ответах нет, шапка
склеивает его на клиенте (`AdminTopbar.vue:17-23`).

`isAuthenticated` — производная фронта от
наличия `currentUser` (`useAuth.ts:66-67`), а сторож роутера считает её иначе — по наличию ключа в
хранилище (`router/index.ts:31-31`, применение `:429`); два разных ответа на один вопрос.
`expires_at` сервер считает и отдаёт, но не читает ни он, ни фронт (см. `POST /api/auth/login`).

## Правила домена

То, что живёт только в этом домене и не выводится из формы ни одного эндпоинта.

1. **Состояние sessions ещё не проверяется.** С0 проверяет подпись и пользователя,
   но не читает token_hash/expires_at/csrf_token. Отзыв и скользящий срок — следующие слайсы.
2. **Возраст подписи проверяется всеми четырьмя потребителями** через единый helper.
3. **Один сериализатор и одна dependency.** session_tokens выпускает и разбирает Bearer,
   dependencies возвращает CurrentUser с tenant_id из пользователя; клиент его не выбирает.
4. **Регистрация — единственный способ появления пользователя** (см. `POST /api/auth/register`).
5. **Пароль меняет чужой домен.** `POST /api/settings/change-password`
   (`settings/features/profile/action.py:83-106`) вызывает изменение пароля через auth internal API.
   Хеширование настроено дважды своим `CryptContext`
   (`login/domain.py:30`, `register/domain.py:34`). Контракт auth про смену пароля не говорит
   ничего, а инвалидировать сессии после неё нечем (пункт 1).
6. **`secret_link` не истекает, приходит вместе с профилем и добирается чужим доменом** (см.
   `GET /api/auth/link`).
7. **Ссылка не даёт входа, она подставляет email** (там же).
8. **Мок-режим отключает авторизацию целиком, а не подменяет её.** Сторож роутера выходит первой
   строкой (`router/index.ts:422-425`), logout не шлёт запроса и не чистит сессию
   (`useAuth.ts:201-208`), ошибки моков — голый `Error` без `status` (`mocks/index.ts:298`).
   Демо не воспроизводит ни одного пути отказа домена (БАГ-14).
9. **Мёртвый код в регистрации.** `_ensure_unique_slug` (`register/domain.py:46-54`) объявлена,
   возвращает аргумент без изменений и не вызывается ни разу; настоящий подбор slug написан
   отдельно на месте (`:90-95`) — БАГ-15.

## Чего в домене нет

Ничего не вычеркнуто молча: строка на каждое описание, снятое из прежнего текста контракта, с
доказательством отсутствия.

| было описано | чем доказано отсутствие |
|---|---|
| `POST /api/auth/refresh` — полный раздел с механикой продления сессии («background-интервал за 5 минут до `expiresAt`») | вызова нет ни одного (`grep -rn "auth/refresh" frontend_vue/src` пуст), ветки мока нет, роута на бэкенде нет. Продление не реализовано ничем: истёк токен — `GET /api/auth/me` вернёт 401 и клиент разлогинит. Нужен refresh — это новая работа, а не восстановление описанного |
| «`POST /api/auth/logout` инвалидирует сессию» | таблица `sessions` пишется и не читается ни разу (`grep -rn "token_hash" backend/app` — семь попаданий, все записи), роута нет вовсе — инвалидировать нечего (БАГ-08) |
| «`logout` идемпотентен: повторный вызов на мёртвой сессии — не ошибка» | требование к несуществующему коду, а не наблюдение: у сервера роута нет, мок не бросает (`mocks/index.ts:1013`) |
| «токен остаётся действительным до истечения `expires_at`» | `expires_at` не читает ни сервер, ни фронт; срок решает `max_age=86400` подписи (`backend/app/modules/auth/shared/session_tokens.py:19`) |
| «проверка magic-link **из письма**» | отправки почты в домене нет (`grep -rn "mail\|Mail" backend/app/modules/auth backend/app/core` — только имена полей), единственный SMTP — чужой домен `bcc` (`backend/app/modules/bcc/features/send_request/transport.py:11`) |
| «срок жизни токена записан в двух местах (24 ч и 86400)» | мест три, и третье — настройка `session_ttl_hours = 8`, которой пользуется только регистрация (`core/config.py:17`, `register/domain.py:140`) — БАГ-09 |
| «TTL сессии сервер назначает сам через `session.expires_at`» | не назначает: срок входа — литерал 24 ч (`login/domain.py:71`), а `expires_at` не читается нигде |
| общие правила: конверт ответа, коды ядра, «сессия не в cookie», мультиарендность, форма `id` | перенесены в [`00-conventions.md`](00-conventions.md) (§1, §2, §5, §4, §19) — правило двух и более доменов в доменном файле не дублируется |
| `INVALID_CREDENTIALS` (код 401 у входа) | `grep -rn "INVALID_CREDENTIALS" backend/app frontend_vue/src` пуст; вход отдаёт `UNAUTHORIZED` |

## С1 · Состояние сеанса, компания входа и регистрация

**Статус:** спроектировано — технический вход С1 поверх принятого С0, не отчёт о реализации.
Для реализации С1 правила ниже имеют приоритет над текущим поведением контракта. Изменение форм, миграций и клиентских действий выполняется отдельной задачей по этим решениям.

### 1. Постоянная ссылка компании (П76)

**Company login context** — сервер разрешает постоянный идентификатор компании из ссылки **до** поиска email/пароль.

- **Параметр URL**: `company_slug` (или `tenant_slug`) в пути `/login/{company_slug}` или query `?company={slug}`
- **Поведение**: сервер резолвит компанию по slug, затем ищет пользователя по паре `(tenant_id, email)`
- **Уникальность email**: составной индекс `ix_users_tenant_id_email` — одинаковый email допускается в разных компаниях
- **Нет глобального переключателя**: чужой пароль не работает, переключателя компаний после входа нет
- **Приглашение отдельно**: постоянная ссылка компании не истекает через 7 суток, не заменяет одноразовый секрет приглашения (С5)

### 2. Политика сеансов (П29, П77)

**Единая политика**: обычный сеанс — 30 минут бездействия, remember — 30 суток от `last_seen_at`.

- **Session state**: таблица `sessions` с полями `token_hash`, `user_id`, `last_seen_at`, `expires_at`, `remember`, `revoked_at`
- **Уникальные сеансы**: каждый вход создаёт уникальный `session_id` в подписанном payload; коллизии `token_hash` исключены
- **Проверка срока**: сервер читает `expires_at` из БД, а не только `max_age` подписи
- **Атомарное продление**: активный запрос обновляет `last_seen_at`/`expires_at` серверным временем в одной транзакции
- **Отказ на границе**: при `now >= expires_at` — отказ, истёкшая/отозванная запись не оживает от запроса
- **RememberMe**: схема принимает `rememberMe` и явно отображает в `sessions.remember`; отсутствие флага = `false`
- **Миграция старых токенов**: техническая миграция отзывает старые токены без нового идентификатора, требует повторный вход

### 3. Вход и регистрация (П76, П79)

**LoginInput** расширяется: `{ email: string; password: string; rememberMe?: boolean }`

- **Company context**: поиск пользователя сужается `tenant_id` из резолва постоянной ссылки
- **Отключённый пользователь**: на входе получает тот же отказ, что неверный пароль (401 UNAUTHORIZED, безопасный текст)
- **RegisterInput** добавляет `country?: string` (П80) — передаётся в settings для инициализации часового пояса
- **Глобальный запрет email убран**: регистрация проверяет уникальность только внутри своей компании
- **Автологин после регистрации**: обычный сеанс (не remember), `rememberMe` по умолчанию `false` на сервере

### 4. Текущий пользователь и зависимости

**CurrentUser dependency** — проверенная личность и компания (уже в С0, расширяется в С1).

- **Контекст**: `CurrentUser(user_id: UUID, tenant_id: UUID, user: User, session_id: UUID)`
- **Session ID**: добавляется в payload токена и контекст для отзыва конкретного сеанса
- **Четыре потребителя**: /me, settings CRUD, profile, uploads — используют `get_current_user`
- **Сторож**: AUTH_DEPENDENCIES знает `get_current_user`; старые обходы не разрешены

### 5. Страна и часовой пояс (П80)

**Передача в settings** через internal API при регистрации и входе.

- **Country**: `country` в RegisterInput (ISO 3166-1 alpha-2), опционально в LoginInput для смены
- **Timezone**: при единственном поясе страны — автоматический выбор; при нескольких — явное уточнение
- **Хранение**: IANA identifier (например, `Europe/Vilnius`), не фиксированный offset
- **Настройка**: выбранный пояс всегда можно изменить в settings; пояс компании не следует за сотрудником
- **UI обязанность**: объяснять влияние на границы суток/месяцев, фильтры, отчётные периоды, зависимые сроки

### 6. Коды ошибок С1

| код | статус | когда |
|---|---|---|
| `MISSING_TOKEN` | 401 | нет заголовка Authorization |
| `INVALID_TOKEN` | 401 | неверная схема, пустой токен, неверная подпись, payload, UUID |
| `TOKEN_EXPIRED` | 401 | `now >= expires_at` в БД (stateful) |
| `UNAUTHORIZED` | 401 | пользователь отсутствует, неактивен, без компании, неверная пара, отключённый аккаунт |

| `VALIDATION_ERROR` | 422 | невалидное поле (явный `fieldErrors`) |

### 7. Зависимости реализации

- **Settings**: internal API для timezone/country инициализации и обновления

- **Migrations**: тестовая PostgreSQL для миграций сессий/уникальности email (отдельная подготовка)
