# Общие соглашения API

Правила, действующие поперёк доменов. Доменный файл на них **ссылается**, а не копирует: второй
экземпляр правила — это линза Л5, и расходиться копии начинают в тот же день, когда появляются.

Как читать этот файл:

- **всё, что здесь написано, доказано кодом** — у каждого утверждения есть `файл:строка`. Пути от
  корня репозитория; во фронтенде корень пути — `frontend_vue/`;
- **правило, живущее ровно в одном домене, сюда не переезжает.** Оптимистическая блокировка
  (`If-Match`) есть только у заказов и остаётся в `orders.md`;
- **решений здесь нет.** Место, где правила не существует нигде, названо прямо и вынесено строкой
  в [`00-решения-владельца.md`](../../plans/api/audit/00-решения-владельца.md);
- **примеры здесь намеренно не оформлены заголовком `###` с методом и путём.** Инвентарь контракта
  (`frontend_vue/src/services/contractInventory.ts:223`) читает такие заголовки как описание
  эндпоинта и требует, чтобы оно лежало в файле своего домена, — пример в общем файле сделал бы
  спеку красной. Пути ниже пишутся строкой в тексте.

Состояние сверки на 2026-09-04: эндпоинтов в коде **175**, из них описано **5** (домен `auth`).
Считает `contract-conformance.spec.ts` внутри `npm run verify`.

Замер бэкенда на 2026-09-04: **31 роут** на весь проект — `settings` 24, `auth` 4, `products` 2,
`core/uploads` 1; у `bcc`, `billing`, `finance`, `notifications`, `services`, `suppliers`,
`warehouse` роутов ноль при живых моделях. Отсюда общее правило старшинства: **по эндпоинту, у
которого есть реализация бэкенда, истина — бэкенд; у остальных — мок и клиент.**

## 1. Конверт ответа

Клиентский разбор — `unwrap()`, [`services/api.ts:108-142`](../../../frontend_vue/src/services/api.ts).
Он принимает **три** формы, и все три законны:

1. **конверт** `ApiResponse<T>` — распознаётся по наличию ключа `success` (`api.ts:128`), при
   `success === false` бросается ошибка (`:130-136`), иначе наружу уходит `json.data` (`:137`);
2. **голое тело** — ответ без ключа `success` возвращается как есть (`api.ts:140-141`);
3. **ошибка FastAPI** — тело с ключом `detail`, разбирается до кода и полей (`api.ts:30-69`).

```ts
// frontend_vue/src/types/api.ts:1-6
interface ApiResponse<T> {
  success: boolean
  data?: T
  message?: string
  code?: string
}
```

Серверная сторона конверта — `backend/app/core/schemas.py:29-33`, и она **уже** совпадает по
именам полей.

**Что из этого следует для бэкенда.** Конверт — предпочтительная форма, потому что только он несёт
`code`; голое тело клиент переживает, но тогда у ответа нет машинного кода ошибки и нет `message`.
Смешивать формы в пределах одного эндпоинта нельзя: клиент различает их по наличию ключа
`success`, а не по методу или пути.

**Наблюдение, требующее проверки на живом сервере.** В серверной модели поле объявлено
`data: dict | None` (`backend/app/core/schemas.py:33`), а списочные эндпоинты настроек кладут в него
список — `data=[r.model_dump(…) for r in result]`, четыре места:
`backend/app/modules/settings/features/crud/action.py:222`, `:301`, `:369`, `:437`. Тип поля списка
не допускает. Проверить это здесь нечем — pydantic в окружении не установлен, — поэтому запись
остаётся наблюдением и уходит в аудит домена `settings`, а не в правило.

**Исключение из конверта — CSV.** `/api/suppliers/export.csv` объявлен как `Promise<string>`
(`services/suppliersService.ts:93`), то есть на проводе текст, а не JSON. Единственный такой
эндпоинт на все 175.

## 2. Ошибки: где лежит код и как он доходит до человека

Клиент бросает `ApiRequestError` (`types/api.ts:25-47`) с четырьмя полями: `status`, `message`,
`code`, `fieldErrors`. **Машинный код лежит в `code`, человеческий текст — в `message`.** Это и
есть контракт для сервера.

Откуда `unwrap()` берёт код (`api.ts:19-83`), в порядке проверки:

- `detail` — массив ошибок pydantic `[{ loc, msg, type }]`: код становится `VALIDATION_ERROR`, а
  имя поля берётся последним элементом `loc` и уезжает в `fieldErrors` (`api.ts:34-51`). **Это
  единственный путь, которым сервер может назвать поле формы точно;**
- `detail` — объект `{ message, code }`: код берётся как есть (`api.ts:54-63`). Так пишет весь
  нынешний бэкенд, например `backend/app/modules/auth/features/me/action.py:47`, `:57`, `:62`;
- `detail` — строка: код `null` (`api.ts:66-68`);
- конверт с `success: false`: код из `code` (`api.ts:71-79`);
- ничего из перечисленного: `Request failed (<status>)`, код `null` (`api.ts:81-82`).

**Каталог кодов ядра** — `backend/app/core/exceptions.py`: `NOT_FOUND` (`:20`),
`VALIDATION_ERROR` (`:27`), `UNAUTHORIZED` (`:34`), `FORBIDDEN` (`:41`), `CONFLICT` (`:48`).
Плюс три кода сессии, объявленные прямо в эндпоинте: `MISSING_TOKEN`, `TOKEN_EXPIRED`,
`INVALID_TOKEN` (`auth/features/me/action.py:47,57,62`).

**Кодов `UNAUTHENTICATED`, `RATE_LIMITED`, `SERVER_ERROR`, `INFECTED` в проекте нет** — ни во
фронтенде, ни на бэкенде (`grep -rn` по каждому даёт пусто). Старый контракт объявлял все четыре.

**`AppError` не обрабатывается ничем.** Классы `NotFoundError`/`ValidationError`/… объявлены
(`core/exceptions.py:13-48`), но обработчика исключений в приложении нет: в
`backend/app/main.py` нет ни одного `exception_handler`, и `grep -rn "AppError" backend/app` вне
объявлений даёт только объявление двух наследников в `bcc/features/send_request/domain.py:23,34`.
То есть код, который их бросит, отдаст 500 без конверта и без `code`. Сейчас все живые эндпоинты
бросают `HTTPException` напрямую.

### Код не должен быть подстрокой другого кода

Правило линзы К3. Замер на 2026-09-04 уточняет его формулировку, и уточнение важно: **сравнений
кода подстрокой на проводе сегодня ноль.** Все места, где код с чем-то сравнивают, сравнивают
точным равенством — `useWarehouseBatch.ts:341`, `useWarehouseOffcutCard.ts:385`,
`useCategories.ts:43`, `useProducts.ts:51`. Единственные два `includes` во всём фронте —
`composables/useOrderCard.ts:1697-1698` — разбирают `String(e)` от **локального** исключения
доменной функции `allocateTotal`, а не ответ сервера.

Правило нужно всё равно, потому что материал для промаха уже лежит. Из литералов вида
`^[A-Z][A-Z0-9_]*$` с подчёркиванием во фронтенде **133**, и среди них **девять** пар, где один код
— подстрока другого (`FORBIDDEN_` из `mocks/orders.ts:1858` в счёт не идёт: это префикс, из
которого код собирается, а не код):

```
AUDIT_ENTRY_NOT_FOUND  ⊂ ORDER_AUDIT_ENTRY_NOT_FOUND
BATCH_NOT_FOUND        ⊂ RETURN_BATCH_NOT_FOUND, SHIPMENT_BATCH_NOT_FOUND
CURRENCY_NOT_FOUND     ⊂ SERVICE_CURRENCY_NOT_FOUND
NO_STOCK               ⊂ NO_STOCK_COST
PRODUCT_NOT_FOUND      ⊂ CATALOG_PRODUCT_NOT_FOUND
SERVICE_NOT_FOUND      ⊂ CATALOG_SERVICE_NOT_FOUND, ORDER_SERVICE_NOT_FOUND
UOM_NOT_FOUND          ⊂ SERVICE_UOM_NOT_FOUND
```

Сверх того ядерный `NOT_FOUND` (`backend/app/core/exceptions.py:20`) — подстрока **всех 33**
доменных кодов, оканчивающихся на `_NOT_FOUND`. Правило: **новый код не должен быть подстрокой
существующего**, а обработка ошибки сравнивает `code` точным равенством, а не `includes`.

### Мок кладёт код не туда, куда сервер

Моки бросают `throw new Error(<КОД>)` — **196** мест в `services/mocks/*.ts`, и ни одного
`ApiRequestError`. Значит под моками код лежит в `message`, а против сервера — в `code`. Два
потребителя читают именно `message` и против настоящего API не сработают:
`composables/useCategories.ts:43` и `composables/useProducts.ts:51`. Ещё двое подстрахованы обеими
ветками: `useWarehouseBatch.ts:341` (`err?.code === … || err?.message === …`) и
`useWarehouseOffcutCard.ts:385`.

Это находка про **фронтенд**, а не про контракт: сервер обязан отдавать код в `code`. Каждый такой
случай записывается в bugs-файл своего домена (для categories — находка 1 в
[`contract-sync-categories-bugs.md`](../../plans/bugs/contract-sync-categories-bugs.md)).

### Имя поля формы сервер обязан называть, а не подсказывать

`inferFieldFromMessage()` (`api.ts:86-106`) угадывает поле по **тексту** сообщения: ищет `vat`,
`email`, `password`, `phone`, `name`. Переформулировка серверного сообщения молча ломает подсветку
поля (БАГ-06 домена auth). Точный путь один — массив `detail` с `loc` (`api.ts:34-51`).

## 3. Авторизация и заголовки

**Сессия живёт не в cookie.** `credentials: 'include'` не выставлен ни в одном `fetch`
(`grep -rn "credentials" frontend_vue/src` — пусто), HttpOnly-cookie не используется нигде.
Сервер возвращает `session.token` и `session.csrf_token` в теле ответа входа; клиент кладёт их в
`localStorage` (когда «запомнить меня») или в `sessionStorage` и шлёт двумя заголовками:

```
Authorization: Bearer <session.token>
X-CSRF-Token: <session.csrf_token>
```

Сборка — `composables/useAuth.ts:100-107`; хранение — `:27-49`, `:81-90`.

**Заголовок ставится не централизованно, а вызывающим.** `services/api.ts` не добавляет
авторизацию сам: она приходит в `options.headers`. Ставят её четыре места — три сервиса
(`services/settingsService.ts:18-22`, `services/auditFeedService.ts`,
`services/uploadsService.ts:14-16`) и сам `composables/useAuth.ts:100-107`. Сервисов, зовущих
хелперы, пятнадцать; остальные **двенадцать** не шлют ни `Authorization`, ни `X-CSRF-Token`
вовсе — включая `ordersService.ts` (35 вызовов) и `warehouseService.ts` (38).

**CSRF-токен сервер выдаёт, но нигде не проверяет.** Он рождается при входе
(`backend/app/modules/auth/features/login/domain.py:44`), хранится в модели сессии
(`auth/shared/models.py:124`) и возвращается в схеме (`login/schemas.py:33`) — а проверки
`X-CSRF-Token` в `backend/app` нет ни одной.

**Пространства `/api/admin/**` не существует** — ни одного вызова с таким префиксом во фронтенде.
Старый контракт строил на нём правило доступа.

Что из этого не решено — какой ответ и какой код обязан прийти на запрос без сессии к каждому из
175 эндпоинтов, и обязан ли сервер проверять `X-CSRF-Token`, — вынесено в
[`00-решения-владельца.md`](../../plans/api/audit/00-решения-владельца.md).

## 4. PATCH против PUT

Правило, а не список путей: список устаревает к следующей странице.

**`PATCH` — правка одной сущности дельтой.** Тело содержит только изменённые ключи верхнего уровня
(RFC 7396 merge-patch), сервер накладывает их поверх текущего состояния и возвращает сущность
целиком. Дельту собирает `useDirtyCheck().diff()`
([`composables/useDirtyCheck.ts:62-…`](../../../frontend_vue/src/composables/useDirtyCheck.ts)):
сравнение идёт по **верхнему уровню**, а вложенный объект или массив, у которого изменился хоть
один лист, уходит целиком. Значит для массивов у PATCH **replace-семантика**, а не merge:
`linkedSuppliers`, `fileIds`, `categories` приходят полным массивом или не приходят вовсе.

**`PUT` — замена коллекции целиком.** Тело — весь массив (или объект-обёртка над ним), сервер
перезаписывает без merge. Применяется там, где одно действие пользователя меняет много записей
атомарно: порядок, матрица, полный набор.

Замер на 2026-09-04: **27** вызовов `apiPatch` и **6** вызовов `apiPut` во фронтенде. Шесть PUT —
это `/api/config/fields` (`configService.ts:12`), `/api/config/sections` (`:51`),
`/api/config/permissions` (`:81`), `/api/settings/order-statuses/reorder`
(`settingsService.ts:128`), `/api/settings/warehouse-map` (`:152`) и `/api/categories/:id/fields`
(`categoriesService.ts:65`). Пять из шести — именно «коллекция целиком»; шестой,
`warehouse-map`, — единичный ресурс без id, у которого PUT заменяет единственный экземпляр.

Пофайловая карта «метод путь → файл» появится в `README.md` этого каталога (задача 38 плана
сверки). До неё точный список даёт команда:

```bash
cd frontend_vue && grep -rn "apiPut\|apiPatch" src --include=*.ts | grep -v '\.spec\.'
```

**Тело PUT не обязано быть массивом.** `/api/categories/:id/fields` шлёт объект-обёртку
`{ fields: [...] }` (`categoriesService.ts:65-71`), `/api/settings/order-statuses/reorder` —
`{ orderedIds }` (`settingsService.ts:128-132`). Форма тела описывается в разделе эндпоинта, а не
выводится из метода.

## 5. TranslatedString

Мультиязычное поле передаётся объектом. Фронтовый тип фиксирован тремя языками:

```ts
// frontend_vue/src/types/i18n.ts:6-10
interface TranslatedString { ru: string; en: string; lt: string }
```

Серверный тип **шире**: `backend/app/core/schemas.py:5-13` объявляет те же три ключа значениями по
умолчанию и разрешает произвольные локали (`model_config = {"extra": "allow"}`, `:13`). То есть
сервер готов к четвёртому языку, а фронт — нет: `toTranslatedString()` создаёт ровно три ключа
(`types/i18n.ts:19-25`), и лишние ключи ответа фронт молча отбросит.

Правила для сервера:

- **все три ключа приходят и возвращаются всегда**, неактивная локаль — пустая строка
  (`types/i18n.ts:20`);
- **сервер не переводит и не заполняет пустые локали**: значение хранится как прислали;
- **клиент шлёт объект целиком**, даже когда правит один язык.

Три функции фронта, и разница между ними — источник потери данных:

| функция | что делает | когда законна |
|---|---|---|
| `toTranslatedString(value, locale)` (`i18n.ts:19-25`) | создаёт новый объект, две другие локали — **пустые строки** | только для нового значения |
| `mergeLocaleValue(existing, value, locale)` (`i18n.ts:53-63`) | правит одну локаль, остальные сохраняет | правка существующего значения из UI |
| `mergeTranslatedString(existing, incoming)` (`i18n.ts:36-46`) | накладывает частичный объект | приём дельты |

Применение `toTranslatedString` к уже существующему значению стирает два перевода. Замеренный
случай: `views/admin/products/CategoryCardPage.vue:135,137,147,152` — редактирование имени поля
категории; в той же странице заголовок и описание для того же случая используют `mergeLocaleValue`
(`:70`, `:84`). Записано находкой 8 домена categories.

**Сортировка по `name.en`, а не по локали пользователя.** Мок категорий сортирует список по
английскому имени независимо от текущего языка (`services/mocks/categories.ts:1364`, `:1403`).
Правило порядка выдачи описывается в домене; сюда вынесено то, что от локали ответа он не зависит.

## 6. Пагинация

```ts
// frontend_vue/src/types/api.ts:8-19
interface PaginatedResponse<T> { items: T[]; total: number; page: number; pageSize: number; totalPages: number }
interface PaginationParams { page: number; pageSize: number }
```

- параметры всегда в **query**, строками: `?page=1&pageSize=25`. Форма одинакова у всех
  списочных эндпоинтов — `page: String(pagination.page), pageSize: String(pagination.pageSize)`,
  в десяти сервисах;
- **страница по умолчанию 25** — `usePagination(defaultPageSize = 25)`
  (`composables/usePagination.ts:3`). Из двадцати вызовов четырнадцать передают 25 явно, два
  полагаются на дефолт, три просят 5 и один 10;
- то же число продублировано в подписи клиента категорий (`categoriesService.ts:9-10`) — то есть
  дефолт живёт в двух местах, и это наблюдение, а не правило;
- у сервера та же модель ответа: `backend/app/core/schemas.py:19-25`, поля в `camelCase`
  (`pageSize`, `totalPages`), в отличие от домена `auth`, который целиком в `snake_case`.

**Справочник — не страница списка.** Там, где выпадающему списку нужен весь набор, для этого
заводится отдельный лёгкий эндпоинт: `/api/products/list` (`productsService.ts:117`) и
`/api/suppliers/list` (`suppliersService.ts:98`) — оба возвращают массив без конверта пагинации.
Домен, у которого такого эндпоинта нет, берёт справочник страницей списка, и это уже стреляло:
селект родителя категории читает первые 25 записей (`CategoryCardPage.vue:63`), а карточка товара
тот же справочник — с `pageSize` 999 (`useProductCard.ts:132`). Нужен ли `/api/categories/list` —
строка владельцу в аудите categories.

## 7. Даты, деньги, длительности

- **дата** — ISO 8601. Обе формы законны и обе встречаются в моках: `2026-04-17` для
  календарного дня и `2026-04-17T14:32:05Z` для момента. Какая именно форма у поля — пишется в
  разделе эндпоинта;
- **деньги** — `number`, minor units не используются. Округление до двух знаков —
  `round2()`/`formatCents()` (`domain/orderPricing.ts:113-132`), и оно **не** `toFixed(2)`:
  `(22.575).toFixed(2)` даёт `22.57` при деньгах `22.58`;
- **производные цены и проценты** — четыре знака, `round4()` (`orderPricing.ts:118-121`);
- **длительность** — целые дни (`leadDays`, `leadTime`);
- **временной штамп внутри текста заметки** — локальный `dd.mm.yyyy hh:mm`, это часть строки, а не
  поле.

## 8. Идемпотентность и повтор

`Idempotency-Key` — заголовок, который клиент формирует сам:
`newIdempotencyKey()` (`services/api.ts:240-245`), UUID v4 через `crypto.randomUUID()` с
запасным вариантом.

Замер на 2026-09-04: заголовок ставится на **пяти** POST-ах, и все пять необратимы:

- `/api/bcc/send` — `services/bccService.ts:43`;
- `/api/bcc/log` — `services/bccService.ts:64`;
- `/api/orders/:id/shipments` — `services/ordersService.ts:295`;
- `/api/orders/:id/payments` — `services/ordersService.ts:386`;
- `/api/orders/:id/returns` — `services/ordersService.ts:352`.

Правило: **заголовок обязателен там, где повтор запроса создаёт вторую сущность с последствиями
вне системы** — второе письмо, вторая отгрузка, второй платёж, второй возврат. Сервер обязан
узнать ключ и вернуть **тот же** ответ, а не выполнить операцию заново.

Мок это уже реализует: `withIdempotency()` (`services/mocks/index.ts:262-269`) кеширует ответ по
ключу; регистр заголовка не важен (`'Idempotency-Key' ?? 'idempotency-key'`, `:263`). Срок жизни
кеша в моке не ограничен ничем — на сервере срок хранения ключа правилом нигде не назван, строка
владельцу.

**На остальных POST-ах ключа нет**, и это осознанно: они либо создают сущность, повтор которой
виден пользователю сразу (создание категории, товара, клиента), либо ретраятся явной кнопкой.
Требовать ключ на всех POST — решение, а не наблюдение.

**`If-Match` — не общее правило.** Версия сущности уезжает заголовком `If-Match` только в заказах
(`services/ordersService.ts:41-43`, потребитель — `composables/useOrderCard.ts:499`, разбор —
`services/mocks/index.ts:1416-1421`). Ни у одной другой сущности поля `version` нет. Правило
живёт в `orders.md`.

## 9. Записи аудита адресуются по id

Аудит есть у **девяти** сущностей, и у всех девяти запись удаляется своим `id`, а не позицией.
Путь одинаков: `/api/<сущность>/:id/audit/:entryId`. Все девять вызовов:

| сущность | вызов |
|---|---|
| поставщик | `services/suppliersService.ts:83` |
| остаток | `services/warehouseService.ts:333` |
| партия | `services/warehouseService.ts:343` |
| обрезок | `services/warehouseService.ts:353` |
| движение | `services/warehouseService.ts:363` |
| дефицит | `services/warehouseService.ts:373` |
| заказ | `services/ordersService.ts:195` |
| товар | `services/productsService.ts:125` |
| клиент | `services/clientsService.ts:45` |

`entryId` уникален **внутри своего лога**, глобальной уникальности не требуется: запись достаётся
через путь своей сущности. В моках он читаемый (`bch-au-2` — вторая запись лога партии), на
бэкенде это идентификатор строки.

**Почему не позиция.** Устаревшая позиция удаляет не ту запись и молча: удалили одну — все
следующие сдвинулись под уже нарисованными строками. Двух пользователей для этого не нужно.
Доказано тестом `services/mocks/audit-entry-identity.spec.ts`, и форма проверки у всех восьми
сущностей одна: удалить первую запись, затем ту, что была третьей. Под индексами вторая двойка
указывает уже на другую запись, и исчезает не та — беззвучно. Девятая сущность, заказ, покрыта
своими спеками (`composables/order-audit-concurrency.spec.ts`,
`services/mocks/order-audit-wire-schema.spec.ts`).

**Неизвестный `entryId` — ошибка, а не тихий no-op**: `AUDIT_ENTRY_NOT_FOUND` (у заказов —
`ORDER_AUDIT_ENTRY_NOT_FOUND`; обе строки существуют, и первая является подстрокой второй — см.
раздел 2). Молчание неотличимо от успеха, и клиент сотрёт у себя строку, которая на сервере
осталась.

Из девяти сущностей заказ единственный требует к удалению версию (`ordersService.ts:195`).

## 10. Save UX: clean-slate и quick-action

Модель — **clean-slate**: сервер знает только сохранённое состояние, всё остальное живёт в
локальном состоянии Vue. Это задание бэкенду не строить черновики, а не только описание фронта.

**Правило 1 — состояние правки локально.** Промежуточных запросов нет, автосейва нет, дебаунса на
сохранение нет.

**Правило 2 — Save шлёт дельту.** Кнопка собирает изменённые ключи через `useDirtyCheck().diff()`
и отправляет их одним PATCH. Не изменилось ничего — запрос не уходит. Композаблов карточек,
построенных на `useDirtyCheck`, десять: supplier, product, client, service, category, order,
warehouse stock / batch / offcut / deficit.

**Правило 3 — перезагрузка это сброс.** Несохранённое теряется без предупреждения:
`beforeunload`-гарда в проекте **нет** (`grep -rn "beforeunload" frontend_vue/src` — пусто), хотя
старый контракт его обещал.

**Правило 4 — черновиков на сервере нет.** Единственное исключение — файл, загруженный до Save
(раздел 11).

**Quick-action — исключение**: действие уходит на сервер сразу, без Save-кнопки, обычно после
модалки подтверждения. Признак — не тип сущности, а то, что действие атомарно и не часть
редактируемой формы: смена статуса, удаление, отправка, добавление платежа, загрузка файла.
Save-режим каждого эндпоинта пишется в его разделе строкой «Save-режим: clean-slate» или
«quick-action».

### Одна кнопка Save — несколько запросов, и атомарности между ними нет

Замерено в трёх доменах, каждый — параллельный `Promise.all` без общей транзакции:

- **categories**: `PATCH /api/categories/:id` и `PUT /api/categories/:id/fields`
  (`composables/useCategoryCard.ts:102-112`). При падении одного второй остаётся применённым, и
  `load()` после ошибки не вызывается — `:113` стоит до `catch`, экран остаётся с несохранённым
  поверх частично сохранённого;
- **config**: `PUT /api/config/fields` + `/sections` + `/permissions`
  (`composables/useCardConfig.ts:45-56`, комментарий там прямо называет это «atomic save batch»);
- **settings**: набор запросов, собранный по «грязным» секциям, уходит одним `Promise.all`
  (`composables/useSettings.ts:518`).

Наблюдение, а не решение: обязан ли сервер дать один транзакционный эндпоинт на такую кнопку —
строка владельцу.

## 11. Файлы

Единый путь для всех файлов: `POST /api/uploads`, `multipart/form-data`, поле `file`, один файл за
запрос (`services/api.ts:224-237`, `services/uploadsService.ts:13-17`). Несколько файлов —
несколько запросов: `components/admin/ui/DropZone.vue:38` шлёт их через `Promise.all`.

Ответ — метаданные файла:

```ts
// frontend_vue/src/services/uploadsService.ts:3-10
interface UploadedFile { fileId: string; name: string; size: number; mime: string; url: string; uploadedAt: string }
```

Реализация бэкенда есть — `backend/app/core/uploads/action.py:79`, ответ завёрнут в `ApiResponse`.
Она проверяет MIME по белому списку и размер (422 и 413 соответственно, оба с кодом
`VALIDATION_ERROR`, `:101`, `:113`) и требует `Authorization: Bearer` (`:34-58`).

**Привязка к сущности — отдельным шагом, по Save.** Загруженный файл сначала ничей; карточка
копит его `fileId` и отправляет массивом `fileIds` в теле сохранения. Замер: так делают карточка
обрезка (`composables/useWarehouseOffcutCard.ts:136-158`, отправка `:277-278`), карточка партии
(`useWarehouseBatch.ts:133-148`), BCC (`bccService.ts:31`) и платёж финансов
(`financeService.ts:47`). Семантика поля — **replace**: пришёл массив, значит он полный; поля нет
в теле — файлы не трогаются.

`PATCH /api/suppliers/:id` в этом списке **больше нет**: `fileIds` в `suppliersService.ts` не
встречается. Старый контракт называл его первым.

## 12. Мультиарендность

`tenant_id` есть в моделях **всех десяти** модулей бэкенда (`grep -rln "tenant_id"
backend/app/modules/*/shared/models.py` — 10 файлов). В категориях, например, он объявлен
`nullable=False, index=True` с внешним ключом на `tenants.id` и `ondelete="CASCADE"`
(`backend/app/modules/products/shared/models.py:19-24`, `:64-69`).

**Во фронтенде арендатор не выражен нигде**: ни поля `tenantId` в теле, ни заголовка. Единственное
место, где он виден, — `UserInfo.tenant_id` в ответе `/api/auth/me`.

Отсюда правило: **арендатор определяется сервером по сессии, а не приходит от клиента**, и любая
выборка ограничивается им. Клиент, приславший чужой `tenant_id`, обязан получить отказ, а не
данные. Как именно сервер отвечает при попытке достать чужую запись — 404 или 403 — не решено
нигде; строка владельцу.

## 13. Права и фичи — два разных механизма

Их постоянно путают, а последствия разные: **право ограничивает роль внутри арендатора, фича
включена или выключена у всего арендатора (тарифом)**.

**Права** размазаны по трём доменам фронта плюс модуль бэкенда, и целиком их не видит ни один
доменный аудит:

- матрица `PermissionMatrix` — `types/config.ts:37-57`, чтение и запись `/api/config/permissions`
  (`configService.ts:81`) — домен `config`;
- три права заказов (`seeCost`, `manualCost`, `correction`) и `/api/settings/order-permissions`
  (`settingsService.ts:36-40`) — домен `settings`;
- потребитель — `composables/useOrderPermissions.ts` — домен `orders`;
- на бэкенде хранение уже описано тремя моделями с `tenant_id`: `PermissionItem`
  (`backend/app/modules/auth/shared/models.py:145`), `RolePermission` (`:169`), `UserPermission`
  (`:202`) — то есть роль, пользовательское переопределение и четыре действия
  (`can_read`/`can_edit`/`can_create`/`can_delete`) там уже есть.

**А проверки нет.** Единственная функция — заглушка `check_permission()`
(`backend/app/modules/auth/internal_api/interface.py:27-38`): её докстринг говорит «Placeholder —
implement actual RBAC logic here», тело — `return True`, и вызывается она **ниоткуда**
(`grep -rn "check_permission" backend/app` даёт одно объявление). Файл
`auth/shared/dependencies.py`, обещающий заголовком «permission checkers», состоит из четырёх
строк докстринга. Эндпоинта `/api/config/permissions` на сервере тоже нет — из 31 роута ни один
не про права.

Отсюда правило контракта: **право проверяется на сервере, в той же функции, которая пишет.**
Фронтовая проверка — это только про то, что показать; отказ обязан приходить с сервера. Как
серверные модели соотносятся с фронтовой матрицей и каким кодом отвечает отказ — не решено нигде;
строка владельцу.

**Фичи** — отдельный механизм, и обе стороны реализованы, но не соединены:

- фронт: **52** флага константой в `config/featureFlags.ts:4-82` плюс переопределения из
  `localStorage` (`:84-91`). Семь из 52 выключены (`:50-54`, `:58`, `:60`);
- бэкенд: `billing/shared/models.py` — `Plan` (`:11`), `PlanFeature` (`:75`),
  `TenantFeatureOverride` (`:108`), `FeatureDefinition` (`:137`) с комментарием «Registry of all
  known feature flag keys — single source of truth» (`:138`); ключи сеются миграцией
  `backend/alembic/versions/8cf3bfa380dd_phase_12_plans_multi_role.py:254-257`;
- **эндпоинта между ними нет ни одного**, роутов у модуля `billing` ноль.

Замер словарей на 2026-09-04: миграция сеет **46** ключей, фронт объявляет **52**. Ключей, которых
нет во фронте, — ноль; ключей, которых нет на бэкенде, — шесть: `orderShipments`,
`orderInvoicesPayments`, `orderReturns`, `settingsAuditLog`, `warehouseMap`, `warehouseCutting`.
Все шесть — фичи, добавленные после миграции.

Что решать владельцу: читает ли админка матрицу фич с сервера и каким эндпоинтом; что сервер
отвечает на запрос к выключенной фиче; сильнее ли переопределение арендатора, чем тариф. Строки
уже стоят в `00-решения-владельца.md`, пункт 1.

**Флаг прячет UI, но эндпоинт не закрывает.** Замерено на категориях: `categoryFieldReorder`
убирает перетаскивание (`CategoryCardPage.vue:165`), а `PUT /api/categories/:id/fields` уходит при
любом изменении полей (`useCategoryCard.ts:111`) — то есть выключенный флаг не мешает вызвать
эндпоинт другим действием той же страницы. Механизма, который закрывал бы путь по флагу, во
фронтенде нет вовсе: `meta.featureFlag` гейтит только навигацию роутера
(`router/index.ts:232`, `:238`). Значит защитой доступа флаг считать нельзя; чем закрыт путь —
вопрос прав, а не фич.

## 14. Аудит-лог и уведомления — обязанности, которых не видно во фронтенде

Обе не проявляются в мок-режиме никак, если их не реализовать, — и именно поэтому расходятся
первыми.

**Аудит-лог.** Записи есть в моках пяти доменов: `products` (121 упоминание `auditLog`),
`warehouse` (37), `clients` (17), `orders` (13), `suppliers` (7) — это те же девять сущностей из
раздела 9. Сводит их в одну ленту домен `audit-feed` (`services/auditFeedService.ts`), у остальных
доменов лога нет вовсе. У категорий его нет, при том что изменение набора полей категории меняет карточку каждого
её товара и всего поддерева, — след не остаётся нигде (строка владельцу в аудите categories).
Каждый доменный файл обязан ответить, что пишется в лог, кто автор записи и что помечается
`sensitive`; ответ «нигде» — строка владельцу, а не пустая графа.

**Уведомления.** Триггеров ровно **семь**, все в `services/mocks/notifications.ts`:
`notifyOrderStatusChanged` (`:542`), `notifyWarehouseReady` (`:566`), `notifyPaymentReceived`
(`:592`), `notifyBatchReceived` (`:616`), `notifyStockDeficit` (`:637`), `notifySupplierResponse`
(`:657`), `notifyPaymentOverdue` (`:684`). Чем они доказаны — `mocks/notification-triggers.spec.ts`.
Домены вне заказов, склада, платежей и поставщиков уведомлений не рождают; ни одно событие
категорий, товаров, клиентов и настроек уведомления не даёт.

**Кастомные поля.** Определения живут в двух несвязанных местах: библиотека полей карточки
поставщика — `FieldDefinition` и `/api/config/fields` (`types/config.ts:5`, `configService.ts:12`);
поля категории — внутри самой категории, `Category.fields` и `Category.inheritedFields`
(`types/category.ts:22-23`), запись `PUT /api/categories/:id/fields`. Значения по определениям
категории хранит товар (`ProductFieldValue`). Жизненного цикла значения нет **нигде**: что делать
при удалении определения и при смене его типа — не знает ни мок, ни схема. Схема при этом удаление
запрещает: `product_field_values.field_id` объявлен `ondelete="RESTRICT"`
(`backend/alembic/versions/25245d4bf874_phase_3_categories_products.py:78`). Строки владельцу —
пункт 2 и строка categories в `00-решения-владельца.md`.
