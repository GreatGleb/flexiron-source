### 2.1 Разбор до причины (не «бывает», не перезапуск на удачу)

Падение:

```
Error: expect(locator).toBeHidden() failed
Locator:  locator('[data-test="allocate-modal"]')
Expected: hidden   Received: visible   Timeout: 5000ms
Call log:
  3 × locator resolved to <div data-test="allocate-modal" class="modal-overlay active">…</div>
  2 × locator resolved to <div class="modal-overlay" data-test="allocate-modal">…</div>
```

Первое, что видно в самом журнале падения: **на последних опросах у оверлея уже нет класса
`active`** — то есть приложение модалку УЖЕ закрыло, а Playwright продолжал считать её
видимой. Значит падает не «модалка не закрылась», а что-то между закрытием и словом «скрыт».

Что стоит за этим «между» — `src/styles/admin/components/_modal.css`:

```css
.modal-overlay { opacity: 0; visibility: hidden; transition: all 0.3s; }
.modal-overlay.active { opacity: 1; visibility: visible; }
```

`visibility` лежит внутри `transition: all`, поэтому закрытый оверлей остаётся
`visibility: visible` всё время затухания — и Playwright, который смотрит на вычисленный
`visibility` и на бокс, всё это время читает «видим». Комментарий в самом CSS про это знает
и говорит именно об этом эффекте.

**Замер, а не рассуждение.** Зонд (Playwright напрямую, dev-сервер, тот же путь:
ORD-001 → 20328.99 → Enter → `allocate-confirm`), опрос вычисленного стиля каждые 150 мс:

```
   6 мс  class="modal-overlay active"  visibility=visible  opacity=1
 317 мс  class="modal-overlay active"  visibility=visible  opacity=1
 470 мс  class="modal-overlay"         visibility=visible  opacity=1     ← приложение закрыло
 624 мс  class="modal-overlay"         visibility=visible  opacity=1     ← затухание ещё не началось
 778 мс  class="modal-overlay"         visibility=visible  opacity=0.03
 932 мс  class="modal-overlay"         visibility=hidden   opacity=0     ← только теперь «скрыт»
```

Между «класс снят» и «скрыт» — 460 мс, из них ~300 мс затухание вообще не стартовало:
`confirmAllocation` сразу после `allocationPreview = null` уходит в `await load()`, страница
перерисовывается в скелетоны (это и видно на снимке падения — панели вверху в скелетонах,
позиции внизу уже с новой ценой 336.02 / 16800.82), и смена стиля не анимируется, пока
главный поток занят перерисовкой.

Тот же зонд с торможением процессора ×20 (`Emulation.setCPUThrottlingRate`):

```
 586 мс  class="modal-overlay"  visibility=visible          ← закрыто
1256 мс  class="modal-overlay"  visibility=hidden           ← скрыт
```

Окно растягивается вместе с загрузкой машины и ничем сверху не ограничено: старт затухания
ждёт кадра, а кадра нет, пока идёт перерисовка после `load()`.

**Причина падения, названная прямо.** Утверждение `toBeHidden()` на `.modal-overlay`
проверяет не факт «модалка закрыта», а окончание CSS-затухания, старт которого отложен
перерисовкой карточки. При полном наборе (1027 тестов, `fullyParallel`, воркеров по числу
ядер, прогон 18 минут) это окно вылезло за таймаут в 5 с — тот же тест в этом прогоне шёл
11.2 с против ~5 с в одиночку, то есть машина была загружена вдвое. Дефект — в тесте
(и в `transition: all` поверх `visibility`), а не в поведении приложения.

Проверка на воспроизводимость (диагностика, а не «прогнать ещё раз, вдруг повезёт»):

```
$ npx playwright test tests/e2e/admin/orders/orders.spec.ts \
    -g "editing the total spreads it across the lines" --repeat-each=6 --workers=1
exit=0   6 passed (35.1s)
```

В одиночку не воспроизводится — согласуется с зависимостью от загрузки, а не от кода.

### 2.2 Причастен ли к падению этот прогон

Нет, и это проверено, а не предположено.

```

```

- `useOrderCard.ts` (в нём `confirmAllocation`) и весь `src/styles/` прогоном **не тронуты**.
- В `OrderCardPage.vue` правка целиком внутри модалки ПЛАТЕЖА: `paymentGoesOut`,
  `paymentInvoiceOptions`, `refundNeedsInvoice`, подсказка, докстринг `openPaymentModal`.
  Разметка `allocate-modal` и её обработчики не менялись ни строкой.
- В `services/orderLineEdits.ts` — одна добавленная строка в таблице кодов ошибок
  (`REFUND_INVOICE_REQUIRED`).

Единственная связь прогона с этим падением косвенная: новые проверки удлинили набор и
подняли нагрузку, на которой давняя гонка в тесте наконец выстрелила.

**Что с этим делать (кодом приёмщик не трогает).** Тест должен ждать факт, а не затухание:
`allocate-modal` внутри `AppModal` — `.modal-overlay.active`, поэтому честное условие
закрытия — `expect(page.locator('[data-test="allocate-modal"].active')).toHaveCount(0)`.
Второй слой — вынуть `visibility` из `transition: all` в `_modal.css`. Оба места одинаково
касаются ВСЕХ модалок приложения, а не только этой, — в наборе шесть `toBeHidden()` по
`allocate-modal` и такие же по остальным. Это находка вне области пункта 14 → её место в
bugs-файле, завести должен тот, кому позволено менять файлы плана багов.

решения, в §2.1 и §4: падение опознано, причина названа, к пункту 14 отношения не имеет.

когда гонка в тесте будет закрыта.
