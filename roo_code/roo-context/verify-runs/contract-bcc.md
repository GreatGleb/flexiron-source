# Прогон контракта: домен bcc

Задача: написать `roo-context/api/bcc.md` по аудиту `plans/api/audit/bcc.md`. Ветка
`auto/contract-2026-09-04`, автономный режим. Код не тронут — правился только сам контракт и
этот журнал.

Входные числа аудита: эндпоинтов 7, источник истины «бэкенд» у 0, решений владельцу 11, находок
про код 11.

## Что написано

Файла контракта у домена не было — он написан целиком, 848 строк.

1. **Семь разделов `### <МЕТОД> <путь>`**, у каждого строка `Реализация:` и строка `Бэкенд:`.
   Модуль `bcc` в бэкенде существует, поэтому `Бэкенд:` обязателен у всех семи, и у всех семи он
   читается «не реализован»: `grep -rn "@router\." backend/app/modules/bcc --include=*.py` → 0.
   Метка `Статус: спроектировано` не поставлена ни разу и это проверено машинно
   (`спроектировано впрок: 0`): у всех семи есть и вызов клиента, и ветка мока, а метка означала
   бы отсутствие кода вообще.
2. **Динамический сегмент один — `:eventId`** у двух `POST` на события. В заголовки не развёрнут;
   внутри разделов сказано прямо, что это непрозрачный идентификатор строки ленты и перечислимого
   набора значений у него нет. Спека нормализует `:eventId` в `:id` с обеих сторон, поэтому
   инвентарь сходится.
3. **Особый случай домена, вынесенный в шапку:** «не реализован» здесь значит не то же, что у
   соседей. У `bcc` есть **написанный и не подключённый** доменный слайс отправки
   (`backend/app/modules/bcc/features/send_request/domain.py`, `transport.py`, тест на 169 строк) с
   нулём вызывающих в `backend/app`. Старшинство «бэкенд» по К5 не наступило ни у одного
   эндпоинта, но **по правилу отправки и по схеме хранения бэкенд уже старше фронта**, и оба места
   описаны по нему: одно письмо со всеми адресами в `Bcc`, снятие дублей, отказ `NO_RECIPIENTS`,
   и пять полей, по которым тип фронта расходится с `bcc_events`.
4. **Общие правила — ссылками, не копиями.** 53 ссылки на 18 разных параграфов
   `00-conventions.md`. Второго экземпляра общего правила нет: `interface ApiResponse`,
   `PaginatedResponse`, `TranslatedString`, `PaginationParams` в файле не объявлены ни разу
   (`grep -n "interface ApiResponse\|interface PaginatedResponse\|interface TranslatedString"` →
   пусто), формы конверта и разбор ошибки не переписаны.
5. **Разделы, которых требует шаг 4 и приёмка:** «Каталог кодов ошибок домена» (два кода),
   «Обязанности сервера» (девять граф аудита, все непустые, 64 ссылки `файл:строка`), «Правила
   домена» (двенадцать правил аудита один к одному), «Чего в домене нет» (21 строка), «Пробелы
   аудита — состояние» (41 строка, из них 11 «осталось»).
6. **Удаляемое оставило строку.** Семь эндпоинтов старого текста (`03-api-contract.md:536-609`)
   совпали с семью нынешними — ни один не исчез. Снято 21 утверждение: ETag-кеш, «видимость по
   товарным правам», четыре примера со строками на месте `TranslatedString`, «смена `page`/
   `pageSize`», «сортировка DESC», вложенное тело `template: { … }`, «сервер создаёт N × M строк»,
   `req-###`, `attachments` у `log`, ответ `{ requestId, events }`, «422 при `price <= 0`»,
   «обновляет `priceHistory`», порванная строка с перечнем единиц и прочее — у каждого в правой
   графе то, чем опровергнуто.
7. **Одиннадцать решений владельца** из `audit/00-решения-владельца.md` стоят строками
   «осталось» — ровно одиннадцать, счёт сверен с файлом решений.

### К2. Мок ↔ контракт ↔ код
**Чем:** свой экстрактор (python) — ветки `path === '/api/…'` и `path.match(/^…$/)` из
`mocks/index.ts`, вызовы `'/api/bcc/…'` из `bccService.ts`, заголовки из контракта; нормализация
`${…}` и `([^/]+)` в `:id`; симметричная разность во все три стороны.
**Что вернулось со второй попытки:** ветки мока 7, вызовы клиента 7, разделы контракта 7 —
**дыр 0, сирот 0**, симметричная разность контракта с кодом пуста. Совпадает с замером аудита:
домена `bcc` не было ни среди одной дыры проекта, ни среди пяти сирот.
**Первая попытка врала молча** — ровно тот питфолл, о котором предупреждает скил: регулярка
`path\.match\(\s*/\^([^/]*bcc[^/]*)\$/` рвалась о `\/` внутри шаблона, две ветки на события
оказались невидимы, и экстрактор отчитался о «двух дырах», которых нет. Пол: экстрактор обязан
находить **все** ветки файла, а не только доменные — исправленный даёт 125 (57 литералов + 68
регулярок). Это меньше проектных 179 из соглашений, то есть формы разбора есть и другие; для
домена это не влияет — все семь найдены и сведены с клиентом в обе стороны, но как общий
инструмент он неполон, и опираться на его глобальный счёт нельзя.
**Инверсия:** в копии `mocks/index.ts` сломаны одна литеральная ветка (`/api/bcc/log` →
`/api/bcc/logXX`) и одна регулярка (`events` → `eventsX`) — экстрактор показал ровно две дыры
(`/api/bcc/log`, `/api/bcc/events/:id/response`) и ровно две сироты. На целом файле — пусто.
