## 3. Приёмочная нога: upgrade → downgrade → upgrade на живой схеме

| шаг | команда | exit | что вернулось |
|---|---|---|---|
| вниз | `cd backend && python3 -m alembic downgrade -1` | 0 | `c9e4a1f70b23 -> b3f7a2c94d10` |
| вверх | `cd backend && python3 -m alembic upgrade head` | 0 | `b3f7a2c94d10 -> c9e4a1f70b23`, снова голова |

Факты схемы до и после, посчитанные по `public`:

- таблиц **48 → 47 → 48**;
- вниз сняты: таблица `warehouse_map` и **два** её индекса (уникальный по арендатору и индекс
  внешнего ключа);
- вверх восстановлены: та же таблица, её **6 колонок** и **те же два индекса**;
- версия вернулась в `c9e4a1f70b23`.

**Почему это отдельный факт, а не повторение §2.** Эта нога была `downgrade` + `upgrade` на живой
схеме — единственная проверка, которая доказывает **обратимость на базе**, а не только в офлайн-SQL.
До этой работы она ни разу не выполнялась, и это признано прямым текстом в
[отчёте c9, §7.1](../../night-2026-09-21/отчёт-c9.md:347): «Живая нога приёмки
(`alembic upgrade head && alembic downgrade -1 && alembic upgrade head`) **не выполнена**;
офлайн-SQL в обе стороны доказывает, что ревизия построена и обратима, но не доказывает применение
к живой схеме». Здесь этот остаток закрыт: нога пройдена целиком, чисто и обратимо.

## 4. БАГ-02: 8 таблиц / 15 операций

`alembic check` на базе, доведённой до головы, печатал `New upgrade operations detected` —
**8 таблиц, 15 операций**. Классификация по видам дрейфа:

| № | что расходилось | таблицы | сколько объявлений правилось |
|---|---|---|---|
| 1 | `UniqueConstraint` в модели против `UNIQUE INDEX` в БД | `currencies`, `field_definitions`, `product_field_values`, `role_permissions`, `user_permissions` | 5 |
| 2 | тип: `BIGINT` в БД против `Integer` в модели | `uploaded_files` (`size`) | 1 |
| 3 | объявлений индексов не было в модели вовсе | `sessions` (FK `user_id`, `expires_at`) | 2 |
| 4 | парная уникальность email у арендатора не была выражена моделью | `users` (`tenant_id` + `email`; плюс индекс `updated_at`) | 2 |

Тот же список по таблицам, в порядке записи БАГ-02: класс 1 — семь таблиц
(`currencies`, `field_definitions`, `product_field_values`, `role_permissions`, `user_permissions`,
`users`, `sessions`), класс 2 — `uploaded_files`; всего **восемь**.

**Разбор состава 15 операций** (реконструкция по четырём группам выше, а не отдельный замер —
`check` сегодня уже зелёный и списка не печатает): пять объявлений класса 1 дают по паре операций
(снятие индекса и постановка ограничения) — 10; `uploaded_files.size` — одна операция смены типа;
два объявления `users` и два `sessions` — по одной на объявление. Итого 15.

**Корень, одной причиной на всю группу.** Миграции создавали уникальность **индексом**
(`CREATE UNIQUE INDEX`), а модели объявляли её **ограничением** (`UniqueConstraint`). Для alembic
это разные виды объектов каталога: он сравнивает метаданные модели с базой **по видам** и потому
предлагает снять индекс и поставить ограничение. Применить это предложение нельзя — следующая
правка возвращает стороны на места, но не сводит их: стороны описывают одну и ту же уникальность
разными видами. Пока так, `check` краснеет при любой базе и **краснел с рождения** — то есть как
гейт не сообщал ничего.

## 5. Правка: пять файлов моделей, только модель

Правка **модельная**: изменены пять файлов моделей, ни одного DDL-объекта, **ни одной миграции не
заведено**, ни один объект базы не снят. Числа и имена оставлены теми, что уже есть в БД, — индекс
остаётся индексом.

| [`backend/app/modules/suppliers/shared/models.py`](../../../backend/app/modules/suppliers/shared/models.py:266) | `UniqueConstraint("tenant_id", "name", name="uq_field_definitions_tenant_name")` | `Index("uq_field_definitions_tenant_name", "tenant_id", "name", unique=True)` |
| [`backend/app/modules/products/shared/models.py`](../../../backend/app/modules/products/shared/models.py:201) | `UniqueConstraint("product_id", "field_id", name="uq_product_field_value")` | `Index("ix_product_field_values_product_field", "product_id", "field_id", unique=True)` |
| [`backend/app/modules/auth/shared/models.py`](../../../backend/app/modules/auth/shared/models.py:219) | `UniqueConstraint("tenant_id", "item_id", "role", name="uq_role_permission")` | `Index("uq_role_permission", "tenant_id", "item_id", "role", unique=True)` |
| тот же файл | `UniqueConstraint("tenant_id", "item_id", "user_id", name="uq_user_permission")` | `Index("uq_user_permission", "tenant_id", "item_id", "user_id", unique=True)` |
| тот же файл, `User` | объявлений индексов нет | `__table_args__ = (Index("ix_users_tenant_id_email", "tenant_id", "email", unique=True), Index("ix_users_updated_at", "updated_at"))` |
| тот же файл, `Session` | `user_id` (FK) и `expires_at` без `index=True` | `index=True` в обоих `mapped_column` |

Имена индексов взяты **из базы**, а не придуманы: `uq_*` остались `uq_*` (это имена индексов
`role_permissions`, `user_permissions`, `field_definitions`), а у валюты и значений полей товара
в БД лежат `ix_currencies_tenant_code` и `ix_product_field_values_product_field` — модель теперь
называет ровно их.

**Что правка НЕ делает:** не заводит ревизию, не меняет DDL, не снимает и не пересоздаёт объекты
в базе, не трогает CI. Парная уникальность email у арендатора **сохранена** — теперь она выражена
моделью, а не только БД (§6, проба 23505). `size` в базе остаётся **`bigint`**; изменилось только
объявление модели, которое раньше обещало `Integer` (§6, проба 3 000 000 000).

## 9. Как воспроизвести

```bash
# 1. изолированная база
docker run -d --name flexiron_pg_verify \
  -e POSTGRES_PASSWORD=<как в DATABASE_URL из backend/.env> \
  -e POSTGRES_DB=flexiron \
  -p 5433:5432 postgres:14

# 2. чистая база (drop/create) — на ней §2 и §3 воспроизводятся с нуля
docker exec flexiron_pg_verify psql -U postgres \
  -c "DROP DATABASE IF EXISTS flexiron;" -c "CREATE DATABASE flexiron;"

# 3. цепочка миграций: все 23 ревизии, exit 0
cd backend && python3 -m alembic upgrade head

# 4. линза Б2 машинно: обязано быть «No new upgrade operations detected.» и exit 0
cd backend && python3 -m alembic check

# 5. обратимость на живой схеме (§3)
cd backend && python3 -m alembic downgrade -1 && python3 -m alembic upgrade head

# 6. бэкенд-набор
cd backend && python3 -m unittest discover -s tests -t .
cd backend && python3 -m pytest tests -q            # то же самое, с subtests в отчёте
```

Перед шагами 3–6 `backend/.env` должен смотреть на **5433**; на 5432 эти команды писать не должны.

## 10. Решения владельца — 2026-09-22

Закрытие остатка §8. Три решения владельца, записанные здесь как применённые.

**Д1. `backend/.env` снят с отслеживания.** Выполнено `git rm --cached backend/.env` (до этого файл
отслеживался), в [`.gitignore`](../../../.gitignore:55) добавлена строка `backend/.env`. **Файл на
диске не тронут:** первая строка — `DATABASE_URL=postgresql+asyncpg://postgres:****@localhost:5433/flexiron`,
порт **5433** остался, `git check-ignore -v backend/.env` возвращает
`.gitignore:55:backend/.env	backend/.env`. Для остальных разработчиков умолчание несёт
[`backend/.env.example`](../../../backend/.env.example:1) — он на месте. Причина ровно такая: коммит
переключения порта увёл бы базу у всех на контейнер, которого у них нет.

**Д2. 5433 — документированное умолчание.** Порт `5432` → `5433` заменён ровно в одной строке
каждого файла: [`backend/.env.example`](../../../backend/.env.example:1) и `backend/alembic.ini`
([строка 5](../../../backend/alembic.ini:5)). Учётки не трогались: `user:password` остался
плейсхолдером в обоих файлах. `git diff --numstat` по обоим даёт `1 1` — по одной изменённой строке.
**Поправка к §8.2:** устаревший URL в `alembic.ini` был **вопросом согласованности, а не
безопасности** — с плейсхолдерными `user:password` он получил бы отказ аутентификации, а не запись в
чужую базу. Правка внесена **из CLI**, потому что файловые инструменты этот файл не открывают
(`.rooignore` закрывает `**/*.ini`); точная команда:

```bash
sed -i 's#@localhost:5432/flexiron#@localhost:5433/flexiron#' backend/alembic.ini
```

**Д3. `roo_code/zoo-code-auto-approve.json` отложен.** В коммит не входит и остаётся грязным; к этой
работе не относится, владелец разберётся с ним отдельно.
