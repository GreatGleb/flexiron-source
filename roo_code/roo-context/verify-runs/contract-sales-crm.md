Обе — ровно тот класс, за который проба домена `categories` потеряла две попытки из трёх:

## Линзы К1–К7 — чем проверял и что вернулось

### К1. Инвентарь: код ↔ контракт

Машинно: `cd frontend_vue && npx vitest run src/services/contract-conformance.spec.ts` →
`Tests 9 passed | 1 skipped`, печать `сведено доменов: 4 · описано эндпоинтов: 40 из 175 ·
спроектировано впрок: 0`, `sales-crm` из строки «не сведено» исчез. Домен подхватился
автоматически по факту появления файла (храповик спеки), список пропущенных эндпоинтов пуст.

**Инверсия — настоящая, не рассуждением:** заголовок в файле временно сломан на
`### GET /api/sales-crm/statistics`, прогон спеки → `Tests 2 failed`, и покраснели именно те два
утверждения, что должны: «вызывается кодом, не описано в контракте» (1 элемент) и «описано в
контракте, в коде нет — контракт не roadmap» (1 элемент). Файл восстановлен из копии, спека снова
`9 passed`.

Формат по шагу 3 проверен отдельно: `grep -n "^### "` по файлу → **ровно один** заголовок,
`### GET /api/sales-crm/stats`. Динамических сегментов у домена нет, разворачивать в заголовки
нечего; примеры и таблицы оформлены не через `###`, поэтому чужого эндпоинта спека не увидит.

### К2. Мок ↔ контракт ↔ код

`grep -rn "api/sales-crm" frontend_vue/src --include=*.ts --include=*.vue` → **две** строки:
`services/ordersService.ts:54` (вызывающий) и `services/mocks/index.ts:540` (ветка мока). То есть
у единственного описанного эндпоинта есть и ветка, и вызывающий — ни дыры, ни сироты. Обратная
сторона: `grep -n "^### "` по контракту даёт один заголовок, и он же — этот путь.

Свой слой у домена отсутствует, поэтому К2 проверяет чужой файл (`mocks/orders.ts`,
`mocks/index.ts`) — записано правилом домена 5, а не оставлено читателю на догадку.

### К3. Коды ошибок

Каталог домена пуст, и это доказано, а не заявлено:
`sed -n '1577,1595p' frontend_vue/src/services/mocks/orders.ts | grep -c "throw"` → **0**;
`sed -n '538,543p' frontend_vue/src/services/mocks/index.ts | grep -c "throw"` → **0**.

**Инверсия:** тот же греп на пути списка заказов (`sed -n '1440,1470p' … | grep -c "throw"`) →
**4**. Значит греп ищет, а не молчит.

Чужие коды, названные в контракте, существуют в коде: `UNKNOWN_SORT_KEY`,
`UNKNOWN_SORT_DIRECTION`, `INVALID_DATE_FILTER`, `INVALID_PAGE` — по `grep -c` в
`mocks/orders.ts` каждый **1**. Правило «ни один код не подстрока другого» проверено по всем
кодам, упомянутым в файле (10 имён, попарная проверка вхождения) → **пустой список пар**.

### К4. Формы запроса и ответа

Скриптом сравнены поля `interface SalesCrmStats` (`types/order.ts:48-57`) с ключами объекта,
который возвращает мок (`mocks/orders.ts:1589-1594`):
`тип: [('activeOrders','number'),('pendingOrders','number'),('salesMtd','number'),('newClientsThisMonth','number')]`,
`мок: ['activeOrders','pendingOrders','salesMtd','newClientsThisMonth']`,
`совпадение имён: True`, `все number: True`, `необязательных (?): []`.

Отсутствия проверены тем же способом: `sed -n '48,57p' src/types/order.ts | grep -cE
"currency|asOf|generatedAt|periodFrom|breakdown"` → **0**, при инверсии `grep -c "currency"
src/types/order.ts` → **10** (в файле валюта есть, в форме ответа — нет). Форма запроса пустая:
вызов без второго и третьего аргументов (`ordersService.ts:54`), а `options?.headers` —
единственный источник заголовков у GET (`api.ts:157-159`);
`grep -c "Authorization\|authHeaders" frontend_vue/src/services/ordersService.ts` → **0**.

Сверять с серверными схемами нечего: модуля нет (К5).

### К5. Источник истины

`ls backend/app/modules/` → `auth bcc billing finance notifications products services settings
suppliers warehouse` — каталога `sales*`/`crm*` нет;
`grep -rn "sales-crm" backend/app --include=*.py | wc -l` → **0**;
`grep -rln -i "sales\|crm" backend/app --include=*.py` → **один** файл, и он про продажи товара
(`backend/app/modules/products/shared/models.py`). Значит старшинство «бэкенд» не наступает,
источник истины — мок и клиент, второй уровень; так и записано в шапке.

Метка `Статус: спроектировано` **не поставлена**: код есть и во фронте, и в моке. Проверено и
машиной — спека печатает `спроектировано впрок: 0`, а её парсер (`isPlanned`) требует строку,
начинающуюся с `Статус:` после заголовка; единственное упоминание метки в файле стоит **до**
заголовка и внутри фразы, поэтому за метку не читается.

Строка `Бэкенд:` у раздела есть (`grep -n "^Бэкенд:"` → одна строка) — со словами «модуля нет» и
доказательством, а не «не реализован»: «не реализован» означало бы, что модуль есть, а роута нет.

Удалённое из старого контракта: удалять было нечего, и это замерено —
`grep -c "^### .*sales-crm" roo_code/roo-context/03-api-contract.md` → **0**,
`grep -c "api/sales-crm"` → **0**, `grep -c "CRM"` → **1** (строка 235, про фича-флаги, в блоке
общих соглашений). **Инверсия:** `grep -c "^### "` по монолиту → **132**, то есть паттерн
заголовка рабочий и просто не находит этот домен. Обе строки всё равно занесены в раздел «Чего в
домене нет» с доказательством — правило «ничего не вычеркнуто молча» действует и когда вычеркнуть
нечего.
