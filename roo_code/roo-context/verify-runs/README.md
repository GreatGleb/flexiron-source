# Журналы цикла проверок

Один файл на цель прогона: `<цель>.md` — например `warehouse-offcut.md`, `review-followups.md`.
Заводит его сам цикл из [`verify.md`](../../skills/verify.md) при первом прогоне по этой цели.

## Имя обязано называть СПИСОК, а не только номер пункта

`followups-8.md` — плохое имя, и это стоило потери. Планов с названием `review-followups.md`
уже два: закрытый в `plans/archive/2026-08/` и текущий в `plans/general/`. Нумерация пунктов у
них своя, и номера совпадают: «пункт 8» есть в обоих, «пункты 2, 7, 11, 12, 13» — тоже.

2026-08-30 журнал пункта 8 прошлого списка (581 строка, «страна справочником») был **затёрт**
журналом пункта 8 нового списка: файл писался через `cat >`, а он усекает молча. Восстановлено
из `git show <коммит>~1:<путь>`; будь правка не закоммичена — восстанавливать было бы нечего.

Отсюда два правила:

1. **Имя журнала содержит дату списка:** `followups-2026-08-29-8.md`. Дата берётся из заголовка
   плана, а не из дня прогона, — иначе два захода по одному пункту разъедутся по разным файлам.
2. **Перед записью проверить, что файла нет.** `cat > файл` затирает без вопроса и без следа в
   выводе. `test -e <путь> && echo ЗАНЯТО` — одна команда, и она отделяет новый журнал от чужого.

Зачем файл, а не контекст: номер итерации и список «рассмотрено» — единственное, что не даёт
циклу ходить по кругу. В контексте они теряются при перезапуске, и тогда лимит в 30 итераций
превращается в декларацию, а отклонённая находка возвращается как новая.

На каждую итерацию: номер, что запускалось (команда целиком), находки, что починено, состояние
линз. Запись «Л4 — чисто» без команды не считается — см. раздел «Что считается пройденной линзой».
