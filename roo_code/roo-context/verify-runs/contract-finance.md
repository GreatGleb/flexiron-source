# Прогон контракта: домен finance

Написан [`roo-context/api/finance.md`](../api/finance.md) по аудиту
[`plans/api/audit/finance.md`](../../plans/api/audit/finance.md). Код не тронут. Находки про код
лежали в [`contract-sync-finance-bugs.md`](../../plans/bugs/contract-sync-finance-bugs.md)
(БАГ-01…БАГ-11) с прошлой задачи; в этом прогоне добавлена **БАГ-12** — её нашла инверсия линзы К3,
и это единственная правка баг-файла.

Домен из пяти эндпоинтов; роутов у модуля `finance` ноль, поэтому источником истины по каждому из
пяти взяты мок и клиент, а схема из трёх таблиц учтена как ограничение. Метка
`Статус: спроектировано` не поставлена ни в одном разделе — код есть, отсутствует серверная часть, и
эту разницу несёт строка `Бэкенд: не реализован` в каждом из пяти разделов.

## Линзы К1–К7

### К1. Инвентарь: код ↔ контракт — сошлось
`npx vitest run src/services/contract-conformance.spec.ts` → 9 passed, 1 skipped; `finance=5` ушёл
из списка непокрытых, пропущенных эндпоинтов нет.

Формат глазами и грепом:
- `grep -n '^###' finance.md` → ровно **5** заголовков, и все пять проходят регекс спеки
  (`grep -c -vE '^[0-9]+:### (GET|POST|PUT|PATCH|DELETE) /api/\S*$'` по этому списку → 0);
- чужих домены в файле нет: `grep -E '^### ' | grep -vc '/api/finance/'` → 0;
- динамический сегмент не развёрнут: `grep -cE '^### .*payments/(pay-|[0-9])'` → 0. `:id` описан
  двумя разделами — `GET` и `PATCH`, — это разные методы, а не разные значения сегмента;
- строк, которые спека прочла бы как метку «спроектировано»
  (`grep -cE '^\*{0,2}Статус:\*{0,2}\s*спроектировано'`) → 0. Упоминания метки в прозе стоят не в
  начале строки и потому невидимы для `isPlanned`.

**Инверсия:** `### GET /api/finance/archive` → `### GET /api/finance/archived`, прогон спеки →
покраснели ровно два утверждения: «вызывается кодом, не описано в контракте: expected [Array(1)]»
и «описано в контракте, в коде нет — контракт не roadmap: expected [Array(1)]». Откат тем же `sed`
(не `git restore` — запрещён), заголовок на месте, спека снова зелёная.

- вызывающие: `grep -rn "'/api/finance\|\`/api/finance" src --include=*.ts --include=*.vue` без

- ветки мока: `grep -n "api\/finance" src/services/mocks/index.ts` → **пять**: `:823` receivables,

Пять ↔ пять: дыр нет (у каждой ветки есть вызывающий), сирот нет (у каждого вызова есть ветка).
Реестр «клиент написан, UI нет» домену не нужен: у всех пяти есть страница-потребитель.

**Инверсия:** счётчик не совпадает с чем угодно —
`grep -c "api/finance/payments'" src/services/mocks/index.ts` → 1, а
`grep -rc "/api/finance/invoices'" src` → 0, то есть несуществующий путь ветки не находит.

### К3. Коды ошибок — сошлось после правки, инверсия нашла находку
Что бросает мок домена: `grep -n "throw new Error" src/services/mocks/finance.ts` → **две** строки,
и обе `PAYMENT_NOT_FOUND` (`:428` чтение, `:475` правка). Больше домен не бросает ничего; каталог
контракта состоит из одной строки, и оба места в ней названы.

Каталог ядра (`awk 'NR>=13&&NR<=48' backend/app/core/exceptions.py | grep -oE '"[A-Z_]+"'`) →
`CONFLICT FORBIDDEN NOT_FOUND UNAUTHORIZED VALIDATION_ERROR`; ни один из пяти домен не бросает —
бросать негде, роутов нет.

Доходит ли код до человека: `grep -rn "ApiRequestError\|\.code" src/services/financeService.ts src/views/admin/finance/`
→ **пусто**. Подтверждает БАГ-06: все четыре страницы держат `error = ref(false)`.

`DOCUMENT_NOT_FOUND` из старого каталога: `grep -rn "DOCUMENT_NOT_FOUND" backend/app frontend_vue/src`
→ **0**. В репозитории он выживает только в документах сверки, и строка об этом стоит в «Чего в
домене нет».

**Инверсия — и она сработала не в мою пользу.** Подстрочный детектор прогнан на подложном наборе
`PAYMENT_NOT_FOUND / NOT_FOUND / FOO`, он честно поймал `NOT_FOUND`. После этого тот же детектор
прогнан на настоящих данных — и выяснилось, что **ядровый `NOT_FOUND` действительно является
подстрокой `PAYMENT_NOT_FOUND`**, то есть требование §2 соглашений («ни один код не подстрока
другого») каталогом домена не выполнено. Аудит утверждал обратное
(`plans/api/audit/finance.md:58` — «Подстрокой ни в кого не входит»): сравнение делалось только с
доменными кодами соседей, каталог ядра в него не попал.

Записано находкой **БАГ-12** и первым фактом раздела «Каталог кодов ошибок домена». Решение о том,
какой из двух кодов уступает, контракт не принимает — своей строки у этого вопроса нет ни в файле
решений владельца, ни в §2 соглашений, и это сказано прямо.

### К4. Формы запроса и ответа — сошлось
Все тринадцать типов, названных контрактом, найдены грепом
(`grep -rn "export \(interface\|type\) <Имя>" src/types/`): десять в `types/finance.ts`, три в
`types/api.ts`.

Пофайловая сверка полей — скриптом, а не глазами: он читает интерфейсы из `types/finance.ts` и
блоки ```ts``` из контракта, требует, чтобы **каждое** поле типа было названо в блоке, и сравнивает
множества nullable-полей:

```
FinancePayment: полей 19; не упомянуто —; nullable тип и контракт совпали (6) OK
FinancePaymentListItem: полей 12; не упомянуто —; nullable совпали (3) OK
Receivable: полей 14; не упомянуто —; nullable совпали (1) OK
FinanceDocumentArchiveItem: полей 12; не упомянуто —; nullable совпали (0) OK
итог: чисто
```

**Поправка к аудиту, найденная этим счётом:** аудит называет у `FinancePayment` «двадцать полей», а
у строки списка «одиннадцать». В коде их **19** и **12**
(`sed -n '15,35p' src/types/finance.ts | grep -cE '^  [a-zA-Z]+\??: '` → 19, то же для `:37-50`
→ 12). В контракте стоят проверенные числа, а расхождение записано строкой в «Пробелах аудита».

**Инверсии (две, на копиях в памяти, файл не тронут):** убрал поле `notes` из блока
`FinancePayment` → скрипт вернул `('FinancePayment', ['notes'], {'notes'})`; снял `| null` у
`paidAt` в блоке `Receivable` → `('Receivable', [], {'paidAt'})`. На настоящем файле — «чисто».

## Что осталось несделанным сознательно

- **аудит соседа не поправлен.** Аудит notifications приписывает `settingsService.ts` пару
  `Authorization` + `X-CSRF-Token`; второго заголовка там нет (`authHeaders()` возвращает один
  ключ, `services/settingsService.ts:18-22`; `X-CSRF-Token` во всём `frontend_vue/src` встречается
  однажды — `composables/useAuth.ts:106`). Наблюдение записано в контракт и в БАГ-01, но чужой файл
  правкой не тронут: он не входит в разрешённые этой задачей;
- **строки владельцу не дописаны.** У БАГ-12 своей строки в `00-решения-владельца.md` нет, и
  завести её эта задача не вправе — файл вне разрешённых. Вопрос назван в самой находке;
- **машинной проверки у К6 по-прежнему нет.** Скрипт этого прогона считает графы и ссылки, но
  живёт во временном файле, а не спекой в дереве; завести её — работа задачи о спеках К2–К4, К6.
