`auto/contract-2026-09-04`. Дата: 2026-09-04.

Вход домена по аудиту: эндпоинтов **12**, источник истины бэкенд у **0**, решений владельцу **14**,

## Итерация 1

### Машинная приёмка

```

```

До появления файла было `сведено доменов: 1 · описано эндпоинтов: 5 из 175` и `config=12` в списке
несведённых. Спека включила домен автоматически, как и обещал храповик.

### К1. Инвентарь: код ↔ контракт

**Чем:** `npx vitest run src/services/contract-conformance.spec.ts` плюс свой разбор формата.

```
9 passed | 1 skipped — ни одного пропущенного эндпоинта у сведённых доменов
свой разбор: разделов ### <МЕТОД> /api/… = 12; у каждого есть строка «Реализация:» и «Бэкенд:»
```

Двенадцать заголовков ровно те, что даёт инвентарь кода: `GET/PUT/POST /api/config/fields`,
`PATCH/DELETE /api/config/fields/:id`, те же пять у `/sections`, `GET/PUT /api/config/permissions`.
Динамический сегмент не развёрнут: `:id` — один раздел на путь, значения (`f-company`,
`f-custom-<ts>`, `sec-general`, `sec-new-<ts>`, UUID на схеме) перечислены прозой внутри.

**Инверсия:** удалил в копии одну строку `Бэкенд:` — проверка покраснела ровно на
`### GET /api/config/fields`, остальные одиннадцать остались зелёными.

**Вывод:** пройдена.

### К2. Мок ↔ контракт ↔ код

**Чем:**

```
grep -nE 'api\\/config|api/config' frontend_vue/src/services/mocks/index.ts   → 12 ветвей
  (411,412,413 GET · 943,946 POST · 1158,1162,1166 PUT · 1220,1229 PATCH · 1476,1482 DELETE)
grep -c "api/config" frontend_vue/src/services/configService.ts               → 12 вызовов
```

Двенадцать ветвей ↔ двенадцать описанных эндпоинтов ↔ двенадцать вызовов клиента: ни дыры (ветка
есть у каждого зовущегося), ни сироты (вызывающий есть у каждой ветки).

Шесть клиентских функций из двенадцати не имеют вызывающего в UI — это реестр «Клиент написан, UI
нет» в контракте, а не сирота мока. Замерено по каждой:

```
patchField / createSection / patchSection / deleteSection  → 0 попаданий вне configService.ts
createField → 3, deleteField → 4  — но это ОДНОИМЁННЫЕ ЛОКАЛЬНЫЕ функции чужих экранов
  (SupplierCardConfigPage.vue:309 — пушит в fieldLibrary; useCategoryCard.ts:142 — чужой домен)
```

**Инверсия:** `grep` по выдуманному пути `api/config/widgets` в `mocks/index.ts` → `0`, то есть
экстрактор не отвечает «есть» на что угодно.

**Вывод:** пройдена.

### К3. Коды ошибок

**Чем:**

```
grep -c "throw" frontend_vue/src/services/mocks/config.ts        → 0
grep -c "throw" frontend_vue/src/services/configService.ts       → 0
grep -c "throw" frontend_vue/src/composables/useCardConfig.ts    → 0
grep -rnoE "'[A-Z][A-Z_]{3,}'" (три файла домена) | wc -l        → 0
grep -rn "IMMUTABLE" frontend_vue/src backend/app | wc -l        → 0
```

**В домене нет ни одного кода ошибки** — четыре независимых замера. Значит правило «ни один код не
подстрока другого» выполняется пусто, а «каждый код доходит до человекочитаемого сообщения» не
применимо: доходить нечему. Каталог раздела в контракте состоит из этого факта и таблицы четырёх
отказов, которых код не умеет, а схема или вёрстка требуют (дубль имени поля, встроенное поле,
системная секция, неизвестный `id`) — с указанием, чем требование доказано, и с пометкой «кода
нет». Какими кодами их закрыть — строка владельцу, не решение контракта.

Бэкендного каталога у домена нет: `grep -rn '@router\.' backend/app | grep -c config` → `0`, то
есть старшего источника кодов не существует.

**Инверсия:** тот же приём в соседнем домене даёт код —
`grep -c "AUDIT_ENTRY_NOT_FOUND" frontend_vue/src/services/mocks/suppliers.ts` → `1`. Ноль в
`config` — свойство домена, а не сломанный греп.

**Вывод:** пройдена.

### К4. Формы запроса и ответа

**Чем:** скрипт-сверка контракта с `types/config.ts` по каждому интерфейсу.

```
типы, названные в контракте, существуют в types/config.ts: 7 из 7
  (FieldDefinition, SectionConfig, SectionField, PermissionMatrix, PermissionItem,
   PermissionAction, FieldType)
поля каждого интерфейса упомянуты в контракте, не упомянутых — 0:
  FieldDefinition 7/7 · SectionConfig 7/7 · SectionField 3/3 · PermissionMatrix 5/5 · PermissionItem 4/4
значения замкнутых типов, не упомянутых — 0:
  FieldType 6/6 (enum, number, text, date, boolean, tags) · PermissionAction 4/4 (read, edit, create, delete)
опциональность перенесена буквально: hidden?, options?, system?, parentId? — все четыре есть в контракте
```

Регистр не «поправлен по привычке»: фронт домена целиком `camelCase`, схема — `snake_case`, и
контракт называет обе формы там, где они расходятся, а не сводит их к одной.

Второй половины линзы («сверять со схемами бэкенда») у домена нет по построению: модуля нет. Но
таблицы есть, и колонки, которые контракт называет, проверены поимённо:
`field_type`, `is_builtin`, `usage_count`, `options`, `uq_field_definitions_tenant_name`,
`name_translations`, `sort_order`, `collapsed`, `visible` (suppliers);
`name_translations`, `can_read/can_edit/can_create/can_delete`, `uq_role_permission`,
`uq_user_permission`, `role_name` (auth) — все находятся. И три колонки, отсутствие которых
контракт утверждает, действительно отсутствуют: `"system"` в миграции → `0`, `created_by` в обоих
файлах моделей → `0`.

**Инверсия:** выдуманное поле `usageTotal` в `types/config.ts` → не найдено, то есть сверка не
зелёная на любой строке.

**Вывод:** пройдена.

### К5. Источник истины

**Чем:**

```
grep -rn '@router\.' backend/app --include=*.py | grep -c config   → 0   (всего роутов 31)
grep -rn '@router\.' backend/app --include=*.py | grep -c settings → 24  (инверсия: греп работает)
строк «Статус: спроектировано» в файле контракта                   → 0
строк «Бэкенд:» у разделов                                         → 12 из 12
```

Старшинство соблюдено по каждому эндпоинту: реализации бэкенда нет ни у одного из двенадцати,
значит источник — мок и клиент, и так написан каждый раздел. Метка «спроектировано» **не поставлена
нигде намеренно**: она про отсутствие кода вообще, а у всех двенадцати клиент и мок есть, нет только
серверной части — и это выражено строкой `Бэкенд: **не реализован**`. Спека это подтверждает с
другой стороны: `спроектировано впрок: 0` и утверждение «метка снимается, когда эндпоинт появился в
коде» зелёное.

Удаляемое из прежнего контракта не вычеркнуто молча: раздел «Чего в домене нет» — **16 строк**,
каждая с тем, что было описано, и с тем, чем опровергнуто. Эндпоинтов, описанных прежде и
отсутствующих в коде, у домена **нет ни одного**: `grep -n "^### .*api/config"` в
`03-api-contract.md` даёт ровно девять заголовков (622, 631, 638, 646, 652, 661, 668, 676, 685), и
все девять путей живы.

**Вывод:** пройдена.

Ни одной пустой графы. Строки с ответом «нигде» вынесены в

индекса начинаются с арендатора. Это записано как обязанность, а не как вопрос.

**Вывод:** пройдена.

Три части, каждая своим замером.

грепом, и цитируемая строка — та самая:

getSections:46 · saveSections:51 · createSection:55 · patchSection:67 · deleteSection:71 ·

**(б) Относительные ссылки** — резолв по файловой системе: 16 уникальных markdown-ссылок, битых 0.
Инверсия: заведомо выдуманный путь `../../plans/api/audit/nope.md` не существует, то есть проверка

**(в) Инлайновые `файл:строка`** — их в разы больше, и именно на них держатся «Обязанности

```

**Проход (в) нашёл шесть настоящих битых ссылок, и это единственные находки цикла — все про мой

**Вывод:** пройдена после починки шести ссылок.

## Находки этого цикла

Все шесть — дефекты моего текста, найденные линзой К7. Кода они не касаются, поэтому в
баг-файл домена не идут. Ключ дедупликации `файл:символ:тип`.

| № | что было | чем поймано | как исправлено |
|---|---|---|---|
| 1 | `SupplierCardConfigPage.vue:166-169` под утверждением «`getUserPerm` откатывается на роль» — самого имени в диапазоне нет, оно на `:160` | токен-проверка: `sed -n '166,169p' … \| grep -c getUserPerm` → `0` | диапазон расширен до `:160-169`; дополнительно проверено, что `getRolePerm` в `:166-169` есть |
| 2 | `03-api-contract.md:626` под примером `"name": "Company"` | строка `:626` — это `` ```json ``, пример на `:627` | `:627` |
| 3 | `03-api-contract.md:642` под «`type` менять нельзя» | утверждение на `:641` | `:641` |
| 4 | `03-api-contract.md:654` под «отсортированный по `order`» | утверждение на `:655` | `:655` |
| 5 | `03-api-contract.md:656` и `:680` под примерами `"name": "Status"` | примеры на `:657` и `:681` | `:657`, `:681` |
| 6 | фраза «`grep -n "api/config" …` даёт девять заголовков» — этот греп даёт **24** попадания, девять из них заголовки | сам греп: 32, 267, 622, 631, 638, 643, 646, 652, 661, 668, 671, 673, 676, 685, 811-815, 3029-3034 | команда уточнена до `grep -n "^### .*api/config"`, а прочие попадания названы и разобраны |

Отдельно — **поправка к аудиту**, найденная при написании раздела `GET /api/config/permissions`:
элементов матрицы **семнадцать**, а не шестнадцать. Аудит пишет «5 секций + 11 их полей = 16 items»;
замер по коду:

```
awk 'NR>=114 && NR<=177' src/services/mocks/config.ts | grep -cP "^    id: 'sec-"      → 5
awk 'NR>=114 && NR<=177' src/services/mocks/config.ts | grep -oP "fieldId: '\K[^']+" | wc -l  → 12
```

5 + 12 = 17. В контракте стоит 17 с этим замером и с явной оговоркой, что цифра аудита поправлена.
Это ошибка счёта в аудите, а не дефект кода, поэтому в `contract-sync-config-bugs.md` она не идёт.

### Рассмотрено и отклонено

| что | почему не находка |
|---|---|
| «`Бэкенд:` не нужен — модуля `config` нет, хватило бы метки о статусе» | метка «спроектировано» здесь была бы **неверна**: она про отсутствие кода вообще, а у всех двенадцати клиент и мок есть. Строка `Бэкенд:` — единственный способ отличить «сервер это уже делает» от «серверу это предстоит», и промпт задачи требует её у каждого раздела |
| «схема хранения — это бэкенд, значит старшинство наступило» | старшинство даёт **реализация эндпоинта**, а не таблица: `grep -rn '@router\.' backend/app \| grep -c config` → `0`. Схема учтена как ограничение формы и как источник шести расхождений, но источником истины не объявлена |
| «в домене нет кодов ошибок — надо назначить» | назначение кода — решение, а не наблюдение; автономный режим его запрещает. Оставлено таблицей четырёх отказов плюс строкой владельцу |
| «шесть функций без вызывающего — удалить из контракта» | клиент их уже определил, формы запроса и ответа существуют; удаление описания не убирает код. Оставлены разделами плюс реестром «Клиент написан, UI нет»; то, что их шесть, — БАГ-05, уже записан |
