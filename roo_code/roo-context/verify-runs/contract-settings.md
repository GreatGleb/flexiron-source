Задача: превратить проверенный аудит в контракт. Код заново не читался — только те места, где
аудит оставлял вопрос или где проверка ссылки требовала посмотреть в файл.

Вход: 31 эндпоинт, у 24 источник истины — бэкенд, 17 решений владельцу, 21 находка про код.
Выход: 31 раздел, 0 меток «спроектировано», 10 строк «осталось», 685 инлайновых ссылок.

## Свип линз К1–К7

Итерация одна: приёмка зелёная с первого прогона, находки свипа были в тексте контракта, а не
в коде, и правились в том же проходе. Второй свип после правок новых находок не дал.

### К1 — инвентарь: код ↔ контракт

Чем проверял — временная спека `src/services/__k2_settings.spec.ts` поверх
`contractInventory.ts` (после снятия показаний удалена, дерево чистое):

```
✓ код и контракт совпадают ровно            — toEqual по отсортированным спискам
✓ эндпоинтов ровно 31
✓ все разделы лежат в settings.md
✓ ни одного «спроектировано»
```

Что вернулось: 31 = 31, ни одного пропущенного, ни одного лишнего, все разделы в своём файле.

**Инверсия:** `toBe(31)` → `toBe(30)` и `be.size toBe(24)` → `toBe(23)` — покраснели ровно эти
два утверждения (`AssertionError: expected 31 to be 30`, `expected 24 to be 23`), остальные пять
остались зелёными. То есть проверка считает, а не выглядит считающей.

Правила формата шага 3 — своя структурная проверка по тексту: 31 заголовок вида
`### <МЕТОД> /api/...`, у каждого есть `Бэкенд:` и `Реализация:`, ни одной метки
«спроектировано»; динамический сегмент нигде не развёрнут в заголовки (`:id` встречается
заголовками ровно у восьми путей коллекций, значения перечислены внутри разделов).
**Инверсия:** убрал одну строку `Бэкенд:` в копии текста — проверка вернула «разделов без
`Бэкенд:` → 1».

### К2 — мок ↔ контракт ↔ код

Чем проверял — `scanMockRoutes()` и `scanCode()` из того же инвентаря, пересечение по домену:

```
✓ у каждого эндпоинта есть ветка мока                   — 31 из 31, дыр нет
✓ у каждой ветки мока есть вызывающий, кроме двух       — ['GET /api/settings', 'PUT /api/settings']
```

Что вернулось: две сироты, ровно те, что названы в `00-conventions.md` для этого домена.
Проверил, что это действительно сироты, а не потеря экстрактора:
`grep -rn "'/api/settings'" frontend_vue/src --include=*.ts --include=*.vue` вне моков пуст, а в
`settingsService.ts` функций чтения и записи всего среза настроек нет (весь файл прочитан). Обе
записаны в «Чего в домене нет».

### К3 — коды ошибок

Чем проверял — скрипт по `mocks/settings.ts` и по всем `.py` модуля: собрать коды, сверить с
каталогом контракта, проверить отношение «подстрока».

Что вернулось:

```
заглавные токены в mocks/settings.ts: CONVERSION_NOT_FOUND CURRENCY_NOT_FOUND MAIL_NOT_CONFIGURED
  MAP_NOT_AN_IMAGE MOCK_MAIL_PASSWORD MOCK_MAIL_SEED MOCK_SETTINGS ORDER_STATUS_NOT_FOUND UOM_NOT_FOUND
классы исключений в модуле: ConflictError ForbiddenError NotFoundError ValidationError
кодов не описано в контракте: MOCK_MAIL_PASSWORD MOCK_MAIL_SEED MOCK_SETTINGS
код-подстрока другого кода: NOT_FOUND ⊂ {CURRENCY,UOM,CONVERSION,ORDER_STATUS}_NOT_FOUND
```

Два разбора:

- три «неописанных кода» — ложные срабатывания экстрактора: `MOCK_MAIL_SEED:28`,
  `MOCK_MAIL_PASSWORD:38`, `MOCK_SETTINGS:40` — это имена констант сида, а не коды. Прочитал
  места, не коды;
- **отношение «подстрока» настоящее, и мой первый текст утверждал обратное.** Написано было «ни
  один код не является подстрокой другого» — неверно: серверный `NOT_FOUND` содержится во всех
  четырёх мок-кодах коллекций. Формулировка исправлена на точную, с доказательством, почему это
  сегодня безобидно: в домене никто не читает `e.code` вообще —
  `grep -rn "\.code" useSettings.ts useWarehouseMap.ts views/admin/settings/` даёт только
  `Currency.code` и `Uom.code`. Заодно поправлена ссылка на подстрочное сравнение: оно в
  `orderLineEdits.ts:418` (`message.includes(code)`), а не в диапазоне словаря `:337-360`, как
  цитируют общие соглашения.

`ForbiddenError` в модуле есть ровно один — удаление системного статуса; в каталоге отражён.

### К4 — формы запроса и ответа

Чем проверял — прочитал целиком `crud/schemas.py` (219 строк) и `profile/schemas.py`, свёл
пофайлово с типами `types/settings.ts`; отдельно выписал номера строк каждого класса и каждого
поля и сверил с каждой цитатой контракта.

Что вернулось: все 18 цитат схем попадают в свои классы. Три уточнения внесены в текст:

- `CurrencyResponse` начинается на `:67`, а не на `:65` (в 65 — комментарий-разделитель) —
  диапазон сужен;
- `OrderStatusResponse` отдаёт `system` и оба флага перехода **всегда**, с дефолтом `False`
  (`crud/schemas.py:183-185`), тогда как в типе фронта все три необязательные
  (`types/settings.ts:92-97`). Для сервера это обязанность присылать их, и она теперь названа;
- минимальная длина нового пароля — **шесть** символов (`profile/domain.py:130-133`), это
  единственное ограничение длины пароля в проекте. В контракте стояло безличное «слишком
  короткий».

Расхождение с типом фронта одно и оно из аудита: `exchangeRate` у валюты (`crud/schemas.py:73`,
обязателен при создании — `:85`), решение владельца, БАГ-05.

### К5 — источник истины

Чем проверял — `scanBackend()` по домену плюс структурная проверка строк `Бэкенд:`.

```
✓ роутов бэкенда 24, и все они среди вызываемых кодом   — бэкенд ни разу не ушёл вперёд
строк «Бэкенд: не реализован»: 7 | со ссылкой на файл: 24   (7 + 24 = 31)
```

Семь «не реализован» — три эндпоинта карты склада, два почтовых, тест почты, права заказа; у
каждого сказано, чем именно доказано отсутствие (нет модели, нет роута, тип в чужом модуле не
конструируется). Метку «спроектировано» не поставил ни разу и это правильно: у всех семи есть
клиент и мок, то есть код существует — отсутствует серверная часть, а не код.

**Отдельно проверил спорное место аудита — «восемь роутов не требуют токена».** Первый,
слишком широкий греп (`grep -c Depends`) дал по 1 попаданию в каждом из восьми диапазонов, то
есть выглядел опровержением. Прочитал подписи: это `Depends(get_db)`. Точный токен:

```
$ for r in 252-257 266-270 320-325 334-338 399-404 413-418 468-473 482-487; do … grep -c '_resolve_user_id'
252-257: 0 …  482-487: 0        (все восемь — ноль)
$ sed -n '146,156p' crud/action.py | grep -c '_resolve_user_id'   → 1   (инверсия: у GET он есть)
```

Заодно уточнил формулировку про мидлвар: единственный `add_middleware` во всём бэкенде — CORS
(`core/middleware/cors.py:9`, подключение `main.py:58`), а не «main.py подключает только CORS»
(он подключает ещё статику и девять роутеров).

### К6 — обязанности сервера

Чем проверял — скрипт по разделу: девять граф по именам плюс длина раздела.

```
граф найдено: 9 из 9; отсутствуют: []
длина раздела обязанностей, символов: 7400

Каждая графа — наблюдение с `файл:строка`; ответ «нигде» вынесен строкой владельцу, и таких

греп по трём деревьям), а не пропущена.

### К7 — ссылки и следы реализации

Чем проверял — скрипт-резолвер по всему файлу: относительные markdown-ссылки резолвом по
файловой системе, инлайновые `файл:строка` — существованием файла и попаданием диапазона в его
границы, с протяжкой контекста для сокращённых `:NNN`.

```
markdown-ссылок: 11  битых: 0
инлайновых файл:строка проверено: 685; нерезолвленных: 0; вне диапазона файла: 0
```

**Инверсия резолвера** — подсунул файл с четырьмя заведомо битыми ссылками
(`.../NOPE.md`, `crud/action.py:99999`, `nosuch/file.ts:3`, `crud/action.py:5-1`): вернул 1 битую
ссылку, 1 нерезолвленную, 2 вне диапазона. То есть резолвер краснеет.

**Границы файла — недостаточная проверка, поэтому вторым проходом — токен внутри диапазона.**
261 утверждение, выписанное вручную по всем разделам («что именно я утверждаю этой ссылкой»),
проверено регуляркой по срезу строк:

```
утверждений проверено: 261; подтверждено токеном в диапазоне: 261; НЕ подтверждено: 0
```

С первого прогона было **семь** неподтверждённых, и три из них — настоящие дефекты ссылок, а не
слабость регулярки:

| ссылка | что было не так |
|---|---|
| `types/settings.ts:29-39` для «добавлен `time`» | `'time'` лежит на **:40**, за границей диапазона. Именно тот класс дефекта, на котором домен `categories` потерял две попытки. Исправлено на `:31-40`, а в правиле №8 — на `:39-40` |
| `useSettings.ts:217-237` для «`fetchAllSections()`» | имени функции в диапазоне нет — она объявлена на **:213**; в 217-237 лежат её девять вызовов. Разведено: `:213` для функции, `:217-237` для девяти запросов |
| `crud/domain.py:469` для «`is_system=False`» | в коде литерал `"is_system": False` (ключ словаря), а не присваивание. Текст приведён к тому, что в коде |

Остальные четыре были слабостью моей регулярки, и каждое утверждение подтверждено чтением места:
`models.py:44-55` (опечатка в пути самой проверки), `crud/domain.py:129-131` (автосоздание —
токен `create_constants`), `profile/domain.py:130-133` и `:136-137` (сообщения «at least 6
characters» и «Passwords do not match»).

**Инверсия второго прохода.** Автоматический сдвиг диапазона обязан давать 0. Из 261 сдвиг дал
ноль у 241. Из оставшихся 20: у **семи** сдвиг вообще не состоялся — диапазон упёрся в конец
файла (не инверсия, а её отсутствие), у **тринадцати** сдвинутый диапазон тоже дал попадание,
потому что токен в файле встречается не раз (`_resolve_user_id` — и объявление, и вызовы;
`authHeaders` — в каждой функции сервиса; `warehouseMap` — во всех трёх функциях карты). Для
каждого нагруженного случая из этих тринадцати сделана ручная инверсия с осмысленным сдвигом, и
все дали ноль — например:

```

types/settings.ts:31-40    /'time'/                        → 1   инверсия 17-26   → 0
useSettings.ts:213         /fetchAllSections/              → 1   инверсия 199     → 0

## Пробелы аудита: 31 из 31 закрыт или помечен

Каждая строка `- Пробел контракта:` аудита (их ровно 31, по одной на эндпоинт) прошла сверку с
текстом контракта. Закрыты в тексте 31 из 31; из них десять несут внутри строку **«Осталось»** —
там, где правила нет ни в коде, ни у владельца, и назначить его значило бы принять решение:

1. порядок выдачи валют не назначен;
2. порядок выдачи единиц не назначен;
3. чем ограничена смена категории единицы;
4. порядок выдачи правил пересчёта не назначен;
5. уникальность имени статуса и валидация цвета;
6. каким кодом отвергать неполный или чужой список в `reorder`;
7. как стирается пароль почты;
8. какие поля почты сервер обязан валидировать;
9. судьба вытесненного файла карты при `PUT`;
10. то же при `DELETE`.

Две находки аудита, которых нет в баг-файле домена (в нём 21 запись, и это другое множество из
21), закрыты по своей природе, а не пропущены:

- **находка 9** — константы не валидируются нигде (`crud/domain.py:140-170` валют не касается).
  Это отсутствующее правило, а не дефект: обещание прежнего контракта снято строкой в «Чего в
  домене нет», а введение правила — решение владельца (строка «какой из двух источников валюты
  по умолчанию главный»);
- **находка 15** — у `PATCH /api/settings/uoms/:id` нет вызывающего. По `00-conventions.md` §20
  это реестр «Клиент написан, UI нет», и раздел под него в контракте есть.

Код не тронут: `git status` по `frontend_vue/src` и `backend/` чист, временная спека К1/К2
удалена после снятия показаний.
