## Итерация 1 — воспроизведение

### Замер: два дефекта, заявленных планом, — подтвердился ОДИН

Пробный спек `tmp-probe.spec.ts` (создан, отработал, удалён), `--workers=1`.

**Дефект 1 «счётчик меняется до данных» — ПОДТВЕРЖДЁН.** Опрос каждые 10 мс после клика
«вперёд» на вкладке движений:

```
PROBE-B: counter changed at T+155.2ms, first row changed at T+479.7ms
```

Разрыв ~325 мс. Ожидание `expect(info).not.toHaveText(shown)` отдавало управление на T+155,
и `evaluateAll` следующей итерации читал строки ПРЕДЫДУЩЕЙ страницы.

**Дефект 2 «`not.toHaveText(innerText)` истинно ВСЕГДА» — НЕ ВОСПРОИЗВОДИТСЯ на этом месте.**
Проверено прямо: то же утверждение, но БЕЗ единого клика.

```
PROBE innerText   = "1-25 of 189"
PROBE-A: Error: expect(locator).not.toHaveText(expected) failed
         Expected: not "1-25 of 189"   Received: "1-25 of 189"   Timeout: 3000ms
```

Утверждение упало, то есть строки совпали, то есть оно НЕ всегда истинно.

Почему план ошибся — установлено, а не угадано. Коды символов:

```
PROBE-D innerText   codes: 31 2d 32 35 a0 6f 66 a0 31 38 39     («1-25 of 189»)
PROBE-D textContent codes: 31 2d 32 35 a0 6f 66 a0 31 38 39
```

Ни табов, ни переносов: `.pagination-info` — это `div` с тремя **строчными** `span`, а
`innerText` вставляет перенос только между блочными боксами. Nbsp стоит по обе стороны
сравнения и потому не мешает.

Само правило при этом ВЕРНО — проверено отдельно на синтетическом узле с блочными детьми:

```
PROBE-E innerText codes: 61 6c 70 68 61 a 62 65 74 61          («alpha\nbeta»)
PROBE-E toHaveText(innerText with \n): DID NOT MATCH (expected side NOT normalized)
```

То есть Playwright нормализует пробелы у ПОЛУЧЕННОГО значения и не нормализует у
ожидаемого. Строка таблицы (`<tr>`, innerText через табы) под это попадает — там дефект
настоящий, и он верно записан в `cutting.spec.ts`. `.pagination-info` — нет.

**Вывод:** правило #68 остаётся, его привязка к ЭТОМУ месту снимается. Записи поправлены
(см. ниже). Чинить нужно было ровно дефект 1 — и его хватает.

### Побочно замерено

`PROBE-C`: страниц 8, первых строк 8, все различны. То есть первая строка — годный признак
на всём пути, а не только на первом шаге.

## Итерация 2 — доказательство инверсией (Л9)

Инверсия — сломать серверную постраничность: `src/services/mocks/index.ts`, обработчик
`/api/warehouse/movements`, `const page = Number(params?.page ?? 1)` → `const page = 1`.

**Первая попытка инверсии была пустой, и это важно.** Сначала я сломал `paginate()` в
`tests/e2e/mocks/warehouse.ts` — оба варианта теста остались зелёными. Причина: приложение
на 5173 поднято с `VITE_USE_MOCKS=true` (`.env`), мок-слой отвечает В ПРОЦЕССЕ, сетевого
запроса нет, и `page.route(**/api/warehouse/movements**)` не срабатывает ни разу. Инверсия,
которая ничего не ломает, доказательством не является — её надо было заметить по тому, что
покраснеть обязан был хотя бы кто-то.

Инверсия в настоящем источнике, оба варианта теста рядом (старое ожидание — точной копией
в `tmp-old.spec.ts`, удалён после):

| ожидание | под сломанной постраничностью |
|---|---|
| старое, по счётчику | **1 passed** — слепо |
| новое, по первой строке | **1 failed** на `expect.poll(...).not.toBe(firstBefore)` |

Инверсия снята, обработчик возвращён к исходному виду (`git status` — в дереве только спек).

## Итерация 3 — свип

| проверка | команда | результат |
|---|---|---|
| машинная приёмка | `npm run verify` | exit 0 · typecheck · lint · dupes · format · 751 unit |
| e2e, уровень 1 | `npx playwright test tests/e2e/admin/warehouse/ --workers=3` | exit 0 · **93 passed** (1.9 мин) |

Уровень 1, а не 2: правка лежит в одном спеке, общего пола (`helpers/`, фикстуры,
диспетчер моков) не касается. Круг «кто читает тот же мок» — каталог складских спеков,
он прогнан целиком.

**Линзы.** Область — один тест, поэтому применимы Л9 и машинная часть остальных.

- **Л9** — инверсия проведена, таблица выше. Ожидание, которое проверяет действие, теперь
  падает без действия; старое не падало. Плюс греп общего пола:
  `grep -rn "await page.waitForLoadState" tests/` → пусто (0 строк);
- **Л5, второй экземпляр правила** — и здесь я сначала записал вывод, которого не измерял
  («вхождений больше нет»), а греп дал **9**. Разобраны все, пробным спеком, а не глазами:

  | место | как снят эталон | `toHaveText(снятое)` совпадает? |
  |---|---|---|
  | `categories.spec.ts:450,454,455` | `textContent()` + `.trim()` | ДА — утверждение настоящее |
  | `audit-log.spec.ts:134` | `textContent()`, без trim | ДА — утверждение настоящее |
  | `clients.spec.ts:297` | `textContent()`, без trim | ДА — утверждение настоящее |
  | `order-offcuts.spec.ts:56,57` | литерал `'—'` | сравнения со снятым нет |
  | `cutting.spec.ts:205,208` | текст комментария | не код |

  Ни одного повтора дефекта: `textContent()` не вставляет переносов от раскладки, в
  отличие от `innerText()`, и все три снятые строки вернулись без единого пробела по краям
  (коды символов в прогоне). Смысловая часть тоже чиста: надпись кнопки после смены языка,
  серверный `total` ленты и ячейка строки — все три меняются только вместе с данными.

  Отдельно проверено, не ждёт ли кто-нибудь ещё по счётчику: `grep -rn "pagination-info" tests/`
  → 3 места (`suppliers-list`, `clients`, `cutting`), и все три **утверждают** содержимое
  счётчика или читают из него итог, ожиданием он не служит нигде;
- **Л1, Л2, Л3, Л4, Л6, Л7, Л8, Л10** — правка не трогает `src/`, кроме временной инверсии,
  которая снята и проверена `git status`. Подтверждены зелёной машинной приёмкой и полным
  прогоном складских спеков.
