# Прогон контракта: домен services

## Попытка 1 — ОТКЛОНЕНА (2026-09-04)

Коммит попытки: `964235d` — откачен ревертом `6f6de48`.

**Причина отклонения: в разделе «Клиент написан, UI нет» напечатана команда проверки вместе
с её результатом, и результат неверен — недосчитан файл.**

### Находка 1 (главная) — реестр потребителей недосчитал файл

Контракт печатает:
`grep -rln "servicesService" frontend_vue/src/views frontend_vue/src/composables` → **три
файла** (`useServices.ts`, `useServiceCard.ts`, `AddOrderServicesModal.vue`).

Настоящий вывод той же команды — **четыре** файла. Пропущен
`frontend_vue/src/views/admin/products/ServicesPage.vue`
(`:6: import { createService } from '@/services/servicesService'`).

Это внутреннее противоречие внутри одного абзаца: двумя предложениями выше тот же абзац
называет `ServicesPage.vue` экраном-потребителем списка, создания и удаления — а в перечне
доказательства его нет. Автор сам в К2 считал `createService` = 2 вызывающих, то есть про
`ServicesPage.vue` знал: строку не перепроверяли после написания.

Вывод раздела («реестр пуст, у каждого из пяти экспортов есть вызывающий») подтверждён
независимо и верен. Отклонение — за ложное доказательство под верным выводом. Ровно на этом
классе (перепутанный или недосчитанный вывод грепа, привязка внутри пары) отклонили
`categories` — см. [`contract-categories.md`](contract-categories.md).

### Находка 2 (мягкая) — «шестой потребитель»

Во вступлении `AddOrderServicesModal.vue` назван «шестым потребителем», хотя в перечисленном
там же списке он пятый файл.

### Находка 3 (мягкая) — неверная формулировка про мок

Заявлено: «мок не смотрит на `name` вовсе (`mocks/services.ts:95-130`)». Мок читает
`data.name` на `:106-107`. По смыслу речь о валидации (её действительно нет), но буквально
формулировка неверна.

### Почему дожило до приёмки

`npm run verify` сверяет инвентарь эндпоинтов, а не напечатанные в тексте выводы команд.
Линзы К1–К7 у автора считали вызывающих по экспортам (и там счёт был верный), но не
перепроверяли строку реестра, написанную отдельно от этого подсчёта.

Следующей попытке: любую напечатанную в контракте команду **прогнать заново перед сдачей** и
сверить её вывод с текстом посимвольно; счётные слова («три файла», «шестой») сверять со
списком, который стоит рядом.

### Что проверено и сошлось

- приёмка зелёная, ~95% текста выдержало сверку;
- ни одного расхождения формы запроса/ответа;
- каталог кодов ошибок сошёлся;
- строк «Реализация:» и метки `Статус: спроектировано` нет нигде;
- следов удалённого не найдено;
- вывод раздела «Клиент написан, UI нет» верен по существу.

**Итог:** правка на три строки. По правилу «хоть одно расхождение — refuted» домен
возвращается в работу.
