## 1. Воспроизведение

Пункт утверждает три вещи. Проверены все три.

**(а) Модуль заказов подписывает единицу ключами `orders.unit_*`.**

```
$ grep -rn "orders.unit_' + " frontend_vue/src
src/views/admin/orders/OrderCreatePage.vue:406
src/views/admin/orders/AddOrderItemsModal.vue:684
src/views/admin/orders/AddOrderServicesModal.vue:103
src/views/admin/orders/OrderCardPage.vue:1526, 2266, 2282, 2330, 2335, 2405, 2407, 2873
```

Одиннадцать мест в четырёх файлах — ровно как в пункте.

**(б) Ключей меньше, чем единиц справочника.**

```
$ grep -n "unit_kg\|unit_m:\|unit_pcs\|unit_m2\|unit_h" frontend_vue/src/i18n/admin/orders.ts
142-146 (ru), 621-625 (en), 1099-1103 (lt)   → пять ключей на локаль
$ grep -c "id: 'uom-" frontend_vue/src/services/mocks/settings.ts
9
```

Пять ключей на девять единиц. У `t()` второй аргумент — дефолт, поэтому `uom-m3`,
`uom-mm`, `uom-t`, `uom-kg-m3` рисовались бы своим id-кодом на всех трёх языках.
(В тексте пункта — «четыре ключа на восемь единиц»: с тех пор в п. 4 добавлены
`unit_h` и `uom-h`, расхождение то же самое, счёт на единицу больше.)

**(в) Вторая система — справочник — уже локализована и уже используется.**

```
$ grep -rn "uoms.find" frontend_vue/src --include=*.vue --include=*.ts
```

и в самом `AddOrderItemsModal.vue` нашлось не две системы, а **три реализации одной**:
`resolveUomCode` (стр. 94), `getProductUnit` (стр. 151), `getProductDisplayUnit`
(стр. 257) — каждая своим кодом вынимала `uom.code[locale] || code.en || code.ru ||
code.lt`, отличаясь только запасным вариантом. Плюс ключи в шаблоне на стр. 684.

Пункт воспроизведён.

## 2. Решение: источник — СПРАВОЧНИК

Пункт требовал решить, какая из двух систем источник. Выбран справочник, три довода:

1. **Полнота по построению.** Ключи надо заводить руками по одному на строку
   справочника, и о пропуске узнаёшь от пользователя: дефолт `t()` молчит. Справочник
   знает все свои единицы всегда.
2. **Единица заводится пользователем.** `UnitsSettings.vue` позволяет добавить единицу
   в настройках. Подписи в заказах она бы не получила никогда — ключи правятся кодом.
3. **Он уже источник де-факто.** Тем же правилом подписаны услуги (`serviceUnitLabel`),
   карточка товара, список товаров, карточка партии и три функции внутри самой модалки
   добавления позиций. Система ключей — исключение из четырёх файлов, а не половина.

### Находка сверх текста пункта, починенная здесь же

`AddOrderItemsModal.getProductUnit()` возвращала **переведённый** код и результат уходил
не в разметку, а в данные: `selectedItems[].unit` → `emit('add', items)` → строка заказа
(стр. 239 и 497). То есть русский сеанс сохранял в заказе `unit: 'шт'`, и никакая подпись
это уже не чинит — справочник такой код не узнаёт. Тот же дефект, что в п. 4b, только
раньше по пути данных.

Починено вместе с пунктом, потому что без этого выбранный источник не держится: половина
строк заказа хранила бы подпись вместо кода. Теперь `unit` собирает `orderLineUnit()` —
тем же правилом, что мок для сидов.

## 5. Линзы

### Л1 — реактивность
```
$ grep -n "structuredClone\|toRaw(\|watch(" src/domain/uom.ts src/composables/useUnitLabel.ts
(пусто)
```
`useUnitLabel()` возвращает замыкание, которое читает `settings.uoms` (reactive) и
`locale.value` (ref) **в момент вызова**, то есть внутри отрисовки — обе зависимости
отслеживаются. Кэша, снимка и `computed`, вычисленного один раз, нет — смена языка
перерисовывает подписи. **Чисто.**

### Л2 — i18n
```
$ npx tsx -e "…сравнить наборы ключей adminOrders.{ru,en,lt}.orders…"
ru 418   en 418   lt 418
ru\en []  en\ru []  ru\lt []  lt\ru []
unit_ left: []
```
Наборы ключей совпадают поштучно после снятия пятнадцати строк, `unit_*` в домене
заказов не осталось. Сырой точечный ключ в DOM невозможен: `t('orders.unit_' + …)` был
единственной конкатенацией ключа в модуле, и её больше нет. **Чисто.**

### Л3 — контракт и HTTP
Новых вызовов нет. Единственный источник данных — `/api/settings/uoms`, он уже
зарегистрирован в моке:
```
$ grep -n "'/api/settings/uoms'" src/services/mocks/index.ts
383:  if (path === '/api/settings/uoms') return delay(mockGetUoms() as T)
1106: if (path === '/api/settings/uoms')
```
Справочник тянет `AdminSidebar.onMounted → loadSettings()` на каждой админской странице,
своего `load()` композабл не делает — второй запрос за теми же восемью разделами не нужен.
`03-api-contract.md` про `orders.unit_*` не упоминал ничего — дописывать нечего. **Чисто.**

### Л4 — мок = правда
Сиды не менялись. Единственная правка мока — `unit:` теперь собирается вызовом
`orderLineUnit()` вместо той же строковой операции на месте: значения побайтово те же,
правило одно. **Чисто.**

### Л5 — один источник правила
```
$ grep -rn "orders.unit_" src/ tests/     → только комментарии и спека, кода нет
$ grep -rn "uoms.find" src/views/admin/orders/   → ни одного
```
В модуле заказов правило подписи осталось ровно одно — `uomCode` в домене; три ручные
копии внутри `AddOrderItemsModal` и обёртка `displayUnit` сняты. `serviceUnitLabel` теперь
зовёт то же `uomCode`, а не повторяет выборку локали.

**Припарковано, вне области пункта:** та же выборка руками живёт ещё в пяти местах вне
заказов — `ProductCardPage.vue:126`, `ProductsPage.vue:161`, `WarehouseBatchCard.vue:30`
и `:57`, `useWarehouseBatchCreate.ts:129/245/246/398`, `UnitsSettings.vue:22`. Две из них
(`WarehouseBatchCard.vue:57`, `useWarehouseBatchCreate.ts:398`) сравнивают строку с
`code.en` — это ровно дефект, описанный в п. 4d плана, и туда же он относится по тексту:
«`batch.unit` — свободная строка». Молча не чинил и в область 4c не тянул. **Пройдена.**

### Л9 — тесты, которые ничего не утверждают
Тесты трогались → инверсия обязательна. Четыре инверсии, каждая на своё утверждение;
после каждой файл возвращался из копии, а не `git restore`.

| # | Что сломано в коде | Что покраснело |
|---|---|---|
| 1 | `uomCode` отдаёт `code.en` всегда | 4 теста: `expected 'EUR/pcs' to be 'EUR/vnt'`, `expected 'pcs' to be 'шт'`, `'t'→'т'`, `'kg'→'кг'` |
| 2 | огрызок id не восстанавливается (`const id = unit`) | 3 теста: `expected null to be 'шт'`, `null to be 'т'`, `'kg' to be 'кг'` |
| 3 | неизвестная единица → прочерк вместо кода | 1 тест: `expected '—' to be 'kg'` |
| 4 | `orderLineUnit` возвращает подпись (тот самый дефект) | 2 теста: `expected 'т' to be 't'`, `expected 'шт' not to be 'шт'` |

Утверждений, которые устраивает бездействие (питфолл #68), в спеке нет: ни одного
`toBeGreaterThanOrEqual`, `toContain` по надмножеству и `toBeTruthy`. Два места, где
проверка могла оказаться пустой, закрыты явно:

- цикл «каждая единица подписана» предварён `expect(uoms.length).toBeGreaterThan(0)` —
  пустой справочник иначе прошёл бы как успех;
- отдельный тест требует, чтобы хотя бы у одной единицы коды по языкам расходились
  (`uom-pcs`) — иначе проверка «подпись в текущем языке» была бы верна и для подписи, не
  зависящей от языка вовсе: у шести единиц из девяти коды совпадают.

## 6. E2E — уровень 1

Правка лежит в одной области (модуль заказов) плюс подпись услуг. Общий пол не тронут:
`tests/e2e/helpers/`, фикстуры, `src/services/mocks/index.ts`, роутер, глобальный CSS —
без изменений. Значит уровень 1: спеки области.

```
$ npx playwright test tests/e2e/admin/orders/orders.spec.ts \
      tests/e2e/admin/products/services.spec.ts \
      tests/e2e/admin/products/service-card.spec.ts \
      --reporter=line --workers=3 > run.txt 2>&1; echo "exit=$?"
exit=0
  126 passed (2.7m)
```

Вердикт снят по коду возврата и по строкам `failed`/`flaky`/`skipped` в полном выводе,
а не по последней строке: ни одной такой строки в `run.txt` нет.

Круг «кто читает тот же мок» проверен, а не взят на глаз: правка
`src/services/mocks/orders.ts` — замена строковой операции вызовом функции, дающей
побайтово тот же результат (`orderLineUnit` доказана тестом на всех девяти единицах),
поэтому для остальных читателей мока данные не изменились вовсе.
