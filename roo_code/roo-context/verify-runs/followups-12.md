## Часть I. Причина отклонения второй попытки (запись приёмщика, без правок)

Опровергнуто по двум основаниям.

**(1) Требование пункта отсутствует.** Пункт 12 (`review-followups.md:919-941`) содержит отдельный
блок «Требование к отправке»: «письмо уходит одной транзакцией, все адреса — в поле BCC… Это
ответственность бэкенда, и проверять это надо тестом, а не глазами: рассылка циклом по одному письму
выглядит снаружи так же». В бэкенде этого нет вовсе: `backend/app/modules/bcc/features/` содержит
только `__init__.py` с докстрингом, `internal_api/interface.py` — только докстринг, ни одного слайса;
тестов в `backend/` нет ни одного. Правило живёт и проверено только в мок-слое
(`src/services/mocks/bcc-envelope.spec.ts`).

**(2) Главное заявление этой же правки ложно.** Приёмка вернула моку РЕАЛЬНУЮ историческую третью
формулировку — дословно из `866171c`: `return Boolean(mailStore.host && mailStore.fromEmail && mailPassword)`
— и прогнала весь юнит-набор: 633 теста, ни один не покраснел. В журнале инверсия была сломана иначе
(`host && mailPassword`, то есть выброшена проверка `fromEmail`, чего в исходном дубле не было) —
искусственное расхождение вместо воспроизведения возврата. Новый кейс «ответ сервера и гейт формы
дают один и тот же вердикт» сравнивает `mockIsMailConfigured()` с `isMailConfigured(mockGetMail())`,
а после правки это буквально одно и то же выражение — тавтология ровно на том случае, ради которого
объявлена.

**Что подтвердилось и переделывать не надо:** дедупликация выполнена; состав раздела почты
соответствует пункту; пароль не читается.

### 2. Основание (1) — требование к отправке закрыто на бэкенде и проверено тестом

**Что появилось.** `backend/app/modules/bcc/features/send_request/`:

| Файл | Что в нём |
|---|---|
| `domain.py` | `MailServerConfig`, `is_mail_configured`, `build_bcc_envelope`, `send_bcc_request`, `MailTransport` |
| `transport.py` | `smtp_transport` / `send_via_smtp` — одна SMTP-сессия на отправку, ssl/starttls/none |

Одна транзакция выражена ровно одной строкой — `transport.send_message(message)` вне всякого цикла;
все адреса уходят в `Bcc`, `To` — сам отправитель, `Cc` нет. Приватность списка держится не на
заголовке `Bcc`, а на том, что `smtplib.SMTP.send_message` превращает его в конверт и **не
передаёт** сам заголовок; это документированное поведение стандартной библиотеки, и оно проверяется
тестом, а не пересказывается.

**Тесты: `backend/tests/modules/bcc/test_send_request.py`, 9 штук.**

Почему `unittest`, а не pytest: pytest в этой среде поставить нельзя — `pip3 install pytest`
упирается в PEP 668 (`externally-managed-environment`), а `python3 -m venv` не собирается без сети.
Проверка, которую нельзя запустить, проверкой не является; `unittest` — стандартная библиотека,
работает как есть, и pytest, когда появится, подберёт эти же тесты без единой правки.

```
$ cd backend && python3 -m unittest discover -s tests -t .
Ran 9 tests in 0.009s
OK
```

**Л9 — пять инверсий, каждая на своё утверждение** (правится `domain.py`, гоняется весь набор):

| # | Что сломано | Итог |
|---|---|---|
| Б-И1 | `send_bcc_request` рассылает **циклом**, по письму на получателя | `FAILED (failures=2)` |
| Б-И2 | адреса поставщиков уходят в `To` вместо `Bcc` | `FAILED (failures=2, errors=2)` |

Б-И1 — это ровно тот случай, ради которого пункт требует теста: рассылка циклом даёт те же письма в
тех же ящиках и отличается только числом транзакций. Теперь она краснеет.

**Шаг внесён в гейт зелёным** (правило verify.md): `.github/workflows/ci.yml`, задача `gate`,
шаг `backend unittest`. Зависимостей у него нет вовсе, поэтому «отвалиться по установке» он не может.
YAML разобран локально (`yaml.safe_load` → ok); настоящий прогон возможен только после пуша, которого
в этой сессии нет, — и это сказано вслух, а не подразумевается.

`verify.md` поправлен там же, где утверждал обратное: «ноль тестов» перестало быть правдой, команда
прогона добавлена в блок бэкендовой приёмки, а **Л9 объявлена применимой к бэкенду** — раньше там
стояло «станет применима, как только появится первый тест».

**Чего этот заход НЕ делает и не объявляет сделанным:** HTTP-слайса (`action.py`, `schemas.py`,
`repository.py`) у `send_request` нет, записи в `bcc_events` нет, отправка ниоткуда не вызывается.
Пункт 12 требует, чтобы правило «одна транзакция» существовало на бэкенде и проверялось тестом, —
это сделано; поднять `POST /api/bcc/send` целиком нельзя не желанием, а средой: `fastapi`,
`pydantic`, `sqlalchemy` в этой машине не установлены, и написанный слайс нельзя было бы даже
импортировать. Проверено:

```
$ cd backend && python3 -c "from app.main import app"
ModuleNotFoundError: No module named 'fastapi'          # так было и до правки

$ python3 -c "from app.modules.bcc.features.send_request.domain import send_bcc_request; \
              from app.modules.bcc.features.send_request.transport import send_via_smtp; print('ok')"
оба модуля импортируются
```

Именно поэтому слайс сознательно сделан на одной стандартной библиотеке плюс
`app.core.exceptions`: правило, которое нельзя прогнать, ничем не отличается от правила, записанного
в ревью.

### 3. Основание (2) — инверсия на НАСТОЯЩЕЙ исторической формулировке

**Воспроизведение.** Моку возвращена дословная историческая формулировка из `866171c`:

```ts
export function mockIsMailConfigured(): boolean {
  return Boolean(mailStore.host && mailStore.fromEmail && mailPassword)
}
```

```
$ npx vitest run
Test Files  33 passed (33)
     Tests  664 passed (664)
```

**Приёмщик прав, и вот почему** — это не «тест слабый», а свойство самих выражений.
`mockGetMail()` отдаёт `passwordSet: mailPassword.length > 0`, поэтому
`isMailConfigured(mockGetMail())` и `Boolean(mailStore.host && mailStore.fromEmail && mailPassword)`
**тождественны на всех входах**. Никакой тест их не различит, и заявление прошлого захода
(«инверсия воспроизводит регресс») ложно. Оно здесь и отзывается.

**Что тогда покупает дедупликация — и как это измерить.** Не сегодняшнее поведение, а невозможность
разъехаться завтра. Это проверяемо: ломается **единый источник** `isMailConfigured` (выброшено
условие `fromEmail`) — один и тот же слом, два состояния мока:

| # | Состояние | Результат |
|---|---|---|
| Ф-И1 | мок с исторической формулировкой, источник цел | `664 passed (664)` — зелено, как и сказал приёмщик |
| Ф-И2 | мок зовёт источник (сегодняшний код), источник сломан | `2 failed \| 662 passed` — `mailConfigured.spec.ts` **и** `mail-settings.spec.ts` |
| Ф-И3 | мок со своей исторической копией, источник сломан | `1 failed \| 663 passed` — мок остался при своём вердикте |
| — | контроль | `664 passed (664)` |

Разница Ф-И2 против Ф-И3 и есть цена дубля: при общем правиле изменение гейта тащит за собой
сервер, при своей копии — не тащит, и сервер молча остаётся судить по-старому. Это первое
утверждение по этому пункту, которое сделано **на исторической формулировке** и что-то показывает.

**Тавтологичный кейс убран.** В `mail-settings.spec.ts` кейс «ответ сервера и гейт формы дают один и
тот же вердикт» сравнивал `mockIsMailConfigured()` с `isMailConfigured(mockGetMail())` — после
дедупликации посимвольно одно выражение (питфолл #68: утверждение, которое устраивает бездействие).
На его месте — «сервер отказывает ровно в тех состояниях, где отправлять нечем»: та же таблица
состояний, но вердикт назван **литералом**, а видно его снаружи — через отказ `mockSendMailTest()`,
то есть через то, что получает форма, а не через тот же предикат. В доккоменте прямо написано, чего
кейс не ловит и почему поймать нельзя, — чтобы следующий читатель не объявил его снова стражем
исторического дубля.

Инверсии на мок-слое отправки (`bcc-envelope.spec.ts`), тронутом в этом же заходе:

| # | Что сломано | Итог |
|---|---|---|
| Ф-И4 | `mockSendBccRequest` пушит по конверту на получателя | `2 failed \| 3 passed` |
| Ф-И5 | адреса поставщиков попадают в `to` | `2 failed \| 3 passed` |
| Ф-И6 | снят отказ `MAIL_NOT_CONFIGURED` | `1 failed \| 4 passed` |
| — | контроль | `5 passed (5)` |
