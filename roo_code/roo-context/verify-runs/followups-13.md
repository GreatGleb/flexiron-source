## 2. Что сделано

### Модель

Реестр «Входящие» перестал быть хранилищем и стал **представлением над счетами заказов**.

- `src/domain/receivable.ts` (новый) — единственное место, где живут два правила:
  `receivableDueDate(issuedAt, paymentTermsDays)` (срок = дата счёта + отсрочка клиента,
  пункт 9) и `receivableStatus({ amount, paidAmount, dueDate })` (оплат ≥ суммы →
  `completed`; меньше и срок прошёл → `overdue`; иначе `pending`). Статус нигде не хранится.
- `src/services/mocks/orders.ts` → `orderReceivables()` — строит строки из `Order.invoices`.
  Лежит в модуле заказов по той же причине, что и `orderAuditSources`: «какой документ
  клиент ещё держит» уже решается здесь (`isWithdrawn`), и второй экземпляр этого правила в
  финансовом моке разошёлся бы с первым.
  - корректировка своей строки не заводит — она поправляет сумму исходного счёта
    (`outstandingGrossOf`);
  - счёт, отозванный корректировкой (`withdrawsOriginal`), из реестра исчезает вовсе;
  - `paidAmount` — только платежи с `invoiceId` этого счёта; аванс без ссылки на документ
    ничей долг не закрывает;
  - `paidAt` — платёж, на котором накопленная сумма впервые покрыла счёт (не последний:
    после закрытия по счёту может пройти возврат).
- `outstandingNetOf` обобщён в `outstandingAmountOf(order, invoice, field)`; брутто-вариант
  нужен потому, что деньги приходят с НДС, и сравнение «нетто против брутто» объявляло бы
  оплаченным счёт, по которому не хватает ровно налога.

## Находка 1 — счёт клиенту-предоплатнику становился просроченным через миллисекунды

### Воспроизведение

Клиентов с нулевой отсрочкой в моке девять:

Зонд (временный спек, удалён после замера): найти заказ с `clientPaymentTermsDays === 0`,

```

terms 0 | issued 2026-08-28T00:21:24.786Z | due 2026-08-28T00:21:24.786Z | status overdue | now 2026-08-28T00:21:24.846Z
```

Без паузы (замер в ту же миллисекунду) статус был `pending` — то есть дефект зависит только от
того, прошло ли хоть одно мгновение, и на живой странице виден всегда. Плюс `receivables()` в
`finance.ts` на такой строке зовёт `notifyPaymentOverdue`: пользователь получал в колокольчик
«оплата просрочена» по документу возрастом в секунду, а в колонке «Срок» стояло сегодняшнее
число.

Косвенное подтверждение, что автор первого захода о нуле знал и обошёл его в тестах:
`finance-receivables.spec.ts` заводил хелпер `clientWithTerms()` с комментарием «Клиент с
ненулевой отсрочкой: у нулевой срок наступает в день выдачи» — то есть проверки специально
уводились от единственного случая, где правило ломалось.

### Правка

`src/domain/receivable.ts`, `receivableStatus`: граница просрочки — **конец дня срока**, а не
сам его момент.

```
было:  const due = new Date(input.dueDate).getTime()
       if (!Number.isNaN(due) && now > due) return 'overdue'
стало: const due = new Date(input.dueDate)
       if (Number.isNaN(due.getTime())) return 'pending'
       const endOfDueDay = new Date(due); endOfDueDay.setHours(23, 59, 59, 999)
       if (now.getTime() > endOfDueDay.getTime()) return 'overdue'
```

День берётся локальный — тот же календарь, в котором дата и показана на странице
(`new Date(iso).toLocaleDateString()` в `IncomingPaymentsPage.vue:110`), иначе пилюля спорила бы
с колонкой рядом. Прецедент локального дня в проекте уже есть: `orders.ts:1503`
(`monthStart.setHours(0, 0, 0, 0)`).

`receivableDueDate` не тронут: он считает срок верно, дефект был в сравнении.

### Проверки

Три юнита в `src/domain/receivable.spec.ts` (нулевая отсрочка — не просрочен через минуту; день
срока не кончился — `pending`; следующий день — `overdue`), один в
`src/services/mocks/finance-receivables.spec.ts` (счёт предоплатнику: `pending` в день выдачи,
`overdue` на следующий) и один в `src/services/mocks/notification-triggers.spec.ts` (колокольчик
молчит в день выдачи).

Время в мок-проверках **задаётся** (`vi.setSystemTime`), а не берётся настоящее. Это не
украшение: первая версия этих двух проверок брала реальные часы, и на сломанном коде они
оставались зелёными — между выдачей счёта и чтением реестра проходит доля миллисекунды. То есть
проверка не проверяла ничего (питфолл #68). Замер обеих версий приведён в инверсиях ниже.
