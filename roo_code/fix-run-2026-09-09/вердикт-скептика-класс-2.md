## а) Откат `errorCode` на `message`. Дыра есть, но регресса нет

Отдельно проверял случай, заданный в задании: `ApiRequestError` с `code === null` и человеческим
текстом, СОДЕРЖАЩИМ чужой код. Написал временную спеку (создана, прогнана, удалена):

```ts
const noCode = new ApiRequestError({
  status: 500,
  message: 'Internal error while checking CATEGORY_HAS_PRODUCTS constraint',
})
expect(noCode.code).toBeNull()
expect(errorMessageKey(noCode, [['CATEGORY_HAS_PRODUCTS', 'categories.toast_error_delete_has_products']],
       'categories.toast_error')).toBe('categories.toast_error_delete_has_products')   // ← прошло
expect(errorCode(new ApiRequestError({ status: 400,
       message: 'Validation failed for field CONFLICT_RESOLUTION_MODE' })).includes('CONFLICT')).toBe(true)  // ← прошло
```

`Tests 3 passed` — то есть **разбор уезжает в чужой ключ**: сервер кода не прислал, а человек
увидит «в категории есть товары»; в `useClients` посторонняя ошибка валидации покажет «у клиента
есть заказы».

**Дефектом правки это не считаю, и вот почему:**

1. **Регресса нет.** До правки те же места читали `e.message` / `String(e)` напрямую — поведение
   на `code === null` ровно то же.
2. **Откат обоснован и задокументирован в коде** (`apiErrorCode.ts:12-17`), а не молчит.
3. **Путь узкий.** `code === null` возникает, когда тело ответа не по контракту; тогда
   `unwrap()` (`api.ts:151`) подставляет `` `${method} ${path} failed: ${status}` `` — заглавных
   кодов там нет. Проверено: `errorCode` на такой ошибке возвращает `GET /api/clients failed: 500`.

**Оговорка к отчёту.** Спека `apiErrorCode.spec.ts:72` называется «человеческий текст сервера не
подменяет собой код» — но покрывает только случай, когда `code` **есть**. Ровно обратный случай
(`code === null`, чужой код в тексте) ведёт себя противоположно и не покрыт. Утверждение шире
того, что доказано.

**Ноль из восьми.** Разбор по формам и по тому, насколько дыра реальна:

| # | форма | поймана | реальность |
|---|---|---|---|
| h1 | `.catch(e => {` без скобок | нет | **закрыта другим**: `arrowParens` у prettier по умолчанию `always`, и `format:check` в гейте краснеет — проверено, `prettier --check` EXIT=1 |
| h2 | `.catch(async (e) => {` | нет | **открыта**, форма обычная |
| h3 | `.catch(onFail)` именованным обработчиком | нет | **открыта** |
| h4 | `.catch((e) => (… ? … : …))` стрелка без тела | нет | **открыта** |
| h5 | код короче 5 символов (`'BUSY'`) | нет | открыта, но инстансов нет: самые короткие настоящие коды — `CONFLICT`, `INFECTED` (8) |

| h8 | в одном `catch` — и `errorCode()`, и сырое сравнение рядом | нет | **открыта и самая опасная** |

**h8 — про существующий код, а не про будущий.** `ASKS_FOR_CODE` проверяется на теле обработчика
целиком: одного вызова `errorCode()` где угодно внутри `catch` достаточно, чтобы **любое** другое
сравнение в том же теле стало разрешённым. Все девять сегодня охраняемых обработчиков этим
иммунизированы: добавить в них сырое сравнение можно, сторож смолчит.

Проверил ещё разбор тела парной скобкой — он не знает ни строк, ни комментариев:

| проба | поймана | почему |
|---|---|---|
| комментарий с `{` внутри `catch` | **да** | лишняя `{` только удлиняет тело, нарушение остаётся внутри |
| шаблонный литерал `` `… ${name}` `` | **да** | `${…}` сбалансирован |
| строка с одиночной `}` — `'скобка: }'` | **нет** | тело закрывается раньше времени, всё после неё невидимо |

**Чего сторож сегодня НЕ пропускает — тоже замерено, и это важно для честной оценки.**

```ts
expect(state.text()).toContain(t('financePayment.not_found_title'))   // consumers.spec.ts:285
```

Когда ключа нет, `t()` возвращает **сам ключ**, и компонент рисует **тот же самый ключ** —
утверждение выполняется одинаково при наличии и при отсутствии перевода. Это питфолл #68 в
чистом виде, в тесте, который журнал предъявляет как доказательство новых ключей.

Первый прогон этой инверсии дал одно падение (`authToken.spec.ts`, 5017 мс) — атрибутировал его,
как требует `verify.md`: `load average` был 16.37 из-за параллельного e2e, тот же файл в одиночку
`34 passed`, а повтор всей инверсии на спокойной машине дал ровно `EXIT=0`. К ключу падение
отношения не имеет.

Отдельно: спеки паритета локалей в проекте нет вовсе
(`grep -rln "translations" src --include=*.spec.ts` → единственный файл — новая
`apiErrorCode.consumers.spec.ts`). То есть пропущенный перевод не ловится **ничем**, и это шире
класса 2 — но правка добавила два ключа именно в эту непроверяемую зону.

## ж) Сверх задания: свип Л5 объявлен чистым по слишком узкому грепу

Журнал (линза Л5) приводит греп

```
grep -rnE "\.message\s*(===|!==|\.includes\()|String\((e|err|error)\)\s*\.includes" src/ …   → пусто
```

и делает вывод «свип чистый, новых находок в области задачи нет». Греп ищет `.message` **рядом со
сравнением** и `String(e).includes`. Форму `error.value = String(e)` — то есть **ровно тот дефект,
из-за которого заведён и починен `orders/БАГ-11`** — он по построению не видит.

Свой греп:

```
grep -rnE "String\((e|err|error)\)" src --include=*.ts --include=*.vue | grep -v "\.spec\.ts"
```

```
src/composables/useClients.ts:37        error.value = String(e)
src/composables/useClientCard.ts:162    error.value = String(e)
src/composables/useOrderCreate.ts:141   clientsError.value = String(e)
src/composables/useOrderCreate.ts:479   error.value = String(e)
src/composables/useSalesCrmDashboard.ts:64  error.value = e instanceof Error ? e.message : String(e)
```

Проверил, что это не мёртвое состояние, а экран:

```
grep -rn "{{ error }}" src/views/admin/clients/ClientsListPage.vue
  → 273:        <p>{{ error }}</p>     (внутри v-if="error", data-test="clients-error-state")
```

**`useClients.ts:37` — это `orders/БАГ-11` слово в слово, в том же файле, который правка меняет на
строке 72.** Правило 1 `fix-bugs.md` требует читать файл целиком; при чтении целиком строка 37
находится на экран выше правки.

Проверил, не отнесены ли эти места к другим классам (тогда молчание было бы дисциплиной, а не
пропуском):

```
grep -rn "useClients\.ts\|useClientCard\.ts\|useOrderCreate\.ts\|useSalesCrmDashboard\.ts" \
     roo_code/plans/bugs/*.md | grep -iE "String\(e\)|текст исключ"   → пусто
```

Ни одного из пяти нет ни в одном баг-файле. (Для сравнения — соседи того же семейства
**заведены**: `analytics:368`, `bcc:355`, `products/БАГ-06`, `settings:503` про `useWarehouseMap`.
То есть механизм парковки в прогоне работает, эти пять просто не найдены.)

Туда же — семейство `e instanceof Error ? e.message : 'Failed to load …'` в `useWarehouse.ts`
(строки 197, 225, 251, 277, 300), `useWarehouseMap.ts:31`, `useWarehouseDeficitCard.ts:74`: текст
исключения на экране плюс английская строка мимо i18n.

**Что это значит.** Семь находок класса это не отменяет — они починены. Отменяет это фразу
«свип чистый». По правилу `verify.md` находка вне области задачи не чинится молча, а **уходит в
bugs-file через `add-bug.md`**, и тогда свип остаётся чистым. Здесь находки не починены и не
припаркованы — они просто не увидены грепом, который был выбран под уже известный ответ.
Чинить их — не моя работа и не работа этого класса; **завести — обязательная**.

## з) Числа в «чем доказано» не сходятся с замером

Четыре штуки. По отдельности мелочь, вместе — система, и в прогоне, где вердикт снимается
замером, это стоит назвать.

| утверждение журнала | замер | команда |
|---|---|---|
| «25 её вызовов» | **20** мест вызова | `grep -rno "lineEditErrorKey(" src … \| grep -v spec` → 21 строка, минус декларация |
| «46 пар» в `ERROR_KEYS` | **91** пара | `sed -n '301,410p' orderLineEdits.ts \| grep -cE "^\s*\['"` |
| база «43 файла / 849 тестов» | **42 / 839** | сейчас 45/863; новых тестов 8+2+12+2 = 24; удалённых 0 (`git diff … \| grep -c "^-.*\bit("` → 0); 865−24 = 841 |
| «81 / 81 / 81» ключей `financePayment` | **27 / 27 / 27** (81 — это сумма) | прямой `Object.keys(…).length` по трём локалям |

Два из этих чисел вписаны **в комментарии исходников**, а не только в журнал:

```
orderLineEdits.ts:418-419        «не находила ни одного из 46 кодов и все 25 её вызовов…»
orderLineEdits.spec.ts:470-472   «ни один из 46 кодов… двадцать пять вызовов»
```

`verify.md` прямо предупреждает об этом («продублированное значение устаревает молча» — и там же
объясняет, почему число тестов в сам скил не вписано). Здесь неверное число не устареет — оно
неверно уже сейчас, и лежит там, где его будут читать как факт.

Числа, которые я перемерил и **подтвердил**: 863 теста, 45 файлов, 1078 e2e, 81 обработчик /
9 охраняемых / 0 нарушителей у сторожа, 0/56/26 у knip, 17 доменов / 175 эндпоинтов контракта.
