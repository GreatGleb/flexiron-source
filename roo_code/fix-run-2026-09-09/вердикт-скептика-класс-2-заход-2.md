## 1. Сторож: 26-й контроль. НАХОДКА Н1

**Способ.** Не чтение кода, а прогон `findOffences()` на образцах: временная спека
`src/services/__probe3.spec.ts` (создана, прогнана, удалена), каждый образец — одна запись
нарушения в одном файле, без межмодульного потока.

```
npx vitest run src/services/__probe3.spec.ts
```

Вернулось:

```
МИМО  A. == вместо ===                 try{f()}catch(e){ if (e.message == 'SOME_CODE') g() }
МИМО  B. код в константе               const CONFLICT_CODE = 'SOME_CODE'; … e.message === CONFLICT_CODE
МИМО  C. шаблонная строка              … e.message === `SOME_CODE`
МИМО  D. именованный массив кодов      const CODES = ['SOME_CODE']; … CODES.includes(e.message)
МИМО  E. indexOf                       … e.message.indexOf('SOME_CODE') !== -1
МИМО  F. регулярка в константе         const RE = /SOME_CODE/; … RE.test(e.message)
МИМО  G. нормализация перед сравнением  … e.message.trim() === 'SOME_CODE'
МИМО  H. словарь по тексту             const MAP = { SOME_CODE: 'k' }; … MAP[e.message]
```

Раньше, тем же способом, прошли мимо ещё четыре направления из задания: поток через параметр
функции (`function check(m){ return m === 'SOME_CODE' } … check(e.message)`), возврат из метода
класса, `const m = await textOf(e)`, и `CODES.some(c => e.message === c)`. Ловятся, и это в плюс
сторожу: `catch` внутри `catch`, `Object.assign({}, e)`, `{...e}`, `switch(true) { case
e.message === … }`, `(await …).message`, тернарник.

**Почему это дефект, а не «ещё одна граница».** Шапка модуля перечисляет четыре вещи, которых
сторож не умеет: межмодульный поток, область видимости, сравнение, собранное во время работы,
и `String(e.поле)`. **Ни один из восьми образцов выше не попадает ни в одну из четырёх** — все
они однофайловые, статические и записаны буквально. Список назван затем, «чтобы зелёное не
читалось как доказательство отсутствия», и в этой роли он не работает: он у́же настоящих границ,
то есть зелёное всё ещё читается шире, чем есть.

**Корень — тот же, что у трёх прежних версий, и он не вылечен переходом на дерево.** Вывод в
журнале записан верно («каждая версия закрывала **запись** дефекта, а записей бесконечно
много»), но применён к одной стороне сравнения из трёх:

| сторона | как разобрана | чем платит |
|---|---|---|
| операнд (текст) | **по смыслу** — цепочка объявлений, присваиваний, деструктуризаций, обёрток | здесь дыр нет, девять форм из девяти |
| литерал (код) | **перечислением записи** — только `ts.isStringLiteral` и `ts.isRegularExpressionLiteral` | B, C мимо |
| операция | **перечислением записи** — `===`/`!==`, пять имён методов, `includes` только по массиву-литералу, `.test` только по литералу-регулярке | A, D, E, F, G, H мимо |

`origins` — готовый механизм резолва — к литералу и к приёмнику `.includes`/`.test` **не
применён**, хотя `const CODES = […]` и `const RE = /…/` разрешаются им в одну строку. Для
оператора достаточно добавить `==`/`!=` к двум существующим. Это не «ещё одна заплатка»: это
тот же приём, которым уже разобран операнд, распространённый на две оставшиеся стороны.

## 2. Ложное срабатывание на реальном коде. НАХОДКА Н2

**Сначала измерил, есть ли ложное обвинение сегодня.** Копия сторожа с ослабленным до
`/^.+$/` `CODE_LITERAL` (то есть кодом считается **любая** строка), прогнана по всему `src`:

```
ФАЙЛОВ ПРОСМОТРЕНО: 216
(срабатываний нет)
КОНТРОЛЬ: [{"operand":"e.message","code":"anything","line":1}]
```

Положительный контроль в том же прогоне обязателен — иначе пустой список ничего не значит
(грабля 3 передачи); он сработал. Значит **живого ложного обвинения сегодня нет**, и это надо
сказать прямо.

**Но место, которое заставит следующего автора отключить сторож, есть, и оно не гипотетическое.**
Взял `src/services/api.ts` как есть, дописал в конец законный хелпер — ровно то, что делает сам
канонический `errorCode()` строкой 24 (откат на `message`, пока мок бросает голый `Error`):

```ts
export function legacyCode(e: Error): string {
  const code = e.message
  return code
}
```

`findOffences()` на этом тексте:

```
api.ts как есть:          []
api.ts + законный хелпер: [{"operand":"code","code":"VALIDATION_ERROR","line":118},
                           {"operand":"code","code":"CONFLICT","line":132}]
  строка 118: «if (code === 'VALIDATION_ERROR') {»
  строка 132: «if (code === 'CONFLICT') {»
```

Обвинены две строки `inferFieldFromMessage()`, где `code` — **параметр**, пришедший из
разобранного поля `code` тела ответа (`api.ts:86`, `:105`). Это не нарушение — это эталонная
реализация правила §2, и сторож называет её нарушителем, потому что в другой функции того же
файла кто-то назвал переменную тем же словом.

Три обстоятельства делают это дефектом, а не приемлемым огрублением:

1. **Цена ложного обвинения — не «лишняя строка в списке», а красный `verify`.** Спека требует
   `expect(offenders).toEqual([])`. Автор, добавивший законный хелпер, получит красный гейт на
   правильном коде, и самый дешёвый выход у него — изъятие или отключение.
2. **`api.ts` — уже второй раз то самое место.** Версия 1 держала его в списке изъятий; версия
   4 изъятие сняла (журнал: «теперь не нужно и отсутствует»). Оно вернётся.
3. **Имя `code` в `api.ts` — не выдумка ради образца.** Оно там уже занято трижды (`:86`,
   `:105`, и параметр `:114`), а откат «код = текст» живёт в `apiErrorCode.ts:24` как
   **сознательное переходное решение**. То есть сойтись этим двум вещам в одном файле — вопрос
   времени, а не случайности.

Фраза шапки «огрубление работает в безопасную сторону: сторож скорее заругается зря, чем
промолчит» неверна в обе половины: он и ругается зря (§2), и молчит (§1).
