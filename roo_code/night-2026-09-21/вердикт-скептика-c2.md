**Вывод:** требование выполнено **по существу** — часовой пояс арендатора хранится колонкой, страна
кодом, на проводе поле `timezone`. Имя колонки под критерий выбрано, и это названо самим
исполнителем (§3.1/§8.3). По правилу 3 это **находка, а не отказ**.

**Что критерий проверяет теперь — точно:** при имени `time_zone` ветка `timezone` не проверяет
новую колонку **ни в каком написании**. Более того, арифметика беспощадна: 3 = чужая
`DateTime(timezone=True)` + `country_code` + `confirmation_code`. Значит **дерево, в котором
добавлены только страна и код подтверждения и нет ничего про часовой пояс, критерий всё равно
покрасит зелёным**. Критерий перестал быть проверкой существования поля времени пояса — это дефект
критерия (лечится ожиданием 3 → 4 при правильном имени), и он живёт в `приёмка.sh`, которого в
«Что можно править» слайса нет. Записано находкой Н2.

## 7. Миграция: ревизия, SQL, жизнеспособность

**Чем проверял:** `alembic heads`, обе генерации SQL, чтение файла ревизии, дифф каталога версий.

```
$ cd backend && python3 -m alembic heads
b3f7a2c94d10 (head)                       ← голова одна, ровно одна новая ревизия

$ python3 -m alembic upgrade 7c4d1e9a3b58:b3f7a2c94d10 --sql

ALTER TABLE company_info ADD COLUMN country_code VARCHAR(2);
ALTER TABLE company_info ADD COLUMN confirmation_code VARCHAR(4) DEFAULT '' NOT NULL;
ALTER TABLE company_info DROP COLUMN logo_url;
ALTER TABLE company_info ADD COLUMN logo_file_id VARCHAR(255);
ALTER TABLE global_constants ADD COLUMN payment_deferral_days INTEGER DEFAULT '0' NOT NULL;
ALTER TABLE global_constants ADD COLUMN default_kerf_mm NUMERIC(6, 2) DEFAULT '3' NOT NULL;
ALTER TABLE global_constants ADD COLUMN reservation_hold_days INTEGER DEFAULT '3' NOT NULL;

$ python3 -m alembic downgrade b3f7a2c94d10:7c4d1e9a3b58 --sql
(симметричные DROP COLUMN, плюс ADD COLUMN logo_url TEXT)

$ git diff --name-only -- backend/alembic/versions/     → пусто (7c4d1e9a3b58_*.py не тронут)
```

`down_revision = "7c4d1e9a3b58"` — совпадает с заявленным; ревизия ровно одна.

**Жизнеспособность, а не существование:**

- **`confirmation_code … NOT NULL` ляжет на непустую таблицу** — `server_default=''` в SQL есть
  (см. выше: `DEFAULT '' NOT NULL`), значит `ALTER TABLE ADD COLUMN` на заполненной таблице
  PostgreSQL выполнится, а не упадёт. В Python-модели умолчание продублировано
  ([`models.py:31-33`](backend/app/modules/settings/shared/models.py:31)). **Риска падения нет.**
- **`logo_url` снимается вместе со значениями** — данные теряются безвозвратно и без конвертации
  (идентификатор из прежней строки не выводится). Это **сказано** в §8.4 отчёта и в комментарии
  ревизии. Обратный ход теряет так же симметрично (`logo_file_id` → `logo_url`), про это в отчёте
  прямо не сказано — мелочь, записана находкой Н5.
- **Целочисленные/числовые умолчания** (`0`, `3`, `3`) присутствуют в `server_default` — падения нет.
- **Живьём не проверялось ничего:** `alembic upgrade head` упирается в
  `asyncpg.exceptions.InvalidPasswordError` (блокер среды). Отчёт **говорит это прямо** (§5, §8.1,
  §7) — правило 4 соблюдено, живого прогона слайс не заявляет.

## Находки

- **Н1 · Ложное «не могу объяснить» в 870 против 918.** 918 воспроизводится мною **точно** на
  `bb5b477` (67 документов · 15476 ссылок · битых 918; разбивка 681/236/1), 870 — на `HEAD` дважды;
  разницу 48 перенумеровал коммит `05abd03`, предок `HEAD`, и его сообщение это документирует
  («битых 918 → 966 … Итог: 966 → 870»). Разбивка в `вопросы-владельцу.md` §1 (680/236/1) не сходится
  сама с собой (сумма 917) и расходится с замером на единицу. Опасность не в цифре, а в том, что
  **непроверенное «необъяснимо» попало в отчёт как факт**. К сведению владельца: база 870 — верная.
- **Н2 · Критерий «часовой пояс, страна, код подтв.» после `time_zone` не проверяет часовой пояс
  вовсе.** Третье совпадение шаблона — чужая строка `DateTime(timezone=True)`. Дерево без колонки
  часового пояса (но со страной и кодом) пройдёт приёмку зелёным. Починка — ожидание `3` → `4` при
  имени `timezone`, либо греп по `mapped_column` колонки, а не по подстроке токена; живёт в
  `приёмка.sh`, вне объёма слайса.
- **Н3 · Три списка через запятую перенумерованы наполовину** — `models.py:127,116` в
  [`00-решения-владельца.md:755`](roo_code/plans/api/audit/00-решения-владельца.md:755) и
  [`00-conventions.md`](roo_code/roo-context/api/00-conventions.md:1457) (верно `125,130`; `116` теперь
  пустая строка), и `models.py:133,122` в
  [`contract-sync-settings-bugs.md`](roo_code/plans/bugs/contract-sync-settings-bugs.md:236) (верно
  `131,136` — так помечено десятью строками ниже в том же файле). Резолвер вторые номера не видит
  (перед ними нет двоеточия), поэтому метрика молчит. Прямое противоречие заявлению §8.6.
- **Н4 · 12 ссылок в нетронутых документах тихо перестали проверяться.** `audit-feed.md` +1,
  `products.md` +1, `audit/settings.md` +10 в графе «глазами» — все из-за правок кода (доказано
  опытом «код + документы из HEAD»: те же +1/+1/+10). Экземпляр, прочитанный глазами:
  `audit-feed.md:60` → `models.py:54`, токен `timezone=True`, строка уехала на 69. Правило 1
  («перенумеровать поехавшее от своих правок») выполнено для шести документов и **не выполнено** для
  этих трёх. Метрикой «битых» невидимо; к сведению оркестратора до коммита.
- **Н5 · Переименованная «уже неверная» ссылка.** `settings-c4.md` → `remove_uom_item`
  `crud/domain.py:397`: сейчас 397 — тело `list_uoms`, а `remove_uom_item` на 466. Скрипт переносит
  ссылку по признаку «строка есть в HEAD», а не «ссылка была верной», поэтому неверная осталась
  неверной, но с новым номером. Плюс мелочь: обратный ход миграции теряет `logo_file_id`
  симметрично потере `logo_url`, в «НЕЗАКРЫТОЕ» названа только прямая потеря.
- **Н6 · `settings.md` противоречит себе.** Раздел `## Правила домена` получил одиннадцатый пункт
  (строка 1598), но сводная строка того же файла
  ([`settings.md:1696`](roo_code/roo-context/api/settings.md:1696)) по-прежнему говорит «десять правил
  домена… пункты 1–10 один к одному». Слайс правил этот файл и эту строку не тронул.

Слайс сделал ровно то, что просил бриф: новые колонки и поля схемы заведены, три константы названы
