# Ночной пилот через Codex

Подготовлен 2026-09-17. Исполнитель — [codex-night.py](codex-night.py), очередь —
[codex-night-queue.json](codex-night-queue.json). **Живой пилот завершён 2026-09-17:** auth-план принят и сохранён в `d777bc7`.
Результаты и ограничения — в [журнале проверки](../roo-context/verify-runs/codex-night-2026-09-17.md).
Этот пилот готовит три доменных плана; реализация приложения начнётся отдельной
очередью с auth С0 после приёмки его уточнённого плана.

## Что будет происходить без участия владельца

1. Проверка чистого checkout на ветке `auto/*`, наличия источников и CLI.
2. Исходный `npm run verify`. Красный результат останавливает запуск задач.
3. Для каждой задачи: отдельная сессия исполнителя → `npm run verify` и строгая
   проверка ссылок документа контроллером → отдельная сессия проверяющего без
   права записи → локальный коммит контроллером. Проверяющий читает реальные логи
   контроллера и сверяет содержание с исходниками. После проверок контролируется
   неизменность файлов; запуск Vitest с записью кэша в read-only сессии не требуется.
4. Если исполнитель или проверяющий вернул `blocked`, причина и черновик сохраняются
   отдельно, а контроллер переходит к следующей независимой задаче. Красная машинная
   проверка после правок тоже блокирует только эту задачу, если файлы и Git не нарушены.
5. Отчёт с выполненными задачами, коммитами, блокировками, ожидающими зависимостями,
   остатком очереди и причиной аварийной остановки, если она произошла.

Порядок пилота: актуализировать auth → устранить замечания к uploads → написать
недостающий backend-план sales-crm. Источники включают заполненный опросник и
актуальный реестр решений, включая П130 о возвратах. Общая очередь находится
[здесь](../plans/general/очередь-работ.md).

**С 18 сентября блокировка задачи не останавливает очередь**, даже если таких задач
несколько подряд. До продолжения черновик записывается во внешний архив и в Git stash
отдельного checkout; контроллер проверяет чистоту дерева и неизменность HEAD/индекса.
Чужие правки в основном рабочем каталоге не затрагиваются. Если сохранить и отделить
черновик не удалось, запуск останавливается с отчётом.

Весь запуск останавливают: красная исходная проверка, истечение времени, сигнал
остановки, сбой CLI/невалидный ответ, правки вне разрешённых файлов, изменение Git
исполнителем, запись проверяющим или машинной проверкой, ошибка сохранения/коммита.
Текущие правки при такой остановке сохраняются в checkout; уже созданные архивы остаются.
Нет автоматического слияния, отправки в remote или развёртывания. Этот режим уже общей
[политики](../plans/general/autonomous-run-policy-plan.md): один исполнитель за раз,
финального merge нет.
Успешный пилот не означает разрешение на непроверенную реализацию всех доменов.

## Подготовленный следующий запуск — 18 сентября

Актуальный вход — [codex-backend-queue-2026-09-18.json](codex-backend-queue-2026-09-18.json).
Четыре задачи: `auth-c0` (реализация), `crm-plan-acceptance` (приёмка плана),
`crm-c0-contract` (точные формы и согласованное чтение), `auth-s1-contract` (подготовка
следующего этапа входа и сеансов). CRM-контракт зависит от приёмки CRM; auth С1 — от
реализации С0. Блокировка CRM не удерживает auth, и наоборот.

Это конечная порция, а не обещание занять любое заданное число часов. Дальнейшая реализация
С1 требует результата `auth-s1-contract` и отдельной PostgreSQL для проверки миграций.
SQLite-проверка текущего окружения не считается такой проверкой.

В очереди есть `baseline_checks` (перед вызовом модели) и `checks` каждой задачи
(после автора, перед проверяющим). Каждая команда задаётся объектом `cwd`/`argv`, без shell;
папка обязана находиться в checkout. Backend-задача без явных `checks` не запускается.
Провал исходной проверки останавливает прогон, провал проверки правок блокирует задачу.
Логи `*-check-extra-*.stdout.log`/`stderr.log` доступны независимому проверяющему.

Авторский `done` означает готовность кандидата. Если sandbox автора не позволяет выполнить
асинхронные тесты, они ожидают контроллера; это прямо указывается без утверждения об успехе.
Контроллер запускается обычным локальным процессом и выполняет обязательные проверки сам.
Приёмка возможна только после их фактического успеха.

Проверенное тестовое окружение Python 3.12 закреплено в
[backend-test-requirements.txt](backend-test-requirements.txt). В ночной копии оно установлено
в `backend/.venv`; системный Python не изменён. Список нужен для воспроизводимой подготовки
тестов, а не для утверждения производственной конфигурации зависимостей.
[backend-smoke.py](backend-smoke.py) проверяет импорты четырёх потребителей, подпись,
хеширование пароля, HTTP и запросы к временной SQLite с двумя компаниями. Он принудительно
заменяет DATABASE_URL до импорта приложения и удаляет временную БД после выполнения.
Не запускать backend-проверки против рабочей БД из `.env`.

Подготовка нового окружения, если его ещё нет:

```bash

uv pip sync --python backend/.venv/bin/python roo_code/workflows/backend-test-requirements.txt
backend/.venv/bin/python -B roo_code/workflows/backend-smoke.py
```

## Зависимости подготовленной очереди

У задачи можно указать `"depends_on": ["auth-plan"]`. Контроллер проверяет существование
id и отсутствие циклов, выполняет зависимости раньше потребителей. Дополнительно он
считает задачами-предшественниками все более ранние записи очереди, чьи `outputs`
пересекаются с `sources` или `outputs` текущей задачи. Так читатель или следующий автор
одного файла не работает поверх непрошедшего проверку результата. Семантические
зависимости без общих файлов нужно указывать явно.

Зависимые от заблокированной задачи, включая всю цепочку дальше, получают состояние
`waiting` и не вызывают модель. Остальные продолжают выполняться. Общий неизменяемый
источник у двух задач сам по себе зависимости не создаёт. Существующая очередь из
трёх доменных планов допускает их независимую подготовку по действующим контрактам.
`--max-tasks` ограничивает число попыток, включая заблокированные; `waiting` лимит
не расходует. Контроллер не придумывает новые задачи после исчерпания очереди.

## Запуск

Число задач и время задаются явно. Пример для **одной задачи и максимум 60 минут**:

```bash
python3 roo_code/workflows/codex-night.py \
  --workspace ../flexiron-night \
  --run-dir ../flexiron-night-results/pilot-001 \
  --run --minutes 60 --max-tasks 1
```

Это пример параметров, а не согласованный бюджет. Используется модель из текущей
конфигурации Codex; скрипт её не меняет. Ограничение времени включает проверки и обе
сессии, при истечении останавливается группа процессов. Жёсткого денежного лимита
или ограничения токенов здесь нет; оценки недельной квоты Claude не применяются.

Для работы после закрытия терминала запустить ту же команду в `tmux` или через
диспетчер служб. Скрипт сам не устанавливает расписание и не отключает сон.
При локальном запуске компьютер должен оставаться включённым, не спать и иметь
интернет. Закрытый чат не является запущенным ночным процессом. На отдельном сервере
потребуются checkout, зависимости и собственная авторизация Codex.

## Результаты и продолжение

Каталог результатов уникален для каждого запуска. Повторное использование имени
отклоняется: старые журналы никогда не перезаписываются. Он находится вне checkout.

- `report.md` — итог, причины блокировок и пути восстановления; `state.json` —
  списки `completed`, `blocked`, `waiting`, `pending` и коммиты принятых задач.
- `journal.jsonl` — дописываемая последовательность событий, сбрасывается на диск.
- `queue.json`, `schema.json` — точные входные данные запуска.
- `controller.py` — версия контроллера, начиная с повторной приёмки первого пилота.
- `*-work.json`, `*-review.json` — структурированные ответы двух сессий.
- `*.stdout.log`, `*.stderr.log` — реальный вывод CLI, проверок и Git.
- `*.prompt.txt` — точный текст задания для каждой сессии.
- `<id>-blocked/` — `changes.patch` (включая бинарные изменения tracked-файлов),
  `files.tar` (все изменённые существующие файлы, включая новые и символические ссылки),
  `manifest.json` (в том числе удаления), `stash.txt` (неизменный hash сохранённого stash).
  Папка создаётся до очистки checkout; даже блокировка без правок имеет запись и архив.

Итог `completed` означает, что всё принято; `completed-with-blockers` — доступные
задачи обработаны, но есть блокировки; `task-limit` — остались нерассмотренные задачи.
У этих исходов код выхода 0: контроллер отработал штатно, это **не** признак приёмки
всех задач. `stopped` и код 1 означают аварийную остановку, код 2 — отказ до запуска.

SIGTERM/Ctrl+C сохраняют отчёт об остановке. При аварийном отключении питания или
SIGKILL итог может остаться `running`: проверить живые процессы и checkout перед
продолжением. Блокировка в общей Git-директории не допускает одновременных запусков
этого контроллера, но не блокирует ручное редактирование другими программами.

Автоматического повторения заблокированных задач в том же прогоне нет: сначала нужно
устранить причину и подготовить повторную задачу. Архив и stash не удаляются автоматически.
Для восстановления использовать записанный hash, а не переменный `stash@{0}`; применять
его только в отдельном чистом checkout с совместимой базой. Архив позволяет восстановить
черновик и без stash. Принятые независимые коммиты остаются на ветке.

`--retry-review` сохраняет совместимость с прежними остановленными прогонами и новыми
аварийными остановками приёмки, когда правки текущей задачи ещё находятся в checkout.
Это не команда восстановления архивированной блокировки. Если исполнитель завершил
работу, исправить замечания только в разрешённых файлах и повторить приёмку:

```bash
python3 roo_code/workflows/codex-night.py \
  --workspace ../flexiron-night-2026-09-17 \
  --retry-review ../flexiron-night-results/pilot-2026-09-17 \
  --run-dir ../flexiron-night-results/pilot-2026-09-17-review-2 \
  --run --minutes 10 --max-tasks 1
```

Повтор требует исходной очереди, прежнего HEAD, неизменённого индекса, завершённого
ответа исполнителя и изменений только внутри текущей задачи. Тесты и независимая
приёмка выполняются заново. Старый каталог результатов не меняется. Указанные имена
первого пилота после использования повторно применять нельзя.

Для следующей завершённой порции исключить принятые задачи из копии очереди и передать
её через `--queue`; обычный запуск требует чистого checkout. Бюджет не входит в тексты
задач и не заставляет пересобирать старые брифы.

Старый [night-queue.js](night-queue.js) остаётся сценарием Claude для прежней очереди.
Его дефекты из [остатка работ](../plans/general/остаток-после-прогонов-2026-09-13.md)
этим пилотом не объявляются исправленными.

Проверка контроллера без модели: `python3 roo_code/workflows/test_codex_night.py`.
Реальные флаги сверены с локальным `codex exec --help`; формат запуска, JSONL и
структурированные ответы описаны в
[официальной документации Codex](https://learn.chatgpt.com/docs/non-interactive-mode).
